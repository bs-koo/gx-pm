## 1. 목표와 확정된 결정

RFP·과업지시서·요구사항 정리 파일에서 **요구사항정의서(AN-02) · 기능명세서(AN-03) ·
테이블정의서(DE-08) · 단위테스트계획서(DE-13) · 추적매트릭스(AN-05)** 5종을 산출하고,
각 문서의 개정이력을 시트로 관리한다.

| 결정 | 내용 |
|------|------|
| 컬럼 정본 | 새 컬럼 세트로 **교체**. 기존 감리형(제안요청ID·수용여부)은 폐기 |
| 추적 축 | **기능 축 단일화**. 화면ID·화면목록표 제거 |
| 개정이력 | **재생성 시 자동 초안 + 사용자 승인** |
| ID 채번 | 프로파일 항목. 미설정 시 커맨드가 AskUserQuestion 으로 묻는다 |
| 결과 판정값 | `Pass` / `Fail` 2값 |
| 이슈·회의록 시트 | 범위 제외 |
| 테이블정의서 | **순방향(요구사항→테이블) 폐지.** 기존 스키마는 역생성으로 고정하고 신규 컬럼만 표준 기반 제안 |
| 테스트 결과 기입 | 별도 커맨드를 만들지 않는다 |
| 산출물 | **5종** — 나머지 8종은 커맨드에서 내린다 |

### 교체의 파급

`제안요청ID`·`수용여부` 소멸로 추적매트릭스(AN-05) 컬럼 3개와 `/gx-감리대응`의
과업이행여부 판정이 근거를 잃는다. 화면 축 제거로 `PG_{화면ID}`·`U_{화면ID}`·
`TC_{화면ID}` 파생 규칙 전부가 무효가 된다. 두 파급 모두 이 설계의 범위에 포함한다.

## 2. 새 ID 체인

```
요구사항ID (기본 REQ-{3자리})
  └→ 기능ID (기본 FN-{3자리})            ← 파생 아님. 독립 채번, N:M 매핑
       ├→ 테이블·컬럼 (DE-08)            ← 입력항목이 컬럼으로 매핑된다
       └→ 테스트ID (기본 UT-{3자리})     ← 파생 아님. 독립 채번, N:1 매핑
            ↑ 컬럼 제약(길이·NotNull)이 경계 케이스의 근거가 된다
```

**테이블정의서가 단위테스트보다 먼저 온다.** 기능명세의 `입력항목`이 `[확인필요]`로
남았을 때 확정되는 자리가 테이블 설계이고, DE-13 의 경계 케이스는 확정된 제약 위에 서야 한다.

기능ID를 요구사항ID에서 파생시키지 않는 이유: **기능 1개가 요구사항 여러 건을 덮는 경우**가
실제로 흔하고, 파생형은 그 경우를 표현하지 못한다. 연결은 `연계요구사항ID` 열이 맡는다.

접두어·자릿수는 프로파일에서 바꿀 수 있다. 미설정 상태로 커맨드를 실행하면 한 번 묻고
프로파일에 저장한 뒤 다시 묻지 않는다.

## 3. AN-02 요구사항정의서

### 3.1 행 분할 규칙 — 요구사항 1건을 무엇으로 세는가

컬럼을 채우기 전에 **몇 행이 되는지**가 먼저 정해진다. 이 건수가 뒤 두 문서의 행 수를
전부 결정한다.

| 상황 | 처리 |
|------|------|
| `ㅇ` · `-` 불릿 하나 | 요구사항 1건 |
| ID 표의 행 하나 (2단계 판정 통과) | 요구사항 1건 |
| 한 문장에 이질적 기능이 `및`·`~와 ~를` 로 묶임 | **쪼갠다** |
| 하나가 다른 하나의 수단인 경우 (`~하여 ~한다`) | 쪼개지 않는다 |

**쪼갬 판정 기준: 테스트를 따로 써야 하면 따로 쪼갠다.**

- `상대평가기준 생성 결과 조회 및 다운로드 기능` → 조회와 다운로드는 입력도 출력도
  다르므로 **2건**
- `헤더정보를 읽어 컬럼 순서를 파악한 후 업로드` → 헤더 읽기는 업로드의 수단이므로 **1건**

애매하면 추정하지 않고 묻는다. 표 판정 애매성과 동일한 중단점 규칙을 따르며,
게이트로 이월하지 않는다.

### 3.2 컬럼별 도출 규칙

| # | 컬럼 | 도출 규칙 |
|---|------|----------|
| 1 | 번호 | 1부터 순차, 행 순서와 동일. 재실행 시 **재부여**(삭제 행 포함). 불변 키는 요구사항ID이고 번호는 표시용 |
| 2 | 요구사항ID | 프로파일 채번. **한 번 부여하면 불변**, 삭제해도 재사용 금지(순번 구멍 허용). 재실행 시 마지막 순번 다음부터 |
| 3 | 대분류 | 출처 우선순위 ① RFP 목차·장 제목 ② ID 표의 분류 열 ③ 모델 분류. ③이면 게이트에서 "문서에 없어 추정" 명시 |
| 4 | 중분류 | 대분류 안에서 유일해야 한다. 같은 중분류명이 다른 대분류에 걸치면 경고 |
| 5 | 요구사항명 | 25자 내외 **명사구**. `~기능`·`~관리`·`~제공` 형태로 끝맺는다. 문장(`~한다`)으로 쓰지 않는다 — 그건 상세내용의 몫 |
| 6 | 요구사항 상세내용 | **원문 표현 유지, 해석 금지.** 3줄 이상이면 요약하되 **조건·제약·수치는 절대 버리지 않는다**(테스트 경계값의 유일한 출처). 요약했으면 비고에 원문 위치 표기 |
| 7 | 비고 | 원문에 괄호·단서로 붙은 **범위 한정·부연**만 옮긴다. 자동 생성하지 않는다 |
| 8 | 상태 | `신규`/`유지`/`변경`/`삭제`. 최초 작성은 전건 `신규`. 재실행 시 대조로 자동 판정 |
| 9 | 요구사항 근거 | 최초 출처(`과업지시서`·`제안서`·`RFP p.12`). 최초 작성 이후 추가분은 `신규(YYYY.MM.DD)`. 원문 ID 가 있으면 병기(`과업지시서 SFR-030`) |
| 10 | 변경 근거 | `상태`가 `변경`·`삭제`일 때 **필수**, 그 외 공란. 형식 `{일자} {주체} {결정}`. **자동 생성 금지 — 사용자에게 묻는다** |

### 3.3 상태 판정 규칙 (재실행 시)

요구사항ID 를 키로 기존 산출물과 입력을 대조한다.

| 대조 결과 | 상태 | 추가 동작 |
|---|---|---|
| 입력에만 있음 | `신규` | 근거에 `신규(오늘)` 자동 기재 |
| 양쪽에 있고 요구사항명·상세내용 동일 | `유지` | |
| 양쪽에 있고 요구사항명·상세내용 다름 | `변경` | 변경 근거 입력 요청(필수) |
| 기존에만 있음 | `삭제` 후보 | 확인 후 상태만 변경. **행은 지우지 않는다** |

**대·중분류나 비고만 바뀐 것은 `유지`다.** 분류 정리는 요구사항의 개정이 아니다.

삭제 행을 남기는 이유: 지우면 "그 요구사항이 왜 사라졌는지"를 문서가 답하지 못한다.
참조 양식도 `REQ-028` 을 상태 `삭제`로 남겨 두었다.

### 3.4 변경 근거가 비면 진행하지 않는다

`상태`가 `변경`·`삭제`인데 `변경 근거`가 비면 게이트에서 차단한다. 이 열이 비면
개정이력의 `개정 내용`을 만들 수 없고, 다음 개정 때 "왜 이렇게 됐는지"를 알 수 없다.

## 4. AN-03 기능명세서 (신설)

### 4.1 입력은 AN-02 뿐이다

승인된 요구사항정의서만 읽는다. **원본 RFP 를 다시 읽지 않는다.** 요구사항정의서가
정본이어야 추적이 성립하고, 두 입력을 함께 보면 AN-02 에 없는 기능이 생겨 추적이 끊긴다.

대가: AN-02 에 담기지 않은 RFP 내용은 기능명세서에 반영되지 않는다. 그래서 누락은
승인 게이트 1에서 잡아야 한다.

### 4.2 행 분할 규칙 — 기능 1건을 무엇으로 세는가

기본은 요구사항 1건 → 기능 1건. 여기서 갈라지고 합쳐진다.

| 상황 | 처리 | 예 |
|------|------|-----|
| 요구사항 하나에 조작 흐름이 둘 이상이고 입력·출력이 다름 | **쪼갠다** | `조회 및 다운로드` → 조회(FN-003) / 다운로드(FN-004) |
| 여러 요구사항이 같은 처리 로직을 공유 | **합친다**, 연계요구사항ID 다중 | 업로드 파이프라인을 공유하는 REQ-007·REQ-027 |

**판정 기준: 처리내용(로직)이 같으면 한 기능이다.** 화면이 같은지는 보지 않는다 —
화면 축을 제거했으므로 화면은 판정 근거가 아니다.

### 4.3 컬럼별 도출 규칙

| # | 컬럼 | 도출 규칙 |
|---|------|----------|
| 1 | 기능ID | 프로파일 채번. 불변, 독립 채번 |
| 2 | 대분류 | AN-02 에서 **승계**. 새로 분류하지 않는다 |
| 3 | 중분류 | 〃. 여러 요구사항을 덮어 분류가 갈리면 **첫 연계 요구사항의 분류**를 따르고 비고에 표기 |
| 4 | 기능명 | 명사구. 1:1 이면 요구사항명과 같아도 된다. 쪼갠 경우 서로 구분되는 이름 |
| 5 | 기능설명 | 2~3문장. **시스템 관점의 동작 서술**이지 요구사항 상세내용의 재진술이 아니다 |
| 6 | 입력항목 | `항목명(타입, 제약, 필수여부, 기본값)` 을 `/` 로 구분. §4.4 참조 |
| 7 | 처리내용(로직) | `① ~ ② ~` 번호 순서, 3~7단계. §4.5 참조 |
| 8 | 출력결과 | **화면 결과 + 데이터 결과를 함께** 적는다(`목록 갱신 / TB_SCORE 1건 저장`). 데이터 결과가 UT 의 사후조건이 된다 |
| 9 | 연계요구사항ID | 다중 허용(쉼표). **모든 기능은 최소 1건을 가진다.** 0건이면 근거 없는 기능이므로 게이트에서 차단 |
| 10 | 비고 | `[확인필요]` 사유, 분류 승계 예외, 다중 연계 사유 |

### 4.4 입력항목 — 이 문서에서 가장 중요한 열

여기 적힌 제약이 그대로 단위테스트의 경계 케이스가 된다. **제약이 비면 테스트가
정상 케이스만 나온다.**

도출 출처를 이 순서로 본다.

1. 요구사항 상세내용에 명시된 입력 (`세부용도별`, `이상치 제외`)
2. 처리내용에서 역산 — 그룹핑하려면 그룹 키가 입력이어야 한다
3. 테이블정의서(DE-08)가 있으면 컬럼 제약(길이·NotNull)

셋 다 실패하면 **`[확인필요]` 로 두고 지어내지 않는다.** 게이트에서 `[확인필요]` 목록을
따로 보여준다.

### 4.5 처리내용 — 예외 케이스의 유일한 출처

`검증 → 처리 → 저장` 3박자가 최소 형태다. **분기와 검증을 반드시 포함한다.**

- 분기(`~이면 ~한다`)가 그대로 UT 의 예외 케이스가 된다
- 트랜잭션 경계가 있으면 명시한다(`⑤ 전체 커밋, 실패 시 롤백`)

분기가 하나도 없는 처리내용은 "정상 흐름만 생각했다"는 뜻이므로 게이트에서 되묻는다.

## 5. DE-13 단위테스트계획서 (전면 개편)

기존 27개 검사기준 체크리스트 시트는 폐지한다. 화면 축 산출물이기 때문이다.
케이스 도출 규칙(동등분할·경계값·정상/예외/경계 강제)은 `design-test-cases` 에서
살려 **내부 도출 규칙**으로 쓴다. 컬럼으로 내보내지 않을 뿐 규칙은 유지한다.

### 5.1 행 분할 규칙 — 기능 1건에서 테스트 N건

기계적으로 도출한다.

| 도출 출처 | 만들어지는 케이스 | 최소 건수 |
|---|---|---|
| 기능 전체 | 정상 흐름 | 1 |
| 입력항목의 각 제약(길이·범위·형식) | 경계 — 최소·최대·초과 | 제약당 2 |
| 입력항목의 각 필수 항목 | 예외 — 미입력 | 필수항목당 1 |
| 처리내용의 각 분기(`~이면`) | 예외 — 분기 미충족 | 분기당 1 |
| 처리내용의 롤백·트랜잭션 | 예외 — 중간 실패 | 있으면 1 |

**정상 케이스만 있는 기능은 게이트에서 차단한다.**

### 5.2 컬럼별 도출 규칙

| # | 컬럼 | 도출 규칙 |
|---|------|----------|
| 1 | 테스트ID | 프로파일 채번. 기능별로 이어서 |
| 2 | 연계기능ID | 필수. 없으면 고아 테스트이므로 차단 |
| 3 | 연계요구사항ID | **기능을 경유해 자동 채움. 사용자 입력 금지** — 수동 입력하면 AN-03 과 어긋난다 |
| 4 | 사전조건 | `계정·권한` / `선행 데이터` / `시스템 상태` 3유형. 기능의 입력항목 중 "이미 있어야 하는 것"이 여기로 온다. `없음`으로 두지 않는다 |
| 5 | 입력 | 구체적인 값(`세부용도=업무시설, 이상치제외=N`). **`유효한 값` 처럼 추상적으로 쓰지 않는다** — 재현이 안 된다 |
| 6 | 기대결과 | 관측 가능한 판정 기준. 화면 문구는 따옴표로 원문 그대로 |
| 7 | 사후조건 | 기능의 `출력결과` 중 데이터 부분에서 도출. **예외 케이스는 "변화 없음"을 명시한다** — 없으면 안내만 띄우고 저장은 되는 결함을 못 잡는다 |
| 8 | 의존성 | 선행 테스트ID. 선행 케이스가 만든 데이터를 쓸 때만. 있으면 실행 순서가 고정되고 병렬 실행이 막힌다는 뜻 |
| 9 | 테스트담당자 | 계획서는 공란 |
| 10 | 수행일 | 계획서는 공란 |
| 11 | 결과 | 계획서는 공란. 값은 `Pass` / `Fail` 2값 |

## 6. DE-08 테이블정의서 (역생성 + 신규 제안)

### 6.1 순방향을 폐지하는 이유

요구사항에서 테이블을 추론해 만든 정의서는 추측이고, 개발이 시작되는 순간 거짓말이 된다.
그런데 문서는 남아 있어 나중에 그것을 보고 개발하려다 어긋난다.

의존 방향은 오히려 반대다 — 기능명세서 `입력항목`의 제약(길이·NotNull)의 가장 정확한
출처가 실제 테이블이다. 그래서 DE-08 은 **AN-03 다음, DE-13 앞**에 놓는다.

### 6.2 기존 스키마는 건드리지 않는다

| 단계 | 처리 |
|------|------|
| 1 | 기존 DDL 로드 (프로파일 `ddl.sql` 또는 사용자 붙여넣기) |
| 2 | AN-03 의 `입력항목`을 기존 컬럼에 매핑 → **매핑 안 되는 것이 신규 컬럼 후보** |
| 3 | 기존 컬럼 전건 `validate_column` — 비표준이어도 **바꾸지 않고 표준형만 병기** |
| 4 | **신규 컬럼만** `translate_column` — 표준 컬럼명과 근거 도출 |
| 5 | **승인 게이트 — 신규 컬럼만 보여주고 승인받는다** |

기존 컬럼을 표준형으로 바꾸자고 제안하지 않는다. 운영 중인 스키마를 바꾸는 것은
이 문서의 권한 밖이다. `표준 판정`을 `현행유지`로 두고 `표준 권고명`에 표준형을 남긴다.

`현행유지` 행은 감리에서 강점이 된다 — "비표준을 몰랐다"가 아니라 "알고 있고 운영 중이라
유지한다"가 문서로 남는다.

### 6.3 표준용어 MCP 호출 규약

`sqi-comn-term` MCP 를 쓴다. 상세 프로토콜의 정본은 `docs/표준용어-mcp-연계.md` 다.

| 대상 | 도구 | 결과 처리 |
|------|------|----------|
| 기존 컬럼 | `validate_column` | `PASS` → `표준준수` / `PARTIAL`·`FAIL` → `현행유지` + 표준 권고명 병기 |
| 신규 컬럼 | `translate_column` | `FULL` → 확정 제시 / `PARTIAL`·`AI_SUGGESTED` → 근거와 함께 제시 / `FAIL`·`decisionRequired` → **그 자리에서 사용자 선택** |

`sourcePriority` 는 프로파일에서 읽고, 없으면 `["BLDG_ENGY", "MOIS_STD"]` 를 제안하고 묻는다.
MCP 가 세션에 없으면 `docs/표준용어-mcp-연계.md` 의 설치 안내를 출력하고 중단한다 —
**표준 검증 없이 컬럼명을 지어내지 않는다.**

### 6.4 컬럼 구성

| # | 컬럼 | 도출 규칙 |
|---|------|----------|
| 1 | 테이블명 | 물리 테이블명 |
| 2 | 테이블 논리명 | DB 코멘트 → 표준용어 역변환 → 기능명세 순으로 복원 |
| 3 | 컬럼명 | 기존은 DDL 그대로, 신규는 승인된 표준 컬럼명 |
| 4 | 컬럼 논리명 | 기능명세 `입력항목`의 항목명과 매칭 |

## 7. 개정이력

### 7.1 시트 구조

다섯 문서 모두 **첫 시트가 `개정이력`, 둘째 시트가 본문**이다.

| 버전 | 개정일 | 개정 사유 | 개정 내용 | 작성자 | 승인자 |
|------|--------|----------|----------|--------|--------|

### 7.2 행이 추가되는 경우

| 트리거 | 개정 사유 | 개정 내용 자동 초안 |
|--------|----------|-------------------|
| 최초 생성 | `신규` | `최초 작성` |
| 항목이 늘어남 | `추가` | `요구사항 7건 추가` |
| 기존 항목의 내용이 바뀜 | `변경` | `요구사항 2건 변경(REQ-005, REQ-012)` |
| 항목이 삭제 상태로 전환 | `삭제` | `요구사항 1건 삭제(REQ-028)` |
| 오탈자·분류 정리 등 내용 무관 수정 | `보완` | `분류 체계 정리` |

여러 종류가 한 번에 일어나면 **행 하나에 합친다.** 사유는 가장 무거운 것을 쓴다:
`삭제` > `변경` > `추가` > `보완`.

### 7.3 행이 추가되지 않는 경우

- **승인 게이트 안에서의 수정** — 게이트에서 고쳐 재출력한 것은 확정 전이므로 개정이 아니다.
  파일 저장 시점에 1행만 만든다
- **다른 문서만 바뀐 경우** — AN-02 만 바뀌면 AN-03·DE-13 의 개정이력은 올라가지 않는다
- **파급 재생성 결과가 기존과 동일한 경우** — diff 가 0이면 행을 만들지 않는다

### 7.4 버전과 승인자

- `1.0` 에서 시작, 개정마다 `+1.0`. 소수점 둘째 자리는 쓰지 않는다
- **문서마다 독립.** AN-02 가 3.0 이어도 DE-13 은 1.0 일 수 있다
- `승인자` 는 자동으로 채우지 않는다. 공란으로 두고 결재 후 사람이 기입한다
- `작성자` 는 프로파일에 저장된 이름을 기본값으로 제시하고 확인받는다

### 8.1 이월 금지 항목 (기존 5개 → 3개)

| 중단점 | 왜 이월 못 하나 |
|--------|---------------|
| 시안/대안 감지 | 시안이 틀리면 뒤 산출물이 전부 틀린다 |
| 표 판정 애매성 | 요구사항 건수가 전체 행 수와 추적 대상을 정한다 |
| **신규 컬럼명 결정 필요** | MCP 가 `decisionRequired` 를 내면 그 자리에서 물어야 한다. 컬럼명이 확정돼야 DE-13 경계값이 그 위에 선다 |

`화면 분리 미결정`(기존 4번)은 화면 축 제거로 소멸한다.

| 테스트ID | 연계기능ID | 연계요구사항ID | 사전조건 | 입력 | 기대결과 |
|---|---|---|---|---|---|
| UT-051 | *(공란)* | REQ-045 | 운영 동등 환경, 데이터 10만건 | 동시 사용자 500명 30분 부하 | 평균 응답 3초 이내, 오류율 1% 미만 |

## 11. 범위 밖으로 확정된 것

- **통합테스트시나리오(DE-14)** — 2차. 5종이 자리 잡은 뒤에 기능 축으로 다시 설계한다

- **xlsx 서식 정밀 일치** — 개정이력 시트의 제목 병합 행, 열 너비, 테두리는 후속 과제.
