# 표 형식 요구사항 추출 설계

**작성일**: 2026-09-01
**대상 버전**: v2.0.1 (동작 수정, 파괴적 변경 없음)

---

## 1. 문제

`extract-requirements` 스킬이 **표로 제시된 요구사항을 놓친다.**

`plugins/gx-pm/skills/extract-requirements/SKILL.md` Step 2 의 추출 패턴은 4개다:

```
- "~해야 한다", "~를 제공한다", "~기능을 구현한다"
- "ㅇ" 또는 "o"로 시작하는 기능 항목
- 번호가 매겨진 기능 목록
- "기능 요구사항", "비기능 요구사항" 섹션의 항목
```

실제 요구사항 문서(`D:\SQ\memo\requirements\mvp.md`, 구현 전 원문)로 실측한 결과:

| 대상 | 결과 |
|------|------|
| `## 5. 기능 요구사항` 의 FR-01~05 | ✅ 섹션 규칙으로 추출 |
| `## 6. 비기능 요구사항` 의 NFR-01~05 (표) | ✅ 섹션 규칙으로 추출 |
| `## 2. 도메인 규칙` 의 BR-01~08 (표) | ❌ **8건 중 1건만** |

BR 8건 중 문장 패턴에 걸리는 것은 `BR-02 "30분 단위여야 한다"` 하나뿐이다:

```
✓ BR-02  예약 시각은 30분 단위여야 한다        ← "~여야 한다"
✗ BR-01  같은 회의실에서 시간이 겹치는 예약은 생성할 수 없다
✗ BR-03  예약 가능 시간대는 09:00 ~ 18:00 이다
✗ BR-04  예약 길이는 최소 30분, 최대 4시간 이다
✗ BR-05  과거 시각으로는 예약할 수 없다
✗ BR-06  오늘로부터 14일 이내만 예약할 수 있다
✗ BR-07  예약 취소는 예약자 본인만 할 수 있다
✗ BR-08  이미 취소된 예약은 다시 취소할 수 없다
```

**애매한 것이 아니라 불안정하다.** 8건 중 임의의 1건만 섞여 들어와 요구사항 건수가
10 / 11 / 18 중 어디로든 간다. 그 차이가 추적매트릭스 행 수, 통합테스트 시나리오 수,
그리고 과업이행여부 판정 대상 전체를 바꾼다.

### 왜 흔한가

공공 RFP 는 요구사항을 **ID 표**로 준다. 그리고 그 표가 늘 "기능 요구사항" 이라는
제목 아래 있지 않다 — 도메인 규칙 · 업무 규칙 · 비즈니스 규칙 · 제약사항 · 정책 ·
준수사항 아래 놓이는 것이 보통이다. 현행 규칙은 **섹션 제목에 의존**해서 이 경우를 전부 놓친다.

## 2. 해결

Step 2 에 **다섯 번째 패턴**을 추가한다: ID 접두 표 행.

### 2.1 인식 규칙

표의 첫 열이 `{영문 2~4자}-{숫자 2~3자리}` 형태이면 그 표를 **요구사항 표**로 본다.

```
^\|\s*\*{0,2}([A-Z]{2,4}-\d{2,3})\*{0,2}\s*\|
```

같은 문서의 다른 표와 실측 대조 — **오탐 0건**:

| 표 | 첫 열 | 판정 |
|----|------|------|
| 겹침 판정표 | `#`, `1`, `2` … | 제외 (숫자) |
| 구현 Phase 표 | `0`, `1` … `7` | 제외 (숫자) |
| 오류 응답 표 | `code`, `OVERLAPPING_RESERVATION` | 제외 (ID 형태 아님) |
| 결정 기록 표 | 산문 | 제외 |
| **도메인 규칙 표** | `BR-01` … | **채택 (8행)** |
| **비기능 요구사항 표** | `NFR-01` … | **채택 (5행)** |

### 2.2 중복 제거

섹션 규칙과 표 규칙에 **모두** 걸리는 항목이 있다(예: `## 6. 비기능 요구사항` 의 NFR 표).
같은 원문 ID 는 요구사항 1건으로 센다.

### 2.3 기능/비기능 판정

표에서 뽑은 행의 `구분` 은 다음 순서로 정한다:

1. 원문 ID 접두어가 `NFR`·`QE`·`QR` 이면 → **비기능**
2. 섹션 제목에 "비기능"·"품질"·"성능"·"보안" 이 있으면 → **비기능**
3. 그 외 → **기능**

`BR`(업무 규칙)은 3번에 걸려 기능이 된다. 업무 규칙은 기능 요구사항이다.

### 2.4 원문 ID 보존

원문 ID(`BR-01`)를 **`근거` 열에 병기**한다: `과업지시서 BR-01`.

`제안요청ID` 열에 넣지 않는다. 그 열의 정본 패턴은 `templates/id-naming-rules.md:48` 의
`SFR-{3자리 순번}` 이고, 거기에 `BR-01` 을 넣으면 ID 체계가 무너진다.
`근거` 열은 원래 "과업지시서 / 제안서 / 협의사항" 을 적는 자리라 출처 표기에 맞다.

이렇게 하면 추적매트릭스에서 `BR-01` 이 어느 요구사항이 됐는지 역추적할 수 있다.

## 3. 검증

마크다운 스킬은 실행 검증이 불가능하다. 대신 **문서에 적힌 규칙 자체를 시험한다.**

1. `SKILL.md` 에 정규식이 **문자 그대로** 실려 있다
2. 그 정규식을 픽스처 문서에 적용하면 기대한 ID 를 정확히 뽑는다
3. 픽스처의 비요구사항 표(숫자 첫 열·코드명 첫 열)에서는 아무것도 뽑지 않는다
4. 중복 제거·구분 판정·원문 ID 보존 규칙이 문서에 존재한다

2·3 이 핵심이다. 정규식을 문서에만 적고 아무도 시험하지 않으면,
`design-test-cases` 의 경계값 규칙처럼 **문서에만 있고 동작하지 않는 규칙**이 된다.

픽스처는 `plugins/gx-pm/tests/fixtures/requirement-tables.md` 로 새로 만든다.
`memo` 를 참조하지 않는다 — 외부 저장소에 의존하는 테스트는 그 저장소가 사라지면 깨진다.

- 다른 스킬의 추출 규칙 — `reverse-scan-source` 등은 소스 대상이라 무관하다
