# gx-pm 파이프라인 커맨드 · `gx-` 접두 개명 설계

**작성일**: 2026-08-31
**대상 버전**: v2.0.0 (파괴적 변경 — 커맨드 이름 전면 변경)

---

## 1. 해결하려는 문제

### 문제 1 — 사용자가 커맨드 순서를 외워야 한다

산출물 사이에는 강한 선행 관계가 있다. `PG_`·`U_`·`TC_` 는 화면ID에서 **문자열로 파생**되므로,
화면목록표를 확정하지 않은 채 프로그램정의서를 만들면 나중에 전부 재채번된다.
그런데 이 관계는 **어디에도 명시되어 있지 않다.** 각 커맨드의 Step 1 이 "이전 결과가 있으면 자동 로드,
없으면 입력을 요청" 이라고만 적혀 있어서, 사용자는 무엇이 먼저인지 스스로 알아야 한다.

### 문제 2 — 커맨드 접두어가 없다

`/요구사항정의서`, `/화면목록표` … 14개가 접두어 없이 등록된다. 자동완성 목록에서 다른 플러그인의
커맨드와 섞이고, 이 플러그인이 제공하는 것이 무엇인지 한눈에 보이지 않는다.

### 문제 3 — 신규 커맨드 3종의 발견 경로가 0이다

v1.5.0 에서 추가한 `/총괄테스트계획서`·`/시스템테스트`·`/결함관리대장` 은 `/프로젝트설정` Step 7 의
유형별 안내에 **한 번도 등장하지 않는다.** 기능은 있는데 사용자가 도달할 방법이 없다.
현행 계약 테스트는 "참조된 커맨드가 존재하는가" 만 검사하고 "존재하는 커맨드가 안내되는가" 는 검사하지 않아,
스킬 배선 테스트와 비대칭이다.

---

## 2. 해결 방식 — 3축

| 축 | 내용 |
|----|------|
| **접두어** | 모든 커맨드에 `gx-` 접두 부여 |
| **파이프라인** | 산출물을 묶어 한 번에 만드는 커맨드 2종 — `/gx-spec`, `/gx-testplan` |
| **선행조건 레지스트리** | 하드/소프트 선행조건을 한 파일에 정의하고 모든 커맨드가 Step 0 에서 검사 |

세 축은 같은 문제의 세 얼굴이다. 파이프라인은 순서를 대신 알아주고, 선행조건 레지스트리는
단독 실행할 때 순서를 알려주며, 접두어는 그 둘을 자동완성에서 한 덩어리로 보이게 한다.

## 3. 커맨드 이름 체계

### 개별 산출물 커맨드 — `gx-` + 기존 한글명

| 기존 | 신규 |
|------|------|
| `/프로젝트설정` | `/gx-프로젝트설정` |
| `/요구사항정의서` | `/gx-요구사항정의서` |
| `/화면목록표` | `/gx-화면목록표` |
| `/프로그램정의서` | `/gx-프로그램정의서` |
| `/인터페이스정의서` | `/gx-인터페이스정의서` |
| `/테이블정의서` | `/gx-테이블정의서` |
| `/총괄테스트계획서` | `/gx-총괄테스트계획서` |
| `/단위테스트계획서` | `/gx-단위테스트계획서` |
| `/통합테스트시나리오` | `/gx-통합테스트시나리오` |
| `/시스템테스트` | `/gx-시스템테스트` |
| `/테스트결과서` | `/gx-테스트결과서` |
| `/결함관리대장` | `/gx-결함관리대장` |
| `/추적매트릭스` | `/gx-추적매트릭스` |
| `/감리대응` | `/gx-감리대응` |

한글명을 유지하는 이유: 사용자가 산출물 이름을 그대로 부르는 것이 이 플러그인의 핵심 사용성이다.
`/gx-` 만 치면 14개가 전부 뜨고, 산출물 이름을 알면 바로 좁혀진다.

### 파이프라인 커맨드 — 영문

| 커맨드 | 묶는 산출물 | 개수 |
|--------|-----------|------|
| `/gx-spec` | 요구사항정의서 · 화면목록표 · 프로그램정의서 · 인터페이스정의서 · 테이블정의서 | 5 |
| `/gx-testplan` | 총괄테스트계획서 · 단위테스트계획서 · 통합테스트시나리오 · 시스템테스트 | 4 |

영문으로 두는 이유: 자동완성 목록에서 **묶음과 낱개가 시각적으로 갈라진다.**
한글로 두면 `/gx-설계생성` 이 `/gx-시스템테스트` 사이에 섞여 낱개처럼 보인다.

`gx-design`·`gx-redesign` 은 다른 플러그인 스킬 이름이라 사용하지 않는다.

### 파이프라인에 들어가지 않는 커맨드 (5종)

`gx-프로젝트설정`(모든 것의 선행), `gx-추적매트릭스`(검증), `gx-테스트결과서`(수행 후),
`gx-결함관리대장`(상시), `gx-감리대응`(사후). 시점이 달라 묶을 수 없다.

**총 16개 커맨드** (개별 14 + 파이프라인 2).

## 5. 파이프라인 모드 규약 — `templates/pipeline-protocol.md`

개별 커맨드는 **단독 실행**과 **파이프라인 실행** 두 경로를 가진다.
생성 로직은 동일하고, 차이는 **어디서 멈추느냐** 뿐이다. 산출물 생성 로직을
파이프라인에 복제하지 않는다 (DRY).

| 단계 | 단독 실행 | 파이프라인 실행 |
|------|----------|---------------|
| Step 0 컨텍스트 로드 | 매번 수행 | 파이프라인이 1회 수행, 개별 커맨드는 생략 |
| 시안/대안 감지 중단점 | 감지 시 중단 | **동일하게 중단** |
| 산출물 생성 | 수행 | 수행 |
| 산출물별 승인 루프 | 매번 중단 | **게이트로 이월** |
| xlsx 추출 질문 | 매번 질문 | 파이프라인 종료 시 1회 |
| "다음 제안" 출력 | 출력 | 생략 |

### 이월 금지 항목

두 가지는 절대 게이트로 미루지 않는다.

1. **시안/대안 감지 중단점** — 시안 선택이 틀리면 뒤 산출물 전부가 틀린다.
2. **ID 확정 게이트** — 화면ID가 바뀌면 `PG_`·`U_`·`TC_` 가 전부 재채번된다.

### 게이트가 하는 일

게이트는 그 시점까지 만든 산출물을 **한꺼번에** 보여주고 AskUserQuestion 으로 승인을 받는다.
수정 요청이 오면 해당 산출물을 재생성하고, 아래 파급 규칙에 따라 **하위 산출물도 함께 재생성**한다.

### 재생성 파급 규칙

| 바뀐 것 | 함께 재생성해야 하는 것 |
|---------|--------------------|
| 요구사항ID | 화면목록표, 통합테스트시나리오, 시스템테스트, 추적매트릭스 |
| 화면ID | 프로그램정의서, 단위테스트계획서(테스트케이스ID 전건 포함) |
| 테이블·컬럼명 | 테이블정의서, 프로그램정의서의 DAO 항목 |
| 종료기준(TE-01 §7) | 단위·통합·시스템 테스트계획서의 판정 기준 |

이 표는 `templates/id-naming-rules.md` 의 ID 체인을 따라 기계적으로 도출된 것이다.
새 ID 유형이 추가되면 두 파일을 함께 고친다.

### 중단 후 재개

파이프라인이 중간에 끊기면 이미 저장된 산출물은 **그대로 둔다.**
다음 실행 시 `detect-existing-artifact` 스킬이 감지하여 "이어서 진행" 을 제안한다.

## 6. `/gx-spec` 워크플로우

```
Step 0  프로파일 로드 (하드) — 없으면 /gx-프로젝트설정 안내 후 종료
Step 1  입력 확인 — RFP/과업지시서 (소프트: 없으면 무엇이 빠지는지 알리고 계속 여부 확인)
Step 2  요구사항정의서 생성          ← gx-요구사항정의서 의 생성 단계
Step 3  화면목록표 생성              ← gx-화면목록표 의 생성 단계
Step 4  [필수 중단점] 게이트 1 — ID 확정
Step 5  프로그램정의서 · 인터페이스정의서 · 테이블정의서 생성
Step 6  [필수 중단점] 게이트 2 — 5종 일괄 검토
Step 7  저장 + xlsx 추출 질문 (1회)
Step 8  다음 안내 — /gx-testplan, /gx-추적매트릭스
```

**게이트 1 의 경고문** (반드시 표시):

> 여기서 승인하면 **화면ID가 확정**됩니다.
> 프로그램ID·단위테스트ID·테스트케이스ID가 전부 이 화면ID에서 파생되므로,
> 나중에 화면ID를 바꾸면 후속 산출물이 **전부 재채번**됩니다.

Step 5 의 세 산출물은 서로 의존하지 않으므로 순서가 자유롭다.
단, 소프트 선행이 없는 산출물은 게이트 2 요약에 "축약 생성됨" 으로 표시한다.

## 7. `/gx-testplan` 워크플로우

```
Step 0  프로파일 + 하드 선행(요구사항정의서·화면목록표) 확인
Step 1  총괄테스트계획서(TE-01) 생성
Step 2  [필수 중단점] 게이트 1 — 종료기준 확정
Step 3  단위테스트계획서 · 통합테스트시나리오 · 시스템테스트 생성
Step 4  [필수 중단점] 게이트 2 — 4종 일괄 검토
Step 5  저장 + xlsx 추출 질문 (1회)
Step 6  다음 안내 — /gx-테스트결과서, /gx-결함관리대장
```

**게이트 1 의 경고문** (반드시 표시):

> 여기서 확정한 **종료기준**이 IM-03·TE-02·ST-02·TE-06 판정의 **유일한 근거**가 됩니다.
> 결과서의 수치가 이 기준과 어긋나면 감리에서 "시험 절차 미준수" 로 지적됩니다.

Step 3 에서 시스템테스트는 **비기능 요구사항이 0건이면 건너뛰고** 그 사실을 게이트 2 에 명시한다.
비기능 요구사항이 없다는 것 자체가 요구사항정의서의 결함일 수 있으므로 조용히 넘어가지 않는다.

## 8. `/gx-프로젝트설정` Step 7 재작성

현행 Step 7 은 유형별로 개별 커맨드만 나열하고, v1.5.0 신규 3종이 빠져 있다.
파이프라인 중심으로 다시 쓰고 **16개 커맨드를 모두 도달 가능하게** 만든다.

| 유형 | 1순위 (파이프라인) | 이어서 | 상시 |
|------|-----------------|--------|------|
| A 신규 구축 | `/gx-spec` | `/gx-testplan` → `/gx-테스트결과서` | `/gx-결함관리대장`, `/gx-추적매트릭스`, `/gx-감리대응` |
| B 추가 개발 | `/gx-spec` (이어쓰기) | `/gx-testplan` (추가분만) | 〃 |
| C 산출물 정비 | `/gx-spec` (역생성) | `/gx-testplan` | 〃 |
