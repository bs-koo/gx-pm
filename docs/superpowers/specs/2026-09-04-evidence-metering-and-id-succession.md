# 근거 계측과 ID 승계 설계

> v3.0.0 을 실제 프로젝트(`D:\SQ\memo`, C유형)에 돌리고 A유형(RFP만) 경로를 역추적해
> 드러난 결함 4건을 막는다. 이 문서가 구속력 있는 정본이다.

**대상 버전**: v3.0.0 → v3.1.0
**선행 정본**: `docs/superpowers/specs/2026-09-03-function-axis-three-doc-design.md`

## 1. 무엇이 틀렸나

### 1.1 확인된 결함 4건

| # | 결함 | 근거 위치 | 실제 피해 |
|---|------|----------|----------|
| **D1** | `새로쓰기` 가 ID 를 처음부터 다시 매긴다 | `skills/detect-existing-artifact/SKILL.md` 「새로쓰기 선택 시」 | memo 에서 `RSV-RE-003` 이 「비밀번호 길이」→「이메일 형식 검증」으로 의미가 바뀌었다. 개정이력의 불변 키 대조가 성립하지 않았다 |
| **D2** | 제약이 **비었다는 사실**을 세는 곳이 없다 | `templates/AN-03-function-spec.md:44` 가 "제약이 비면 테스트가 정상 케이스만 나온다"고 경고하지만 계측하지 않는다 | 경계 케이스가 없는 기능이 조용히 통과한다 |
| **D3** | `[확인필요] 0건` 의 의미를 판정할 수 없다 | `commands/gx-spec.md:143` 이 `{K}건` 만 낸다 | 0건이 "입력이 충분했다"인지 "지어냈다"인지 구분이 안 된다 |
| **D4** | DDL 부재 사실이 문서에 안 남는다 | `commands/gx-spec.md:128` — 게이트 2 **화면에만** 적는다 | 게이트가 지나가면 사라진다. 나중에 이 문서가 실제 스키마로 오독된다 |

### 1.2 결함이 아니었던 것 (기록)

- **비기능 요구사항이 DE-13 에 안 간다** — 사실이 아니다. memo 에서 비기능 7건이 전부
  DE-13 에 반영됐고 `연계기능ID` 공란 행도 6건 존재한다. 앞선 관찰이 틀렸다.
- **ID 재채번이 규칙 위반이다** — 규칙 위반이 아니다. `새로쓰기` 의 설계된 동작이었다.
  결함은 "규칙을 어겼다"가 아니라 **"컬럼만 바꿔 다시 뽑으면서 ID 는 지키는 경로가 없다"** 이다.

### 1.3 D1 의 파급 — 왜 이게 가장 무거운가

`skills/manage-revision-history/SKILL.md` Step 2 가 산출물의 **불변 키**로 직전 버전과 대조한다.

| 산출물 | 불변 키 |
|--------|--------|
| AN-02 | 요구사항ID |
| AN-03 | 기능ID |
| DE-13 | 테스트ID |

ID 가 밀리면 이 대조가 전건 「삭제 + 추가」로 나온다. **개정이력이 무의미해진다.**
개정이력은 이 플러그인이 v3.0.0 에서 새로 세운 축이므로, D1 은 그 축을 무너뜨린다.

### 1.4 D2·D3 이 같은 뿌리인 이유

둘 다 **"근거가 없다는 사실을 세지 않는다"** 이다.

`templates/AN-03-function-spec.md:41-48` 의 도출 사다리:

```
1. 요구사항 상세내용에 명시된 입력
2. 처리내용에서 역산
3. 기존 DDL 이 있으면 컬럼 제약(길이·NotNull)
셋 다 실패하면 [확인필요] 로 두고 지어내지 않는다.
```

여기에 두 구멍이 있다.

- **항목은 찾았으나 제약을 못 찾은 경우**가 사다리에 없다. `이메일(필수)` 처럼 제약 없이
  적히면 실패로 치지 않아 `[확인필요]` 가 붙지 않는다 (memo `RSV-FN-002` 가 실제로 그렇다).
- **소스 역추출**이 사다리에 없다. memo 에서 「검증 순서 고정」·「capacity 없으면 0」 같은
  규칙은 전부 소스에서 나왔는데, 정본에 없는 근거다. 근거 단수를 셀 수 없다.

A유형(RFP만)에서는 3단이 통째로 없어져 이 구멍이 전면화된다.

## 2. 고침의 원칙

1. **컬럼 정본은 건드리지 않는다.** 사용자가 정한 열 구성(10·10·15·11·9)이 정본이다.
   계측 결과는 컬럼이 아니라 **게이트 출력**과 **비고 열**로 낸다.
2. **지어내지 않는다.** 근거가 없으면 채우는 게 아니라 **세어서 보고한다.**
   경계값을 자동 보강으로 메우면 근거 없는 테스트가 된다.
3. **구조 신호를 만드는 주체를 확인한다.** 어떤 사실이 "구조적으로 드러난다"고 말하려면
   그 신호를 누가 만드는지를 봐야 한다 (v3.0.0 최종 리뷰 I2 에서 배운 것).
4. **게이트를 늘리지 않는다.** 새 판단은 기존 게이트 3개 안에 넣는다.

## 3. 근거 규칙 정본 (신설: `templates/evidence-rules.md`)

D2·D3 의 정본이다. AN-03·DE-13·`/gx-spec` 이 이 문서를 참조한다.

### 3.1 근거 4단

기능명세의 `입력항목`·`처리내용(로직)` 을 채우는 근거는 넷이다.
번호가 작을수록 우선한다.

| 단 | 근거 | 가용 판정 | 비고 |
|---|------|----------|------|
| 1 | 요구사항 상세내용 | 항상 가용 | AN-02 가 하드 선행이다 |
| 2 | 처리내용 역산 | 항상 가용 | 자기 산출물이다 |
| 3 | 기존 DDL 의 컬럼 제약 | `profile.assets.ddlFile` 이 있으면 가용 | |
| 4 | 기존 소스의 구현 | `profile.assets.sourcePath` 또는 `source-index.json` 이 있으면 가용 | v3.0.0 정본에 빠져 있던 단이다 |

**3·4 단이 실제 변수다.** A유형(신규 구축)은 둘 다 없어 2/4 가 된다.

### 3.2 `[확인필요]` 는 두 종류다

| 표기 | 뜻 | 결과 |
|------|-----|------|
| `[확인필요:항목]` | 입력항목 자체를 못 정했다 | 그 항목이 아예 없다 |
| `[확인필요:제약]` | 항목은 정했으나 타입·길이·범위·형식·열거값을 못 정했다 | **경계 케이스가 안 나온다** |

AN-03 `입력항목` 열의 형식은 `항목명(타입, 제약, 필수여부, 기본값)` 이다.
괄호 안에서 **정량 제약 자리가 비면** `[확인필요:제약]` 을 `비고` 열에 적는다.

`필수` 만 있고 길이·범위·형식·열거값이 하나도 없으면 제약이 빈 것이다.
`이메일(필수)` 는 제약이 비었고, `이메일(필수, 1~255자)` 는 차 있다.

집계할 때는 두 종류를 합쳐 `[확인필요] {K}건 — 항목 {K1} / 제약 {K2}` 로 낸다.

### 3.3 근거 가용도 경고 (D3 의 핵심)

게이트 2 에 근거 가용도를 함께 낸다.

```
근거 가용도 2/4 — 요구사항 상세 ✓ / 처리내용 역산 ✓ / 기존 DDL ✗ / 기존 소스 ✗
```

**가용도가 4/4 미만인데 `[확인필요]` 가 0건이면 경고한다.**

```
⚠ 근거 4단 중 2단만 살아 있는데 [확인필요] 가 0건입니다.
   문서 근거 없이 채운 값이 없는지 확인하세요.
```

근거가 덜 살아 있는데 아무것도 확인이 필요하지 않다는 건 산술적으로 이상하다.
이 한 줄이 없으면 A유형에서 "지어낸 값"과 "충분한 입력"이 화면에서 똑같아 보인다.

### 3.4 제약 미상은 자동 보강 대상이 아니다

`skills/generate-unit-test-plan/SKILL.md` Step 6 의 자동 보강은
**제약이 있는데 케이스가 없을 때만** 적용한다.

제약 자체가 없으면 보강하지 않는다. 경계값을 지어내는 것이 되기 때문이다.
`제약 미상` 목록에 넣어 게이트 3 에 보고하고, 사용자가 제약을 주면 그때 보강한다.

## 4. DDL 부재 표기 (D4)

### 4.1 규칙

기존 DDL 이 없어 **컬럼 전건이 `신규`** 가 된 경우, DE-08 문서의 `## 개정이력` **바로 위**에
이 줄을 넣는다.

```
> ⚠ **기존 DDL 부재** — 이 문서는 AN-03 기능명세의 입력항목에서 도출한 **설계 초안**이다.
> 실제 스키마가 아니므로, 개발 착수 후 실제 DDL 로 `/gx-테이블정의서` 를 다시 돌려 재생성한다.
```

기존 컬럼이 **1건이라도** 있으면 넣지 않는다. 전건 신규일 때만이다.

### 4.2 왜 화면이 아니라 문서인가

`commands/gx-spec.md:128` 은 이 사실을 게이트 2 **화면**에 적는다.
게이트를 승인하면 화면은 사라지고 문서만 남는다. 이 문서를 나중에 여는 사람은
그것이 설계 초안인지 실제 스키마인지 알 방법이 없다.

**이 플러그인이 없애려던 문제가 정확히 그것이다** — 문서와 실제가 어긋나는 것.

## 5. ID 승계 (D1)

### 5.1 `새로쓰기` 의 의미를 바꾼다

| | 지금 | 바꾼 뒤 |
|---|------|--------|
| 백업 | `backup/` 에 저장 | 그대로 |
| 본문 | 처음부터 다시 도출 | 그대로 |
| **ID** | **1번부터 다시 매김** | **직전 버전과 대조해 승계** |
| 완전 초기화 | 기본 동작 | 대조 결과 화면의 **3번 선택지** |

선택지는 3개를 유지한다 (`이어쓰기` / `새로쓰기` / `열기`).
`새로쓰기` 를 골랐을 때 실수로 ID 를 날리는 경로가 사라진다.

### 5.2 신설 스킬 `reconcile-ids`

**언제 도는가**: 산출물 본문을 도출한 직후, **게이트 승인 전**.
게이트에서 사용자가 보는 표에 이미 최종 ID 가 있어야 한다.

**대상**: AN-02 · AN-03 · DE-13 셋뿐이다.
DE-08 은 `테이블명 + 컬럼명` 이 자연 키라 승계가 필요 없고, AN-05 는 ID 를 갖지 않는다.

#### Step 1 — 직전 버전 로드

`backup/` 에서 해당 산출물의 가장 최근 파일을 읽는다.
없으면 전건 신규로 보고 순번 1부터 부여한 뒤 종료한다.

#### Step 2 — 대조 키

| 산출물 | 1차 키 (완전일치) | 2차 키 (의미일치) |
|--------|------------------|------------------|
| AN-02 | 요구사항명 | 요구사항 상세내용의 주 동작 + 대분류 |
| AN-03 | 기능명 | 처리내용(로직)의 주 동작 + 연계요구사항ID |
| DE-13 | 연계기능ID + 입력 | 기대결과 + 사전조건 |

#### Step 3 — 판정 사다리

| 순서 | 조건 | 처리 |
|---|------|------|
| ① | 1차 키가 완전히 같다 | **승계**. 묻지 않는다 |
| ② | 1차 키는 다르나 2차 키가 같다 | **승계 후보**. 그 자리에서 묻는다 |
| ③ | 둘 다 다르다 | **신규**. 마지막 순번 다음부터 |
| ④ | 직전에 있는데 새 결과에 없다 | **삭제**. §5.3 |

한 항목이 ①과 ② 양쪽에 걸리면 ①이 이긴다.
②에서 후보가 둘 이상이면 전부 보여주고 고르게 한다.

**②는 이월하지 않는다** (§7).

#### 5.3 삭제 처리

| 산출물 | 처리 |
|--------|------|
| AN-02 | `상태` 열을 `삭제` 로 두고 **행을 남긴다**. `변경 근거` 에 사유를 적는다 |
| AN-03 | 행을 만들지 않는다. ID 는 폐기하고 재사용하지 않는다 |
| DE-13 | 〃 |

AN-03·DE-13 에는 `상태` 열이 없어 남길 자리가 없다. 컬럼 정본은 늘리지 않는다(§2-1).
삭제 건수는 게이트에 보고한다.

#### Step 4 — 신규 순번 시작점

직전 버전의 **최대 순번 + 1**. 삭제된 항목의 순번도 차지한 것으로 본다
(`templates/id-naming-rules.md` 불변 규칙 — 구멍을 허용한다).

#### Step 5 — 승계안 보고 + 승인

**AskUserQuestion** 으로 묻는다.

```
직전 버전과 대조했습니다. ({산출물명})

  승계   {S}건   기존 ID 유지
  신규   {N}건   {첫ID} 부터 부여
  삭제   {D}건   ID 폐기 (재사용 안 함)

  ⚠ 판정 필요 {A}건
     · "{직전 이름}" ↔ "{새 이름}"  → 같은 항목이면 {기존ID} 승계

  1. 위 승계안대로 진행
  2. 판정 필요 건을 하나씩 확인
  3. ID 를 전부 새로 매기기 (기존 ID 폐기)
```

`{A}` 가 0이면 2번을 빼고 1·3번만 낸다.

3번을 고르면 한 번 더 확인한다.

```
기존 ID {S}건이 폐기됩니다. 개정이력의 불변 키 대조가 성립하지 않아
직전 버전과의 변경 내역을 만들 수 없습니다. 계속할까요?
```

#### Step 6 — 개정이력으로 넘긴다

**`reconcile-ids` → `manage-revision-history` 순서를 지킨다.**
ID 가 확정돼야 불변 키 대조가 성립한다. 뒤집으면 개정이력이 전건 「삭제 + 추가」로 나온다.

## 6. 게이트 출력 변경

기존 게이트 3개의 출력에만 항목을 더한다. **게이트를 늘리지 않는다.**

### 게이트 2 (기능 + 테이블)

기존 목록에 세 줄을 더한다.

```
  • 근거 가용도 {n}/4 — 요구사항 상세 {✓} / 처리내용 역산 {✓} / 기존 DDL {✗} / 기존 소스 {✓}
  • [확인필요] {K}건 — 항목 {K1} / 제약 {K2}
  • 제약 미상 기능 {P}건 — 입력항목에 정량 제약이 없어 경계 케이스가 안 나옵니다
```

`{n} < 4` 이고 `{K} == 0` 이면 §3.3 의 경고를 함께 낸다.

### 게이트 3 (테스트 + 추적)

```
  • 제약 미상으로 경계 케이스가 없는 기능 {P}건 — 지어내지 않고 남겨둔 것입니다
```

## 7. 이월 금지 항목이 넷이 된다

`templates/pipeline-protocol.md` 의 이월 금지 목록에 **ID 승계 판정 애매성**을 더한다.

| # | 항목 | 이월하면 안 되는 이유 |
|---|------|---------------------|
| 1 | 시안/대안 감지 | 시안 선택이 틀리면 뒤 산출물이 전부 틀린다 |
| 2 | 표 판정 애매성 | 게이트로 미루면 이미 그 건수로 만들어진 뒤다 |
| 3 | 신규 컬럼명 결정 | MCP 가 `decisionRequired` 를 내면 그 자리에서 |
| 4 | **ID 승계 판정 애매성** | **게이트로 미루면 그 ID 로 이미 아래 산출물이 만들어진 뒤다** |

4번의 근거를 DE-13 으로 확인한다. 테스트ID 를 게이트 3 에서 고치면

## 10. 검증

이 플러그인은 프롬프트라 동작 테스트가 불가능하다.
`tests/test_plugin_consistency.py` 의 기존 방식대로 **규칙문의 존재와 정합**을 검사한다.

| 검사 | 무엇을 막나 |
|------|------------|
| `evidence-rules.md` 가 `[확인필요:항목]`·`[확인필요:제약]` 을 모두 정의한다 | 2종 분리가 말뿐인 것 |
| 근거 단 표가 4행이다 | 소스 역추출이 다시 빠지는 것 |
| `generate-function-spec` 이 2종을 모두 안다 | 정본만 고치고 실행부를 안 고치는 것 |
| 게이트 2 블록에 `근거 가용도`·`[확인필요]`·`제약 미상` 이 있다 | 계측하고 안 보여주는 것 |
| `generate-unit-test-plan` 이 `제약 미상` 을 자동 보강에서 제외한다 | 경계값을 지어내는 것 |
| DE-08 템플릿과 `convert-ddl-to-tablespec` 이 `설계 초안` 을 문서에 남긴다 | 화면에만 적고 끝내는 것 |
| `detect-existing-artifact` 의 새로쓰기 절이 `reconcile-ids` 를 부른다 | D1 이 그대로 남는 것 |
| 이월 금지 항목이 4개다 | ID 승계 판정이 게이트로 밀리는 것 |
| `manage-revision-history` 가 `reconcile-ids` 선행을 명시한다 | 순서가 뒤집혀 개정이력이 무의미해지는 것 |

기존 검사(스킬 배선·정본 참조·버전 정합·개수 표기)는 새 스킬 1개가 늘면서 자동으로 걸리므로
따로 만들지 않는다.
