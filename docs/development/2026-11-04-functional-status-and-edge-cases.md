# 기능 개선 반영 현황과 엣지케이스 실측

점검일: 2026-11-04 (Asia/Seoul)

## 0. 후속 개선 반영

아래 1~6절과 실측 JSON은 **개선 전 점검 기록**이다. 후속 작업에서 다음 내용을 실제 수정했다.
원본 관측 JSON과 당시 소스 지문은 과거 증거로 보존한다.

| 영역 | 후속 반영 |
|---|---|
| 요구사항 검토 | 단독 작성·게이트 1의 전체 승인 전 품질 검토, 추천·근거·대안·영향·직접 의견, 실제 응답 대기 |
| 변경 관리 | 전체/부분/추가 자료 구분, 혼합 변경 대조, 누락 자동 삭제 금지, 현재 승인본·삭제 번호 이력 기반 ID 승계 |
| 검토 기준 | 원문·내용 지문·CQ 적용 기준과 미반영 후속 변경의 상태 양식 및 관리 절차 추가 |
| 문체 | 명세·시험 결과·확인요청·개정이력의 공통 업무 문체, 문서별 작성 초점과 저장 전 문장 검토 |
| E01·E07·E08·E09 | 이스케이프 파이프 보존, 코드 블록 표 제외, 등호 입력 텍스트 저장, 셀 한도 초과 거부 |
| E02·E03·E04·E05·E06 | 업무 출력의 `--strict` 구조·ID·미결·검토 상태 검사. 일반 표 변환 API는 호환 경로 유지 |
| E10 | 사람 응답 덮어쓰기 차단, 반영·백업한 기준 SHA-256 확인, 저장 중 변경 감지와 임시 파일 후 교체 |
| E11 | 시험 입력의 내부 공백을 보존해 변경된 데이터에 과거 증적을 재사용하지 않음 |

회귀 검사는 `plugins/gx-pm/tests/test_export_integrity.py`에서 임시 파일을 생성·재개방해 수행한다.
후속 전체 검사 397개, 스킬 정적 검사 20개와 `git diff --check`가 통과했다.
업무 질문·상태 관리·문체는 공통 스킬·템플릿의 실행 지침이며, 실제 두 호스트의 전체 대화를 종단 실행한 결과와는
구분한다. 원문 해석의 타당성·문장의 자연스러움·MCP가 포함된 사용자 흐름은 실프로젝트 시나리오 검토가 남아 있다.
위 검증 시점에는 설치 캐시 교체·릴리스·커밋·PR을 수행하지 않았다. 이후 버전 반영 내역은
플러그인 CHANGELOG의 v4.6.0을 따른다. 실제 두 호스트 대화 검증과 설치 캐시 교체는 이 검사에 포함하지 않는다.

## 1. 초기 점검 당시 반영 상태

**초기 점검 당시 앞서 제안한 기능 개선은 구현 전이었다.** 당시 변경은 플러그인·커맨드·스킬 설명, README, 소개 메타데이터와 안내 문구 정비였다. 아래 표는 그 시점의 기록이며 현재 후속 반영은 0절을 따른다.

초기 점검 시 작업 트리와 HEAD를 대조한 결과는 다음과 같다.

| 대상 | 반영 상태 |
|---|---|
| 플러그인·마켓플레이스 소개 | 문구 정비 완료 |
| 활성 커맨드 9개·스킬 20개 | description만 변경. 실행 본문은 변경하지 않음 |
| README·공통 지침 | 용어·시작 안내·설명 정비. 요구사항 단독 작성 경로 안내 강화 |

기능 분석과 문서 정비는 각각 완료했지만, 기능 수정과 실제 사용자 흐름 검증은 남아 있다. 종전 테스트 385개 통과는 현재 검증 범위에 대한 결과이며, 제안한 기능이 구현됐거나 모든 엣지케이스가 안전하다는 증거가 아니다.

## 2. 이번 점검 방법

기존 산출물을 건드리지 않는 임시 폴더에서 현재 Excel 변환기로 통합문서를 생성한 뒤 다시 열어 값·열·시트·셀 타입을 확인했다. 시험 증적 도구는 실제 케이스 지문 함수와 표 파서를 호출했다. 관측 자료는 [엣지케이스 실측 JSON](evidence/2026-11-04-edge-case-observations.json)에 저장했다.

총 **15개 조건을 확인해 문제 조건 11개와 정상 대조 4개**를 기록했다. 이 수치는 기존 unittest의 실패 개수가 아니다. 일부는 값이 변하는 결함이고, 일부는 변환기 단독 사용에서 검증·보호를 보장하지 않는 설계 한계다.

Claude·Codex의 실제 명세 작성 대화를 종단 실행하지 않았다. 따라서 프롬프트 규칙의 모순은 문서 검토 결과로, 실행 도구의 관측은 실측으로 구분한다. 가상의 업무 수치나 사용자 승인 기록을 만들지 않았다.

## 3. 실제 확인한 문제 조건

| ID | 조건 | 관측 결과 | 개선 판단 |
|---|---|---|---|
| E01 | 요구사항 셀 안에 `A\|B` 포함 | 상세내용이 잘리고, 상태 칸은 빈칸·근거 칸은 `유지`로 이동 | **출력 값 손상.** 이스케이프 파이프를 인식하는 공통 파서 필요 |
| E02 | DE-13의 필수 `결과` 열 누락 | 오류 없이 11열 Excel 생성 | 필수 헤더 검증 필요 |

| E04 | `요구사항ID` 헤더를 중복하고 다른 값 입력 | 재정렬 후 첫 ID 칸에 REQ-999, 추가 칸에 원래 REQ-001 출력 | **열 의미 변경.** 중복 헤더를 먼저 거부해야 함 |
| E05 | 헤더는 10열인데 본문 행은 8칸 | 부족한 칸을 빈칸으로 보정해 출력 | 행 구조 오류를 조용히 보정하지 말고 위치를 알려야 함 |

| E07 | 코드 블록 안에 참고용 요구사항 표 포함 | 참고 ID REQ-999가 실제 본문 REQ-001과 함께 출력 | **가짜 요구사항 혼입.** 코드 블록의 표와 실제 데이터 표를 구분해야 함 |

| E09 | 상세내용 33,000자 입력 | 저장 후 값이 32,767자로 줄어듦 | **원문 일부 누락.** 저장 전에 초과 길이를 검출해 분할·별도 첨부·출력 보류 중 처리 필요 |
| E10 | 확인요청서 Excel에 답을 적은 뒤, 이전 md로 같은 파일 재출력 | `수정 / 관리자`가 빈칸 두 개로 바뀜 | **응답 보호가 호출 절차에 의존.** 기존 응답 대조 없이 같은 경로를 덮는 작업 차단 필요 |

E09에서는 변환기가 행 높이 경고와 함께 “원문은 보존되어 있다”고 안내했지만, 다시 읽은 셀 값은 233자 짧았다. 표시 높이 초과와 저장 가능한 문자열 길이 초과를 별도로 검증해야 한다.

## 4. 정상 동작도 확인한 대조 조건

| ID | 확인한 내용 | 결과 |
|---|---|---|
| C01 | 소량 확인요청서의 4개 시트와 빈 응답 | 안내·가정 확인·미확정 확인·요청 이력 유지. 응답 자동 선택 없음 |

C04는 같은 저장소에 이미 다른 파서가 있음을 보여준다. Excel 파서 수정 시 이를 참고할 수 있지만, 공통화 전에 각각의 코드 블록·줄바꿈·이스케이프 계약도 확인해야 한다.

## 5. 요구사항 생애주기에서 추가로 조사한 엣지케이스

아래는 **현행 규칙 대조로 확인한 위험**이다. 실제 에이전트가 해당 결과를 만들었다고 관측한 것은 아니다.

| 사례 | 현재 규칙의 빈틈 | 필요한 동작 |
|---|---|---|
| 일괄 게이트 1에 중요한 모호성 1건 | 공통 수집 규칙은 있지만 게이트 본문은 일반 승인·저장 중심 | 구체 질문·추천·응답 수신 여부를 확인한 뒤 의존 작업 진행 |
| 요구사항만 작성했는데 정책 미설정 | 단독 실행은 기본 정책 사용 | 분할·가정 등 결과를 바꾸는 정책을 설명하고 빠진 판단만 확인 |
| “추가 자료”에 기존 요구 일부만 등장 | 기존에만 있는 행을 삭제 후보로 보는 규칙 | 전체 개정본과 부분 자료 구분. 입력 부재를 삭제 요청으로 해석하지 않음 |
| 신규 2건·기존 수정 1건이 한 파일에 섞임 | 이어쓰기는 기존 행 수정 금지 | 먼저 추가·변경·동일·충돌을 구분하고 한 번의 검토로 처리 |
| 동일 원문 ID의 내용이 개정됨 | 같은 원문 ID의 중복 제거와 원본 개정 추적 부족 | 중복 자료와 동일 항목의 변경을 구별 |

## 6. 권장 구현 순서와 검증 기준

### 1차: 요구사항 검토·질문

- AN-02 단독·게이트 1에서 동일한 품질 점검 → 질문 등록 → 추천·대안 제시 → 실제 응답 반영 절차 사용.
- 초안 저장과 내용 확정 구분. 중요한 미결을 일반 승인으로 닫지 않음.
- 소량 질문과 다량 확인요청서 모두 사용자에게 실제 질문·파일·응답 방법을 제시.
- 검증: 중요한 모호성 1건에서 답 전 의존 확정 금지, 6건에서 실제 파일 발행, 부분 답변에서 해당 항목만 반영.

### 2차: 변경 반영·ID·사용자 응답 보존

- 전체/부분 입력의 성격, 변경 전후, 기존 ID와 출처 개정 기준을 대조.
- 질문·제안·응답의 적용 버전과 갱신 범위 관리.
- 완료 문서 기준선과 사용 번호 이력을 보존.
- 검증: 신규·수정 혼합 파일, 같은 이름의 다른 요구, 최대 번호 삭제, 옛 답 정정, 5종 중 일부 갱신, 사람이 편집한 Excel을 포함.

### 3차: 출력과 시험 결과의 신뢰성

- E01·E04·E07~E09의 값·의미 변경 방지, E02·E03·E05의 구조 검증.
- E06·E10은 출력 전 검증과 응답 대조를 공통 실행 단계로 보강.
- E11은 표시상의 공백과 실제 입력 리터럴의 차이를 구별.
- 검증: 문제 조건의 기대 결과를 회귀 테스트로 고정하고, C01~C04의 정상 동작도 유지.

### 두 환경의 실제 사용성 확인

정적 규칙 검사와 파일 도구 검증 이후, Claude와 Codex 각각에서 질문 도구 호출·추천 표시·응답 대기·파일 발행·수정 반영·중단 후 재개를 관측한다. 그 검증 전에는 두 환경의 실제 사용자 흐름을 검증 완료로 표시하지 않는다.

기존 전체 개선 분석은 [요구사항 중심 운영 고도화 분석](2026-11-04-requirements-lifecycle-audit.md)에 있으며, 이번 문서는 실제 반영 상태와 추가 관측을 기록한다.
