# 요구사항 중심 운영과 명세 5종 고도화 분석

분석일: 2026-11-04 (Asia/Seoul)
대상: gx-pm 4.5.0, 저장소 HEAD `39c5ac9`
환경 범위: Claude Code와 Codex 모두
작업 범위: 분석과 개선안 작성. 실행 지침·커맨드·스킬·변환기 코드는 변경하지 않았다.

## 1. 판단

**요구사항정의서의 최초 작성·질문·반복 변경을 중심에 놓고, 나머지 문서는 확정된 요구사항에서 필요한 시점에 파생시키는 구조로 바꾸는 것이 좋다.**

현재도 요구사항 단독 작성, 확인요청서, ID 승계, 영향 안내, 근거 버전 대조가 있다. 이를 새로 전부 만드는 문제가 아니다. 각 규칙이 서로 다른 시점과 문구로 연결되어 있고, 가장 중요한 AN-02 단계의 실행 절차와 변경 입력 처리가 상대적으로 약하다. 따라서 질문 문구만 추가하면 같은 누락이 반복될 수 있다.

실무의 기본 경로는 다음 세 가지로 잡는 것이 적절하다.

1. 요구사항정의서만 먼저 작성하고, 모호한 부분을 질문·추천·확인요청서로 정리한다.
2. 요구사항을 여러 번 추가·변경하면서 기존 ID와 사용자의 결정을 유지한다.
3. 후속 문서가 생긴 뒤에는 변경 영향을 보여주고, 요청한 문서와 영향을 받은 행을 갱신한다.

명세일괄은 이 세 경로와 같은 규칙을 사용하는 편의 실행이어야 한다.

설치본의 줄바꿈 형식 차이는 있었지만, 이번에 비교한 활성 자원 내용은 동일했다. 현재 확인한 질문 누락 위험을 단순한 Codex 캐시 구버전 문제로 설명할 근거는 없다. Claude 설치본은 별도로 비교하지 않았다.

## 3. 질문과 확인요청서가 빠질 수 있는 이유

### 3.1 게이트 1의 구체성이 부족하다 — P0

[명세일괄 커맨드](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/commands/gx-명세일괄.md:15)는 모든 게이트에서 `review-confirmations`를 쓰라고 한다. 그러나 [게이트 1 본문](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/commands/gx-명세일괄.md:213)은 표 표시 → 일반 승인 → 개정이력 → 저장으로 이어진다.

게이트 2·3에는 미결 1~5건의 실제 질문, 6건 이상 파일 생성, xlsx 추출, 중단과 재개의 절차가 상세히 적혀 있다. 게이트 1에는 그에 대응하는 구체적인 분기가 없다. AN-02에 태그가 없어도 확인 항목을 모으는 공통 스킬은 있지만, 핵심 단계 본문은 일반적인 “전체 요구사항을 확인해 달라”는 승인으로 읽히기 쉽다.

**개선:** 게이트 1 자체를 `품질 점검 → CQ 등록 → 추천·선택지 제시 → 응답 수신 또는 초안 보류 → 반영 검증 → 요구사항 확정`으로 명시한다. 전체 승인 화면과 개별 미결 질문을 구분한다. 공통 스킬을 정본으로 유지하되, 호출 시점·필수 결과·다음 단계 진입 조건은 커맨드에 명확히 둔다.

### 3.2 단독 작성에서는 확인 항목 수집이 저장 뒤에 온다 — P0

[요구사항정의서 커맨드](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/commands/gx-요구사항정의서.md:110)는 “승인된” AN-02를 저장한 뒤 확인 항목 합계를 판정한다. [공통 실행 규약](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/templates/pipeline-protocol.md:20)도 단독 실행의 확인요청서를 저장 뒤로 둔다.

초안을 먼저 보존하는 것은 필요하다. 다만 초안 보존과 내용 확정을 같은 “승인된 문서 저장”으로 표현하면, 이후에 발견된 범위 미결이 최종 문서처럼 보이는 파일에 남는다. 후속 커맨드의 “승인된 AN-02” 조건도 실제로 판별하기 어렵다.

**개선:** 초안 저장은 허용하고 완료 상태를 별도로 기록한다. 최종 확정 전에 반드시 품질 점검과 확인 항목 검토를 거치게 한다. 파일 존재나 생성 표지만으로 승인됐다고 판단하지 않는다.

### 3.3 질문을 줄이는 정책과 꼼꼼한 확인 요구가 충돌한다 — P1

- [명세일괄 안내](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/commands/gx-명세일괄.md:9)는 “게이트 3곳에서만 판단”이라고 한다. 실제로는 그 밖에도 정책·시안·표 판정·ID 승계·컬럼 결정 질문이 필요하다.
- [단독 실행 규약](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/templates/pipeline-protocol.md:23)은 정책을 묻지 않고 기본값을 사용한다. 가장 자주 쓸 요구사항 단독 경로에서 분할·가정 정책을 설명받지 못할 수 있다.
- [정책 선택지](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/commands/gx-명세일괄.md:149)는 가정으로 채우기를 권장하고, 비워 두는 선택을 테스트가 얇아지는 것으로 설명한다. 정확성을 중시하는 사용자에게 중립적인 비교가 아니다.
- [응답 반영 스킬](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/skills/apply-confirmations/SKILL.md:87)은 설명 요청에도 대화로 답하지 않고 다음 차수 파일로 답하게 한다. 대화에서 즉시 이해하고 선택하려는 흐름과 맞지 않는다.

**개선:** 행정적인 재승인은 줄이고, 업무 판단은 충분히 묻는다. 단독·일괄 모두 같은 질문 정책을 공유한다. 대화로 설명·추가 질문을 주고받은 내용도 CQ 이력에 함께 기록하면 된다. 기록을 남기는 것과 대화를 금지하는 것은 별개다.

### 3.4 모호성을 발견하는 기준과 추천 형식이 충분하지 않다 — P1

현재 AN-02 수집 기준은 원문 충돌·범위·해석 미결 등으로 비교적 넓게만 기술돼 있다. 반면 시안 감지는 특정 표현에 집중한다. “적절하게”, “필요시”, “일정 기간”, “관리자”, “신속하게”처럼 대안 표기가 없는 요구사항도 점검해야 한다.

확인요청서에는 `AI 가 정한 값`과 `근거`가 있지만, 미확정 시트에는 추천안·대안·답에 따른 영향의 일관된 표현 규약이 없다. 후보를 요청하면 다음 차수에 제시하는 경로는 있으나, 처음부터 사용자가 비교할 수 있는 질문 카드가 기본은 아니다.

**개선:** 질문마다 대상·원문·부족한 판단·추천안·추천 근거·대안·영향·직접 의견·보류를 보여준다. 근거가 부족하면 “지금은 확정 보류를 추천”할 수 있어야 한다. 추천을 만들기 위해 임의의 업무 수치를 채우지 않는다.

I01은 지침 연결에서 확인한 위험이며, 실제 에이전트 실행으로 ID 초기화까지 재현한 것은 아니다. 관련 근거: [완료 문서 생성 표지](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/commands/gx-명세일괄.md:517), [중간본 백업 규칙](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/skills/detect-existing-artifact/SKILL.md:139), [승계 기준선 탐색](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/skills/reconcile-ids/SKILL.md:40).

## 5. 각 문서의 내용 품질과 규칙 충돌

### AN-02 요구사항정의서

- **품질 점검을 추출·분류와 분리한다.** 행위자, 실행 조건, 대상, 동작, 결과, 예외, 수치·단위, 권한, 데이터 범위, 검수 가능성, 용어 일관성, 원문 충돌을 점검한다. 모든 항목을 모든 요구사항에 강제로 채우지는 않는다.
- **원문 충실성과 명확화 제안을 구별한다.** 원문 표현을 보존하는 현재 장점은 유지한다. 추가 해석은 원문 사실로 합치지 않고 추천·질문으로 둔다. 사용자가 선택한 뒤 본문과 결정 근거에 반영한다.
- **기능/비기능 키워드 규칙을 고친다.** 현재 `지원`, `인증`, `차단`, `이내` 등이 비기능 보조 키워드다. 규칙을 그대로 대입하면 “회원가입을 지원한다”, “인증번호를 발송한다” 같은 시스템 동작을 비기능으로 보낼 위험이 있다. 이는 실제 모델 오분류 실험 결과가 아니라 현행 판정 사다리의 반례다.
- **복합 요구 처리의 충돌을 없앤다.** 분류 스킬은 정본 판정을 뒤집지 말라고 하면서, 주의사항에서는 기능+비기능 혼합이면 기능으로 분류하라고 한다. 혼합 요구를 분리할지, 공통 품질 제약으로 연결할지 정본을 하나로 정해야 한다.
- **분류를 재계산만 하지 않는다.** 원래 섹션 제목을 대분류로 옮겨 판정 맥락을 복원하려 하지만, 대분류를 업무 중심으로 정리하면 그 맥락이 사라질 수 있다. 사용자가 승인한 판정과 원문 맥락을 내부 기록에 보존한다.
- **같은 원문 ID의 반복과 분할을 구분한다.** 현재 “같은 원문 ID는 1건”이라는 중복 제거와 검증 단위별 분할이 함께 있다. 같은 ID 아래 여러 의무가 있거나, 서로 다른 개정본에 같은 ID로 다른 내용이 있으면 단순 중복 제거를 적용하면 안 된다.
- **변경 사유를 불필요하게 되묻지 않는다.** 현재 자동 생성 금지는 좋지만 “왜 바뀌었는지는 문서에 없다”는 단정은 맞지 않을 수 있다. 새 변경요청서·회의록에 사유가 있으면 그 실제 근거를 제시하고, 정말 없을 때만 묻는다.

### AN-03 기능명세서

- 원본 RFP를 다시 읽지 않는 것은 AN-02를 기준으로 범위를 관리한다는 장점이 있다. 따라서 **AN-02에서 누락·미결이 남으면 이를 해결할 경로가 더 중요**하다. 생성 과정에서 부족한 점을 발견하면 AN-02 보완 후보로 돌려야 한다.
- 입력·처리·출력마다 확정 근거, 설계 제안, 미결을 구별한다. “검증→처리→저장”을 모든 기능에 강제하면 조회·계산·외부 전달 기능에도 가짜 저장 단계가 생길 수 있다. 기능 성격에 맞춰 작성한다.
- 정상·대안·오류 흐름과 권한, 중복 요청, 동시 수정, 외부 실패, 트랜잭션 경계를 점검하되, 근거가 없는 정책은 질문한다.
- `[가정]` 여부를 “그 값 없이도 구현할 수 있나”만으로 판단하기에는 부족하다. 업무 범위·요금·권한·보존·동의처럼 사용자가 결정해야 할 정책인지와 구현상 선택인지도 구분해야 한다.
- 근거 가용도 4단 중 “자기 처리내용 역산”을 항상 가용으로 세는 것은 독립된 외부 근거와 다르다. 실제 파일을 읽었는지, 그 항목의 근거를 찾았는지, 모순이 있는지를 보여주는 쪽이 유용하다. 자료가 적어도 요구가 충분할 수 있으므로 4/4 미만·미결 0건을 산술적 이상으로 단정하지 않는다.

### DE-08 테이블정의서

- **입력항목을 전부 DB 컬럼으로 보지 않는다.** 검색어·페이지 번호·파일 스트림·확인용 비밀번호·외부 API 인자는 저장 대상이 아닐 수 있다. 영속 데이터·조회 조건·임시값·계산값·외부 데이터로 먼저 가른다.
- DDL이 없는 신규 구축에서 “역생성 전용”과 “전건 신규 컬럼 제안”이 함께 작동한다. 테이블 소속 자체가 없는 상황은 컬럼 표준화만으로 해결되지 않는다. 기존 DDL 반영본과 설계 후보를 명확히 구별하고, 소속 미결은 질문한다.
- **업무 제약과 저장 제약은 둘 중 하나만 정답인 관계가 아니다.** 기능에서 최대 50자, DB에서 100자이면 업무는 50자·저장은 100자일 수 있다. 불일치의 의미를 설명하고 사용자가 정책·구현 차이를 판단하게 한다.
- 응답 반영 예시는 DE-08 기존 컬럼 길이도 바로 바꾸는 것으로 읽힐 수 있다. 기존 이름·타입·제약을 유지하는 규칙과 충돌한다. 기존 DDL 사실은 유지하고, 변경 제안·승인·새 DDL 수신을 별도 단계로 둔다.
- 문자 수와 바이트 수, Unicode, 정밀도·스케일, 날짜·시간대, 복합 키·FK·UNIQUE·CHECK·NULL 규칙도 테스트 근거로 다룰 수 있어야 한다. 제출 양식을 무작정 늘리기보다 부속 근거와 구조화된 제약 기록을 활용한다.
- `sourcePriority`는 읽고 저장하는 설명이 있지만 프로파일 스키마에는 정식 필드가 없다. 저장 위치·허용값·프로젝트별 변경과 재검증 범위를 정한다. 특정 도메인 기본값도 프로젝트 맥락에 따라 제안해야 한다.

### DE-13 단위테스트계획서

- **제약 우선순위가 충돌한다.** 생성 스킬은 DE-08을 무조건 우선하지만 설계 스킬은 AN-03이 더 좁으면 그쪽을 우선한다. 업무 허용 범위와 저장 허용 범위를 각각 검증하도록 정본을 통일한다.
- 기능 유형별 최소 4~8건 강제와 `testDensity=null`, 근거 없는 케이스를 만들지 않는 원칙이 충돌한다. 건수는 충분성 경고로 쓰고, 실제 분기·제약·위험을 기준으로 케이스를 만든다.
- “정상만 있으면 차단”은 단순 무입력 조회에서도 무조건 적용하지 않는다. 예외가 불필요한 이유를 검토·기록하는 예외 경로가 필요하다.
- `[미확정]` 제약은 보강하지 않는 규칙과 “제약 미확인 케이스를 만들고 비고에 표시”하는 설계 스킬 문구가 충돌한다. DE-13에는 비고 열도 없다. 실행 불가 초안 케이스의 표현·상태를 하나로 정한다.
- 계획서 예시의 “101자”, “유효한 파일”만으로는 바로 실행하기 어렵다. 실제 문자열·생성 절차·파일·체크섬 등 재현 가능한 입력을 제공한다. 에러 문구를 원문 그대로 쓰려면 확인한 원문이 있어야 한다. 제안 문구를 확정된 화면 문구로 만들지 않는다.
- 일부 요구가 바뀌면 영향 케이스를 재도출하고, 의존성·입력 파일·관련 IM-03 결과의 재검증 필요를 함께 표시한다.

### AN-05 추적매트릭스

- 누락 한 가지를 먼저 매칭하면 실패·설계 미반영·예외 누락이 동시에 있어도 다른 문제가 가려진다. 제출 표에 대표 문제를 두더라도 부속 리포트는 적용 가능한 문제 전부를 보여준다.
- 템플릿은 “전부 정상 흐름이면 예외 없음”으로 정의하지만 스킬은 테스트 수 1건으로 추정한다. 정상 케이스가 2건이면 놓치고, 1건이 예외 케이스여도 같은 판정을 할 수 있다. 케이스 성격·커버리지 근거로 판단해야 한다.
- 요구사항만 먼저 작성한 단계에서는 후속 문서 부재가 정상이다. “미작성”, “아직 작성 대상 아님”, “대조 불가”, “작성됐으나 누락”을 구분해 진행 단계에 맞게 보고한다.
- 기능 도출률의 분모는 실제 기능 요구사항이어야 한다. 현재 `id-trace`의 전체 요구사항 분모는 비기능을 포함해 정상 구조도 낮게 보일 수 있다. 비기능 검증률도 단순히 기능 미연계 요구사항 전체를 분모로 쓰지 않는다.
- 문서 연결 완료율, 최신 기준 반영률, 테스트 작성률, 수행률, 통과율을 구분한다. 낡은 결과를 보여줄 수는 있지만 현재 요구의 검증 완료로 합산하지 않는다.

### IM-03 결과서와 내부 수행대장

- 실제 수행·관측·증적을 요구하는 기존 설계는 유지할 가치가 크다. 요구사항 변경 시 해당 테스트 결과의 유효성·재시험 필요가 자연스럽게 연결돼야 한다.
- 현재 “수행률”은 실제로는 일부 미검증을 분모에서 뺀 통과율이다. 보고 화면에서는 실제 수행률·전체 대비 통과율·판정 대상 통과율·제외 건수를 별도로 설명하는 편이 안전하다.
- 결과서 xlsx 직접 수정은 반영되지 않는다. 요구사항 Excel과 마찬가지로, 사용자 편집 반영 여부를 파일을 제공하는 시점부터 명확하게 안내해야 한다.
- 결과서와 수행대장은 순서대로 파일을 쓴다. 두 번째 쓰기에 실패할 때의 부분 반영을 줄이도록 임시 파일 검증·쓰기 상태·복구 절차를 보강한다. 승인 후 입력 변경 감지는 이미 일부 구현돼 있으므로 이를 공통 문서 갱신에도 확장할 수 있다.

## 6. 실제 재현한 Excel 출력 문제

기존 파일을 건드리지 않는 임시 폴더에서 현재 `export-xlsx.py`를 불러 실제 xlsx를 만들고 다시 열었다.

| 사례 | 재현 결과 | 판단 |
|---|---|---|
| 미확정이 있는 AN-02를 `draft=False`로 출력 | `[미확정] 가입 대상`이 들어간 최종본 형식의 xlsx 생성 성공 | 최종 확정 제한은 지침에 있고 변환기에는 없다. 호출자가 절차를 놓치면 막지 못함 |
| DE-13의 12개 필수 열 중 `결과` 열을 뺀 표 출력 | 오류 없이 11열 xlsx 생성 | 양식 필수 열 검사 부재 |
| AN-02 상세내용에 `권한=A\|B` 입력 | 헤더 10칸·본문 11칸으로 파싱. 결과의 상태 칸은 빈칸, 요구사항 근거 칸에는 `유지`가 들어감 | 셀 안 이스케이프 파이프 처리 실패로 실제 값이 다른 열에 배치됨 |

근거 코드: [표 파싱](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/utils/export-xlsx.py:292), [열 매칭](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/utils/export-xlsx.py:356), [최종 출력](D:/SQ/gx-pm/gx-pm/plugins/gx-pm/utils/export-xlsx.py:674).

변환기는 현재 범용 출력 도구이므로, 첫 사례는 기존 API 계약을 어긴 버그라고 단정하기보다 **최종본 규칙을 실행 코드로 보장하지 못하는 설계 한계**로 본다. 반면 세 번째는 출력 내용이 변하는 재현 가능한 결함이다.

권장 조치:

1. 제출용 문서는 필수 헤더·중복 헤더·행 칸 수·ID·상태·참조 무결성을 엄격히 검증한다.
2. 이스케이프 파이프·셀 줄바꿈·코드 표기·표 내부 문자열을 보존하는 공통 파서를 사용한다.
3. 최종본 출력은 문서의 확정 상태·미결 목록·근거 최신성을 검사한다. 검토용 초안은 별도 경로로 계속 제공한다.
4. 출력 파일을 다시 열어 주요 값·시트·필수 열·드롭다운·응답 빈칸을 확인한다.
5. `--dir .`로 프로젝트의 모든 md를 무조건 출력하지 않고, 요청한 산출물 목록을 명시적으로 전달한다. 확인요청서 재출력은 기존 사람 응답 보호 절차를 거치게 한다.

## 7. 권장 사용자 흐름

### 7.1 요구사항정의서만 처음 작성

1. 현재 자료와 프로젝트 정보를 읽는다. 요구사항 작성에 필요 없는 DB·프레임워크·미사용 접두어는 나중에 받을 수 있게 한다.
2. 원문 자료를 등록하고 추출 범위·원문 위치를 기록한다.
3. 요구사항을 추출·분할·분류한다. 원문 사실과 명확화 제안을 구분한다.
4. 품질 점검에서 질문이 필요한 항목을 CQ로 모은다.
5. 중요한 판단부터 대화로 제시한다. 각 질문에 추천과 이유·대안을 붙이고 직접 의견·보류를 받는다.
6. 질문이 많거나 사용자가 파일을 원하면 확인요청서 xlsx를 실제 생성하고 링크·대표 항목·응답 방법을 보여준다.
7. 응답을 반영해 달라진 요구사항을 보여준다. 미결이 남으면 초안과 남은 결정을 명시한다.
8. AN-02가 확정되면 단독 산출물로 종료한다. 후속 4종은 사용자가 요청했을 때 이어간다.

프로젝트 설정을 완전히 제거하자는 뜻은 아니다. 요구사항 작업에 필요한 최소 맥락과 후속 설계·시험 준비 정보를 단계적으로 받자는 제안이다. 기존 프로파일은 호환되게 읽는다.

### 7.2 요구사항정의서만 있는 상태에서 새 파일 수신

1. 새 입력이 전체 개정본인지, 추가·변경 메모인지 먼저 확인한다. 명시된 경우 다시 묻지 않는다.
2. 이전 자료와 AN-02를 기준으로 변화 목록을 만든다.
3. `추가 3 / 변경 2 / 동일 18 / 충돌 1 / 삭제 후보 0`처럼 결과와 대표 변경 전후를 보여준다.
4. 충돌·삭제·범위·검수 기준의 미결만 묻는다. 입력에 없는 기존 항목을 자동 삭제하지 않는다.
5. 기존 ID를 유지하고 실제 추가만 새 번호를 받는다.
6. 후속 문서가 아직 없으면 “후속 문서 영향 대조 대상 없음”으로 마친다. 없는 문서를 자동 생성하지 않는다.

### 7.3 5종 작성 후 요구사항 추가·수정

1. 같은 변화 비교와 질문 절차를 적용한다.
2. 영향받는 기능·컬럼·테스트·추적 행, 기존 시험 결과, 사용자 편집 부분을 함께 표시한다.
3. “요구사항만 반영”, “영향 문서까지 반영”, “일부 선택”, “초안으로 보관” 중 현재 요청에 빠진 범위만 확인한다.
4. 이미 후속 문서 갱신까지 요청했다면 그 범위에서 진행하고, 새 업무 판단만 묻는다.
5. 후속 문서는 필요한 행을 재도출한다. 영향 없는 행과 사용자 확정값을 보존한다.
6. 반영하지 않은 문서는 어떤 요구 변경을 따라오지 못했는지 표시한다. 관련 과거 Pass는 재검증 필요로 구분한다.

### 7.4 명세일괄

게이트 1을 통과하기 전에 AN-02의 중요한 미결을 해결하거나, 사용자가 선택한 범위만 초안으로 진행한다. 미결 항목에 의존하는 기능·컬럼·테스트를 확정값으로 만들지 않는다. 게이트 2·3도 같은 수집·질문·반영 규칙을 사용한다.

게이트는 검토를 묶는 위치다. 질문 개수를 세 번으로 제한한다는 의미로 안내하지 않는다.

## 8. 질문·추천·확인요청서의 구체적인 형식

### 질문 한 건에 필요한 정보

| 정보 | 목적 |
|---|---|
| CQ 번호·요구사항ID·필드 | 어느 판단에 답하는지 알 수 있게 함 |
| 원문과 실제 위치·개정 기준 | 사람이 원문을 다시 찾고, 옛 답과 새 질문을 구분 |
| 무엇이 모호한지 | 단순 “확인 필요” 대신 빠진 판단 설명 |
| AI 추천안 | 사용자가 바로 검토할 출발점 |
| 추천 근거와 한계 | 원문 사실·기존 운영 기준·설계 제안을 구분 |
| 대안과 차이 | 비용·범위·운영·테스트에 생기는 변화 설명 |
| 직접 의견·보류 | 제시된 선택지만 강요하지 않음 |
| 영향 문서·ID | 선택 이후 어디를 바꿀지 예측 |
| 받은 답·처리 상태 | 미응답과 승인, 반영 완료를 구분 |

제출 문서의 본문 열을 모두 늘릴 필요는 없다. 대화·확인요청서·내부 상태가 같은 질문 정보를 사용하면 된다. 기존 4시트 양식을 유지한다면 우선 기존 근거 칸에 추천·대안·영향의 서술 규약을 추가하고, 반복 사용성이 확인된 뒤 필요한 열을 버전 이관과 함께 추가한다.

### 예시: 요구사항 분할 질문

아래는 형식 설명용 가상 사례다.

> CQ-012 · REQ-014 · 요구사항 분할
> 원문: “보고서 조회 및 다운로드를 제공한다.”
> 확인할 점: 조회와 다운로드를 별도 검수할지 정해야 합니다.
> **AI 추천: 2개 요구사항으로 구분.** 출력과 검증 방법이 달라 누락 여부를 따로 확인하기 쉽습니다. 같은 원문 항목에서 나왔다는 관계는 유지합니다.
> 선택: `2개로 구분(추천)` / `1개 요구사항·기능만 분리` / `보류`
> 직접 의견도 입력할 수 있습니다. 선택에 따라 요구사항과 기능·테스트의 매핑이 달라집니다.

분할 기준이 이미 명시적으로 정해졌고 사례가 명확하면 그 기준대로 처리하고 결과를 보여준다. 단순 반복 사례마다 다시 묻지는 않는다.

### 질문의 우선순위

| 등급 | 예 | 진행 원칙 |
|---|---|---|
| 먼저 답이 필요한 판단 | 적용 대상, 업무 범위, 권한, 원문 충돌, 삭제, 핵심 계산·검수 기준 | 그 판단에 의존하는 문서를 확정하기 전에 해결 |
| 초안으로 남길 수 있는 판단 | 확정 전 인터페이스 항목, 운영 수치, 후속 협의 값 | CQ와 영향 범위를 표시하고 독립 작업 진행 |
| 표시·작성상의 제안 | 명사구 정리, 분류명 통일, 문장 가독성 | 변경 제안으로 묶어 검토. 업무 의미를 바꾸지 않으면 일일이 질문하지 않음 |

**6건이라는 숫자는 전달 방식을 정하는 기본값일 수는 있지만 중요도를 정하지 않는다.** 1건의 중요한 질문을 일반 승인에 묻어서는 안 된다. 6건 이상이어도 가장 중요한 1~3건은 대화에서 요약하고 파일에 무엇이 있는지 알려준다. 반대로 반복되는 같은 원인은 묶되, 서로 독립인 판단을 한 번의 답으로 뭉개지 않는다.

세 번 묻는 기존 상한을 유지하더라도 사용자 설명 요청을 단순 미응답과 같은 방식으로 소모하지 않는다. 자동 재촉 상한과 사람이 질문·답을 주고받을 기회는 별도로 관리한다.

## 9. 상태와 근거를 남기는 방식

프롬프트 문구만으로 모든 갱신을 보장하기 어렵다. 제출 양식은 유지하면서 내부 상태를 작은 실행 도구가 관리하는 방식을 권장한다. 아래는 제안이며 아직 구현된 구조가 아니다.

| 관리 대상 | 최소로 남길 정보 |
|---|---|
| 원본 자료 | 자료 ID, 파일 위치, 개정/수신일, 내용 지문, 적용 범위, 우선 근거 여부 |
| 요구사항 | 안정적인 ID, 원문 연결, 판정·분류, 내용 지문, 검토 상태, 사용자의 결정 |
| 질문 | CQ 번호, 판단 종류, 원문·제안 기준, 추천·대안·근거, 응답, 영향 ID, 처리 상태 |
| 변경 | 변경 전후, 입력 자료, 사유, 적용한 범위, 미반영 문서 |
| 문서 | 문서 버전, 내용 지문, 읽은 상위 기준, 초안/확정 여부, 영향 미반영 여부 |
| 실행 | 현재 단계, 승인된 범위, 질문 대기, 파일 발행 여부, 재개 위치, 복구 기준선 |

세 상태를 섞지 않는다.

1. **요구사항 개정 상태:** 기존 양식의 유지·변경·삭제.
2. **검토 상태:** 초안·질문 대기·검토 완료·확정·전제 변경으로 재확인 필요.
3. **후속 반영 상태:** 최신·영향 미반영·대조 불가·재시험 필요.

승인 기록은 “사용자가 승인했다”만 남기지 않는다. 어떤 자료·질문·제안·문서 범위에 대한 승인인지 남긴다. 출력 형식·작성자처럼 변하지 않은 선택은 재사용하고, 업무 전제가 바뀐 결정만 재확인한다.

응답 이력은 가능한 한 추가 기록으로 남긴다. 현재 규칙은 늦은 답이 오면 마지막 `미해소` 행을 수정한다. 이를 유지한다면 최소한 원래 요청과 뒤늦은 응답 시점을 별도로 보존해야 한다. 질문 횟수와 응답 이벤트 수는 같지 않다.

## 14. Claude와 Codex 공통 검증

업무 규칙은 기존 커맨드·스킬·템플릿에 둔다. Codex 어댑터에 별도 업무 규칙을 복제하지 않는다. 사용자 질문은 해당 환경에서 실제 제공하는 입력 도구로 변환한다.

검증은 세 층으로 나누는 것이 좋다.

1. **규칙 계약:** 참조 경로·필수 단계·정본 일치·스키마. 현재 테스트의 장점을 유지한다.
2. **실행 도구:** 변경 비교·응답 가져오기·출력 검증·ID 이력·기준선 보존·충돌 처리. 실제 파일 입력과 결과로 검사한다.
3. **대화 시나리오:** Claude/Codex 각각에서 실제 입력 도구 호출·제시한 추천·응답 대기·파일 링크·미결 보류·재개를 관측한다.

최소 대화 시나리오:

- AN-02 단독, 중요한 모호성 1건: 구체 질문과 추천을 제시하고 답 전에 확정하지 않는다.
- AN-02 단독, 미결 6건: 실제 확인요청서 xlsx와 초안을 제공한다.
- 일괄 게이트 1, 범위 미결: 해당 범위의 AN-03 확정으로 넘어가지 않는다.
- 요구사항만 작성한 뒤 변경 메모 수신: 기존 행 유지, 해당 ID만 수정한다.
- 5종 작성 후 부분 변경: 영향 목록·갱신 선택·기존 ID·수동 수정 보존을 확인한다.
- Excel 답변 일부 입력·충돌·재실행: 한 번만 반영하고 빈칸은 남긴다.
- 질문 답변을 기다리는 동안 자료가 변경됨: 옛 전제의 답을 자동 확정하지 않는다.
- 완료 일괄 문서 재생성: 정상 기준선을 찾아 ID를 승계한다.

테스트 개수와 특정 문구의 존재만으로 질문 품질을 평가하지 않는다. “정확히 게이트 3개”, 특정 문장·백틱이 있어야 통과하는 검사는 실제 사용자 경험의 개선을 막지 않도록 책임을 재검토한다.

## 15. 구현 방향과 우선순위

| 접근 | 장점 | 한계 | 판단 |
|---|---|---|---|
| 지침·문구만 보강 | 빠르고 현재 구조를 적게 바꿈 | 변경 비교·응답 보존·게이트 상태가 계속 에이전트 해석에 의존 | 긴급 보완용 |
| 기존 스킬 + 공통 상태·비교·검증 도구 | 현재 사용법과 양식을 유지하며 핵심 불변 조건을 검사 가능 | 상태 이관·입력 스키마·실제 대화 검증 필요 | **권장** |
| 별도 전체 워크플로 엔진·관리 UI | 장기적인 협업·역할·결재 관리에 유리 | 범위와 유지비가 커지고 플러그인 개선을 넘어감 | 후속 검토 |

### 1차 — 요구사항 작성과 질문 누락 방지

- 게이트 1과 단독 AN-02에 동일한 품질 검토·추천·CQ·응답 대기 흐름 적용.
- 초안 저장·내용 확정·최종본 출력을 분리.
- 요구사항 단독 시작을 기본 안내로 바꾸고 불필요한 설정 질문 축소.
- 중요 질문과 파일 발행 결과를 사용자에게 반드시 보여주는 출력 규약 마련.
- 파이프·필수 열·최종본 검증 보강.

### 2차 — 실제로 많이 발생하는 변경 반영

- 전체/부분 입력 구분, 기존·새 자료 비교, ID 승계·삭제·복원 처리.
- 자료 버전·내용 지문·결정 이력·사용 번호 기록.
- AN-02 변경 전후와 후속 영향·미반영 상태 표시.
- 완료 표지·기준선·부분 백업 충돌 해결.
- 오래된 답·사용자 Excel 편집·충돌의 안전한 반영.

### 3차 — 문서 품질과 검증 정합성

- 기능/비기능·제약 우선순위·테스트 최소 수·데이터 매핑 충돌 해소.
- 추적 지표·복수 문제·시험 결과 유효성 개선.
- 개정이력 호출 책임과 소스 캐시 정책 정리.
- 실행 지침에서 개발 이력을 분리하고 두 환경 시나리오 평가 상시화.

정확한 일정·공수는 이번 분석에서 산정하지 않았다. 단순한 문구 수정과 실행 도구·이관·대화 검증은 작업 성격이 달라 별도로 산정해야 한다.

## 16. 완료 판단 기준

1. 사용자가 요구사항정의서만 요청하면 그 문서의 작성·질문·검토·초안/확정까지 독립적으로 끝낼 수 있다.
2. 중요한 모호성이 있으면 원문·추천·이유·대안·직접 의견·보류를 실제로 제시한다.
3. 미결 1건도 전체 승인으로 사라지지 않고, 다량이면 실제로 열린 파일과 응답 칸을 제공한다.
4. 새 파일의 추가·변경·동일·충돌·삭제 후보를 구분하고, 부분 입력의 누락을 삭제로 오인하지 않는다.
5. 기존 ID·사용자 확정값·수동 수정·과거 답변을 보호하며, 전제가 바뀐 판단만 재확인한다.
6. 요구사항이 바뀌면 영향받는 문서·행·시험 결과와 미반영 상태를 정확히 보여준다.
7. 셀 값과 필수 열이 보존되고, 최종본·초안 규칙을 실행 도구가 검사한다.
8. Claude와 Codex 모두 실제 질문·응답·파일 발행·재개 시나리오로 확인한다.

이 기준의 핵심은 **질문 수 자체를 늘리는 것이 아니라, 사람이 결정해야 할 부분을 빠뜨리지 않고 이해 가능한 추천과 함께 제시하며, 그 답을 이후 변경에서도 신뢰할 수 있게 관리하는 것**이다.
