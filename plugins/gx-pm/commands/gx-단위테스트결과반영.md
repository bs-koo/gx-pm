# /gx-단위테스트결과반영 — DE-13 수행 결과 반영

> **공통 규칙**: `templates/approval-protocol.md`의 승인 루프 프로토콜을 적용한다.
> **선행조건**: `templates/prerequisites.md` 의 이 커맨드 행을 따른다.
> **파이프라인**: `/gx-명세일괄` 에 들어가지 않는다 — 시험 수행 이후에 따로 부르는 커맨드다.
> 그래서 `templates/pipeline-protocol.md` 의 파이프라인 규약은 적용되지 않는다.

계획서를 **만드는** 커맨드는 `/gx-단위테스트계획서` 다. 이 커맨드는 이미 있는 계획서에
**시험 결과를 채운다.** 근거는 개발 레포에 지금 있는 테스트 코드다 — 개발자가 어떤 도구로
일했는지는 상관없다. 규칙의 정본은 **apply-test-results** 스킬이고, 여기에는 단계와
중단점만 둔다.

## 워크플로우

### Step 0: 프로젝트 컨텍스트 로드

**load-project-profile** 스킬로 활성 프로젝트를 확인한다. 프로파일이 없으면 `/gx-프로젝트설정`을 먼저 실행하라고 안내 후 종료.

**선행조건 검사** — `templates/prerequisites.md` 의 이 커맨드 행을 읽고:
- **하드 선행이 없으면**: 안내하고 **종료한다**.
  - `{시스템코드}-단위테스트계획서.md` 가 없으면 `/gx-단위테스트계획서` 를 먼저 안내한다 —
    결과를 채울 계획서가 없다.
  - 개발 소스 경로는 Step 1 이 채우므로 여기서 막지 않는다.
- **소프트 선행이 없으면**: AskUserQuestion 으로 "그대로 진행 / 중단하고 준비" 를 묻는다.

생성 커맨드의 기존 산출물 감지(`detect-existing-artifact` 의 이어쓰기/새로쓰기/열기)는 하지 않는다.
이 커맨드는 있는 계획서를 제자리에서 고친다 — 계획서가 있다는 것이 전제다.

### Step 1: 개발 레포 경로

테스트를 읽을 개발 레포는 하나 이상이다 — 백엔드·프론트·배치가 레포로 나뉘어 있으면 모두 준다.

1. 인자로 경로가 왔으면 그 경로들을 쓴다. 요청 문장 안에 경로가 들어 있어도(「D:\projects\reb-api 랑 reb-web 으로
   반영해줘」) 인자로 본다.
2. 아니면 프로파일 `assets.testSourcePaths` 를, 그것도 없으면 `assets.sourcePath` 하나를 쓴다.
3. 다 없으면 **AskUserQuestion** 으로 개발 레포 경로를 묻는다. 경로는 자유 입력이라
   `templates/approval-protocol.md` 인자 규칙대로 선택지를 `경로 입력` / `중단` 두 개로 두고 경로는
   기타 입력으로 받는다(여러 개면 줄바꿈이나 `;` 로). `중단` 이면 종료한다.

쓸 경로는 레포마다 한 줄로 보여준다 — Step 0 의 프로젝트 확인 화면에 나오는 `소스경로` 는
`assets.sourcePath` 하나라서 이 커맨드가 읽는 경로와 다를 수 있다.

인자나 질문으로 받은 경로는 프로파일 `assets.testSourcePaths` 에 저장한다 — 다음 반영 때 다시 묻지
않는다. 이 저장과 Step 0 의 **load-project-profile** 이 하는 `lastUsed` 갱신이 승인 전에 하는 쓰기의
전부다. 둘 다 산출물이 아니라 설정이라 승인 루프 밖에 둔다.

없는 경로가 있으면 알리고 **종료한다.** 색인 결과 테스트가 하나도 없으면 「테스트 코드를 찾지
못했습니다 — 개발 레포 경로를 확인해 주세요」를 알리고 **종료한다.**

**레포는 최신이어야 한다.** PM 이 받아 둔 사본이면 반영 전에 최신으로 받으라고(`git pull`·
`svn update`) 한 줄로 안내한다. 이 커맨드는 소스 레포에 아무것도 쓰지 않으므로 대신 실행하지 않는다.

### Step 2: 대조 [필수 중단점 — 승인 루프]

**apply-test-results** 스킬의 Step 1~3 을 따른다. 테스트를 색인하고, 계획서 행과 테스트를
짝지어 판정하고, 신규·보강 제안과 함께 승인을 받는다. **승인 전에는 위 프로파일 쓰기 말고
아무 파일도 고치지 않는다** — 신규 행의 testdata 파일도 승인 뒤에 만든다.

### Step 3: 반영

**apply-test-results** 스킬의 Step 4~5 를 따른다. 담당자 실명을 확인하고, 계획서 md 에
쓰고(`사유` 열이 없는 옛 계획서면 `결과` 바로 뒤에 열을 더한다. 반영 전 원본은 도구가 `backup/` 에 남긴다), **manage-revision-history** 스킬로 개정이력을 남기고, 수행대장을 갱신한다.

### Step 4: xlsx 추출

**AskUserQuestion 도구**로 다음 내용을 질문한다:

```
결과를 반영한 단위테스트계획서를 xlsx로 추출할까요?
  1. xlsx 추출
  2. 마크다운만 저장
```

추출은 `utils/export-xlsx.py` 로 계획서만 한다. 수행대장은 내부 증적이라 추출하지 않는다.

### Step 5: 다음 제안

- "`/gx-추적매트릭스` 로 요구사항별 미구현·미검증을 다시 대조할까요?"
- 기대결과가 테스트와 **불일치**한 행이 있으면: "정책이 바뀐 것일 수 있습니다 — 발주처
  확인이 필요하면 확인요청서에 올려 주세요."
- `미검증 — 실행 결과 없음` 이 남은 레포가 있으면: "테스트를 돌린 작업 폴더(개발 PC·빌드 서버)를 경로로
  주고 다시 반영하면 실행 결과가 붙습니다." — 결과 파일은 커밋되지 않아 받아 둔 사본에는 없고,
  따로 관리할 필요도 없다고 덧붙인다. Jest·Vitest 레포면 JUnit 리포터를 켜야 결과 파일이 생긴다고도 알린다.
