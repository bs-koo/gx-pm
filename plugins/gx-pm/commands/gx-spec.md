# /gx-spec — 명세 5종 일괄 생성

요구사항부터 추적매트릭스까지, 서로 의존하는 산출물 5종을 순서대로 만든다.
사용자는 커맨드 순서를 알 필요가 없다. **게이트 3곳에서만** 판단하면 된다.

> **공통 규칙**: `templates/approval-protocol.md`의 승인 루프 프로토콜을 적용한다.
> **선행조건**: `templates/prerequisites.md` 의 `/gx-spec` 행을 따른다.
> **실행 규약**: `templates/pipeline-protocol.md` 를 따른다. 개별 커맨드의 산출물별 승인 루프는 게이트로 이월하고, **이월 금지 4항목은 이월하지 않는다**.

## 만드는 것

| 순서 | 산출물 | 단독 커맨드 |
|------|--------|-----------|
| 1 | AN-02 요구사항정의서 | `/gx-요구사항정의서` |
| 2 | AN-03 기능명세서 | `/gx-기능명세서` |
| 3 | DE-08 테이블정의서 | `/gx-테이블정의서` |
| 4 | DE-13 단위테스트계획서 | `/gx-단위테스트계획서` |
| 5 | AN-05 추적매트릭스 | `/gx-추적매트릭스` |

낱개로 다시 만들고 싶으면 위 단독 커맨드를 쓴다. 생성 로직은 같다.

**갈래가 둘이다.** 기능 요구사항은 기능명세서를 거쳐 테스트로 가고, 비기능 요구사항은
기능을 거치지 않고 바로 테스트로 간다 (DE-13 의 `연계기능ID` 공란 행).

## 워크플로우

### Step 0: 프로젝트 컨텍스트 로드

#### 0-1. 프로파일 검사

**load-project-profile** 스킬로 활성 프로젝트를 확인한다.

**프로파일이 없으면 `/gx-프로젝트설정` 을 먼저 실행하라고 안내 후 종료한다.**
프로파일은 하드 선행이다 (`templates/prerequisites.md`). **여기서 프로파일을 대신 만들지 않는다** —
`/gx-프로젝트설정` 의 `[필수 중단점]` 3개(유형 선택 · 기본 정보 · 설정 승인)를 건너뛰게 되기 때문이다.
특히 프로젝트 유형(A 정방향 / B 이어쓰기 / C 역생성 / D 변경분만)은 사용자가 고르는 것이고,
틀리면 5종 전부가 틀린다.

**아래를 그대로 출력하고 끝낸다.** 안내 문구를 주지 않고 "종료한다" 라고만 적어두면
실행이 자기 나름대로 안내하다가 이어서 프로파일을 만들어버린다 — v3.2.0 에서 실제로
그랬고, 그래서 유형 선택 `[필수 중단점]` 이 통째로 건너뛰어졌다.

```
프로젝트 프로파일이 없습니다.

  /gx-프로젝트설정 을 먼저 실행해주세요.

  거기서 프로젝트 유형(A 신규구축 / B 추가개발 / C 산출물정비 / D 변경관리)과
  기본 정보, 설정 승인을 받습니다. 이 셋은 여기서 대신 정할 수 없습니다.

/gx-spec 을 종료합니다.
```

#### 0-2. 기존 산출물 감지

**먼저 생성 표지를 읽는다** (§생성 표지). `게이트 N 통과` 가 보이면 파이프라인이
중간에 끊긴 것이므로, 3분기를 묻기 **전에** 이어서 진행할지 먼저 묻는다.

```
게이트 2 까지 통과한 중간 산출물이 있습니다. (AN-02 · AN-03 · DE-08)

  1. 이어서 진행 — 게이트 3 부터. 통과한 게이트를 다시 세우지 않습니다
  2. 처음부터 — 이어쓰기/새로쓰기/열기 중에서 고릅니다
```

**detect-existing-artifact** 스킬로 5종 각각의 기존 파일을 확인한다.
- 일부만 있음 → "이미 만들어진 것을 건너뛰고 이어서 진행할까요?" 를 AskUserQuestion 으로 묻는다
- 전부 있음 → 어느 것부터 다시 만들지 묻는다

**산출물마다 고른 처리 방식(`이어쓰기` / `새로쓰기` / `열기`)을 기억해 뒤 단계로 넘긴다.**
`새로쓰기` 를 고른 산출물만 `backup/` 에 직전 버전이 생기고, 그것만 ID 승계 대상이다.
이어쓰기에 `reconcile-ids` 를 걸면 백업본이 없어 순번 1부터 다시 매겨진다
(`skills/reconcile-ids/SKILL.md` Step 1).

프로파일의 `type` 에 따라 각 산출물의 생성 방식이 분기한다 (A 정방향 / B 이어쓰기 / C 역생성 / D 변경분만).
분기 규칙은 각 단독 커맨드의 Step 0 정의를 그대로 따른다.

#### 0-3. 채번 규칙

**프로파일은 있는데 `idNaming` 만 비어 있으면 여기서 한 번 묻고 저장한다.** 규칙의 정본은
`templates/id-naming-rules.md`, 저장 위치는 `templates/project-profile-schema.md` 의
`idNaming` 객체다. 한 번 저장하면 뒤 단계에서 다시 묻지 않는다.

**이 항목만 여기서 채운다.** 프로파일의 다른 항목(유형·시스템코드·작성자·프레임워크·DB·자산)이
비어 있으면 채우지 말고 위 하드 선행 규칙대로 `/gx-프로젝트설정` 을 안내하고 종료한다.

```
요구사항ID·기능ID·테스트ID 채번 규칙을 정해주세요.
  1. REQ-001 / FN-001 / UT-001   (참조 양식과 동일)
  2. B-RE-001 / B-FN-001 / B-UT-001   (시스템코드 포함)
  3. 직접 입력
```

### Step 1: 묶음 선행조건 검사

**하드 선행**은 `templates/prerequisites.md` 의 **`/gx-spec` 행**만 따른다
(프로파일 · `sqi-comn-term` MCP).
구성 5종 각각의 하드 선행 행(예: 기능명세서는 요구사항정의서, 단위테스트계획서는 기능명세서)은
이 파이프라인이 Step 2~8 에서 스스로 만드는 산출물이다. Step 1 에 그대로 적용하면 파이프라인이
자기 산출물을 이유로 스스로를 막게 되므로 여기서는 적용하지 않는다.

**소프트 선행**은 구성 5종 각각의 행을 **합집합으로 모아 한 번에** 검사한다.

- 하드 선행(프로파일) 누락 → 안내 후 종료
- 하드 선행(`sqi-comn-term` MCP) 누락 → `docs/표준용어-mcp-연계.md` 의 설치·재연결 안내 후 종료.
  이 MCP 는 Step 5 에서만 쓰이지만 **여기서 막는다** — Step 5 는 게이트 2 **전**이라
  게이트 1 통과분 AN-02 는 남지만 **AN-03 은 사라진다.** 게이트별 저장이 원래 근거를
  절반만 해소했다. 근거는 `templates/prerequisites.md` 의 「`sqi-comn-term` MCP 가 하드인 이유」
- 소프트 선행 누락 → 무엇이 빠지는지 **한 화면에 모아** 보여주고 AskUserQuestion 으로 계속 여부를 묻는다

```
다음 입력이 없습니다:

  • RFP/과업지시서 원문 없음
      → 요구사항 근거 열이 빈 채로 남고, 요구사항 상세내용이 추정값이 됩니다
  • DDL 없음
      → 기존 스키마가 없는 것으로 보고 컬럼 전건을 신규로 제안하게 됩니다

  1. 그대로 진행 (해당 산출물 비고에 "축약 생성" 표기)
  2. 중단하고 입력을 준비
```

### Step 2: 요구사항정의서 생성

`/gx-요구사항정의서` 의 시안/대안 감지 → 추출 → 행 분할 → 분류 단계를 수행한다.

**이월하지 않는 중단점 3개가 이 단계에 있다** (`templates/pipeline-protocol.md` §이월 금지 항목).

- **시안/대안 감지** — 시안 선택이 틀리면 뒤 산출물이 전부 틀린다
- **표 판정 애매성** — ID 표가 요구사항 표인지 애매하면 그 자리에서 묻는다.
  판정 기준은 `skills/extract-requirements/SKILL.md` Step 2 가 정본이다.
  게이트 1 로 미루면 이미 그 건수로 만들어진 뒤다
- **ID 승계 판정 애매성** — `새로쓰기` 를 고른 산출물이고 `backup/` 에 직전 버전이 있으면
  **reconcile-ids** 스킬로 ID 를 승계한다.
  어느 항목과 같은 것인지 애매하면 그 자리에서 묻는다. 이월하지 않는다.
  판정 기준은 `skills/reconcile-ids/SKILL.md` Step 3 이 정본이다

산출물별 승인 루프만 게이트 1 로 이월한다.

### Step 3: 게이트 1 — 요구사항 승인 [필수 중단점]

요구사항 건수가 뒤 산출물 전체의 행 수를 정하므로 **반드시 단독 게이트**다.
AN-02 표를 출력한 후, **AskUserQuestion 도구**로 승인을 요청한다.

```
요구사항 {N}건을 확인해주세요. (기능 {F}건 / 비기능 {NF}건)

⚠ 여기서 승인한 건수가 기능명세·테이블·테스트·추적매트릭스의 행 수를 정합니다.

주요 확인:
1. 한 행으로 묶인 것 중 테스트를 따로 써야 하는 것이 있는지
2. 기능/비기능 구분이 맞는지
3. 대분류·중분류가 문서 근거에서 나왔는지 (추정한 것은 표시돼 있습니다)
4. 누락된 요구사항이 있는지

승인하려면 '승인' 또는 'OK'를 입력하세요.
수정하려면 변경할 내용을 입력하세요.
```

승인 후 **manage-revision-history** 스킬로 AN-02 개정이력을 기록한다.
승인할 때까지 수정 → 재출력 → AskUserQuestion 을 반복한다.

**개정이력까지 기록했으면 AN-02 를 파일로 저장한다.** 게이트를 통과한 산출물은
그 자리에서 저장한다 — Step 10 까지 들고 가면 중간에 끊겼을 때 승인까지 마친
것이 사라진다. 머리말에 생성 표지를 남긴다 (아래 §생성 표지).

### Step 4: 기능명세서 생성

`/gx-기능명세서` 의 생성 단계를 수행한다. `[가정]`·`[미확정]` 목록을 모아 둔다 — 게이트 2 에서 함께 보여준다.

`새로쓰기` 를 고른 산출물이고 `backup/` 에 직전 버전이 있으면 **reconcile-ids** 스킬로
기능ID 를 승계한다.
**ID 승계 판정 애매성 중단점은 이월하지 않는다** — 어느 기능과 같은 것인지 애매하면
그 자리에서 묻는다. 판정 기준은 `skills/reconcile-ids/SKILL.md` Step 3 이 정본이다.

### Step 5: 테이블정의서 생성

`/gx-테이블정의서` 의 생성 단계를 수행한다. 역생성 전용이므로 요구사항에서 테이블을 추론하지 않는다.
DDL 이 없으면 기존 스키마가 없는 것으로 보고 전건을 신규 컬럼으로 취급하며, 그 사실을 게이트 2 에 적는다.

**신규 컬럼명 결정 중단점은 이월하지 않는다** — 표준용어 MCP 가 `decisionRequired` 를 내면
그 자리에서 묻는다. 판정 기준은 `skills/convert-ddl-to-tablespec/SKILL.md` Step 5 가 정본이다.

### Step 6: 게이트 2 — 기능 + 테이블 승인 [필수 중단점]

기능의 입력항목이 곧 컬럼이라 따로 보면 판단이 안 된다. 함께 출력한 후,
**AskUserQuestion 도구**로 승인을 요청한다.

```
기능명세 {M}건 / 테이블 {T}개를 확인해주세요.

  • AN-03 기능명세 표
  • DE-08 테이블정의 표 (신규 컬럼 강조)
  • 근거 가용도 {n}/4 — 요구사항 상세 {✓} / 처리내용 역산 {✓} / 기존 DDL {✗} / 기존 소스 {✓}
  • [가정] {N}건 · [미확정] {M}건 — 항목 {M1} / 제약 {M2}
  • [미확정] 제약 기능 {P}건 — 발주기관이 정할 값이라 경계 케이스가 안 나옵니다
  • 제약 불일치 목록 {C}건 — 기능의 입력 제약과 컬럼 제약이 어긋난 곳
  • 분할 누락 의심 {Q}건 — 산출물이 여럿 열거됐는데 기능이 1건인 곳
  • 데이터 출처 없음 {R}건 — 읽는 데이터를 만드는 기능이 AN-03 에 없는 곳
  • 설계 제약 미반영 후보 {D}건 — 데이터 요구사항인데 반영할 컬럼을 특정하지 못한 곳

주요 확인:
1. 요구사항 ↔ 기능 매핑에 빠진 것이 없는지 (N:M 이므로 1:1 이 아니어도 정상입니다)
2. 기능의 입력항목이 컬럼으로 다 내려갔는지
3. 신규 컬럼의 표준 권고명을 받아들일지

승인하려면 '승인' 또는 'OK'를 입력하세요.
수정할 산출물과 내용을 입력하세요. (예: "FN-007 입력항목에 첨부파일 추가")
```

`{n} < 4` 이고 `{K} == 0` 이면 `templates/evidence-rules.md` §근거 가용도 경고의
경고 문구를 위 목록 아래에 함께 낸다. 근거가 덜 살아 있는데 확인할 것이 하나도
없다는 건 산술적으로 이상하다 — 지어낸 값이 있다는 신호다.

승인 후 **manage-revision-history** 스킬로 AN-03·DE-08 개정이력을 기록한다.

**기록 후 AN-03·DE-08 을 파일로 저장한다.** 생성 표지는 `게이트 2 통과` 다.

### Step 7: 단위테스트계획서 생성

`/gx-단위테스트계획서` 의 생성 단계를 수행한다.
비기능 요구사항은 `연계기능ID` 공란 행으로 만든다 — 기능을 거치지 않는 갈래다.

`새로쓰기` 를 고른 산출물이고 `backup/` 에 직전 버전이 있으면 **reconcile-ids** 스킬로
테스트ID 를 승계한다.
**ID 승계 판정 애매성 중단점은 이월하지 않는다** — 게이트 3 으로 미루면 Step 8 에서
이미 만들어진 AN-05 를 다시 만들어야 한다. 그 자리에서 묻는다.
판정 기준은 `skills/reconcile-ids/SKILL.md` Step 3 이 정본이다.

### Step 8: 추적매트릭스 생성

`/gx-추적매트릭스` 의 생성 단계를 수행한다. 누락 목록을 유형별로 뽑는다.

### Step 9: 게이트 3 — 테스트 + 추적 결과 승인 [필수 중단점]

테스트와 추적은 같은 판단을 요구한다 — "빠진 것이 진짜 빠진 것인가". 함께 출력한 후,
**AskUserQuestion 도구**로 승인을 요청한다.

```
테스트 {U}건 / 추적 결과를 확인해주세요.

  • DE-13 단위테스트계획 표
  • AN-05 추적매트릭스 표
  • 누락 유형별 건수
  • [미확정] 제약으로 경계 케이스가 없는 기능 {P}건 — 지어내지 않고 남겨둔 것입니다

주요 확인:
1. 누락이 실제 누락인지, 아직 진행 중이라 그런 것인지
2. 비기능 요구사항의 연계기능ID 공란은 누락이 아닙니다
3. 경계값의 근거가 요구사항·컬럼 제약에서 나왔는지
4. `[미확정]` 제약 {P}건에 지금 값을 줄지, 다음 차수로 남길지

승인하려면 '승인' 또는 'OK'를 입력하세요.
수정하려면 변경할 내용을 입력하세요.
```

승인 후 **manage-revision-history** 스킬로 DE-13·AN-05 개정이력을 기록한다.

**기록 후 DE-13·AN-05 를 파일로 저장한다.** 생성 표지는 `게이트 3 통과` 다.

**`[가정]` 과 `[미확정]` 합계가 10건을 넘으면 확인요청서를 만든다.**
양식과 임계치의 정본은 `templates/confirmation-request.md` 다.
10건 이하면 파일을 만들지 않고 위 게이트 화면의 목록으로 갈음한다.

```
[가정] 34건 · [미확정] 46건 — 합계 80건이라 확인요청서를 만듭니다.
  REB-확인요청서.md  (가정 확인 34행 · 미확정 확인 46행)

  xlsx 로 뽑으면 판정·상태 열이 드롭다운이 됩니다. 그대로 발주기관에
  보내 답을 받고, 다음 실행에서 반영할 수 있습니다.
```

### Step 10: 결과 저장 + xlsx 추출

5종은 게이트를 통과할 때 이미 저장됐다 (Step 3·6·9). 여기서는 **아직 저장되지
않은 것만** 저장하고 xlsx 를 추출한다.

**AskUserQuestion 도구**로 한 번만 질문한다:

```
승인된 산출물 5종을 xlsx로 추출할까요?
  1. 5종 전부 xlsx 추출
  2. 일부만 추출 (산출물 번호 입력)
  3. 마크다운만 저장
```

**추출은 반드시 `--separate` 로 한다.**

```bash
# 5종 .md 가 한 폴더에 있을 때
python utils/export-xlsx.py --dir . --separate

# 파일을 골라서 낼 때
python utils/export-xlsx.py --separate {시스템코드}-요구사항정의서.md {시스템코드}-기능명세서.md
```

`--separate` 를 빼면 5종이 `{시스템코드}-산출물.xlsx` **한 권으로 합쳐지고**, 개정이력이
`개정이력` · `개정이력_1` ~ `개정이력_4` 로 흩어진다. 다섯 템플릿의 「시트 구성」은 전부
`1. 개정이력 2. 본문` — **문서마다 한 권**을 전제하고, 감리에 제출되는 형태도 그것이다
(`templates/revision-history.md` 「마크다운 표현」). 2번(일부만 추출)도 같다.

### Step 11: 다음 안내

## 생성 표지

게이트를 통과해 저장한 산출물은 **어디까지 통과했는지**를 파일에 남긴다.
파일이 있다는 것만으로는 게이트 통과의 증거가 못 된다 — `/gx-요구사항정의서`
단독 실행도 같은 파일을 만든다.

자리는 **H1 다음 · `## 개정이력` 앞** 행이다. DE-08 의 DDL 부재 경고가 이미 같은
자리를 쓰므로, 경고가 있으면 그 **아래**에 둔다.

```markdown
# AN-02 요구사항정의서 — {사업명}

> 생성: /gx-spec 게이트 1 통과 · 2026-09-07 12:48

## 개정이력
```

단독 커맨드로 만든 것은 게이트 대신 커맨드 이름을 적는다.

```markdown
> 생성: /gx-요구사항정의서 · 2026-09-07 12:48
```

**재개할 때 이 줄을 읽어 판정한다.** Step 0-2 가 `게이트 N 통과` 를 보면 3분기를
묻기 전에 이어서 진행할지 먼저 묻는다. 표지가 없으면 게이트별 저장이 성립하지
않는다 — 상태를 저장할 다른 자리가 없다.

## 재생성 파급

게이트에서 수정 요청이 오면 `templates/pipeline-protocol.md` 의 재생성 파급 규칙에 따라
하위 산출물도 함께 재생성한다. **영향 범위를 먼저 보여주고 묻는다.**

파생 ID 가 없으므로 ID 를 바꿔도 재채번 파급은 없다. 다시 만들어야 하는 것은
`연계~ID` 열로 이어진 행들뿐이다.
