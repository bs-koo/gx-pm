# /gx-총괄테스트계획서 — TE-01 총괄 테스트계획서 생성

> **공통 규칙**: `templates/approval-protocol.md`의 승인 루프 프로토콜을 적용한다.
> **선행조건**: `templates/prerequisites.md` 의 이 커맨드 행을 따른다.
> **파이프라인**: `/gx-spec` 또는 `/gx-testplan` 에서 호출된 경우 `templates/pipeline-protocol.md` 의 규약을 따른다.
> **양식**: `templates/TE-01-master-test-plan.md` 참조

**개별 테스트 산출물(DE-13/DE-14/ST-01)보다 먼저 실행한다.**
이 문서의 진입·종료기준이 이후 모든 결과서의 판정 근거가 된다.

## 워크플로우

### Step 0: 프로젝트 컨텍스트 로드

**load-project-profile** 스킬로 활성 프로젝트를 확인한다. 프로파일이 없으면 `/gx-프로젝트설정`을 먼저 실행하라고 안내 후 종료.

**detect-existing-artifact** 스킬로 기존 `{시스템코드}-총괄테스트계획서.md` 파일을 확인한다.
- 파일 있음 → 이어쓰기/새로쓰기/열기 선택
- 파일 없음 → 새로 생성

**선행조건 검사** — `templates/prerequisites.md` 의 이 커맨드 행을 읽고:
- **하드 선행이 없으면**: 해당 선행 커맨드를 안내하고 **종료한다**. 추정으로 채우지 않는다.
- **소프트 선행이 없으면**: AskUserQuestion 으로 "그대로 진행 / 중단하고 준비" 를 묻는다.
  그대로 진행하면 산출물 비고에 "축약 생성" 을 남긴다.

파이프라인에서 호출된 경우 이 검사는 파이프라인이 이미 수행했으므로 **건너뛴다**.

모든 유형(A/B/C/D)에서 동일하게 동작한다. C유형(산출물 정비)은 이미 개발이 끝난 상태이므로
일정 섹션을 "역산 불가"로 두고 나머지를 채운다.

### Step 1: 요구사항정의서 로드

- 이전 `/gx-요구사항정의서` 결과가 있으면 자동 로드
- 없으면 입력 요청
- **구분(기능/비기능) 집계**가 범위 산정의 기준이 된다

### Step 1-1: 시안/대안 감지

**detect-alternatives** 스킬 적용. 테스트 전략에 대안이 있으면 선택을 요청한다:
- 자동화 테스트 도입 여부
- 성능 테스트 범위 (전 화면 vs 주요 화면)
- 인수테스트 수행 방식 (발주처 단독 vs 합동)

감지되지 않으면 안내 없이 다음 단계로 진행한다.

### Step 2: 범위 산정 + 제외 범위 확인 [필수 중단점]

**generate-master-test-plan** 스킬로 범위를 집계한 뒤, **AskUserQuestion 도구**로 제외 범위를 묻는다:

```
대상 요구사항: 기능 {N}건 / 비기능 {N}건 / 수용불가 {N}건
대상 화면: {N}개 · 인터페이스: {N}건

테스트 제외 범위가 있나요? (사유와 함께 입력)

  흔한 제외 대상:
  • 상용 솔루션 내부 기능
  • 외부 연계기관 시스템 내부 처리
  • 수용여부 "불가"로 판정된 요구사항
  • 차기 사업 이관 범위

  (없으면 "없음")
```

> 제외 범위를 비워 두면 감리에서 "테스트 범위 미정의"로 지적된다.

### Step 3: 테스트 레벨 확정 [필수 중단점]

**AskUserQuestion 도구**로 다음 내용을 질문한다:

```
테스트 레벨을 확정해주세요. (기본 4단계)

  1. 단위테스트 (DE-13/IM-03) — 개발팀, 화면 단위
  2. 통합테스트 (DE-14/TE-02) — 개발팀+현업, 업무 흐름
  3. 시스템테스트 (ST-01/ST-02) — 개발팀+인프라, 비기능
  4. 인수테스트 (DE-14/TE-06) — 발주처

비기능 요구사항이 {N}건 있습니다.
시스템테스트를 빼면 이 {N}건의 검증 칸이 추적매트릭스에서 비게 됩니다.

  A. 4단계 전부 (권장)
  B. 시스템테스트 제외 (비기능 검증 방법을 별도로 지정해야 합니다)
```

### Step 4: 추진 체제 + 일정 [필수 중단점]

**AskUserQuestion 도구**로 역할별 담당자와 레벨별 일정을 받는다.

- 인수테스트 주관자는 **발주처 담당자 실명**이어야 함을 안내
- **결함 조치 예비기간**이 일정에 없으면 경고

### Step 5: 환경 + 테스트 데이터 [필수 중단점]

**AskUserQuestion 도구**로 테스트 환경과 데이터 방침을 받는다.

- Mock 처리 인터페이스를 반드시 나열
- 운영 데이터 사용 선택 시 **비식별 조치 방법 입력을 강제** (개인정보보호법 P1)

### Step 6: 진입·종료기준 확정 [필수 중단점 — 승인 루프]

기본값을 표로 출력한 후, **AskUserQuestion 도구**로 승인을 요청한다:

```
진입·종료기준을 확인해주세요. 이 수치가 이후 모든 결과서의 판정 근거가 됩니다.

  종료기준 기본값:
    계획 케이스 실행률   100%
    Critical 결함 잔존   0건
    Major 결함 잔존      0건
    Minor 결함 조치율    90% 이상
    요구사항 커버리지    100%
    적합률               95% 이상

⚠ 지킬 수 없는 기준은 쓰지 않는 편이 낫습니다.
   미달 상태로 종료하면 계획서가 오히려 불리한 증거가 됩니다.

승인하려면 '승인' 또는 'OK'를 입력하세요.
수정하려면 변경할 내용을 입력하세요.

수정 예시:
• "Minor 조치율은 80%로"
• "적합률 기준 제외"
```

사용자가 승인할 때까지 수정 → 재출력 → AskUserQuestion으로 승인 요청을 반복한다.

### Step 7: 결함 관리 기준 + 위험 [필수 중단점 — 승인 루프]

심각도(Critical/Major/Minor/Trivial)·우선순위(High/Medium/Low)·상태 흐름 정의를 출력하고 승인을 받는다.
기본값은 `templates/DF-01-defect-log.md`를 따른다.

위험 항목은 프로젝트 상황에서 자동 식별한 뒤 사용자 보강을 받는다.

### Step 8: 결과 저장 + xlsx 추출

파일명: `{시스템코드}-총괄테스트계획서.md`

**AskUserQuestion 도구**로 다음 내용을 질문한다:

```
승인된 산출물을 xlsx로 추출할까요?
  1. xlsx 추출
  2. 마크다운만 저장
```

### Step 9: 다음 제안

- "`/gx-단위테스트계획서` 로 화면별 테스트를 계획할까요?"
- "`/gx-시스템테스트` 로 비기능 요구사항 검증을 계획할까요?"
- 비기능 요구사항이 있는데 시스템테스트 레벨을 제외했으면 그 검증 방법을 다시 확인
