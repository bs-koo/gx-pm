# /gx-단위테스트실행 — 계획서대로 로컬 시험 수행

> **공통 규칙**: `templates/approval-protocol.md`의 승인 루프 프로토콜을 적용한다.
> **선행조건**: `templates/prerequisites.md`의 이 커맨드 행을 따른다.
> **파이프라인**: `templates/pipeline-protocol.md`의 명세 5종(`/gx-명세일괄`) 밖에서 실행한다. 계획서 작성 이후 실제 시험을 수행하는 커맨드다.

규칙의 정본은 **apply-test-results** 스킬이다. 계획서의 조건을 로컬 애플리케이션에 적용하고 응답·화면·데이터 변화를 확인한다. 계획서는 유지하며 IM-03 결과서와 내부 수행대장에 기록한다.

## 워크플로우

### Step 0: 프로젝트 컨텍스트 로드

**load-project-profile** 스킬로 활성 프로젝트를 로드한다. 프로파일이나 계획서가 없으면 선행조건 레지스트리에 따라 `/gx-프로젝트설정` 또는 `/gx-단위테스트계획서`를 안내한다. 소프트 선행이 없으면 빠지는 보조 맥락을 알리고 계속 여부를 확인한다.

결과서는 하나를 계속 갱신한다. 기존 산출물의 이어쓰기/새로쓰기/열기 선택은 하지 않는다.

### Step 1: 계획서·실행 환경 준비

**apply-test-results** Step 1~2를 따른다. 요청의 프로젝트 경로를 우선하고 없으면 프로파일이나 현재 프로젝트에서 찾는다. 그래도 경로가 없으면 AskUserQuestion으로 필요한 경로를 받는다. 로컬 실행 명령·URL·시험 계정·데이터 환경을 확인하고 프로젝트를 실제로 기동한다.

이미 승인된 로컬 시험을 시작하기 위해 다시 승인을 요구하지 않는다. 운영 대상이나 시험 환경이 불분명한 연결은 실행 전에 확인한다. 결과서 확정 승인은 Step 3에서 받는다.

### Step 2: 계획서 행별 실제 수행

**apply-test-results** Step 3을 따른다. 사전조건·의존성을 준비하고 API 요청 또는 브라우저 조작을 수행한다. 기대결과·사후조건을 관측해 행별 실행 증적을 보존한다. 환경 문제와 기능의 실제 실패를 구분하며, 일부 행이 막혀도 독립적으로 수행할 수 있는 행은 계속한다.

### Step 3: 결과 승인 [필수 중단점 — 승인 루프]

**apply-test-results** Step 4를 따른다. 기동한 프로세스와 시험 데이터를 정리하고 상태·실제결과·근거·이전 기입과의 차이를 제시한다. dry-run으로 검증한 개정이력 초안과 출력 형식도 같은 검토에 포함하여 결과서 반영 승인을 받는다. 승인 전에는 실행 증적과 설정만 저장하고 결과서·수행대장은 바꾸지 않는다.

### Step 4: 반영과 xlsx 추출

**apply-test-results** Step 5를 따른다. 실행 증적을 검증하는 dry-run 뒤 **manage-revision-history** 스킬로 개정이력을 확정하고 결과서·수행대장을 기록한다. 계획서 원문은 바뀌지 않는다.

결과서가 바뀌면 이미 정한 출력 형식을 적용해 `utils/export-xlsx.py --separate`로 결과서만 추출한다. 출력 형식이 미정이면 Step 3 검토에 `xlsx 추출 / 마크다운만 저장` 선택을 포함한다. 내부 증적은 고객 xlsx에 포함하지 않는다.

### Step 5: 다음 안내

- `/gx-추적매트릭스`로 요구사항별 실패·미수행을 대조한다.
- 실패 행은 관측한 불일치와 재현 입력을, 미검증 행은 필요한 환경·데이터·도구를 안내한다.
- 계획서 변경이 필요하면 `/gx-단위테스트계획서`의 열기로 수정한 뒤 다시 수행한다.
