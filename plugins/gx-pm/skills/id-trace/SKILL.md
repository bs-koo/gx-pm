# ID 양방향 추적 (id-trace)

임의의 산출물 ID를 입력받아 해당 ID와 연결된 전체 추적 체인을 양방향으로 조회하고, 누락된 매핑을 탐지한다. 단건 추적과 전체 교차 검증 두 가지 모드를 제공한다.

## ID 체인 전체 구조

```
제안요청ID (SFR-xxx)
    ↓
요구사항ID ({시스템코드}-RE-xxx)
    ├─[기능]──→ 화면ID ({접두}_{xx}_{xx}_{xxx})
    │              ├→ 프로그램ID (PG_{화면ID})
    │              └→ 단위테스트ID (U_{화면ID})
    │                     └→ 테스트케이스ID (TC_{화면ID}_{nn})
    ├─[기능]──→ 통합테스트ID ({시스템코드}-TE-xxx)
    └─[비기능]→ 시스템테스트ID ({시스템코드}-ST-xxx)

                    모든 테스트 → 결함ID ({시스템코드}-DF-xxx)
```

**갈래별 검증 경로가 다르다.** 기능 요구사항은 화면·흐름 갈래로, 비기능 요구사항은 품질 갈래로 검증된다.
비기능 요구사항에 화면ID가 없는 것은 정상이며, **시스템테스트ID가 없는 것이 누락**이다.

## 입력

- 추적 모드 선택:
  - **단건 추적**: 특정 ID 1개 입력 → 해당 ID 기준 위·아래 전체 체인 추적
  - **전체 교차 검증**: "전체" 입력 → 모든 산출물의 모든 ID 교차 검증
- 산출물 데이터 (요구사항정의서, 화면목록표, 프로그램정의서, 테스트계획서, 추적매트릭스)

## ID 유형 자동 판별

입력된 ID를 정규식 패턴으로 자동 판별한다.

시스템코드와 시스템접두어는 프로파일에서 읽어 패턴에 대입한다.
**고정 문자 클래스를 쓰지 않는다** — 프로파일은 시스템코드로 "A~I 또는 프로젝트별 자유 코드"를,
접두어로 "2~4자리 영문"을 허용하므로 `[A-I]`나 `[A-Z]{3,4}`로 고정하면 판별에 실패한다.

| ID 유형 | 정규식 패턴 | 예시 | 판별 근거 |
|--------|-----------|------|---------|
| 제안요청ID | `^SFR-\d{3}$` | SFR-027 | 고정 접두어 SFR + 3자리 |
| 요구사항ID | `^{systemCode}-RE-\d{3}$` | B-RE-003, EHR-RE-003 | 시스템코드 + -RE- + 3자리 |
| 화면ID | `^{prefix}_\d{2}_\d{2}_\d{3}$` | EHR_03_01_010, CM_03_01_010 | 접두어 + _숫자2_숫자2_숫자3 |
| 프로그램ID | `^PG_{화면ID}$` | PG_EHR_03_01_010 | `PG_` + 화면ID |
| 단위테스트ID | `^U_{화면ID}$` | U_EHR_03_01_010 | `U_` + 화면ID |
| **테스트케이스ID** | `^TC_{화면ID}_\d{2}$` | TC_EHR_03_01_010_04 | `TC_` + 화면ID + _2자리 |
| 통합테스트ID | `^{systemCode}-TE-\d{3}$` | B-TE-002 | 시스템코드 + -TE- + 3자리 |
| **시스템테스트ID** | `^{systemCode}-ST-\d{3}$` | B-ST-001 | 시스템코드 + -ST- + 3자리 |
| **결함ID** | `^{systemCode}-DF-\d{3}$` | B-DF-047 | 시스템코드 + -DF- + 3자리 |
| 인터페이스ID | `^IF-{systemCode}-\d{3}$` | IF-B-001 | `IF-` + 시스템코드 + 3자리 |

**프로파일이 없을 때의 폴백**: `systemCode`는 `[A-Za-z0-9]{1,4}`, `prefix`는 `[A-Za-z]{2,4}`로 완화하여 판별하고,
판별 결과를 사용자에게 확인받는다.

- 패턴에 맞지 않는 ID 입력 시: "ID 형식을 인식하지 못했습니다." 안내 후 가장 유사한 유형 제안
- 접두어 우선순위: `TC_` → `PG_` → `U_` → (접두어 없음) 화면ID. `TC_`는 뒤에 `_\d{2}`가 더 붙는 것으로 구분

## 처리 절차

### 모드 A: 단건 추적

#### Step 1: ID 유형 판별 및 시작 위치 결정

입력 ID의 유형을 위 정규식으로 판별하고, 체인에서의 위치(레벨)를 결정한다.

#### Step 2: 상향 추적 (입력 ID → 상위 체인)

입력 ID보다 상위에 있는 ID를 역방향으로 추적한다.

| 시작 ID 유형 | 상향 추적 경로 |
|-----------|------------|
| 화면ID | 화면ID → 요구사항ID → 제안요청ID |
| 프로그램ID | 프로그램ID → 화면ID → 요구사항ID → 제안요청ID |
| 단위테스트ID | 단위테스트ID → 화면ID → 요구사항ID → 제안요청ID |
| 통합테스트ID | 통합테스트ID → 요구사항ID → 제안요청ID |
| 요구사항ID | 요구사항ID → 제안요청ID |

#### Step 3: 하향 추적 (입력 ID → 하위 체인)

입력 ID보다 하위에 있는 ID를 순방향으로 추적한다.

| 시작 ID 유형 | 하향 추적 경로 |
|-----------|------------|
| 제안요청ID | 제안요청ID → 요구사항ID(복수 가능) → 화면ID → 프로그램ID + 단위테스트ID → 통합테스트ID |
| 요구사항ID | 요구사항ID → 화면ID(복수 가능) → 프로그램ID + 단위테스트ID → 통합테스트ID |
| 화면ID | 화면ID → 프로그램ID + 단위테스트ID |

#### Step 4: 트리 시각화 출력

추적 결과를 트리 형태로 출력한다. 트리 문자(┌─ ├─ │ └─)를 사용한다.

```
## ID 추적 결과 — B-RE-003

┌─ 제안요청: SFR-015 (교육 과정 관리 기능)
└─ 요구사항: B-RE-003 (교육 과정 등록/수정/삭제) ← [시작]
    ├─ 화면: EHR_03_01_010 (과정 목록)
    │   ├─ 프로그램: PG_EHR_03_01_010 ✅
    │   └─ 단위테스트: U_EHR_03_01_010 ✅
    ├─ 화면: EHR_03_01_020 (과정 등록)
    │   ├─ 프로그램: PG_EHR_03_01_020 ✅
    │   └─ 단위테스트: U_EHR_03_01_020 ⚠ 미작성
    └─ 통합테스트: B-TE-002 (과정 등록 및 수강 신청 흐름) ✅
```

- ✅: 해당 ID가 산출물에 등록되어 있음
- ⚠: 해당 위치에 ID가 있어야 하지만 누락됨
- ?: 산출물이 제공되지 않아 확인 불가

### 모드 B: 전체 교차 검증

#### Step 1: 모든 요구사항ID 수집

요구사항정의서의 모든 요구사항ID를 수집한다.

#### Step 2: 각 요구사항에 대해 하향 추적 수행

모든 요구사항에 대해 단건 추적의 하향 추적을 수행한다.

#### Step 3: 역방향 불일치 확인

하향 추적과 별도로 역방향 불일치를 확인한다:
- 화면목록표에 존재하지만 어떤 요구사항에도 매핑되지 않은 화면ID
- 프로그램정의서에 존재하지만 화면목록표에 없는 프로그램ID
- 테스트계획서에 존재하지만 추적매트릭스에 없는 테스트ID

#### Step 4: 전체 추적 완료율 계산

```
추적 완료율 = 과업완료 요구사항 수 / 전체 요구사항 수 × 100%
```

세부 완료율도 함께 계산한다:
- 화면 매핑률: 화면 매핑된 **기능** 요구사항 / 전체 기능 요구사항 × 100%
- 프로그램 등록률: 프로그램ID 있는 화면 / 전체 화면 × 100%
- 단위테스트 작성률: 단위테스트ID 있는 화면 / 전체 화면 × 100%
- **테스트케이스 커버리지**: TC 1건 이상 있는 화면 / 전체 화면 × 100%
- 통합테스트 연결률: 통합테스트 연결된 **기능** 요구사항 / 전체 기능 요구사항 × 100%
- **비기능 검증률**: 시스템테스트 연결된 **비기능** 요구사항 / 전체 비기능 요구사항 × 100%
- **결함 종결률**: Closed 결함 / (전체 결함 − Rejected) × 100%

## 누락 탐지 7가지 유형

| 유형 | 정의 | 탐지 방법 |
|------|------|---------|
| **화면 미매핑** | 기능 요구사항인데 화면ID가 없음 | 구분=기능 AND 화면ID 공백 |
| **프로그램 미등록** | 화면ID는 있는데 `PG_{화면ID}`가 없음 | 화면ID SET − 프로그램정의서 화면ID SET |
| **단위테스트 미작성** | 화면ID는 있는데 `U_{화면ID}`가 없음 | 화면ID SET − 단위테스트 ID에서 `U_` 제거한 SET |
| **테스트케이스 미작성** | 단위테스트는 있는데 `TC_` 케이스가 0건 | 단위테스트ID SET − 케이스가 존재하는 화면ID SET |
| **비기능 검증 누락** | 비기능 요구사항인데 시스템테스트ID가 없음 | 구분=비기능 AND 시스템테스트ID 공백 |
| **결함 미종결** | 테스트에 연결된 결함이 Closed가 아님 | DF-01에서 상태 ≠ Closed/Rejected |
| **역방향 불일치** | 화면/프로그램/테스트가 어떤 요구사항에도 연결되지 않음 | 추적매트릭스 매핑 역방향 검증 |

> **비기능 검증 누락**이 v1.5.0에서 새로 잡히는 항목이다. 종전에는 비기능 요구사항을
> "화면 미매핑 오탐 제외" 처리하고 끝냈기 때문에, 검증이 아예 없어도 탐지되지 않았다.

### 요구사항 구분별 판정 기준

| 컬럼 | 기능 요구사항 | 비기능 요구사항 |
|------|-------------|---------------|
| 화면ID | 없으면 **누락** | 없는 것이 정상 |
| 프로그램ID | 없으면 **누락** | 없는 것이 정상 |
| 단위테스트·케이스 | 없으면 **누락** | 없는 것이 정상 |
| 통합테스트 | 없으면 **누락** | 선택 |
| **시스템테스트** | 선택 | **없으면 누락** |

## 출력

### 단건 추적 출력

```
## ID 추적 결과 — {입력 ID}

{트리 시각화}

### 누락 항목
- ⚠ U_EHR_03_01_020: 단위테스트ID 미작성
```

### 전체 교차 검증 출력

```
## 전체 ID 교차 검증 결과 — {시스템명}

### 추적 완료율
| 항목 | 완료 | 전체 | 완료율 |
|------|------|------|--------|
| 전체 요구사항 과업완료 | N | N | N% |
| 기능 요구사항 화면 매핑 | N | N | N% |
| 화면 → 프로그램 등록 | N | N | N% |
| 화면 → 단위테스트 작성 | N | N | N% |
| 요구사항 → 통합테스트 연결 | N | N | N% |

### 누락 목록

#### 화면 미매핑 (N건)
| 요구사항ID | 요구내역 |
|-----------|--------|
| B-RE-010 | 교육 수료 증명서 발급 |

#### 프로그램 미등록 (N건)
| 화면ID | 화면명 | 연결 요구사항ID |
|-------|------|-------------|
| EHR_05_02_010 | 수료증 발급 | B-RE-010 |

#### 테스트 미작성 (N건)
| 화면ID | 화면명 | 연결 요구사항ID |
|-------|------|-------------|
| EHR_03_01_020 | 과정 등록 | B-RE-003 |

#### 역방향 불일치 (N건)
| ID | 유형 | 불일치 내용 |
|----|------|-----------|
| EHR_07_01_010 | 화면ID | 추적매트릭스에 미연결 |
```

## 체크포인트

추적 결과를 사용자에게 확인한다:

"ID 추적 결과를 확인해주세요:
- B-RE-003: 화면 2개 매핑, U_EHR_03_01_020 단위테스트 누락 ⚠
- 전체 추적 완료율: N/N = N%
- 누락 항목 총 N건 발견
추적매트릭스(AN-05) 보완이 필요하면 trace-requirements 스킬을 사용하세요.
누락 항목을 한 번에 정리할까요?"

## 주의사항

- 비기능 요구사항은 화면ID/프로그램ID 누락이 정상 — 대신 **시스템테스트ID가 없으면 누락**으로 판정한다
- 수용여부 "불가" 요구사항은 모든 누락 판정에서 제외 대상
- 화면ID와 프로그램ID가 `PG_` 접두어만 다른 경우 자동 연결로 처리
- 통합테스트는 여러 요구사항을 묶는 시나리오 단위 → 1:N 매핑이 정상
- 예외 시나리오는 정상 시나리오와 별도 ID이므로, 하나의 요구사항에 TE ID가 여럿인 것이 정상
- **정규식에 시스템코드·접두어를 하드코딩하지 않는다** — 프로파일 값을 대입한다
- 전체 교차 검증 모드는 산출물 데이터가 모두 제공된 경우에 가장 정확 — 일부만 있으면 확인 불가 항목(?)으로 표시
