# 통합테스트 시나리오 생성 (generate-integration-test)

요구사항정의서(AN-02)와 화면목록표(DE-03)를 기반으로, 업무 흐름에 따른 통합테스트 시나리오를 생성한다. 단순 CRUD가 아닌 업무 프로세스 기반의 시나리오를 작성한다.

## 입력

- 요구사항정의서 데이터 (필수)
- 화면목록표 데이터 (필수)
- 화면정의서 내용 (선택 — 더 정확한 시나리오 생성)

추가 확인:
- 시스템 코드 (A~I)
- 주요 사용자 역할 (관리자, 일반사용자, 민원인 등)

## 처리 절차

### Step 1: 요구사항-화면 매핑 확인
요구사항정의서의 각 요구사항이 어떤 화면에 매핑되는지 확인:
- 이미 추적매트릭스가 있으면 참조
- 없으면 요구사항 내용과 화면명을 기반으로 매핑 추론

### Step 2: 시나리오 그룹핑
관련 요구사항과 화면을 업무 흐름으로 그룹핑:
- 같은 업무 프로세스에 속하는 화면들을 하나의 시나리오로 묶음
- 예: "과정 등록 → 대상자 배정 → 교육 실시 → 결과 확인" = 1개 시나리오

### Step 3: 통합테스트ID 부여
- 패턴: `{시스템코드}-TE-{3자리순번}`
- 예시: `A-TE-001`
- 시나리오 단위로 부여 (Step이 아닌 시나리오에 ID)
- **예외 시나리오는 정상 시나리오와 별도 ID**를 받는다 (같은 ID의 Step으로 붙이지 않는다)

### Step 4: 사전조건 작성

시나리오마다 **Step 1을 시작할 수 있는 상태**를 기재한다. 다음 4요소 중 해당하는 것을 적는다.

| 요소 | 예시 |
|------|------|
| 계정·권한 | 관리자 계정(`admin01`)으로 로그인된 상태 |
| 선행 데이터 | 과정코드 `C001` 등록 완료, 수강 신청 5건 존재 |
| 시스템 상태 | 외부 연계 시스템 정상, 야간 배치 미수행 |
| 환경 | 테스트 DB 초기화 완료 |

> "로그인 후"는 불충분하다. **어느 권한의 계정인지**가 들어가야 권한 관련 시나리오가 성립한다.
> 사전조건이 없으면 다른 사람이 같은 시나리오를 재현할 수 없다.

### Step 5: Step 분해
각 시나리오를 구체적인 Step으로 분해:

각 Step에 포함할 내용:
- **Step 번호**: 1, 2, 3...
- **사용자구분**: 이 Step을 수행하는 역할
- **예상 입력 (사용자 행위)**: 사용자가 하는 구체적 행동
  - "~메뉴 클릭", "~버튼 클릭", "~입력 후 저장"
- **예상 출력 (시스템 결과)**: 시스템이 보여주는 결과
  - "~리스트 조회", "~팝업 호출", "~등록 완료 메시지"

### Step 6: 예외 흐름 시나리오 생성 (v1.5.0 추가)

**정상 시나리오 1건마다 최소 1건의 예외 시나리오**를 별도 ID로 만든다.

업무 흐름의 성격에서 필수 예외를 자동 도출한다:

| 흐름 성격 | 판별 키워드 | 필수 예외 시나리오 |
|---------|-----------|-----------------|
| 권한이 나뉘는 업무 | 관리자, 승인, 권한 | **권한 없음** — 하위 권한 계정으로 접근 |
| 신청·접수 업무 | 신청, 접수, 등록, 지원 | **중복 신청**, **상태 위반**(마감·기간 외) |
| 승인·반려 업무 | 승인, 반려, 처리, 검토 | **상태 위반** — 이미 처리된 건 재처리 |
| 외부 연계 업무 | 연계, API, 전송, 조회 | **연계 실패·타임아웃** |
| 결제·정산 업무 | 결제, 납부, 환불, 정산 | **중복 결제**, **결제 실패 후 롤백** |
| 파일 처리 업무 | 첨부, 업로드, 다운로드 | **허용 외 확장자·용량 초과** |

공통 예외 (모든 흐름에 검토):

| 예외 유형 | 시나리오 | 기대 결과 |
|---------|--------|---------|
| 필수 입력 누락 | 필수 항목 공란으로 다음 단계 진행 | 진행 차단, 안내 메시지 |
| 동시성 충돌 | 두 사용자가 같은 데이터 동시 수정 | 후행 저장 시 충돌 안내 |
| 세션 만료 | 장시간 방치 후 저장 시도 | 재로그인 유도, 데이터 유실 안내 |

**생성 규칙**

- 정상 시나리오의 사전조건을 바꿔 예외 상황을 만든다 (예: "A001 미등록" → "A001 등록 상태")
- 예외 시나리오는 **차단되는 Step에서 종료**한다. 이후 Step을 억지로 늘리지 않는다
- 기대 결과에 **차단 여부 + DB 반영 여부**를 함께 적는다

> **정상 흐름만 있는 통합테스트는 감리에서 검증 충분성 지적을 받는다.**
> 예외 시나리오가 0건이면 승인 요청 전에 자동 보강하고 보강 내역을 표시한다.

### Step 7: 테스트 데이터 제안
각 시나리오에 필요한 테스트 데이터를 제안:
- 사전 등록 필요 데이터
- Step에서 입력할 테스트 값
- 예외 시나리오용 데이터 (중복 키, 마감된 건, 권한 없는 계정 등)

## 시나리오 작성 원칙

1. **업무 흐름 기반**: 단순 CRUD가 아닌 실제 업무 프로세스를 반영
2. **End-to-End**: 시작부터 완료까지의 전체 흐름
3. **사용자 관점**: 기술 용어가 아닌 사용자 행위로 기술
4. **구체적 행위**: "데이터 입력" (X) → "과정명, 교육기간 입력 후 저장 버튼 클릭" (O)
5. **기대 결과 명확**: "정상 동작" (X) → "과정 리스트에 신규 등록 과정 표시" (O)
6. **예외 필수**: 정상 시나리오마다 예외 시나리오 1건 이상 — 별도 ID로
7. **사전조건 필수**: 계정·권한과 선행 데이터 상태를 명시

## 작성 주체

> 통합테스트 시나리오는 **업무 흐름을 아는 현업·운영 담당자와 합동 작성**하는 것이 원칙이다.
> 개발자 단독 작성 시 설계 단계에서 중요하게 다뤄진 항목과 예외 업무 흐름이 누락되기 쉽다.
> 현업 참여가 어려우면 최소한 시나리오 목록에 대해 **현업 검토·확인 이력을 남기도록** 안내한다.

## 결과 기입 시 (fill-integration-test-result 연계)

부적합 판정이 나오면 `manage-defects`가 결함ID를 발급하고, 시나리오 표에는 결함ID만 참조한다.
판정값은 **적합 / 부적합 / 점검제외** 3종이며, 점검제외는 사유가 필수다.

## 체크포인트

시나리오 구성을 사용자에게 확인:

```
통합테스트 시나리오 {N}건을 생성했습니다. (정상 {N} / 예외 {N})

주요 확인:
1. 시나리오 그룹핑이 실제 업무 흐름과 일치하는지
2. 사전조건이 재현 가능한 수준인지 (계정·권한·선행 데이터)
3. 예외 시나리오가 실제로 차단되어야 하는 상황인지
4. 현업 검토를 받을지

승인하려면 '승인' 또는 'OK'를 입력하세요.
```
