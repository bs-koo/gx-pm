# 화면목록표 생성 (generate-screen-list)

요구사항정의서(AN-02)의 요구사항을 분석하여 필요한 화면을 식별하고, DE-03 화면목록표 양식에 맞는 데이터를 생성한다.
본 스킬은 ID 체인의 **요구사항ID → 화면ID** 단계를 처리한다.

---

## 입력

| 항목 | 필수 여부 | 설명 |
|---|---|---|
| 요구사항정의서 데이터 | 필수 | AN-02 기준. 요구사항ID(예: B-RE-001), 요구사항명, 요구사항 설명 포함 |
| 시스템 접두어 | 필수 | 영문 대문자 2~4자 (예: EHR, KSC, CMS) |
| 프로젝트 망 유형 | 권장 | 내부망 전용 / 외부망 전용 / 혼재 여부 |
| 기존 화면목록표 | 선택 | 있으면 기존 번호 체계 유지, 없으면 신규 부여 |

---

## 처리 절차

### Step 1: 요구사항 파악 및 대분류 그룹핑

요구사항 전체를 검토하여 **업무 영역(대분류)**을 파악한다.

그룹핑 기준:
- 동일한 업무 주체가 수행하는 기능 묶음 (예: 관리자, 환자, 의사)
- 동일한 데이터 도메인을 다루는 기능 묶음 (예: 회원, 게시판, 결제)
- 요구사항 설명에 반복 등장하는 업무명 키워드 추출

기능구분ID 부여 규칙:
- 패턴: `{접두}_{2자리순번}` (순번은 01부터 시작)
- 예시: `EHR_01` = 시스템관리, `EHR_02` = 회원관리, `EHR_03` = 진료관리

> 실무 팁: 요구사항이 10개 미만이면 기능구분 1~2개로 통합하고, 30개 이상이면 5~7개 수준으로 분리한다.

---

### Step 2: 세부 기능(기능ID) 식별

각 기능구분 내에서 **독립적으로 개발·테스트 가능한 단위**를 기능ID로 분리한다.

기능ID 부여 규칙:
- 패턴: `{접두}_{대분류순번}_{2자리순번}` (순번은 01부터 시작)
- 예시: `EHR_01_01` = 운영자 권한 관리, `EHR_01_02` = 메뉴 관리, `EHR_02_01` = 환자 등록

분리 기준:
- 요구사항 설명에 CRUD(등록/조회/수정/삭제)가 별도로 명시된 경우 → 1개 기능ID
- 하나의 요구사항ID가 다수의 업무 절차를 포함하는 경우 → 절차별 분리 검토

---

### Step 3: 화면 식별 및 화면ID 부여

기능ID 하나당 필요한 **화면 수를 추론**한다.

#### 3-1. 추정하기 전에, 결정돼 있는지 본다

아래의 화면 수 추론표는 **추정**이다. 추정하기 전에 문서가 실제로 답을 주는지 확인한다.

| 미결정이다 | 결정돼 있다 |
|---|---|
| 화면·UI 요구사항인데 화면 수를 셀 근거가 본문에 없다 | 화면명이 열거돼 있다 (목록·등록·상세 등) |
| "열린다 / 표시된다 / 이동한다" 만 있고, 그것이 같은 화면 안인지 밖인지 말하지 않는다 | 모달·팝업·탭·페이지라고 명시돼 있다 |
| 소스에 모달 프래그먼트·탭이 있는데 화면 단위 규정이 없다 | 기존 화면목록표에 같은 기능의 분리 기준이 있다 |
| 한 요구사항이 조회·입력·확인을 모두 포함하는데 그 경계를 말하지 않는다 | 화면 수가 본문에 숫자로 적혀 있다 |

**detect-alternatives** 는 여기서 아무것도 잡지 못한다. 그 스킬은 **말해진** 대안
(`1안`/`2안`, "또는", "검토 필요")을 찾는데, 이 경우는 문서가 **아무 말도 하지 않는** 것이다.

미결정인데 그냥 추론표를 적용하면, 그렇게 나온 수가 그대로 화면ID가 된다.
`templates/pipeline-protocol.md` 의 재생성 파급 규칙에 따라 `PG_`·`U_`·`TC_` 가 전부
화면ID에서 파생되므로, 나중에 화면 수를 정정하면 후속 산출물이 전건 재채번된다.

#### 3-2. 유형별로 다르게 다룬다

| 유형 | 동작 | 근거 |
|------|------|------|
| **A** 신규 구축 | 묻는다 | 화면 분리의 근거가 RFP 밖에 없다 |
| **B** 추가 개발 | 기존 화면목록표의 분리 기준을 따르고, 같은 기능이 없을 때만 묻는다 | 기존 체계와 어긋나면 한 산출물에 분리 기준이 두 벌 생긴다 |
| **C** 산출물 정비 | 묻는다 | 모달 프래그먼트·탭을 화면으로 셀지는 소스 파일 목록이 답하지 않는다 |
| **D** 변경 관리 | **묻지 않는다** | 기존 화면ID는 바뀌면 안 된다. 답에 따라 화면 수가 달라지면 변경 범위 밖에서 재채번이 일어난다 |

화면 수 추론 기준:

| 요구사항 패턴 | 예상 화면 수 | 화면 구성 |
|---|---|---|
| 목록 조회만 있는 경우 | 1개 | 목록 화면 |
| 목록 + 상세 | 2개 | 목록, 상세/조회 |
| 목록 + 등록 + 상세 | 3개 | 목록, 등록, 상세 |
| 목록 + 등록 + 수정 + 상세 | 3~4개 | 목록, 등록, 수정(또는 상세와 통합) |
| 팝업 검색창 포함 | +1개 | 팝업 화면 추가 |
| 단계별 처리(승인/반려) | +1~2개 | 처리 화면 추가 |

화면ID 부여 규칙:
- 패턴: `{기능ID}_{SN}` (SN은 010부터 10단위 증가)
- 예시: `EHR_01_01_010` = 운영자 권한 관리 목록, `EHR_01_01_020` = 운영자 권한 등록

화면명 명명 규칙:
- `{기능명} {화면유형}` 형식 (예: "운영자 권한 관리 목록", "운영자 권한 등록")
- 화면유형 표준어: 목록, 등록, 수정, 상세, 조회, 팝업, 처리

---

### Step 4: 망구분 판별

요구사항 설명에서 다음 키워드로 망구분을 판별한다.

| 키워드 | 망구분 | 비고 |
|---|---|---|
| 관리자, 운영자, 담당자, 내부, 인트라넷, 관리화면 | 내부망 | 관리자 시스템 |
| 민원인, 국민, 사용자, 외부, 포털, 공개 | 외부망 | 사용자 포털 |
| 명시 없음 | 내부망 | 기본값 |

> 주의: 하나의 기능이 내부/외부 양쪽에 화면이 존재할 수 있다 (예: 공지사항 관리=내부, 공지사항 조회=외부).

---

### Step 5: 신규/변경 판별

| 판별 기준 | 값 |
|---|---|
| 기존 화면목록표에 없는 화면 | 신규 |
| 기존 화면목록표에 동일 기능이 있고 요구사항 변경 명시 | 변경 |
| 기존 화면목록표 미제공 시 | 신규 (기본값) |

---

### Step 6: 담당자 및 개발예정일 처리

- 담당자: 입력받은 경우 그대로 기재, 없으면 공란
- 개발예정일(UI/LOGIC): 입력받은 일정이 있으면 기재, 없으면 공란
- 개발진행(UI/LOGIC): 초안 생성 시점에는 공란

---

## 체크포인트 (사용자 확인 필수)

화면목록표 초안 생성 후 아래 문구로 확인을 요청한다:

> "화면 구성이 맞는지 확인해주세요.
> - 기능구분/기능 분류가 실제 업무와 일치하는지
> - 화면 수가 적절한지 (누락된 화면, 불필요한 화면)
> - 망구분(내부/외부)이 올바른지
> 수정이 필요한 경우 화면ID나 기능명을 알려주시면 반영하겠습니다."

사용자 확인 후 수정사항을 반영하여 최종 화면목록표를 출력한다.

## 주의사항 / 규칙

1. **SN 채번**: 동일 기능ID 내에서 010, 020, 030 순으로 부여. 중간 삽입 여지를 위해 10단위 사용.
2. **화면ID 고유성**: 전체 화면목록표에서 화면ID는 중복 불가.
3. **기존 목록 존재 시**: 기존에 부여된 기능구분ID/기능ID는 변경하지 않고 신규 항목만 채번하여 추가.
4. **팝업 화면**: 독립 화면으로 간주하여 SN을 별도 부여 (예: EHR_02_01_090 = 주소 검색 팝업).
5. **공통 화면 처리**: 로그인, 메인 대시보드 등 공통 화면은 `{접두}_00` 기능구분으로 별도 관리 권장.
6. **요구사항ID 연결**: 화면ID는 이후 프로그램정의서(DE-05), 단위테스트(U_{화면ID}), 통합테스트({시스템코드}-TE-xxx)로 연결되므로 ID 변경 시 후속 산출물도 함께 갱신 필요.
