# 결함 관리 (manage-defects)

테스트 레벨(단위/통합/시스템/인수)과 무관하게 **모든 결함을 하나의 대장에서 관리**한다.
결과서의 부적합 항목은 결함ID로 이 대장을 참조하고, 조치·재테스트 이력은 대장에만 기록한다.

**호출 시점**: `fill-unit-test-result` · `fill-integration-test-result` · `generate-system-test`에서
부적합 판정이 나올 때마다. 또는 `/gx-결함관리대장` 커맨드로 단독 실행.

---

## 입력

| 항목 | 필수 | 설명 |
|------|------|------|
| 부적합 항목 | Y | 결과서에서 부적합으로 판정된 항목 (테스트ID, 현상) |
| 기존 결함관리대장 | 선택 | 있으면 이어서 채번, 중복 결함 병합 |
| 총괄 테스트계획서 | 권장 | TE-01의 심각도 정의·종료기준을 판정 근거로 사용 |
| systemCode | Y | 결함ID 채번용 (profile.json) |

---

## 처리 절차

### Step 1: 결함ID 채번

- 패턴: `{시스템코드}-DF-{3자리}`
- **프로젝트 전체에서 연속 채번**한다. 테스트 레벨별로 번호를 나누지 않는다
- 기존 대장이 있으면 마지막 번호 다음부터

### Step 2: 중복 결함 판별

새 부적합 항목이 기존 결함과 같은 원인인지 확인한다.

| 판별 신호 | 처리 |
|---------|------|
| 동일 화면 + 동일 증상 | 중복 → 기존 결함의 "발견 테스트ID"에 추가, 새 ID 미발급 |
| 다른 화면 + 동일 원인 (공통 모듈) | 중복 → 기존 결함에 병합하고 영향 화면 목록에 추가 |
| 동일 화면 + 다른 증상 | 별개 → 새 ID 발급 |
| 조치 완료(Closed) 후 재발 | 별개 → **새 ID 발급 + 비고에 원 결함ID 참조** |

중복으로 판단되면 사용자에게 확인을 받는다:

```
{시스템코드}-DF-007과 동일한 원인으로 보입니다.

  기존: B-DF-007 "중복 검사 미작동" (화면 EHR_01_01_020, 상태 Assigned)
  신규: TC_EHR_03_01_020_04 "과정 등록 시 중복 검사 미작동"

  1. 기존 결함에 병합 (발견 위치만 추가)
  2. 별개 결함으로 등록 (새 ID 발급)
```

### Step 3: 심각도 자동 판정

부적합 내역의 키워드로 1차 판정한 뒤 사용자 확인을 받는다.

| 심각도 | 판별 키워드 | 판별 질문 |
|--------|-----------|---------|
| **Critical** | 데이터 유실·손실·오염, 저장 안 됨, 시스템 다운, 서버 오류, 500, 무한루프, 정보 노출, 인증 우회, 권한 우회, SQL, 스크립트 | 이대로 오픈하면 사고가 나는가? |
| **Major** | 저장 실패, 조회 불가, 처리 불가, 승인 안 됨, 진행 불가, 오류 발생 | 사용자가 목적을 달성할 다른 방법이 있는가? (없으면 Major) |
| **Minor** | 일부 누락, 정렬 오류, 표시 안 됨, 새로고침 필요, 느림 | 불편하지만 업무는 되는가? |
| **Trivial** | 오탈자, 문구, 정렬, 여백, 색상, 폰트 | 기능이 아니라 보기의 문제인가? |

**자동 격상 규칙** — 아래에 해당하면 키워드와 무관하게 Critical로 올린다:

- 보안 관련 부적합 (인증·권한·암호화·개인정보) → **Critical**
- 데이터 정합성 훼손 (저장값 ≠ 조회값) → **Critical**
- 물리 삭제 발생 (`DEL_YN` 소프트 삭제 위반) → **Critical**

> 보안·개인정보는 P1 법적 필수 영역이라 심각도 하향 판단을 하지 않는다.

### Step 4: 우선순위 판정

심각도와 **독립적으로** 매긴다. 다음 질문으로 결정한다.

| 질문 | Yes → |
|------|-------|
| 이 결함이 후속 테스트를 막는가? | High |
| 발주처 시연·인수테스트 대상 화면인가? | High |
| 해당 레벨 종료기준(Critical/Major 0건)에 걸리는가? | High |
| 종료 전까지 고치면 되는가? | Medium |
| 미뤄도 인수에 지장 없는가? | Low |

기본 매핑(사용자가 조정 가능):

| 심각도 | 기본 우선순위 |
|--------|-------------|
| Critical | High |
| Major | High |
| Minor | Medium |
| Trivial | Low |

### Step 5: 재현 절차 작성

**제3자가 그대로 따라할 수 있는 수준**으로 만든다. 결과서의 부적합 내역이 한 줄이면 보강을 요청한다.

| 불충분 | 충분 |
|--------|------|
| 저장 시 오류 | 1. 관리자(`admin01`) 로그인 2. 시스템관리 > 권한관리 > 등록 3. 권한코드 `A001` 입력(이미 등록된 코드) 4. 저장 클릭 → 오류 없이 중복 저장됨 |

재현 절차에 반드시 포함할 것: **계정·권한 / 진입 경로 / 입력값 / 조작 / 실제 결과**

### Step 6: 상태 관리

```
Open ──→ Assigned ──→ Fixed ──→ Retest ──→ Closed
  │                                 │
  │                                 └──→ Reopen ──→ Assigned
  ├──→ Deferred   (발주처 승인 근거 필요)
  └──→ Rejected   (판단 사유 필요)
```

상태 전이 시 검증한다:

| 전이 | 필수 입력 |
|------|---------|
| → Assigned | 담당자 |
| → Fixed | 원인, 조치내역, 조치일, 조치자 |
| → Closed | 재테스트 결과=적합, 재테스트일, 재테스트자 |
| → Reopen | 재테스트 결과=부적합, 사유 |
| → Deferred | **발주처/PM 승인 근거** (회의록·메일 참조) |
| → Rejected | **판단 사유** (결함이 아닌 이유) |

> Deferred와 Rejected는 근거 없이 설정할 수 없다. 근거가 없으면 Open으로 되돌린다.

### Step 7: 통계 산출 및 종료기준 판정

```
[결함 현황] — {시스템명} / {기준일}

총 결함: N건

심각도별:
| 심각도 | 전체 | Closed | 진행중 | Deferred | Rejected | 잔존 |
|--------|------|--------|--------|----------|----------|------|
| Critical | N | N | N | N | N | **N** |
| Major    | N | N | N | N | N | **N** |
| Minor    | N | N | N | N | N | N |
| Trivial  | N | N | N | N | N | N |

조치율 = Closed ÷ (전체 − Rejected) × 100 = N%

발견 단계별: 단위 N · 통합 N · 시스템 N · 인수 N
```

종료기준 판정 (TE-01 §7 대조):

```
[종료기준 판정]

| 기준 | 목표 | 현재 | 판정 |
|------|------|------|------|
| Critical 잔존 | 0건 | N건 | 충족 / **미충족** |
| Major 잔존 | 0건 | N건 | 충족 / **미충족** |
| Minor 조치율 | 90% 이상 | N% | 충족 / **미충족** |

종합: 다음 레벨 진입 가능 / **진입 불가**
```

**미충족 시 안내**:

```
종료기준 미충족으로 다음 테스트 레벨 진입 조건을 만족하지 않습니다.

  미조치 Critical: B-DF-003, B-DF-011
  미조치 Major: B-DF-007

  1. 결함 조치 후 재판정
  2. PM 승인으로 진입 (사유를 기록합니다)
```

## 출력

DF-01 결함관리대장 마크다운 표 + 통계 + 종료기준 판정.

```

| 결함ID | 발견단계 | 발견 테스트ID | 화면ID | 요구사항ID | 결함 제목 | 심각도 | 우선순위 | 상태 | 발견일 | 발견자 | 담당자 | 원인 | 조치내역 | 조치일 | 조치자 | 재테스트 | 재테스트일 | 비고 |
|--------|---------|-------------|-------|----------|---------|--------|--------|------|-------|-------|-------|------|--------|-------|-------|--------|----------|------|
| B-DF-001 | 단위 | TC_EHR_01_01_020_04 | EHR_01_01_020 | B-RE-001 | 권한코드 중복 검사 미작동 | Major | High | Closed | 2026-04-10 | 홍길동 | 김개발 | 중복 검사 쿼리 조건절 누락 | selectDuplCheck에 USE_YN 조건 추가 | 2026-04-11 | 김개발 | 적합 | 2026-04-12 | |
| B-DF-002 | 통합 | B-TE-003 | EHR_03_01_020 | B-RE-003 | 과정 신청 시 마감 상태 미검증 | Critical | High | Assigned | 2026-04-12 | 이현업 | 박개발 | | | | | | | 마감 후 신청 가능 — 데이터 정합성 훼손 |
```

각 결함의 **재현 절차**는 표가 길어지므로 별도 섹션으로 출력한다:

```
### 재현 절차

**B-DF-002** 과정 신청 시 마감 상태 미검증
1. 일반사용자(`user01`) 로그인
2. 교육관리 > 과정 신청 진입
3. 신청 마감일이 경과한 과정 `C005` 선택
4. 신청 버튼 클릭
→ 마감 안내 없이 신청 완료 처리됨 (DB에 신청 이력 생성)
```

## 주의사항

1. **결과서에만 있고 대장에 없는 결함은 감리 지적 대상**이다 — 부적합 판정 시 반드시 결함ID를 발급한다
2. 결함ID는 프로젝트 전체 연속 채번. 레벨별 분리 채번 금지
3. 심각도는 테스터, 우선순위는 PM이 판정하는 것이 원칙 — 두 값을 같은 근거로 매기지 않는다
4. 보안·개인정보·데이터 정합성 결함은 **심각도 하향 판단을 하지 않는다**
5. Critical 결함은 대장 등록과 별개로 **즉시 PM 보고**를 안내한다
6. Deferred는 발주처 승인 근거 없이 설정하지 않는다 — 근거 없는 Deferred는 "결함 미조치"로 본다
7. 조치 완료 후 재발한 결함은 새 ID를 발급한다 (같은 ID를 Reopen하는 것과 구분)
8. 대장의 잔존 결함은 추적매트릭스(AN-05)의 "잔존 결함" 컬럼과 동기화한다
