# 총괄 테스트계획서 생성 (generate-master-test-plan)

개별 테스트 산출물(DE-13/DE-14/ST-01)보다 **먼저** 작성하는 전략 문서.
감리에서 "테스트를 계획하고 수행했는가"를 증명하는 근거이며, **진입·종료기준의 유일한 출처**다.

---

## 왜 먼저 만드나

종료기준이 없으면 테스트가 언제 끝나는지 문서로 설명할 수 없다.
"모든 결함을 발견해야 끝난다"는 성립하지 않으므로, **완료 기준을 세우고 목표에 도달하면 종료**하는 것이 원칙이다.

계획서 없이 결과서만 있으면 감리에서 다음이 지적된다:
- 테스트 범위 미정의 (무엇을 안 했는지 알 수 없음)
- 종료 판정 근거 부재 (적합률 92%로 끝낸 근거가 없음)
- 결함 심각도 기준 부재 (Critical 판정이 자의적)

---

## 입력

| 항목 | 필수 | 설명 |
|------|------|------|
| 요구사항정의서 | Y | 기능/비기능 건수 산출 (AN-02) |
| 프로파일 | Y | 시스템코드·프레임워크·DB·작성자·감리일정 |
| 화면목록표 | 권장 | 테스트 대상 규모 산출 |
| 프로젝트 일정 | 권장 | 레벨별 일정 배분 |
| 인터페이스정의서 | 선택 | Mock 처리 대상 식별 |

---

## 처리 절차

### Step 1: 범위 산정

요구사항정의서에서 자동 집계한다.

```
대상 요구사항
  기능 요구사항:   N건
  비기능 요구사항: N건 (성능 N · 보안 N · 접근성 N · 호환성 N · 유지보수성 N · 법적준수 N)
  수용여부 "불가": N건 → 테스트 범위 제외

대상 화면: N개
대상 인터페이스: N건
```

**제외 범위를 반드시 사용자에게 묻는다.** 비워 두면 감리에서 "테스트 범위 미정의"로 지적된다.

```
테스트 제외 범위가 있나요? (사유와 함께 입력)

  흔한 제외 대상:
  • 상용 솔루션 내부 기능 (예: 전자결재 엔진 내부 로직)
  • 외부 연계기관 시스템 내부 처리
  • 수용여부 "불가"로 판정된 요구사항
  • 차기 사업 이관 범위

  (없으면 "없음")
```

### Step 2: 테스트 레벨 확정

기본 4단계를 제시하고 프로젝트 상황에 맞춰 조정한다.

| 레벨 | 산출물 | 수행 주체 | 대상 |
|------|--------|----------|------|
| 단위테스트 | DE-13 / IM-03 | 개발팀 | 기능 (화면 단위) |
| 통합테스트 | DE-14 / TE-02 | 개발팀 + 현업 | 기능 (업무 흐름) |
| 시스템테스트 | ST-01 / ST-02 | 개발팀 + 인프라 | **비기능** |
| 인수테스트 | DE-14 / TE-06 | **발주처** | 기능 + 비기능 |

**비기능 요구사항이 1건이라도 있으면 시스템테스트 레벨은 필수**로 안내한다.
없으면 비기능 요구사항의 검증 칸이 추적매트릭스에서 통째로 비게 된다.

### Step 3: 추진 체제 수집

**AskUserQuestion**으로 역할별 담당자를 받는다. 미입력 시 프로파일의 `author`를 PM 기본값으로 제안한다.

```
테스트 추진 체제를 입력해주세요.

  1. 테스트 총괄(PM):
  2. 단위테스트 수행:
  3. 통합테스트 수행:
  4. 시스템테스트 수행(성능·보안):
  5. 인수테스트 주관(발주처 담당자):   ← 개발팀 인원 기재 금지
  6. 결함 조치 총괄:
```

> **인수테스트 수행자에 개발팀 인원이 들어가면 감리 지적 대상**이다. 발주처 담당자 실명을 받는다.

### Step 4: 일정 배분

감리일정(`auditDate`)과 납기를 기준으로 역산한다.

```
레벨별 일정 (감리일 {auditDate} 기준 역산)

| 레벨 | 시작 | 종료 | 소요 | 선행 조건 |
|------|------|------|------|---------|
| 단위테스트 | | | | 개발 완료 |
| 통합테스트 | | | | 단위 종료기준 충족 |
| 시스템테스트 | | | | 통합 종료기준 충족 |
| 인수테스트 | | | | 시스템 종료기준 충족 |
| 결함 조치 예비기간 | | | | — |
```

**결함 조치 예비기간을 반드시 일정에 넣는다.** 테스트 종료일 = 납기일이면 조치 시간이 0이 된다.
예비기간이 없으면 경고한다.

### Step 5: 테스트 환경 정의

프로파일의 `framework`·`db`에서 기본값을 채우고 나머지를 묻는다.

```
테스트 환경을 확인해주세요.

  서버: {framework 기반 기본값}
  DB: {db} — 테스트 스키마명?
  브라우저: 지원 대상? (Chrome/Edge/Safari/IE11)
  네트워크: {networkType}
  외부 연계: 실 연계 / Mock — Mock이면 어느 인터페이스인지
  테스트 도구: (성능 JMeter / 보안 진단도구 / 수동)
```

**Mock 처리 인터페이스를 반드시 나열**한다. 실 연계 미검증분은 인수 조건에 영향을 준다.

### Step 6: 테스트 데이터 방침

```
테스트 데이터 방침을 확인해주세요.

  출처: 신규 생성 / 운영 데이터 복제 / 혼합
  ⚠ 운영 데이터 사용 시 비식별 조치 방법을 명시해야 합니다
     (개인정보보호법 — 미조치 시 P1 법적 필수 위반)
  준비 담당:
  초기화 방침: 레벨별 초기화 / 누적
  폐기 시점:
```

운영 데이터 사용을 선택하면 **비식별 조치 방법 입력을 강제**한다.

### Step 7: 진입·종료기준 확정

기본값을 제시하고 조정을 받는다.

**진입기준 기본값**

| 레벨 | 진입기준 |
|------|---------|
| 단위 | 개발 완료 · 빌드 배포 성공 · 테스트 데이터 준비 |
| 통합 | 단위 종료기준 충족 · 통합 환경 구축 · 시나리오 승인 |
| 시스템 | 통합 종료기준 충족 · 운영 유사 환경 · 목표치 확정 |
| 인수 | 시스템 종료기준 충족 · 발주처 일정 확정 · 매뉴얼 제공 |

**종료기준 기본값**

| 기준 | 목표치 |
|------|--------|
| 계획 케이스 실행률 | 100% (미실행은 점검제외 + 사유) |
| Critical 결함 잔존 | 0건 |
| Major 결함 잔존 | 0건 |
| Minor 결함 조치율 | 90% 이상 |
| 요구사항 커버리지 | 100% |
| 적합률 | 95% 이상 |

> 종료기준을 완화하려면 **근거를 개정이력에 남기도록** 안내한다.

### Step 8: 결함 관리 기준 확정

`templates/DF-01-defect-log.md`의 심각도·우선순위·상태 정의를 그대로 채택하는 것이 기본값이다.
프로젝트별 조정이 필요하면 여기서 확정하고, 이후 `manage-defects`가 이 정의를 따른다.

### Step 9: 위험 식별

프로젝트 상황에서 자동 식별하고 사용자 보강을 받는다.

| 자동 식별 조건 | 위험 항목 |
|-------------|---------|
| 인터페이스정의서에 외부 연계 존재 | 외부 연계기관 테스트 환경 미개방 |
| 프로젝트 유형 C (산출물 정비) | 실제 코드와 산출물 불일치로 케이스 재작성 |
| 감리일까지 4주 이하 | 결함 조치 기간 부족 |
| 비기능 요구사항에 성능 항목 존재 | 성능 목표 미달 시 아키텍처 변경 필요 |
| 운영 데이터 사용 | 개인정보 비식별 조치 누락 |

---

## 출력

TE-01 총괄 테스트계획서 (9개 섹션). `templates/TE-01-master-test-plan.md` 구조를 따른다.

각 섹션을 순차 생성하되, **§7 진입·종료기준과 §8 결함 관리 기준은 별도 승인**을 받는다.
이 두 섹션이 이후 모든 결과서의 판정 근거가 되기 때문이다.

## 체크포인트 (승인 루프)

```
총괄 테스트계획서를 생성했습니다.

  범위: 기능 {N}건 / 비기능 {N}건 / 제외 {N}건
  레벨: {N}단계
  일정: {시작} ~ {종료} (결함 조치 예비기간 {N}일)
  종료기준: Critical 0 · Major 0 · Minor 조치율 90% · 적합률 95%

주요 확인:
1. 제외 범위와 사유가 발주처와 합의된 내용인지
2. 인수테스트 주관자가 발주처 담당자인지
3. 결함 조치 예비기간이 현실적인지
4. 종료기준 수치를 지킬 수 있는지 (지킬 수 없는 기준은 안 쓰는 게 낫습니다)

승인하려면 '승인' 또는 'OK'를 입력하세요.
수정하려면 변경할 내용을 입력하세요.
```

## 주의사항

1. **개별 테스트 산출물보다 먼저 작성**한다. 나중에 만들면 결과에 기준을 끼워 맞춘 문서가 된다
2. 종료기준은 **수치로** 적는다 — "충분히 테스트한다"는 감리 지적 대상
3. 지킬 수 없는 종료기준을 쓰지 않는다. 미달 상태로 종료하면 계획서가 오히려 불리한 증거가 된다
4. 제외 범위·Mock 인터페이스·비식별 조치는 **사유·방법과 함께** 명시한다
5. 이 문서의 종료기준과 결과서의 통계가 어긋나면 안 된다 — `manage-defects`가 이 값을 참조한다
6. 종료기준 완화는 개정이력에 근거를 남긴다
7. 비기능 요구사항이 있는데 시스템테스트 레벨을 빼면 **추적매트릭스에 빈칸이 남는다**는 점을 반드시 안내한다
