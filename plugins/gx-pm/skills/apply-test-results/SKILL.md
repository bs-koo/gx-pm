# 단위테스트 수행 결과 반영 (apply-test-results)

## 언제 도는가

`/gx-단위테스트결과반영` 이 부른다. 시험 수행 이후 결과를 기록할 때다.
계획서를 만드는 `/gx-단위테스트계획서` 와는 따로 돈다 — 그 커맨드는 이 스킬을 부르지 않는다.

**계획서를 고치지 않는다.** 계획서의 행을 옮긴 **IM-03 단위테스트결과서**(`templates/IM-03-unit-test-result.md`)를
만들고, 반영할 때마다 그 결과서를 지금 계획서에 맞춰 갱신한다. 계획서는 고객사에 낸 약속이고 결과서는 그
약속을 시험한 기록이라 따로 둔다.

## 왜 이 방식인가

**계획서는 고객사에 보여준 약속이고, 결과는 그 약속을 지켰다는 증적이다.**
그래서 Pass 는 근거가 있을 때만 찍고, 그 근거를 수행대장에 남긴다. 감리에서
「이 Pass 는 무엇으로 확인했나」에 파일로 답할 수 있어야 한다.

**근거는 레포에 지금 있는 테스트 코드다.** 개발자가 어떤 도구로 일했는지 — oh-my-gx 의
gx-tdd, 다른 플러그인, 세션에서 바로 고친 것, 손으로 쓴 것 — 와 상관없이 테스트 코드는
레포에 남는다. 특정 개발 방식의 기록에 기대면 그 방식을 안 쓴 팀원의 작업이 통째로 빠진다.

**결과는 네 상태 — `Pass`·`Fail`·`미구현`·`미검증` — 이고 모든 행에 사유를 붙인다.** 빈칸은
「안 한 것인지, 확인이 안 된 것인지, 일부러 뺀 것인지」 알 수 없어서, 반영한 뒤에는 빈 결과 칸이 없다.

**테스트가 있다는 것과 실행해서 통과했다는 것은 다르다.** 짝이 맞는 테스트가 있어도
실행 결과가 없으면 `미검증 — 실행 결과 없음` 으로 남기고 Pass 는 찍지 않는다. 실행 결과는 따로
관리하지 않는다 — 빌드 도구가 테스트를 돌릴 때 남기는 결과 파일(JUnit XML)이 소스 폴더에
있으면 있는 그대로 읽고, 개발에 gx-tdd 를 썼으면 그 verify 통과 기록도 실행 근거로 쓴다.
둘 다 없으면 PM 이 승인 화면에서 확인해 준 행만 Pass 가 된다.

**결과 파일은 테스트를 돌린 그 폴더에만 생기고 커밋되지 않는다.** PM 이 받아 둔 사본에서
돌리면 결과가 없는 것이 정상이다. 실행 결과를 붙이려면 테스트를 돌린 작업 폴더(개발 리더 PC·
빌드 서버의 사본)를 경로로 준다.

**개발 쪽은 계획서를 읽지 않는다.** 대조는 언제나 **지금의 계획서**와 **지금 레포의
테스트**로 사후에 한다. 계획서가 개발 뒤에 생겨도, 중간에 바뀌어도 같은 절차로 돈다.

## 입력

| 항목 | 필수 | 설명 |
|------|------|------|
| 계획서 md | Y | `{시스템코드}-단위테스트계획서.md` — **읽기만 한다** |
| 결과서 md | N | `{시스템코드}-단위테스트결과서.md` — 있으면 갱신하고 없으면 새로 만든다. xlsx 는 이 파일에서 뽑는다 |
| 소스 경로 | Y | 개발 레포 하나 이상. 커맨드 Step 1 이 확보해 넘긴다 (프로파일 `assets.testSourcePaths`, 없으면 `assets.sourcePath`) |
| AN-03·AN-02 | N | 기능명·요구사항명으로 대조 후보를 좁힌다 |
| `source-index.json` | N | 프로젝트 폴더의 소스 색인(**scan-source-index**). 기능 → 컨트롤러·서비스 → 그 테스트로 좁힌다 |
| 레포의 `context/` | N | oh-my-gx 도메인 문서. `PROJECTS.md`(도메인 ↔ 소스 경로), `glossary.md`(업무 용어 ↔ 코드명)로 기능의 코드 위치를 찾는다. **구현 기록이지 시험 근거는 아니다** |
| 수행대장 | N | `증적/{시스템코드}-단위테스트수행대장.md`. 지난 판정·제외·PM 확인·담당자 매핑 |

도구는 플러그인 루트의 `utils/test-evidence.py` 다 (Python 3.10 이상, 외부 패키지 없음).
**사실을 모으고 쓰는 일은 이 도구가, 짝짓는 판단은 이 스킬이 한다.** 결과서·수행대장을 손으로
쓰지 않는다 — 169행 표에서 `|` 하나가 밀리면 xlsx 가 통째로 어긋나고, 지난 판정과의 비교·건수·수행률도
손으로 세면 틀린다.

결과서 양식의 정본은 `templates/IM-03-unit-test-result.md`, 수행대장은 `templates/DE-13-execution-ledger.md` 다.

## Step 1: 색인

임시 폴더는 **OS 임시 폴더 아래**(Windows `%TEMP%`, 그 밖 `$TMPDIR`·`/tmp`)에 만들고 두 파일을
뽑는다. 프로젝트 폴더를 어지럽히지 않고, Codex 샌드박스에서도 쓸 수 있는 자리다. 경로는 먼저
절대 경로로 정해 **명령마다 글자 그대로** 적는다 — 셸 변수는 명령 사이에 남지 않는 환경이 있다.

```
python {플러그인 루트}/utils/test-evidence.py index --source "{레포1}" [--source "{레포2}" ...] --out "{임시}/tests.json"
python {플러그인 루트}/utils/test-evidence.py plan --de13 "{계획서}" --result "{프로젝트 폴더}/{시스템코드}-단위테스트결과서.md" --ledger "{프로젝트 폴더}/증적/{시스템코드}-단위테스트수행대장.md" --out "{임시}/plan.json"
```

결과서·수행대장이 아직 없으면(첫 반영) 그 경로를 그대로 준다 — 도구가 없는 파일로 본다.

`tests.json` 의 `tests[]` 하나가 테스트 메서드 하나다 (JUnit·Kotlin `@Test` 계열, Jest·Vitest `it`/`test`).

| 필드 | 뜻 |
|------|----|
| `repo`·`file`·`line` | 위치. 근거를 적을 때 `{repo}:{file}#{name}` 으로 쓴다 |
| `class`·`name`·`display` | 클래스(JS 는 describe 경로), 메서드 이름, `@DisplayName` |
| `literals` | 본문의 문자열·세 자리 이상 숫자 — 화면 문구·한계값으로 후보를 찾는 데 쓴다 |
| `asserts` | 단언 호출 수. 0 이면 아무것도 확인하지 않는 테스트다 |
| `disabled` | `@Disabled`·`it.skip`·`xit` — **근거가 아니다** |
| `last_change` | 그 테스트 파일의 마지막 커밋 날짜·작성자 |
| `run` | 실행 근거. `status` 는 `passed`·`failed`·`skipped`·`none`. 실패면 `message` 에 실패 메시지 한 줄 — Fail 사유에 그대로 옮긴다 |

`run` 은 가장 최근 실행 하나다.

| `run.by` | 출처 |
|----------|------|
| `report` | 빌드 도구의 결과 파일 (`build/test-results/`, `target/surefire-reports/`, `junit*.xml` 등) — `source` 가 그 파일 |
| `gx-tdd verify` | gx-tdd 기록(`.dev/{브랜치}/`)이 그 테스트 파일을 자기 태스크로 두고 verify 를 통과했다 |

`run.stale` 이 `true` 면 그 실행 뒤에 테스트 파일이 바뀌었다 — **지금 코드의 결과가 아니다.**
실행 결과가 없는 것과 같게 다룬다. 낡음은 **파일 단위**로 본다 — 같은 파일의 다른 메서드만
바뀌어도 낡음이다. 어느 메서드가 그대로인지 결과 파일만으로는 증명할 수 없어서 보수적으로 잡는다.
판단은 파일 수정 시각으로 한다(고치고 → 돌리고 → 커밋하는 보통 흐름에서 맞는 기준이다). 그래서
테스트를 돌린 폴더를 **복사해 옮기면** 모든 결과가 낡아 보인다 — 원래 폴더를 가리킨다. 도구가 그런
낌새를 `warnings` 로 알린다.

- `sources[].warnings` 가 있으면 승인 화면 맨 위에 그대로 알린다. VCS 를 읽지 못하면 수행일·
  담당자를 알 수 없다. (Codex 샌드박스처럼 다른 계정으로 도는 환경의 git 소유권 거부는 도구가
  그 저장소 하나만 명령마다 허용해 스스로 넘긴다.)
- `vcs` 가 `git` 이고 `branch` 가 main·master·develop 이 아니면 알린다 — 아직 머지되지 않은
  작업이 섞였을 수 있다. 수행으로 칠지 PM 이 판단하도록 승인 화면에 적는다.
- `gx_tdd[]` 는 gx-tdd 를 쓴 작업의 기록이다. 있으면 AC 문장(Given-When-Then)이 그 테스트가 무엇을
  확인하려 했는지 읽는 데 도움이 된다. **없어도 대조는 똑같이 돈다.**

`plan.json` 의 행에는 계획서 케이스와 행 지문, **지금 결과서의 수행 칸**(결과서가 없으면 계획서 칸의 값),
그리고 도구가 지난 수행대장과 견준 사실이 붙는다. **이 비교를 손으로 다시 하지 않는다** — 170행을 눈으로
견주면 틀린다.

| 필드 | 뜻 |
|------|----|
| `written_by` | 결과·사유·수행일·테스트담당자 칸을 누가 썼나. `tool` = 지난 반영이 쓴 값(네 칸이 수행대장과 같다), `human` = 사람이 쓴 값(미리 배정한 담당자 포함, 수행대장이 없으면 값이 있는 칸은 모두), `empty` = 네 칸이 비었다 |
| `prev` | 지난 수행대장의 그 행(상태·사유·근거·수행일·담당자·행 지문·비고). 없으면 `null` |
| `case_changed` | 지난 반영 뒤 행 지문이 바뀌었다 — 누군가 케이스를 고쳤다 |
| `inherit` | 넘겨받을 사람의 판단 — `제외` 또는 `PM 확인`. 케이스가 바뀌었으면 비어 있다 |
| `in_result` | 결과서에 이 행이 있다. 없으면 계획서에 새로 생긴 행(또는 첫 반영) |
| `result_case_edited` | 결과서에서 케이스 칸을 고친 열 — 다음 쓰기에서 계획서 원문으로 돌아간다 |

맨 위에는 `plan_hash`(승인 뒤 계획서가 바뀌었는지 가리는 값), `duplicates`(겹치는 테스트ID),
`result`(결과서 — `exists`·`hash`·`last_version`·`basis_version`(맞춘 계획서 버전)·`malformed`·`only`(계획서에서
빠진 행)·`xlsx_newer`), `ledger`(담당자 매핑 `mapping`, 반영 이력 `history`, 계획서에 없는 행 `ledger_only`,
결과서와 어긋남 `stale`, 계획서 개정이력 없이 고친 케이스 `unrecorded`)가 있다.

### 실행 결과 점검 — 전체 테스트를 돌린 폴더인가

이 스킬은 테스트를 돌리지 않는다. 빌드 도구가 테스트를 돌릴 때 **자동으로** 남기는 결과 파일만 읽는다 —
사람이 만들거나 고치는 파일이 아니고, 그 폴더에는 **마지막 실행분만** 남는다. 고친 부분만 돌렸으면 그만큼만
있고, Jest·Vitest 는 JUnit 리포터를 켜지 않으면 아예 남지 않는다. 그래서 대조 전에 `tests.json` 의
`sources[].runs` 를 레포마다 한 줄로 보여준다 (색인 명령이 같은 줄을 출력한다):

```
실행 결과 점검
  kreb-grep-2026-web [Gradle backend · Vitest frontend 리포터 꺼짐]
    테스트 10251 · 지금 결과 449 · 결과 없음 9438 · 낡음 364 (마지막 실행 2026-10-14 16:39)
```

| `runs` 필드 | 뜻 |
|------|----|
| `tests` | 사용 중인 테스트 수 (`disabled` 제외) |
| `current` | 지금 코드의 실행 결과가 있는 테스트 |
| `missing` | 실행 결과가 없는 테스트 |
| `stale` | 결과는 있지만 그 실행 뒤에 테스트 파일이 바뀐 테스트 |
| `last_report` | 그 폴더 결과 파일의 가장 최근 실행 시각. 비면 결과 파일이 없다 |

`sources[].runners` 는 그 레포에서 테스트를 돌리는 도구다 — `dir`(레포 기준 폴더, 루트면 `.`), `tool`
(`gradle`·`maven`·`vitest`·`jest`), JS 면 `junit`(JUnit 리포터가 설정에 있는가).

`missing` 이나 `stale` 이 있는 레포가 하나라도 있으면 **AskUserQuestion** 으로 묻는다:

```
결과가 없거나 낡은 테스트가 {missing + stale}건입니다 — 이대로 반영하면 그 테스트와 짝지은 행은 「미검증」으로 남습니다.
  1. 전체 테스트를 돌리고 다시 부르기 (권장)
  2. 지금 결과로 진행
```

- `전체 테스트를 돌리고 다시 부르기` — `runners` 마다 아래 표의 명령을 폴더와 함께 안내하고 **종료한다.**
  아무 파일도 바뀌지 않았다(경로 저장·`lastUsed` 제외). 명령은 안내만 한다 — 대신 실행하지 않는다.
- `지금 결과로 진행` — 그대로 대조로 넘어간다. 결과가 없는 행은 `미검증 — 실행 결과 없음`, 낡은 결과만 있는
  행은 `미검증 — 실행 후 테스트 변경` 이 된다.

모든 테스트에 지금 결과가 있으면 묻지 않고 점검 줄만 보여준다.

| `tool` | 그 `dir` 에서 돌릴 명령 | 결과 파일 |
|------|------|------|
| `gradle` | `./gradlew test` (Windows `.\gradlew.bat test`, 래퍼가 없으면 `gradle test`) | `build/test-results/` |
| `maven` | `./mvnw test` (래퍼가 없으면 `mvn test`) | `target/surefire-reports/` |
| `vitest` | `junit` 이 거짓이면 `npx vitest run --reporter=default --reporter=junit --outputFile.junit=test-results/junit.xml`, 참이면 그 레포의 테스트 명령 그대로 | `test-results/junit.xml` |
| `jest` | `junit` 이 거짓이면 `npx jest --reporters=default --reporters=jest-junit` (`jest-junit` 을 먼저 개발 의존성으로 설치), 참이면 그 레포의 테스트 명령 그대로 | `junit.xml` |

안내에 함께 적는다:

- **전체를 돌린다.** 빌드 설정이 일부 테스트를 기본 실행에서 빼면(태그·프로필 — DB 가 떠 있어야 도는 테스트
  등) 그 옵션까지 준다. 그 `dir` 의 빌드 파일에서 그런 설정을 찾으면 옵션을 명령에 붙여 적는다. 결과 수가
  테스트 수보다 크게 모자라면 대개 이 경우다.
- **납품할 코드의 브랜치에서 돌린다.** 결과서는 그 코드의 결과다.
- **다 돌렸으면 테스트 코드를 고치기 전에 바로 다시 부른다.** 실행 뒤에 고친 테스트의 결과는 낡음이 된다.
- 결과 파일을 따로 만들거나 고치거나 커밋할 일은 없다 — 테스트를 돌린 그 폴더를 경로로 주면 된다.
- `runners` 가 비었으면 「그 레포의 테스트 명령으로 전체를 한 번 돌리고, JUnit XML 결과 파일이 남는지 확인」으로
  안내한다.

### 시작 전 점검 — 다시 부를 때 생기는 일

이 커맨드는 여러 번 부른다. 그 사이 계획서·결과서·수행대장이 따로 바뀌었을 수 있어서, 대조 전에
`plan.json` 으로 상태를 가린다.

| 상황 | 할 일 |
|------|------|
| 테스트가 하나도 없다 | 대조할 것이 없다. 커맨드가 멈추고 경로를 다시 확인하게 한다 |
| 계획서 `malformed`(칸 수가 머리글과 다름)·`duplicates` | **멈춘다.** 결과서를 쓸 수 없다 — 계획서를 `/gx-단위테스트계획서`(열기)로 고친 뒤 다시 부르라고 안내한다 |
| 결과서 `result.malformed` | **멈춘다.** 결과서 md 의 그 행을 고친 뒤 다시 부르라고 안내한다 |
| 결과서는 있는데 수행대장이 없다 | 결과서 값을 누가 썼는지 가릴 근거가 없다(모두 `human` 으로 나온다). **AskUserQuestion** 으로 한 번 묻는다 — `모두 다시 판정 (권장)`: 결과서 값을 지난 반영 값으로 보고 이번 판정으로 쓴다 / `값이 있는 행은 사람 값으로 유지`: 그 행들은 `keep` |
| 수행대장은 있는데 결과서가 없다 | 결과서를 새로 만든다(1.0 신규). 반영 이력은 이어서 쌓인다 |
| `ledger.stale` | 결과서가 수행대장 기록보다 앞서 있다(손 수정, 끊긴 반영). 승인 화면 맨 위에 알리고, 다른 값은 `human` 으로 보여 덮지 않는다 |
| `result.basis_version` 이 계획서 `last_version` 보다 낮다 | 결과서가 낡았다 — 이번 반영이 계획서에 맞춘다. 승인 화면 결과서 줄에 적는다 |
| `result.only` | 계획서에서 빠진 행 — 결과서에서도 빠진다. 사람이 적어 둔 값이 있던 행은 승인 화면에 따로 보인다(반영 전 사본에 남는다) |
| 행의 `result_case_edited` | 결과서에서 케이스 칸을 고친 행 — 이번 쓰기에서 계획서 원문으로 돌아간다. 승인 화면 `[결과서에서 고친 케이스 칸]` 에 보이고, 바꾸려면 계획서를 고치라고 안내한다 |
| `result.xlsx_newer` | 결과서 xlsx 가 md 보다 나중에 바뀌었다 — xlsx 를 직접 고친 내용은 반영되지 않는다. 승인 화면에 알리고, 남길 값이 있으면 승인 화면에서 말하게 한다 |
| 승인 전에 멈췄다(대화 종료·중단) | 아무 파일도 바뀌지 않았다(경로 저장·`lastUsed` 제외). 다시 부르면 처음부터 대조한다 |

## Step 2: 대조

### 대상 행

| 행 | 대조하나 | 이유 |
|----|---------|------|
| `연계기능ID` 가 있는 행 | 예 | |
| `연계기능ID` 공란 (비기능) | **아니오** → `미검증 — 비기능 …` | 응답시간·동시접속은 단위 테스트로 판정하지 않는다. 프로파일 `policy.nonFunctionalVerification` 의 절차로 따로 검증한다 |
| 기능 행인데 `[미확정]` 이 들어간 행 | **아니오** → `미검증 — 기준값 미확정` | 판정 기준값이 없다 (`templates/evidence-rules.md`) |

비기능 행에 `[미확정]` 이 있어도 비기능으로 센다 — 한 행을 두 갈래에 두 번 세지 않는다.

### 후보 좁히기

행마다 169행 × 테스트 수백 개를 모두 견주지 않는다. **기능**으로 먼저 좁힌다.

1. 행의 `연계기능ID` → AN-03 의 기능명·화면·처리 설명
2. 그 기능의 코드 위치 — `source-index.json` 의 컨트롤러·서비스, 레포 `context/` 가 있으면 그 `PROJECTS.md`·
   `glossary.md` 에서 업무 용어에 맞는 패키지·클래스 이름
3. 그 클래스를 시험하는 테스트 — 이름이 이어지는 테스트 클래스(`SourceUploadService` →
   `SourceUploadServiceTest`), 같은 패키지의 테스트, `literals` 에 행의 화면 문구·한계값이 있는 테스트

기능의 코드 위치를 못 찾은 행은 대조하지 않는다 — 억지로 짝지으면 비슷한 이름끼리 엉뚱하게
붙는다. 결과는 `미구현`, 사유는 `대응 테스트 없음 — 기능 코드 미확인` 이다.
승인 화면에서는 기능별로 묶어 센다 — 그 기능의 레포 경로가 빠졌을 수 있어서 PM 이 알아야 한다.

**후보 테스트는 본문을 읽고 판단한다.** 이름·설명만 보고 짝짓지 않는다 — `rejectsLargeFile` 이
1,001MB 를 넣는지 10GB 를 넣는지, 저장이 안 됐는지까지 확인하는지는 본문에만 있다.
`file`·`line` 으로 그 메서드를 연다.

### 짝 기준

**시험하는 것이 같아야 한다.** 사전조건 ≈ 테스트의 준비(given/arrange), 입력 ≈ 실행(when/act),
기대결과·사후조건 ≈ 단언(then/assert). 값이 글자 그대로 같을 필요는 없지만 **판정 대상**(어느
분기·어느 경계·어느 예외)은 같아야 한다.

| 계획서 행 | 테스트 | 짝인가 |
|----------|--------|------|
| 1,001MB 파일 → "파일 용량 초과" 안내, 저장 없음 | 1,001MB 업로드 → 예외 메시지 단언 + 저장 호출 없음 단언 | **예** |
| 1,001MB 파일 → "파일 용량 초과" 안내, 저장 없음 | 1,001MB 업로드 → 예외만 단언 | **예, 일부** — 저장 없음을 확인하지 않는다 (`미검증 — 일부만 검증`) |
| 1,000MB 파일 → 정상 등록 | 1,001MB 업로드 → 거부 | **아니오** — 같은 경계의 다른 쪽이다 |
| 목록 조회 → 등록일 역순 5건 | 목록 조회 → 100건 단위 페이지 | **아니오** — 정렬과 페이징은 다른 판정이다 |

짝은 N:M 이다. 행 하나를 테스트 여럿이 나눠 덮을 수 있고(서비스 테스트가 예외를, 저장소
테스트가 저장을), 테스트 하나가 행 여럿을 덮을 수도 있다(경계 양쪽을 매개변수로 돌리는 테스트).
행 하나를 덮는 테스트들을 **덮는 테스트**라 부른다.

### 상태와 사유

결과서의 행마다 결과 칸에 **네 상태 중 하나**를, 옆 `사유` 칸에 그 이유 한 줄을 적는다. 정의의 정본은
`templates/IM-03-unit-test-result.md` §결과 상태다.

| 상태 | 조건 | 사유 (첫머리 고정어 — 뒤에 ` — ` 로 구체 내용) |
|------|------|------|
| `Pass` | 덮는 테스트가 기대결과와 사후조건을 모두 단언하고, **모두** 실행 결과 `passed` 이며 낡지 않았다. 또는 PM 이 확인했다 | `테스트 통과 — FileSizeLimitTest.rejectsOverLimit (2026.10.10)`, `PM 확인 — 2026.10.11` |
| `Fail` | 덮는 테스트 중 하나라도 실행 결과가 `failed` 이고 낡지 않았다 | `테스트 실패 — SourceUploadServiceTest.continuesWhenOneFileFails: expected 3 saved but was 0` |
| `미구현` | 덮는 테스트가 없다 | `대응 테스트 없음`, `대응 테스트 없음 — 기능 코드 미확인`, `대응 테스트 비활성 — SourceUploadServiceTest.rejectsMissingFile (@Disabled)` |
| `미검증` | 위 셋이 아니다 — 테스트는 있는데 이 케이스가 확인되지 않았거나, 단위 시험 대상이 아니다 | 아래 표 |

`미검증` 의 사유 첫머리:

| 사유 첫머리 | 언제 |
|------------|------|
| `실행 결과 없음` | 다 덮는 테스트는 있는데 실행 결과가 없다(`none`·`skipped`). PM 이 확인하면 Pass 가 된다 |
| `실행 후 테스트 변경` | 실행 결과가 낡았다(`stale`) — 그 뒤에 테스트를 고쳤다 |
| `일부만 검증` | 짝은 있는데 일부만 덮는다 — `일부만 검증 — 저장 없음 미확인` |
| `기준 불일치` | 같은 대상을 다른 기준값으로 시험한다 — `기준 불일치 — 계획 1,000MB ↔ 테스트 500MB`. 개발이 정책을 바꾼 것일 수 있어 확인요청서 후보다 |
| `케이스 변경` | `case_changed` 이고 이번 근거로 Pass 가 나오지 않았다 — PM 이 케이스를 고쳤다. 뒤에 바뀐 칸과 이번 대조에서 걸린 것을 적는다 — `케이스 변경 — 기대결과 수정, 테스트는 "회차 없음" 확인`. 계획서를 고친 쪽이 PM 이라 확인요청서 후보가 아니다 — 개발 쪽에 테스트를 바뀐 케이스에 맞추라고 알린다 |
| `제외` | PM 이 사유와 함께 뺐다 — `제외 — 통합 환경 필요`. `inherit` 가 `제외` 면 지난 사유를 그대로 승계한다 |
| `비기능` | `연계기능ID` 가 공란인 행. 뒤의 문구는 프로파일 `policy.nonFunctionalVerification` 으로 정한다 — 아래 표 |
| `기준값 미확정` | 기능 행인데 `[미확정]` 이 들어 있다 (`templates/evidence-rules.md`). 비기능 행이면 `비기능` 이 먼저다 |

| `nonFunctionalVerification` | 사유 |
|------------------------------|------|
| `measurement-procedure` | `비기능 — 측정 절차로 검증` |
| `design-review` | `비기능 — 설계 검토로 검증` |
| `tool` | `비기능 — 도구 측정으로 검증` |
| 없음 | `비기능 — 단위 시험 대상 아님` |

**사유는 고객 문서에 나가는 문장이다.** 레포 경로 대신 테스트 이름으로 쓰고 한 줄로 끝낸다 — JUnit·Kotlin 은
`클래스.메서드`, Jest·Vitest 는 `파일 이름 "테스트 이름"`(`cycle-list.test.ts "등록일 역순으로 5건을 보여준다"`).
덮는 테스트가 여럿이면 대표 하나에 ` 외 N건` 을 붙인다. 전체 경로와 실행 근거는 수행대장 `근거` 열에 둔다.

**판정이 지난번과 같으면 지난 문장을 그대로 쓴다.** 상태·근거(같은 테스트의 같은 실행 — 날짜까지)·수행일·
담당자가 `prev` 와 같으면 사유도
`prev.사유` 를 옮긴다 — 같은 판정을 다른 말로 쓰면 아무것도 안 바뀐 재반영에서도 결과서가 바뀌어 개정이력이
의미 없이 쌓인다. 지난 사유가 지금 표기 규칙과 다를 때만 고쳐 쓰고, 승인 화면에 `[사유 표기 갱신]` 으로 센다.

한 행에 여러 조건이 맞으면 `비기능`·`기준값 미확정` → `케이스 변경` → `제외` → `기준 불일치` →
`Fail` → `일부만 검증` → `Pass`·`실행 결과 없음`·`실행 후 테스트 변경` → `미구현` 순으로 앞의 것을 쓴다.

**일부만 검증한 행은 Pass 가 아니다.** 일부만 시험했는데 Pass 를 찍으면 전체를 한 것처럼 보인다 —
증적으로는 없느니만 못하다. **기준이 다른 행도 Pass 가 아니다** — 다른 값으로 시험했으니 이 행의
약속을 지켰다는 증적이 아니다.

**예외 케이스의 `변화 없음`·`저장 없음` 도 사후조건이다.** 테스트가 「예외가 난다」만 단언하고
데이터가 안 바뀌었다는 것(저장 호출 없음, 건수 그대로)을 단언하지 않으면 `일부만 검증` 이다. 이
사후조건은 「안내만 띄우고 저장은 되는」 결함을 잡으려고 둔 것이라(`templates/DE-13-unit-test-plan.md`
§작성 규칙), 예외 단언만으로는 그 결함을 못 잡는다. 조회처럼 원래 데이터를 바꾸지 않는 동작의
`변화 없음` 은 따로 단언하지 않아도 된다.

판정을 가르는 경우 몇 가지를 정해 둔다.

| 경우 | 상태 |
|------|------|
| 계획서의 화면 문구(따옴표 원문)와 테스트가 단언하는 문구가 다르다 | `미검증 — 기준 불일치`. 공백·문장부호만 다르면 같은 문구다 |
| 검증기·파서 같은 부품 테스트가 행의 기대결과(검증 문구)를 정한다 | 덮는 테스트가 될 수 있다. 사후조건(실패 기록, 다른 파일은 계속 진행 등)을 단언하지 않으면 `미검증 — 일부만 검증` |
| 테스트가 결과의 일부 성질만 단언한다 (실패 사유가 "있다"만, 기록 저장은 확인 안 함) | `미검증 — 일부만 검증` |
| 테스트가 문구의 일부만 단언한다 (`hasMessageContaining("용량")` ↔ 계획 "파일 용량 초과") | `미검증 — 일부만 검증`. 다른 문구를 단언하면 `기준 불일치` 다 |
| 행이 대상을 나열하지 않는다 (`연계 데이터 삭제`, `변화 없음`) | 대조 기준은 DE-13 행의 글자다 — AN-03 처리 설명까지 넓히지 않는다. 테스트가 그 말에 해당하는 데이터를 하나라도 단언하면 덮는다 |

**수행일과 담당자.** `Pass`·`Fail` 의 수행일은 덮는 테스트의 실행 날짜(`run.date`) 중 가장 늦은 것이고
(PM 확인이면 PM 이 말한 날짜), 담당자는 덮는 테스트 파일 중 가장 최근에 바뀐 파일의
`last_change.author` 다 (Step 4 에서 실명으로). `미구현`·`미검증` 행은 두 칸을 비운다.

날짜가 이상하면 승인 화면 `[날짜 확인]` 에 띄운다. 기본값은 정해 두고 PM 이 고치게 한다.

| 경우 | 기본값 |
|------|-------|
| 실행 날짜·커밋 날짜·PM 이 말한 날짜가 오늘보다 늦다 | 그 날짜를 그대로 쓴다 — 개발 PC 나 이 PC 의 시계가 어긋났을 수 있다고 알린다 |
| 실행 날짜가 비었다 | Pass·Fail 로 쓰지 않는다 — 수행일 없는 결과는 증적이 아니다. `미검증 — 실행 결과 없음` 으로 두고, PM 이 날짜를 주면 그때 쓴다 |

행 지문은 `plan.json` 의 `fingerprint` 이고, 지난 값은 `prev` 의 `행 지문` 이다.

### 계획서 반영 후보 — 신규 케이스

**계획서에 넣지 않는다.** 계획서는 `/gx-단위테스트계획서` 만 고친다. 이 스킬은 후보를 승인 화면과 출력에
보여 주고 건수를 수행대장에 남긴다 — 넣을지는 PM 이 계획서 커맨드(`열기`)로 정하고, 넣은 뒤 다시 반영하면
결과서에 그 행이 생긴다.

어느 행과도 짝이 안 된 테스트 중 **셋 다 맞는 것만** 후보로 올린다.

1. 기능이 정해졌다
2. 기능 경계에서 시험한다 — 컨트롤러·서비스·API·화면 단위 테스트. 검증기·매퍼·유틸 같은 부품
   테스트는 계획서 수준이 아니다
3. 바깥에서 관측되는 결과를 단언한다 — 응답·화면 문구·저장된 데이터

리팩터링·성능·로그·내부 캐시를 확인하는 테스트는 후보로 올리지 않고 출력의 `대응 없는 테스트` 로만
센다. 같은 동작을 여러 테스트가 확인하면 한 행으로 묶는다.

후보 행은 PM 이 계획서에 그대로 옮길 수 있게 쓴다 — 같은 기능 기존 행의 문체, `templates/DE-13-unit-test-plan.md`
의 작성 규칙, **design-test-cases** 의 입력 규칙(항목명과 값을 짝지어, 화면 문구는 따옴표 원문, 예외의
사후조건은 `변화 없음`)을 따른다. **값은 테스트에서 옮긴다.** 테스트에 없는 값을 지어내지 않는다 — 없으면
항목명만 적는다. 사전조건이 도우미 함수 뒤에 숨어 값이 없으면 같은 기능 행의 사전조건을 빌리고 그렇게 적는다.
입력이 파일이면 만들 파일을 적기만 한다(`testdata/` 파일은 계획서 커맨드가 만든다).

### 계획서 반영 후보 — 기대결과 보강

짝지은 행의 기대결과가 판정 기준으로 모호하고(「정상 처리」, 문구 원문 없는 「안내」) 테스트의 단언이
관측 가능한 기준을 주면, 그 기준으로 다시 쓴 문장을 후보로 올린다. 이것도 계획서에 넣지 않는다.

**뜻이 바뀌면 보강이 아니다.** 계획서는 「1,000MB 초과 차단」인데 테스트는 「500MB 초과
차단」이면 개발이 정책을 바꾼 것이다. `미검증 — 기준 불일치` 로 적는다 — 이건 PM 이
발주처에 확인할 일이고, 확인요청서로 가는 것이 맞다.

`templates/approval-protocol.md` 의 승인 루프를 따른다. 화면은 이렇게 보인다.

```
  소스: reb-api (git · main · a1b2c3d) — 테스트 412건, 실행 결과 파일 38개 (2026.10.10 실행)

  전체 169건 — Pass 30 · Fail 1 · 미구현 95 · 미검증 43

  | 테스트ID | 상태 | 사유 | 근거 (수행대장에 남는다) |
  | REB-UT-002 | Pass | 테스트 통과 — FileSizeLimitTest.rejectsOverLimit (2026.10.10) | reb-api:src/test/java/kr/reb/source/FileSizeLimitTest.java#rejectsOverLimit |

  [계획서에서 빠진 행 0건]  [결과서에서 고친 케이스 칸 0건]  [표 깨짐 0건]

수정 예시:
• "REB-UT-011 은 통과 확인함 (2026.10.11)"
• "REB-UT-047 제외: 통합 환경 필요"
• "REB-UT-006 은 고치는 중이니 미검증으로"
• "REB-UT-001 사유는 '4건 저장 확인 필요' 로"
```

- **`미검증` 을 Pass 로 바꾸는 것은 PM 의 확인으로만 한다.** "통과 확인함" 이면 Pass 로 쓰고 사유는
  `PM 확인 — {날짜}`, 수행일은 PM 이 말한 날짜(없으면 오늘), 담당자는 위 규칙대로 테스트 작성자다.
  수행대장 근거에도 `PM 확인` 과 날짜를 남긴다 — 실행 결과 파일이 아니라 사람의 확인이 근거라는 것을
  감리에서 구분할 수 있어야 한다.
- 요청에 이미 확인이 들어 있으면("REB-UT-011 은 2026.10.11 에 직접 돌려 통과 확인했어") 승인 화면에서
  그 문장을 인용해 Pass 로 보여준다. 확인한 행이 `실행 결과 없음` 이 아니어도(일부만 검증 등) PM 판정으로
  Pass 를 쓰고, 수행대장 비고에 원래 상태를 남긴다 — PM 이 단위 테스트 밖에서 확인했을 수 있다.
- **PM 확인은 다음 반영에 승계한다.** `inherit` 가 `PM 확인` 인 행은 이번에도 그 확인을 근거로 둔다
  — 실행 결과 파일이 계속 없다고 사람의 확인을 거두면 PM 이 반영할 때마다 같은 말을 해야 한다. 행 지문이
  바뀌었으면 도구가 `inherit` 를 비운다 — `케이스 변경` 이다(확인한 것은 그때의 케이스다). 확인 날짜 뒤에
  생긴 실행 결과가 있으면 그것으로 판정한다 — 낡지 않은 `failed` 면 `Fail`, 모두 `passed` 면 `테스트 통과`.
- **Fail 은 그대로 적는다.** 최근 실행에서 실패한 것이 사실이고, 사유에 실패 메시지가 남는다. 고치는
  중이라 지금 적고 싶지 않으면 PM 이 `미검증` 으로 바꾸고 사유를 주게 한다.
- **제외에는 사유가 있어야 한다.** 사유 없는 제외는 받지 않고 다시 묻는다.
- PM 이 상태나 사유를 직접 바꾸면 그대로 따르고 수행대장 비고에 `PM 판정` 을 남긴다.
- **결과서의 결과·사유·수행일·테스트담당자 칸에 이미 값이 있으면 누가 쓴 값인지 먼저 가린다** —
  `written_by` 다. 네 칸이 지난 수행대장과 같으면(`tool`) 이 스킬이 쓴 값이고, 그 밖에는(`human`) 사람이
  쓴 값이다. 결과서가 아직 없으면 계획서 칸에 손으로 적어 둔 값(결과, 배정 담당자)이 그 자리에 온다.
- 사람이 쓴 값(손으로 적은 `Fail`, 배정 담당자 등)과 이번 결과가 다르면 **덮지 않는다.**
  `[기존 기입값과 다름]` 으로 따로 보여주고 PM 이 고르게 한다. PM 이 고르지 않고 「승인」만 하면 사람
  값을 유지한다(`keep`). **이 규칙은 사람 값에만 적용한다.**
- **예외 — 케이스가 바뀐 행의 사람 값.** `human` 인데 `case_changed` 면 그 값은 옛 케이스에 대한 것이다
  (계획서를 새로 써서 같은 ID 가 다른 케이스가 된 경우도 여기다). 기본은 이번 판정으로 쓰고(`keep` 아님)
  옛 값은 수행대장 비고에 `이전 케이스의 기존 기입(Fail, 홍길동, 2026.10.12)` 으로 남긴다. 승인 화면
  `[기존 기입값과 다름]` 에 「케이스가 바뀜」을 붙여 PM 이 유지를 고를 수 있게 한다.
- **이 스킬이 쓴 값은 이번 결과로 새로 쓴다.** 그중 Pass 였던 행이 이번에 Pass 가 아니면(테스트를
  고쳤거나 지웠거나 결과가 낡은 경우) `[Pass 철회]` 로 사유와 함께 보여준다 — 결과는 이번 상태(대개
  `미검증 — 실행 후 테스트 변경`·`케이스 변경`)로 바꾸고 수행일·담당자는 비운다. 낡은 Pass 를 남기면
  고객 문서가 근거 없는 약속을 지킨 것으로 보인다. PM 이 유지를 고르면 둔다(`keep`). 낡아서 철회한 행은
  「그 테스트 파일을 다시 돌리면 돌아온다」고 함께 알린다 — 같은 파일의 다른 메서드만 바뀌어도 철회되기 때문이다.
- 유지한 행도 수행대장의 상태·사유·수행일·담당자는 이번 대조 결과로 남는다(도구가 비고에
  `기존 기입 유지(…)` 를 붙인다). 그래야 다음 반영 때도 결과서 값이 수행대장과 달라 사람 값으로 가려진다.

**건수는 반영 뒤 결과서의 `결과` 칸으로 센다.** 사람 값을 유지한 행은 그 값으로 센다 — 승인 화면은 PM 이
고르기 전이라 기본값(사람 값 유지)으로 센다 — 고객이 보는 문서와
숫자가 맞아야 한다. 승인 화면·출력·개정이력·수행대장 반영 이력이 모두 이 숫자이고, 네 상태의 합은 계획서
행 수다(결과서는 계획서 행만 담는다). 유지 행 때문에 수행대장 「수행 현황」의 상태(대조 결과)를 센 숫자와는
다를 수 있다. 사람이 쓴 사유는 첫머리 고정어가 아닐 수 있다(`수동 시험 실패 — …`) — 수행률 분모에서 빼지 않는다.

## Step 4: 담당자 실명

담당자는 덮는 테스트 파일의 마지막 커밋 작성자다 (`last_change.author`). VCS 아이디라 실명으로
바꿔 적는다.

이번에 결과서에 담당자를 쓰는 행(Pass·Fail)의 작성자 중, 수행대장 「담당자 매핑」
(`plan.json` 의 `ledger.mapping`)에 없는 아이디만 **AskUserQuestion** 으로 묻는다. 쓰지 않을 행의 작성자는 묻지 않는다. 여러 명이면
한 번에 묶어 묻는다(개수 한도는 `templates/approval-protocol.md` 인자 규칙). 실명은 자유 입력이라
선택지는 `아이디 그대로 쓰기` / `실명 입력` 두 개로 두고 실명은 기타 입력으로 받는다. 답은 매핑
표에 저장해 다음에는 묻지 않는다.

## Step 5: 반영

**계획서는 건드리지 않는다.** 결과서와 수행대장을 `write` 한 번으로 함께 쓴다 — 둘 사이에서 멈추면
다음 반영 때 이 스킬이 쓴 값을 사람 값으로 잘못 가린다. 그래서 **개정이력 승인을 쓰기 전에** 받는다.

1. `changes.json` 을 임시 폴더에 만든다.
   ```json
   {"plan_hash": "{plan.json 의 plan_hash}", "result_hash": "{plan.json 의 result.hash — 결과서가 없으면 빈 문자열}",
    "date": "2026.10.14", "project": "",
    "sources": "reb-api D:\\projects\\reb-api (main · a1b2c3d), reb-web D:\\projects\\reb-web (main · 9f8e7d6)",
    "note": "", "mapping": {"kim.dev": "김개발"}, "basis": "reb-api main · a1b2c3d, reb-web main · 9f8e7d6",
    "candidates": {"new": 1, "boost": 0}, "revision": null,
    "rows": {"REB-UT-001": {"상태": "미검증", "사유": "일부만 검증 — TB_SRC_FILE 4건 저장 미확인", "수행일": "", "담당자": "",
                            "근거": "reb-api:…/SourceUploadServiceTest.java#registersFourFiles (결과 파일 2026.10.10)",
                            "비고": "", "keep": false}}}
   ```
   - `rows` 에는 **계획서의 모든 행**을 넣는다. 상태·사유·수행일·담당자는 이번 판정, 근거·비고는 수행대장용이다.
   - 사람 값을 지키는 행은 `"keep": true`. 도구가 결과서에 그 값을 그대로 두고(사유가 비었으면
     `기존 기입 — 사유 미기재`), 결과 없이 배정 담당자만 있던 행은 결과·사유만 판정으로 채운다. 수행대장
     비고의 `기존 기입 유지(…)` 도 도구가 붙인다. 지킬 결과가 네 상태가 아니면(`통과`·`N/A` 등) 도구가
     거부한다 — PM 에게 네 상태 중 무엇인지 물어 그 값으로 쓴다.
   - 해시는 대조 때 뽑은 값이다. 승인을 받는 동안 누가 계획서나 결과서를 고쳤으면 도구가 거부한다 —
     Step 1 부터 다시 대조한다. 승인한 것은 그때의 내용이다.
   - 소프트 선행이 없어 「그대로 진행」 했으면 `note` 에 `축약 생성(AN-03 없음)` 처럼 적는다.
   - `project` 는 비워 둔다 — 수행대장이 처음이면 도구가 계획서 제목의 사업명을 써서 결과서 제목과 맞춘다.
   - JSON 에 Windows 경로를 적을 때 역슬래시는 `\\` 로 적는다. 이스케이프로 풀린 제어 문자가 섞이면 도구가 거부한다.
2. 쓰지 않고 바뀔 내용을 본다 — 개정이력을 정하기 전이라 `"revision": null` 로 돌린다.
   ```
   python {플러그인 루트}/utils/test-evidence.py write --de13 "{계획서}" --result "{결과서}" --ledger "{수행대장}" --changes "{임시}/changes.json" --dry-run
   ```
   결과서는 `{프로젝트 폴더}/{시스템코드}-단위테스트결과서.md`, 수행대장은 `{프로젝트 폴더}/증적/{시스템코드}-단위테스트수행대장.md` 다.
   바뀐 행·추가·계획서에서 빠진 행의 ID, 건수·수행률, 개정이력이 필요한지(`needs_revision`)와 다음 버전
   (`next_version`)이 나온다. 결과서가 처음이면 모든 행이 추가다. **`inherit_dropped` 가 있으면** 이어받을 판단
   (제외·PM 확인)을 이번 판정이 버린 행이다 — 확인 날짜 뒤의 실행 결과나 PM 판정 때문이면 그대로 두고 승인
   화면에 그렇게 적었는지 확인한다. 아니면 판정 실수이니 `changes.json` 을 고친다.
3. 결과서 개정이력 행을 정한다 — **manage-revision-history** 스킬로 초안을 만들고 승인을 받는다.
   계획서 개정이력에는 아무것도 붙지 않는다.
   - 결과서가 처음이면 `1.0 / 신규 / 최초 작성 — 수행 결과 기입(Pass 4·Fail 1·미구현 131·미검증 33)`.
   - 그 뒤로는 dry-run 의 `next_version`(결과서 마지막 버전 + 1.0)이다. 그 스킬 Step 1 의
     「직전 버전 파일」 찾기는 적용하지 않는다. 사유는 무게 순서(`삭제` > `변경` > `추가` > `보완`)로 —
     계획서에서 행이 빠졌으면 `삭제`, 케이스가 바뀐 행이 있으면 `변경`, 행이 늘었으면 `추가`, 결과나 근거
     버전만 바뀌었으면 `보완`. 내용에는 바뀐 행을 ID 로 적는다 — `수행 결과 재반영(Pass 3·Fail 1·미구현 131·
     미검증 35), Pass 철회 3건(REB-UT-002·003·012), Fail→Pass 1건(REB-UT-006)`. 건수는 dry-run 의 숫자다.
   - **dry-run 의 `needs_revision` 이 거짓이면(바뀐 행·추가·빠짐 0, 근거 버전 그대로) 개정이력 행을 만들지 않는다.**
     결과서는 그대로 두고 수행대장에 반영 이력 한 행만 남는다 — 그날 대조했다는 기록이다.
   - 승인된 행을 `changes.json` 의 `revision` 에 넣는다 —
     `{"버전": "2.0", "개정일": "2026.10.15", "개정 사유": "보완", "개정 내용": "…", "작성자": "구본승"}`.
   - PM 이 지난 반영 뒤 계획서를 손으로 고친 것(`case_changed`)은 계획서 쪽 일이다 — 결과서 개정이력에는
     「케이스 변경 반영」만 적고, 계획서 개정이력은 출력에서 따로 알린다.
4. 쓴다 — 같은 명령에서 `--dry-run` 을 뺀다. 도구가 결과서를 계획서 행에 맞춰 다시 쓰고(케이스 칸은
   계획서 원문, 수행 칸은 판정), 머리말 `> 근거:` 를 지금 계획서 버전으로 올리고, 개정이력 행을 붙이고,
   수행대장을 함께 쓴다. 결과서가 이미 있으면 쓰기 직전 원본을 `backup/{파일 이름}_{YYMMDD}.md` 로 남긴다
   (같은 날이면 그날 처음 원본). 검증에 하나라도 걸리면 아무 파일도 건드리지 않는다 — 메시지대로 고친다
   (해시 불일치면 다시 대조, 개정이력 오류면 3번을 다시).
5. xlsx 추출은 커맨드 Step 4 를 따른다 — 결과서만 뽑는다. 계획서는 바뀌지 않았고 수행대장은 내부 증적이다.

**소스 레포에는 아무것도 쓰지 않는다.** 읽기만 한다. 테스트도 돌리지 않는다.

라고 적는다.

수행률은 정수 %로 반올림한다. 「미구현이 많은 기능」은 기능 코드를 찾은 기능 중 미구현 건수 순으로 5개까지
보이고, 기능 코드를 못 찾은 기능은 한 줄로 센다 — 기능마다 다 미구현이면 순위가 뜻이 없다.

**지난 반영 뒤 계획서 행 지문이 바뀌었는데 계획서 개정이력에 그 수정이 없으면**(`plan.json` 의
`ledger.unrecorded` — 도구가 지난 반영 뒤의 계획서 개정 내용에서 그 ID 를 찾아 본다) 출력에 따로 알린다 — PM 이
손으로 고친 것이라 계획서 개정이력을 남길지는 PM 이 정한다. 이 스킬은 계획서를 고치지 않는다.

**계획서 반영 후보는 출력에만 남는다.** 건수는 수행대장 반영 이력의 `신규 후보`·`보강 후보` 에 남지만 내용은
남지 않는다 — PM 이 지금 계획서에 넣지 않으면 다음 반영 때 같은 후보가 다시 나온다.

**수행률 = Pass ÷ (전체 − 비기능 − 기준값 미확정 − 제외).** 단위 시험으로 판정하지 않는 행만 분모에서
뺀다. `미구현`·`미검증`(실행 결과 없음 포함)을 빼면 숫자가 좋아 보이지만 약속한 시험을 다 했는지라는
질문에 답하지 못한다.

## 주의사항

- **계획서를 고치지 않는다.** 결과는 결과서에, 근거는 수행대장에 쓴다. 신규·보강은 후보로만 알린다
- **테스트를 실행하지 않는다.** 이미 남은 실행 결과(빌드 결과 파일, gx-tdd verify 기록)만 읽는다
- **실행 결과 없이 Pass 를 쓰지 않는다.** PM 이 확인한 행만 예외이고, 그 사실을 사유와 수행대장에 남긴다
- 모든 행에 네 상태 중 하나와 사유를 적는다. 사람이 적은 값은 지우지 않는다(케이스가 바뀐 행만 예외)
- 결과서의 케이스 칸은 계획서 원문이다 — 결과서에서 고친 케이스 칸은 다음 쓰기에서 되돌아간다
- 결과서 md 가 원본이다 — xlsx 를 직접 고친 내용은 반영되지 않는다
- 비기능 행은 판정하지 않고 `미검증 — 비기능 …` 만 적는다
- 소스 레포에 쓰지 않는다. 레포 상태를 볼 때도 `git --no-optional-locks status` 처럼 인덱스를 건드리지 않는 명령을 쓴다
