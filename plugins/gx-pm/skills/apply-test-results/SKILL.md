# 계획서 기반 로컬 시험 수행과 결과 반영

`/gx-단위테스트결과반영`이 부른다. 계획서의 사전조건과 입력을 실제 애플리케이션에 적용하고 기대결과·사후조건을 관측한다. 테스트 코드 검색, JUnit XML, gx-tdd verify 기록으로 현재 시험을 대체하지 않는다. 기존 테스트 코드가 없어도 수행할 수 있다.

공공 산출물 명칭은 단위테스트계획서·결과서를 유지하지만, 실행 방식은 실제 시스템의 기능을 확인하는 API·브라우저 시험이다. 응답 하나로 내부 로직 전체가 검증됐다고 주장하지 않는다.

에이전트는 프로젝트 기동·요청·관측을 맡고, `utils/test-evidence.py`는 계획서 읽기와 실행 증적 검증·문서 기록을 맡는다. Python 도구가 서버나 브라우저를 대신 실행하지는 않는다. 양식은 `templates/IM-03-unit-test-result.md`와 `templates/DE-13-execution-ledger.md`가 정본이다.

## 입력과 기록 위치

| 항목 | 용도 |
|------|------|
| 프로젝트 프로파일·DE-13 계획서 md | 시험 대상과 원래 약속. 계획서는 읽기만 한다 |
| 실행할 프로젝트 경로 하나 이상 | 백엔드·프론트·배치 등 실제 실행에 필요한 소스 |
| AN-03·AN-02·프로젝트 API 명세 | 기능·화면·요청 경로를 찾는 보조 자료 |
| 기존 결과서·수행대장 | 사람의 수정값, 개정이력, 이전 관측과의 차이 |
| 로컬 설정·시험 계정·시험 데이터 | 프로젝트에서 먼저 찾고 필요한 누락만 묻는다 |

실행마다 고유한 `run_id`를 정하고 산출물 폴더의 `증적/{시스템코드}/{run_id}/`에 기동 로그, 행별 요청·응답, 화면·데이터 확인 파일, `execution.json`을 보존한다. 토큰·쿠키·비밀번호는 저장 전에 가리고, 가린 파일의 SHA-256을 계산한다. **승인 전에도 실행 증적은 저장한다.** 이미 수행한 사실을 잃지 않는다. `plan.json`·`changes.json`은 OS 임시 폴더에 둔다.

## Step 1: 계획서와 환경 점검

설치된 플러그인 루트 기준 도구를 사용한다. 결과서·수행대장이 없으면 생성할 경로를 준다.

```text
python {플러그인 루트}/utils/test-evidence.py plan --de13 "{계획서}" --result "{결과서}" --ledger "{수행대장}" --out "{임시}/plan.json"
```

1. 계획서 표 깨짐·중복 ID·빈 본문은 실행 전에 중단하고 해당 행을 알린다.
2. `의존성`의 선행 테스트ID를 따라 순서를 정한다. 순환이나 없는 ID가 걸린 행은 해결 전까지 실행하지 않는다. 무관한 행은 계속 수행할 수 있다.
3. 프로젝트 지침·README·실행 스크립트·라우트·로컬 설정을 읽어 작업 디렉터리, 시작 명령, 포트, 준비 완료 확인 방법, DB·스토리지·로그인을 확인한다. 예제 명령을 추측해서 실행하지 않는다. 소스는 경로와 관측 방법을 찾는 자료이며 시험 결과는 아니다.
4. 요청에서 지정한 경로를 우선한다. 없으면 프로파일 `assets.testSourcePaths`, `assets.sourcePath`, 실제 애플리케이션인 현재 작업 폴더 순으로 찾는다. 모노레포는 서비스별 실행 디렉터리를 구분한다. 사용자가 제공한 경로는 프로파일에 저장한다.
5. 원본 코드를 고치거나 pull하지 않는다. 기동에 필요한 기존 빌드 명령과 로컬 시험 데이터 생성·정리는 수행 범위다. 설정·계정이 없으면 필요한 값만 요청하고 기다린다.

## Step 2: 로컬 프로젝트 기동

대상 경로·시작 명령·접속 URL·데이터 환경을 짧게 보여준다. 이미 허용된 로컬 실행은 반복 승인 없이 진행한다. 이 커맨드의 승인 루프는 **결과 문서 확정 전**에 둔다.

- 기존 로컬 인스턴스가 올바른 프로젝트인지 확인되면 재사용한다. 소스와 실행 버전이 같은지 알 수 없으면 확인하거나 자신이 기동한 인스턴스를 쓴다.
- 새 프로세스는 하네스가 관리하는 실행 세션이나 백그라운드로 실행하고 세션/PID·로그·종료 방법을 기록한다. Windows에서 별도 백그라운드 프로세스를 띄울 때는 숨김 창을 사용한다. 포트 충돌 때 기존 프로세스를 임의 종료하지 않는다.
- 준비 완료는 포트뿐 아니라 프로젝트의 health 요청이나 실제 진입 화면으로 확인한다. 준비 대기에 제한 시간을 두고 실패하면 로그를 보존한다.
- 포트 설정 누락처럼 URL을 확정하기도 전에 막히면 전 행을 미검증으로 기록하고 대상 URL은 비워 둔다. 주소를 추측해 증적에 넣지 않는다.
- 대상 URL은 localhost·127.0.0.0/8·::1의 HTTP(S)다. 연결된 DB·외부 연동도 시험 환경인지 확인한다. 운영 데이터·실제 결제·실제 알림에 연결되는 행은 필요한 시험 설정을 요청한다. 로컬 URL이라고 연결된 데이터도 로컬이라고 추정하지 않는다.
- 브라우저 시험은 현재 하네스의 브라우저 도구 또는 프로젝트에 마련된 실행 환경을 사용한다. 없으면 해당 행은 `미검증 — 브라우저 도구 없음`이다. 화면 조건을 API 응답으로 대신 통과시키지 않는다.

## Step 3: 각 행 수행

`사전조건 → 입력 → 기대결과 → 사후조건`을 한 케이스로 수행한다. 값은 계획서대로 사용하고 `〃`는 `plan.json`이 풀어 준 값을 쓴다. 메서드·URL·요청 필드·화면 선택자는 프로젝트에서 확인한다. 실행 경로 미확인은 `미검증`이며 미구현으로 단정하지 않는다.

1. **준비:** 계정·권한·데이터를 맞춘다. 이번 실행을 식별할 수 있는 데이터를 사용한다. 계획서의 `testdata/` 파일은 실제로 전송한다. 재수행할 때 중복 데이터가 판정을 바꾸지 않도록 정리·재설정한다. 기존 데이터와 이번 생성 데이터를 구분한다.
2. **입력:** API 행은 실제 요청을 보내고, 화면의 문구·버튼·권한·흐름을 약속한 행은 실제 브라우저로 조작한다. HTTP 상태뿐 아니라 본문·헤더 등 약속한 관측값을 보존한다.
3. **확인:** 기대결과와 사후조건을 각각 확인한다. 저장·삭제·변화 없음은 후속 조회 API 또는 시험 DB의 읽기 조회로 전후 값을 확인한다. 안내만으로 DB 미저장을 추정하지 않는다. 단순 조회의 `변화 없음`은 별도 부작용 확인이 필요 없는 이유를 명시할 수 있다.
4. **기록:** 사용한 사전조건·입력, 실제 응답/화면/데이터, 일치 여부를 즉시 기록한다. 증적과 변경안의 계약은 `references/execution-evidence.md`를 읽는다. 실행하지 않은 응답을 만들지 않는다.
5. **다음 행:** 선행 실패로 필요한 데이터가 없으면 `미검증 — 선행조건 미충족`이다. 독립된 사전조건을 마련할 수 있으면 그렇게 수행하고 기록한다.

재시도는 일시적인 환경 문제에 한해 제한적으로 한다. 변경 요청이 시간 초과되면 먼저 실제 반영 여부를 조회한다. 성공할 때까지 같은 저장·삭제 요청을 반복하지 않는다. 앱의 결함을 고쳐 시험을 통과시키는 작업은 포함하지 않는다. 수정 후 재수행은 새 실행으로 기록한다.

### 판정

| 상태 | 이번 실행의 근거 |
|------|-----------------|
| `Pass` | 사전조건·입력을 확인하고 필요한 기대결과·사후조건을 모두 관측하여 일치 |
| `Fail` | 올바른 사전조건·입력으로 실제 수행했고 기대결과 또는 사후조건에 구체적 불일치가 있음 |
| `미구현` | 기능이 아직 제공되지 않음을 라우트·화면·명시적 미구현 응답 등으로 확인 |
| `미검증` | 기동·계정·데이터·도구 문제, 선행조건 미충족, 일부 관측, 기준값 미확정, 제외 등 |

HTTP 400을 기대한 예외 케이스가 약속한 메시지와 미저장을 확인하면 Pass다. HTTP 200이어도 잘못 저장되면 Fail이다. 404 한 번이나 테스트 코드 부재만으로 미구현이라 하지 않는다. 일부만 관측하고 불일치도 확인하지 못했으면 미검증이다. 사전조건이 틀린 시험은 Fail로 세지 않는다.

비기능 행은 자동 제외하지 않는다. 측정 조건과 기준을 실제로 충족할 수 있으면 그 절차로 측정한다. 900만 건·동시접속 조건을 준비하지 않은 로컬 응답시간으로 통과시키지 않는다. 별도 환경/설계 검토가 필요하면 `미검증 — 비기능 …`, `[미확정]` 행은 `미검증 — 기준값 미확정`으로 남긴다.

사유는 `실행 확인`, `기대결과 불일치`, `사후조건 불일치`, `실행 환경 미준비`, `일부만 관측`, `기능 미제공`처럼 구체적으로 적는다. `실제결과`에는 반환값·문구·데이터 변화를 적는다. Pass·Fail의 수행일은 실행 완료일, 담당자는 프로파일 작성자 또는 지정된 **시험 수행 책임자**다. 커밋 작성자로 추정하지 않는다. 미구현·미검증의 수행일·담당자는 새 판정에서 비운다.

## Step 4: 종료와 결과 승인

성공·오류·중단 모두 증적을 보존하고 자신이 시작한 프로세스와 생성한 시험 데이터만 정리한다. 사용자가 열어 둔 서버는 유지한다. 정리에 실패하면 남은 프로세스/데이터와 정리 방법을 알린다. 미완료 실행도 완료한 행과 막힌 행을 구분해 제시한다.

중단한 실행은 완료 행과 미검증 행을 모두 포함하여 마감한다. 다시 실행하면 새 `run_id`에서 계획서 전 행을 재수행한다. 이전 완료 결과를 새 실행 결과에 섞지 않는다. 삭제처럼 선행 데이터가 필요한 행은 선행 행을 재수행하거나 독립적으로 사전조건을 복원하고 그 과정을 기록한다.

`templates/approval-protocol.md`의 승인 루프를 적용한다. 상태별 건수, 각 행의 실제결과·사유·증적, 실패·미검증 원인, 이전 결과와의 차이를 보여준다. **결과서·수행대장은 승인 전에 바꾸지 않는다.**

- 이전 자동 Pass와 PM 확인을 이번 Pass로 승계하지 않는다. 새 실행 근거로 판정한다.
- 계획 내용이 같은 행에서 사람이 수정한 수행 칸(`실제결과` 포함)은 기본 유지하고 이번 관측과의 차이를 보여준다. 유지 여부는 `keep`으로 넘긴다. `case_changed`인 행은 `keep: false`로 새 판정을 반영한다. 옛 사람 값은 백업에 보존하며 바뀐 케이스의 판정으로 사용하지 않는다.
- 사람 값 유지 시 결과서는 유지값, 수행대장은 이번 관측을 기록한다. 이번에 통과한 것처럼 설명하지 않는다.
- PM이 통과라고 말한 것만으로 새 Pass를 쓰지 않는다. 실제 수행·관측 증적이 필요하다.
- 결과서 케이스 칸은 계획서 원문으로 맞춘다. xlsx는 md에서 추출하며 xlsx 손수정은 읽지 않는다.
- 계획서가 틀리거나 모호하면 변경 후보를 알린다. 기대결과를 실제결과에 맞춰 바꾸지 않는다.

## Step 5: 문서 반영

`references/execution-evidence.md` 계약으로 모든 행을 포함한 `changes.json`을 만든다. 승인 때의 `plan_hash`·`result_hash`를 사용한다. 실행 증적은 위 보존 위치에 둔다.

```text
python {플러그인 루트}/utils/test-evidence.py write --de13 "{계획서}" --result "{결과서}" --ledger "{수행대장}" --changes "{임시}/changes.json" --evidence "{실행 폴더}/execution.json" --dry-run
```

dry-run의 건수·차이·다음 버전으로 **manage-revision-history** 스킬을 통해 개정이력을 확정한다. 최초는 `1.0 / 신규`, 이후 변경은 다음 버전이다. 변화가 없으면 개정 없이 대조 이력만 남긴다. 같은 명령에서 `--dry-run`을 빼 결과서와 수행대장을 기록한다. 증적·계획서·결과서가 바뀌어 검증에 걸리면 다시 대조한다. 바뀐 행에 옛 실행을 재사용하지 않는다.

결과서 변경 시 xlsx 여부를 묻고 `utils/export-xlsx.py`로 결과서만 추출한다. 마지막에는 실제 수행 범위, 상태별 건수·수행률, 실패·미검증 원인, 증적과 결과서 경로를 알린다. `/gx-추적매트릭스`로 요구사항별 수행 상태를 다시 대조할 수 있다.
