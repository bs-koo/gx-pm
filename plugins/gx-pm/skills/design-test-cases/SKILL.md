# 테스트 케이스 도출 규칙 (design-test-cases)

**이 스킬은 산출물을 만들지 않는다.** `generate-unit-test-plan` 이 케이스를 뽑을 때
따르는 내부 규칙이다. 설계기법 이름은 DE-13 컬럼으로 내보내지 않는다.

도출 출처는 AN-03 의 `입력항목`·`처리내용(로직)` 과 DE-08 의 `길이`·`NotNull` 이다.
화면 유형은 더 이상 도출 근거가 아니다.

**호출 시점**: `generate-unit-test-plan` Step 1(기능별 케이스 도출)에서, 기능마다
어떤 설계기법으로 몇 건을 만들지 정할 때 이 규칙을 따른다.

---

## 왜 필요한가

기능당 정상 흐름 1건만으로는 감리의 검사기준서가 요구하는 **예상결과·판정기준**을
만족하지 못한다. "정상 케이스만 있는 기능은 게이트에서 차단한다"는 규칙(DE-13 정본)이
실제로 서려면, 무엇을 세어 몇 건을 만드는지가 애매하면 안 된다 — 애매하면 정상
케이스만 나온다.

체크리스트 방식은 구조적으로 **경계값과 예외 케이스를 만들어내지 못한다**.
"입력값이 유효하다"고 적혀 있어도, 최대길이+1을 실제로 넣어봤는지는 알 수 없다.

## 입력

| 항목 | 필수 | 설명 |
|------|------|------|
| AN-03 기능 목록 | Y | 기능ID, `입력항목`, `처리내용(로직)`, `출력결과` |
| 연계요구사항ID 매핑 | 권장 | AN-03 의 `연계요구사항ID` (추적성 컬럼용) |
| DE-08 테이블정의서 | 선택 | **있으면 컬럼 길이·NotNull·타입에서 경계값을 정확히 도출** |
| 도메인 검증 코드 | 선택 | **정책 클래스·검증 메서드·오류코드 enum** (C유형에서 주 출처) |

> DE-08 이 있으면 경계값 케이스의 정확도가 크게 올라간다.
> `USER_NM VARCHAR2(100) NOT NULL` → 100자·101자·공란 케이스가 자동으로 나온다.

### 제약 출처 우선순위

1. **DE-08 테이블정의서** — 컬럼 길이·NotNull·타입
2. **AN-03 입력항목** — 기능명세에 적힌 제약 (테이블보다 좁으면 이쪽이 우선)
3. **도메인 검증 코드** — 정책 상수 + **검증 메서드 본문** + 오류코드 enum
4. **사용자 확인** — 위 셋에서 못 찾으면 임의 추정하지 않고 물어본다

> 산출물이 없는 C유형(산출물 정비)에서는 3번이 사실상 유일한 출처다.
> 애노테이션(`@Column(length=)`·`@Size`)이 없는 프로젝트도 흔하므로,
> **정책 클래스의 상수와 검증 메서드를 함께 읽는다.**

### 오류코드 enum 은 예외 케이스의 완전한 목록이다

오류코드 enum 이 있으면 **각 코드가 곧 예외 케이스 1건 이상**이다.
enum 전건을 훑어 대응 케이스가 없는 코드를 찾으면 예외 누락을 구조적으로 막을 수 있다.

```
ErrorCode 13종 → 대응 케이스 12종 생성, INVALID_DATE_FORMAT 1종 미커버
→ 해당 기능에 날짜 형식 오류 케이스 추가
```

## 처리 절차

### Step 1: 기능 유형별 설계기법 매핑

기능 유형에 따라 적용할 설계기법과 최소 케이스 수를 정한다.

## 기능 유형별 기본 설계기법

| 기능 유형 | 적용 기법 | 최소 케이스 수 |
|----------|---------|-------------|
| 조회·목록 | 동등분할(검색조건 유효/무효), 경계값(페이징 첫·끝·범위초과) | 6건 |
| 등록 | 동등분할(필수/선택), 경계값(길이·범위), 결정테이블(필수값 조합), 예외(중복) | 8건 |
| 수정 | 상태전이(상태별 수정 가능 여부), 경계값, 예외(동시 수정 충돌) | 6건 |
| 삭제 | 예외(참조 무결성, 이미 삭제된 건) | 4건 |
| 파일 업로드·배치 | 동등분할(형식), 경계값(건수·용량), 예외(형식 오류·중간 실패 롤백) | 8건 |
| API·연계 | 동등분할(파라미터), 경계값, 예외(오류 응답 코드) | 6건 |
| 산출·계산 | 경계값(입력 범위 끝), 예외(0 나눗셈·결측치) | 6건 |

최소 케이스 수는 하한선이다. 입력 항목 수와 분기 수에 따라 늘어난다.

### Step 2: 설계기법별 케이스 도출

#### 동등분할 (Equivalence Partitioning)

입력값을 유효/무효 그룹으로 나누고 **각 그룹의 대표값 1건씩**을 뽑는다.

```
입력 항목: 사용자 권한코드
  유효 그룹: 등록된 권한코드 (A001, A002, …)  → 대표값 A001    [정상]
  무효 그룹1: 미등록 권한코드                  → 대표값 Z999    [예외]
  무효 그룹2: 공란                             → 대표값 ""      [예외]
→ 3건 도출
```

#### 경계값분석 (Boundary Value Analysis)

**제약 유형별로 도출 규칙이 다르다.** 아래 3유형을 구분해서 적용한다.

##### 유형 A — 길이·수량 제약

**영값 / 최소-1 / 최소 / 최대 / 최대+1** 을 만든다.

```
제약: 권한명 VARCHAR2(50) NOT NULL
  0자   → 저장 차단 (필수값 위반)        [예외]
  1자   → 정상 저장 (하한 경계)          [경계]
  50자  → 정상 저장 (상한 경계)          [경계]
  51자  → 저장 차단 (길이 초과 안내)      [경계]
```

**영값(0·빈 문자열·0분·0건)을 반드시 포함한다.** 상수값(`MIN=30`)만 보면 29/30 만 나오지만,
실제 검증은 `duration < MIN` 이므로 **0 도 걸린다**. 영값은 별도 오류로 갈리는 경우가 많아
빠뜨리면 실제 결함을 놓친다.

```
제약: 예약 길이 30분 이상 4시간 이하
  0분      → INVALID_DURATION (시작==종료)   [경계] ← 영값. 놓치기 쉬움
  30분     → 정상                              [경계]
  4시간    → 정상                              [경계]
  4시간30분 → INVALID_DURATION                [경계]
```

##### 유형 B — 시각·순서 제약 ("이후/이전/이하")

**경계-1 / 경계 정확히 일치 / 경계+1** 3건을 만든다.
**"정확히 일치"가 통과 측인지 차단 측인지는 비교 연산자가 결정**하므로 코드를 확인한다.

| 검증 코드 | 경계 일치 시 |
|---|---|
| `start.isBefore(now)` → 차단 | **일치는 통과** (isBefore 는 같으면 false) |
| `start.isAfter(limit)` → 차단 | **일치는 통과** |
| `end > CLOSE` → 차단 | **일치는 통과** |
| `duration < MIN` → 차단 | **일치는 통과** |

```
제약: 지난 시간 예약 불가 (start.isBefore(now) → PAST_DATETIME)
  현재 -1분  → PAST_DATETIME     [경계]
  현재 정각  → **정상 저장**      [경계] ← 통과 측 경계. 놓치기 쉬움
  현재 +1분  → 정상 저장          [정상]
```

##### 유형 C — 단위(step) 제약

배수/비배수뿐 아니라 **하위 정밀도 잔여값**까지 만든다.
검증 메서드가 초·나노초까지 보는 경우가 많다.

```
제약: 30분 단위 (isOnUnit: minute % 30 == 0 && second == 0 && nano == 0)
  10:00      → 정상                    [경계]
  10:15      → INVALID_TIME_UNIT       [경계]
  10:00:30   → INVALID_TIME_UNIT       [경계] ← 초 잔여. 놓치기 쉬움
  10:00:00.5 → INVALID_TIME_UNIT       [경계] ← 나노초 잔여
```

##### 공통 — 검증 메서드 조건절 전개

**검증 메서드 본문의 `if` 하나당 최소 2건**을 만든다: 차단되는 케이스 1건 + 통과 측 경계 1건.
상수만 훑으면 위 3유형의 "놓치기 쉬움" 표시 케이스가 전부 빠진다.

##### 날짜 범위 제약

```
제약: 조회 시작일 ≤ 종료일
  시작일 = 종료일          → 정상 조회 (당일)   [경계]
  시작일 = 종료일 + 1일    → 오류 안내          [예외]
```

#### 결정테이블 (Decision Table)

조건 조합에 따라 결과가 달라질 때, **조합별 1건**을 만든다.

```
조건: 필수 항목 3개 (권한코드 / 권한명 / 사용여부)
  C1 권한코드 입력  | Y | Y | Y | N |
  C2 권한명 입력    | Y | Y | N | - |
  C3 사용여부 선택  | Y | N | - | - |
  ───────────────────────────────────
  결과: 저장         | O | X | X | X |
→ 4건 도출 (조합 폭발 시 페어와이즈로 축약)
```

> 조건이 5개를 넘으면 전 조합(2⁵=32건)이 비현실적이다. **필수값 누락 1건씩 + 전체 정상 1건**으로 축약하고,
> 축약 근거를 비고에 남긴다.

#### 상태전이 (State Transition)

데이터에 상태가 있으면 **유효 전이 + 무효 전이**를 각각 만든다.

```
상태: 신청 → 승인 → 완료
              ↘ 반려
  유효 전이: 신청 상태 건을 승인 처리      → 정상   [정상]
  유효 전이: 신청 상태 건을 반려 처리      → 정상   [정상]
  무효 전이: 이미 승인된 건을 재승인 시도  → 차단   [예외]
  무효 전이: 완료된 건을 반려 시도         → 차단   [예외]
→ 4건 도출
```

### Step 3: 케이스 구분 강제 검증

도출된 케이스를 정상/예외/경계로 분류하고, **누락을 차단**한다.

| 검증 규칙 | 위반 시 |
|---------|--------|
| 기능당 정상 케이스 ≥ 1건 | 정상 케이스 자동 추가 |
| AN-03 `처리내용` 에 분기가 있는 기능은 **예외 케이스 ≥ 1건** | 예외 케이스 자동 추가 |
| 길이·범위 제약이 있는 항목마다 **경계 케이스 ≥ 2건** | 경계 케이스 자동 추가 |
| 수량·기간 제약마다 **영값 케이스 1건** | 영값 케이스 자동 추가 |
| 시각·순서 제약마다 **경계 정확히 일치 케이스 1건** | 통과 측 경계 자동 추가 |
| 오류코드 enum 이 있으면 **전 코드에 대응 케이스 존재** | 미커버 코드 목록 표시 |
| 기능당 총 케이스 ≥ 유형별 최소 케이스 수 | 사용자에게 부족분 안내 |

> **정상 케이스만 있는 기능은 산출물로 내보내지 않는다.**
> 예외·경계가 0건이면 승인 요청 전에 자동 보강하고, 보강 내역을 사용자에게 표시한다.

> **단순 조회 기능은 최소 케이스 수를 강제하지 않는다.** 입력 제약이 없어 경계값이
> 본질적으로 적으므로, 미달 시 자동 보강 대신 사용자에게 기준 적용 여부를 묻는다.

### Step 4: 사전조건 작성

각 케이스에 사전조건을 반드시 붙인다. DE-13 정본이 정한 3유형 중 해당하는 것을 적는다.

| 유형 | 예시 |
|------|------|
| 계정·권한 | 관리자 계정(`admin01`)으로 로그인 |
| 선행 데이터 | 권한코드 `A001` 등록 상태 / 미등록 상태 |
| 시스템 상태 | 테스트 DB 초기화 완료, 배치 실행 전 |

> "로그인 후"는 불충분하다. **어느 권한의 계정인지**가 들어가야 권한 케이스가 성립한다.
> `없음` 으로 비워두지 않는다 — 재현 불가능한 사전조건은 케이스가 아니다.

### Step 5: 기대결과 작성

판정 가능한 문장으로 쓴다.

| 나쁜 예 | 좋은 예 |
|--------|--------|
| 정상 동작 | 목록에 신규 권한 1건 추가 표시, 총 건수 +1 |
| 오류 발생 | "권한명은 50자 이내로 입력하세요" 안내 후 저장 차단, DB 미반영 |
| 접근 불가 | 403 응답, 권한 없음 안내 |

**DB 반영 여부까지 적는다.** 화면·응답에는 안내만 뜨고 DB에는 저장되는 결함을 잡으려면 필요하다.
예외 케이스의 사후조건에는 "변화 없음"을 명시한다 — DE-13 정본의 작성 규칙이다.

---

## 주의사항

1. 경계값은 **DE-08 → AN-03 입력항목 → 도메인 검증 코드 → 사용자 확인** 순으로 근거를 찾는다.
   근거 없이 임의 추정하지 않는다
2. **상수값만 보고 경계를 만들지 않는다** — 검증 메서드의 조건절을 함께 읽는다.
   상수만 보면 영값(0분·빈 문자열)과 통과 측 경계(현재 정각·18:00 정각), 하위 정밀도(초·나노초)가 전부 빠진다
3. 검증 조건이 순차 검사되면 **먼저 걸리는 조건이 실제 결과**다.
   (예: 15분 예약은 길이 위반이자 단위 위반이지만, 단위 검사가 앞서므로 `INVALID_TIME_UNIT`)
   기대결과에 이 순서를 반영하지 않으면 케이스가 실패한다
4. 제약 근거를 찾지 못한 항목은 케이스를 만들되 **비고에 "제약 미확인"을 표시**하고 사용자 확인을 받는다
5. 결정테이블 조건이 5개를 넘으면 전 조합 대신 축약하고 **축약 근거를 남긴다**
6. 케이스가 지나치게 많아지면(기능당 20건 초과) 정상·필수 예외·필수 경계만 우선 두고
   나머지는 보강 후보로 표시한다
7. 연계요구사항ID는 연계기능ID를 경유해 AN-03 에서 그대로 옮긴다 — 사용자에게 묻지 않는다
8. 비기능(성능·보안 등) 케이스는 여기서 만들지 않는다 — `generate-unit-test-plan` Step 4 가
   AN-02 비기능 요구사항에서 직접 만든다 (연계기능ID 공란 행)
