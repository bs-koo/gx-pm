# 테스트케이스 설계 (design-test-cases)

단위테스트계획서(DE-13)의 **검사기준 체크리스트를 실행 가능한 케이스로 분해**한다.
"권한(7) 적합"이 아니라 "어떤 계정으로 어떤 URL에 접근했을 때 무엇이 나와야 하는가"를 기록한다.

**호출 시점**: `generate-unit-test-plan`이 화면 유형 판별과 검사기준 배정을 마친 직후.

---

## 왜 필요한가

검사기준 27개 체크리스트만으로는 감리의 검사기준서가 요구하는 **예상결과·판정기준**을 만족하지 못한다.
체크리스트는 "무엇을 확인했나"이고, 테스트케이스는 "어떤 데이터로 어떤 결과를 기대했나"다.

또한 체크리스트 방식은 구조적으로 **경계값과 예외 케이스를 만들어내지 못한다**.
"입력(2) 유효성 = 적합"이라고 찍혀 있어도, 최대길이+1을 실제로 넣어봤는지 알 수 없다.

---

## 입력

| 항목 | 필수 | 설명 |
|------|------|------|
| 화면 목록 | Y | 화면ID, 화면명, 화면 유형 (generate-unit-test-plan 판별 결과) |
| 검사기준 배정 | Y | 화면별 해당/해당없음 배정 결과 |
| 요구사항 매핑 | 권장 | 화면ID ↔ 요구사항ID (추적성 컬럼용) |
| 화면정의서 | 선택 | 있으면 입력 항목·길이 제약을 정확히 반영 |
| 테이블정의서 | 선택 | **있으면 컬럼 길이·NotNull·타입에서 경계값을 정확히 도출** |

> 테이블정의서(DE-08)가 있으면 경계값 케이스의 정확도가 크게 올라간다.
> `USER_NM VARCHAR2(100) NOT NULL` → 100자·101자·공란 케이스가 자동으로 나온다.

## 처리 절차

### Step 1: 화면 유형별 설계기법 매핑

화면 유형에 따라 적용할 설계기법과 최소 케이스 수를 결정한다.

| 화면 유형 | 적용 설계기법 | 최소 케이스 |
|----------|-------------|-----------|
| 목록형 | 동등분할(검색조건 유효/무효), 경계값(페이징 첫·끝·초과, 날짜 시작=종료·역전) | 6건 |
| 등록형 | 동등분할(필수/선택), 경계값(길이·수량·금액), 결정테이블(필수값 조합), 예외(중복) | 8건 |
| 수정형 | 상태전이(상태별 수정 가능 여부), 경계값, 예외(동시 수정 충돌) | 6건 |
| 상세형 | 동등분할(존재/미존재 ID), 예외(타인 데이터 접근) | 4건 |
| CRUD통합형 | 위 전부 | 12건 |
| 설정형 | 결정테이블(설정 조합), 상태전이 | 6건 |
| API/배치형 | 동등분할(파라미터), 경계값, 예외(오류 응답 코드) | 6건 |

### Step 2: 설계기법별 케이스 도출

#### 동등분할 (Equivalence Partitioning)

입력값을 유효/무효 그룹으로 나누고 **각 그룹의 대표값 1건씩**을 뽑는다.

```
입력 항목: 사용자 권한코드
  유효 그룹: 등록된 권한코드 (A001, A002, …)  → 대표값 A001    [정상]
  무효 그룹1: 미등록 권한코드                  → 대표값 Z999    [예외]
  무효 그룹2: 공란                             → 대표값 ""      [예외]
→ 3건 도출
```

#### 경계값분석 (Boundary Value Analysis)

길이·수량·날짜·금액 제약마다 **최소-1 / 최소 / 최대 / 최대+1** 4건을 만든다.
테이블정의서의 컬럼 길이가 1차 근거이고, 화면정의서의 입력 제약이 우선한다.

```
제약: 권한명 VARCHAR2(50) NOT NULL
  0자   → 저장 차단 (필수값 위반)        [예외]
  1자   → 정상 저장                       [경계]
  50자  → 정상 저장                       [경계]
  51자  → 저장 차단 (길이 초과 안내)      [경계]
→ 4건 도출
```

날짜 범위는 별도 규칙을 적용한다.

```
제약: 조회 시작일 ≤ 종료일
  시작일 = 종료일          → 정상 조회 (당일)   [경계]
  시작일 = 종료일 + 1일    → 오류 안내          [예외]
```

#### 결정테이블 (Decision Table)

조건 조합에 따라 결과가 달라질 때, **조합별 1건**을 만든다.

```
조건: 필수 항목 3개 (권한코드 / 권한명 / 사용여부)
  C1 권한코드 입력  | Y | Y | Y | N |
  C2 권한명 입력    | Y | Y | N | - |
  C3 사용여부 선택  | Y | N | - | - |
  ───────────────────────────────────
  결과: 저장         | O | X | X | X |
→ 4건 도출 (조합 폭발 시 페어와이즈로 축약)
```

> 조건이 5개를 넘으면 전 조합(2⁵=32건)이 비현실적이다. **필수값 누락 1건씩 + 전체 정상 1건**으로 축약하고,
> 축약 근거를 비고에 남긴다.

#### 상태전이 (State Transition)

데이터에 상태가 있으면 **유효 전이 + 무효 전이**를 각각 만든다.

```
상태: 신청 → 승인 → 완료
              ↘ 반려
  유효 전이: 신청 상태 건을 승인 처리      → 정상   [정상]
  유효 전이: 신청 상태 건을 반려 처리      → 정상   [정상]
  무효 전이: 이미 승인된 건을 재승인 시도  → 차단   [예외]
  무효 전이: 완료된 건을 반려 시도         → 차단   [예외]
→ 4건 도출
```

### Step 3: 케이스 구분 강제 검증

도출된 케이스를 정상/예외/경계로 분류하고, **누락을 차단**한다.

| 검증 규칙 | 위반 시 |
|---------|--------|
| 화면당 정상 케이스 ≥ 1건 | 정상 케이스 자동 추가 |
| 입력/수정/삭제 검사기준이 해당인 화면은 **예외 케이스 ≥ 1건** | 예외 케이스 자동 추가 |
| 길이·범위 제약이 있는 항목마다 **경계 케이스 ≥ 2건** | 경계 케이스 자동 추가 |
| 화면당 총 케이스 ≥ 유형별 최소 케이스 수 | 사용자에게 부족분 안내 |

> **정상 케이스만 있는 화면은 산출물로 내보내지 않는다.**
> 예외·경계가 0건이면 승인 요청 전에 자동 보강하고, 보강 내역을 사용자에게 표시한다.

### Step 4: 테스트케이스ID 부여

- 패턴: `TC_{화면ID}_{2자리 순번}`
- 순번은 화면ID 안에서 01부터 1단위 증가
- 정렬 순서: 정상 → 경계 → 예외 (읽는 사람이 기본 흐름부터 보게)

### Step 5: 사전조건 작성

각 케이스에 사전조건을 반드시 붙인다. 다음 4요소 중 해당하는 것을 적는다.

| 요소 | 예시 |
|------|------|
| 계정·권한 | 관리자 계정(`admin01`)으로 로그인 |
| 선행 데이터 | 권한코드 `A001` 등록 상태 / 미등록 상태 |
| 화면 상태 | 등록 화면 진입 완료 |
| 환경 | 테스트 DB 초기화 완료 |

> "로그인 후"는 불충분하다. **어느 권한의 계정인지**가 들어가야 권한 케이스가 성립한다.

### Step 6: 기대 결과 작성

판정 가능한 문장으로 쓴다.

| 나쁜 예 | 좋은 예 |
|--------|--------|
| 정상 동작 | 목록에 신규 권한 1건 추가 표시, 총 건수 +1 |
| 오류 발생 | "권한명은 50자 이내로 입력하세요" 안내 후 저장 차단, DB 미반영 |
| 접근 불가 | 403 화면 표시, 메뉴 미노출 및 URL 직접 입력 시에도 차단 |

**DB 반영 여부까지 적는다.** 화면에 안내만 뜨고 DB에는 저장되는 결함을 잡으려면 필요하다.

## 체크포인트 (승인 루프)

케이스 생성 후 **AskUserQuestion 도구**로 승인을 요청한다:

```
테스트케이스 {N}건을 생성했습니다. (정상 {N} / 경계 {N} / 예외 {N})

주요 확인:
1. 경계값이 실제 컬럼 길이·업무 제약과 맞는지
2. 예외 케이스가 실제로 차단되어야 하는 것인지
3. 사전조건이 재현 가능한 수준인지
4. 최소 기준 미달 화면 {N}건을 보강할지

승인하려면 '승인' 또는 'OK'를 입력하세요.
수정하려면 변경할 내용을 입력하세요.

수정 예시:
• "권한명 길이는 50이 아니라 100이야"
• "EHR_01_01_030에 타인 데이터 조회 케이스 추가"
• "동시 수정 충돌 케이스는 이번 범위에서 제외"
```

## 주의사항

1. **테스트케이스 시트는 검사기준 체크리스트를 대체하지 않는다** — 두 시트가 공존하며 역할이 다르다
2. 경계값은 **테이블정의서 → 화면정의서 → 사용자 확인** 순으로 근거를 찾는다. 근거 없이 임의 추정하지 않는다
3. 제약 근거를 찾지 못한 항목은 케이스를 만들되 **비고에 "제약 미확인"을 표시**하고 사용자 확인을 받는다
4. 결정테이블 조건이 5개를 넘으면 전 조합 대신 축약하고 **축약 근거를 남긴다**
5. 케이스가 지나치게 많아지면(화면당 20건 초과) 우선순위 High만 필수로 두고 나머지는 선택 실행으로 표시한다
6. 요구사항ID는 화면ID를 경유해 채운다. 매핑이 없으면 공란으로 두고 추적매트릭스에서 보완한다
7. 성능·보안 관련 케이스는 여기서 만들지 않는다 — **시스템테스트(`generate-system-test`)의 몫**이다
