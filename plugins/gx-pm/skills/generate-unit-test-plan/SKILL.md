# 단위테스트계획서 생성 (generate-unit-test-plan)

화면목록표(DE-03)의 화면 목록을 기반으로, 각 화면의 유형을 판별하고 검사기준을 자동 매핑하여 DE-13 단위테스트계획서 데이터를 생성한다.

## 입력

다음 중 하나:
- 화면목록표 데이터 (마크다운 표 또는 텍스트)
- 화면목록표 Excel 파일 업로드
- `/화면목록표` 결과로 생성된 화면목록
- (C유형) `scan-source-index`의 views 데이터 — JSP/HTML 파일 목록

필요 정보:
- 시스템 코드 (profile.json)
- 화면별 사용자구분 (관리자/일반사용자/민원인)

권장 입력 (있으면 테스트케이스 정확도가 크게 올라감):
- 테이블정의서 (DE-08) — 컬럼 길이·NotNull에서 경계값 도출
- 화면정의서 — 입력 항목 제약

## 처리 절차

### Step 1: 화면 목록 파싱
화면목록표에서 추출:
- 기능구분ID, 기능구분명
- 기능ID, 기능명
- 화면ID, 화면명

### Step 2: 화면 유형 판별
화면명과 기능명에서 유형을 추론한다:

| 키워드 | 화면 유형 |
|--------|----------|
| 목록, 리스트, 조회, 현황, 이력 | 목록형 |
| 등록, 신청, 작성, 입력 | 등록형 |
| 수정, 편집, 변경 | 수정형 |
| 상세, 보기, 확인 | 상세형 |
| 관리 (단독) | CRUD 통합형 |
| 매핑, 설정, 배정 | 설정형 (≈ 수정형) |
| 대시보드, 통계 | 조회형 (≈ 목록형) |
| 팝업 | 부모 화면 유형 따름 |

### Step 3: 검사기준 자동 매핑
화면 유형에 따라 적합/해당없음을 자동 배정:

**목록형:**
- 공통(1~8): 모두 해당
- 조회(1~4): 모두 해당
- 입력(1~6): 해당없음
- 수정(1~2): 해당없음
- 삭제(1~2): 해당없음
- 첨부(1~3): 해당없음
- 출력(1~2): 해당 (엑셀 다운로드 등)

**등록형:**
- 공통(1~8): 모두 해당
- 조회(1~4): 해당없음
- 입력(1~6): 모두 해당
- 수정(1~2): 해당없음
- 삭제(1~2): 해당없음
- 첨부(1~3): 해당 (파일 업로드 있으면)
- 출력(1~2): 해당없음

**수정형:**
- 공통(1~8): 모두 해당
- 조회(1~4): 해당없음
- 입력(1~6): 해당없음
- 수정(1~2): 모두 해당
- 삭제(1~2): 해당 (삭제 기능 있으면)
- 첨부(1~3): 해당 (파일 기능 있으면)
- 출력(1~2): 해당없음

**상세형:**
- 공통(1~8): 모두 해당
- 조회(1~4): 해당 (상세 조회)
- 입력~삭제: 해당없음
- 첨부(1~3): 해당없음
- 출력(1~2): 해당 (인쇄 등)

**CRUD 통합형:**
- 모든 검사기준: 해당

### Step 4: 단위테스트ID 부여
- 패턴: `U_{화면ID}`
- 예시: `U_EHR_01_01_010`

### Step 5: 사용자구분 판별
- 관리자 전용 (시스템관리, 권한관리 등) → "관리자"
- 일반 사용자 화면 → "일반사용자"
- 민원/외부 화면 → "민원인"
- 판별이 어려우면 사용자에게 확인

### Step 6: 테스트케이스 설계 (design-test-cases 호출)

검사기준 배정이 승인되면 **design-test-cases** 스킬을 호출하여
각 검사기준 항목을 실행 가능한 테스트케이스로 분해한다.

- 화면 유형별 설계기법 적용 (동등분할·경계값분석·결정테이블·상태전이)
- 케이스ID `TC_{화면ID}_{2자리}` 부여
- 정상·경계·예외 케이스 강제 검증
- 사전조건·입력데이터·기대결과 작성

> **이 단계를 건너뛰면 안 된다.** 검사기준 체크리스트만으로는 감리 검사기준서가 요구하는
> **예상결과·판정기준**을 만족하지 못한다. 체크리스트는 "무엇을 확인했나", 케이스는 "어떻게 확인했나"다.

## 검사기준 항목 정의

27개 검사기준의 항목명·예상결과·판정기준·점검방법은 **`templates/inspection-criteria.md`가 단일 정본**이다.
이 스킬과 `fill-unit-test-result`는 모두 그 정의를 참조한다. 여기에 항목명을 중복 정의하지 않는다.

## 출력 형식

### 시트 1 — 단위테스트계획 (검사기준 체크리스트)

```
## 단위테스트계획서 — {시스템명}

| 기능구분ID | 기능구분명 | 기능ID | 기능명 | 화면ID | 화면명 | 사용자 | 테스트ID | 공통(1) | ... | 공통(8) | 조회(1) | ... | 출력(2) |
|-----------|-----------|--------|--------|--------|--------|--------|---------|--------|-----|--------|--------|-----|--------|
| EHR_01 | 시스템관리 | EHR_01_01 | 권한관리 | EHR_01_01_010 | 운영자 권한 관리 | 관리자 | U_EHR_01_01_010 | | ... | | | ... | 해당없음 |
```

계획서이므로 적합/부적합 칸은 빈칸으로 둔다. 화면 유형에 따라 **"해당없음"만 미리 기입**한다.

> "해당없음"은 계획 단계의 배정값이다. 결과서에서 나오는 "점검제외"(적용 대상인데 못 쟀음)와 다르며,
> 결과서에서 임의로 변경하지 않는다.

### 시트 2 — 테스트케이스

design-test-cases 스킬의 출력. 화면별 케이스를 정상 → 경계 → 예외 순으로 배치한다.

## 체크포인트

화면 유형 판별 결과를 사용자에게 확인:
"다음 화면 유형 판별이 맞는지 확인해주세요:
- EHR_01_01_010 (운영자 권한 관리) → CRUD 통합형
- EHR_01_01_020 (권한-메뉴 매핑) → 설정형
- ..."

승인 후 design-test-cases를 호출하고, 케이스 생성 결과에 대해 다시 승인을 받는다.
