# 요구사항 추출 (extract-requirements)

RFP, 과업지시서, 제안서 등의 텍스트에서 기능/비기능 요구사항을 추출하고, AN-02 요구사항정의서 양식에 맞는 구조화된 데이터를 생성한다.

## 입력

사용자로부터 다음 중 하나를 받는다:
- RFP/과업지시서 텍스트 (붙여넣기)
- 파일 업로드 (PDF, HWP 텍스트, Word)
- 구두 설명

추가로 확인할 정보:
- 시스템 코드 (A~I 중 해당 코드, 또는 새 프로젝트면 코드 정의)
- 시스템 접두어 (화면ID에 사용할 3~4자리 영문, 예: EHR, KSC)

## 처리 절차

### Step 1: 시스템 정보 확인
- 시스템 코드와 접두어를 사용자에게 확인
- 기존 산출물이 있으면 기존 코드 체계를 따름

### Step 2: 요구사항 추출
문서에서 다음 패턴으로 요구사항을 식별한다:
- "~해야 한다", "~를 제공한다", "~기능을 구현한다"
- "ㅇ" 또는 "o"로 시작하는 기능 항목
- 번호가 매겨진 기능 목록
- "기능 요구사항", "비기능 요구사항" 섹션의 항목
- **ID 접두 표 행** — 아래 참조

#### ID 접두 표 행

공공 RFP 는 요구사항을 **ID 표**로 주고, 그 표가 늘 "기능 요구사항" 이라는 제목 아래
있지 않다. 도메인 규칙 · 업무 규칙 · 비즈니스 규칙 · 제약사항 · 정책 · 준수사항 아래
놓이는 것이 보통이다. 섹션 제목에만 의존하면 이 경우를 전부 놓친다.

**정규식만으로는 갈리지 않는다.** "첫 열이 ID 형태이면 요구사항 표"로는 부족하다 —
산출물 목록표(`| AN-02 | 요구사항정의서 |`), 일정표(`| WBS-01 | 착수 | 2026-03 |`),
투입인력표(`| PM-01 | 홍길동 | PM |`)도 첫 열이 ID 형태라 함께 걸려 유령 요구사항이
들어온다. 반대로 정보화사업 요구사항정의서 표준 표는 순번·분류가 ID 앞에 오는 일이
흔해(`| 1 | SFR-001 | 회원 관리 |`), 첫 열만 보면 진짜 요구사항 표를 통째로 놓친다.
그래서 규칙을 두 단계로 나눈다.

**1단계 — 후보 찾기 (기계적)**

첫 열 **또는 둘째 열**이 `{영문 2~4자}-{숫자 2~3자리}` 형태인 행을 후보로 모은다.
앞 공백(HWP 변환에서 목록 아래 중첩된 표), 강조·백틱 표기는 있든 없든 무시한다.

```regex
^\s*\|(?:[^|]*\|)?\s*[`*]*\s*([A-Z]{2,4}-\d{2,3})\s*[`*]*\s*\|
```

**2단계 — 요구사항 표인지 판정 (판단)**

후보가 있다고 바로 뽑지 않는다. 그 표가 요구사항 표인지 아래 신호로 가른다.

| 요구사항 표다 | 요구사항 표가 아니다 |
|---|---|
| 같은 행에 "~한다 / ~해야 한다 / ~할 수 없다" 형태의 서술이 있다 | 산출물·문서 목록 — 행이 문서명이다 |
| 표 헤더에 요구사항·규칙·내용·요구내역·설명 이 있다 | 일정·WBS — 행이 날짜나 단계다 |
| 섹션이 요구사항·규칙·제약·정책·준수사항 을 다룬다 | 조직·투입인력 — 행이 사람이나 역할이다 |
| | 코드 정의표 — 행이 코드와 그 뜻이다 |

**애매하면 사용자에게 묻는다.** 유령 요구사항이 들어가면 추적매트릭스 행 수와
과업이행여부 판정 대상 전체가 틀어진다. 조용히 추정하지 않는다.

**표가 여러 개면 정책 하나로 묶어 한 번만 묻는다.** 판정이 갈리는 지점은 표마다 다르지
않고 "산출물 목록·WBS·투입인력표를 요구사항으로 셀 것인가" 하나로 뭉친다. 후보 표가 5개면
질문 5개를 내는 대신, 애매한 표를 **한 화면에 모아** 놓고 AskUserQuestion 을 한 번 부른다.

```
요구사항 표인지 애매한 표가 {N}개 있습니다.

  1. 전부 요구사항으로 센다        → 요구사항 {M1}건
  2. 전부 제외한다                  → 요구사항 {M2}건
  3. 표별로 정하겠다                → {N}개를 하나씩 확인

⚠ 여기서 센 건수가 추적매트릭스 행 수와 과업이행여부 판정 대상이 됩니다.
```

선택지 1·2 의 요구사항 건수를 **양쪽 다 계산해서** 보여준다. 감당할 비용을 모르는 채로
고르게 하면 묻는 의미가 없다. 3번을 고르면 그때만 표별로 묻는다.

이 중단점은 **게이트로 이월하지 않는다** — `templates/pipeline-protocol.md` §이월 금지 항목
5번. 요구사항 건수가 뒤 산출물 전부의 행 수를 정하므로, 게이트에 도달했을 때는 이미
그 건수로 만들어진 뒤다.

> 1단계 정규식은 `tests/test_extract_rules.py` 가 이 문서에서 그대로 꺼내
> `tests/fixtures/requirement-tables.md` 에 적용해 검사한다. 고치면 픽스처도 함께 본다.

#### 판정 예시

1단계 정규식이 무엇을 후보로 뽑고 거르는지, 그리고 정규식은 후보로 뽑지만 2단계
판단이 요구사항 표가 아니라고 거르는 것이 무엇인지 — 이 목록이 정본이다.
`tests/test_extract_rules.py` 가 이 목록을 파싱해 정규식과 대조한다 — 목록과 정규식이
어긋나면 테스트가 실패한다. 예시를 고치면 정규식도 함께 본다.

**뽑는다**

- `| PER-01 | 응답시간 3초 이내 |` — 성능 요구사항. 공공 RFP 표준 접두어
- `| SER-012 | 관리자 권한 분리 |` — 3자리 순번
- `| ECRM-01 | 연계 이력 보관 |` — 4자 접두어(상한)
- `| **BR-03** | 09:00 ~ 18:00 |` — 굵게 표기된 ID
- `|  NFR-01  | H2 인메모리 |` — 여백이 넉넉한 표
- `| 1 | SFR-001 | 회원 관리 |` — 정보화사업 표준 레이아웃. 순번이 ID 앞에 온다
- ``| `BR-03` | 내용 |`` — 백틱으로 표기된 ID
- `  | BR-03 | 내용 |` — 들여쓴 표 (HWP 변환에서 흔하다)

**정규식이 거른다**

- `| B-1 | 내용 |` — 1자 접두어에 1자리 순번
- `| BR_03 | 내용 |` — 하이픈이 아니라 밑줄
- `| br-03 | 내용 |` — 소문자
- `| 1 | 08:00~09:00 | 허용 |` — 판정표의 일련번호
- `| OVERLAPPING_RESERVATION | 409 |` — 오류 코드명

**정규식은 걸리지만 요구사항 표가 아니다**

1단계 후보에는 걸리지만, 2단계 판단(위 표)에서 요구사항 표가 아니라고 걸러진다.

- `| AN-02 | 요구사항정의서 |` — 산출물 목록표. 행이 문서명이라 유령 요구사항이 된다
- `| WBS-01 | 착수 | 2026-03 |` — 일정표. 행이 날짜·단계다
- `| PM-01 | 홍길동 | PM |` — 투입인력표. 행이 사람이다

#### 뽑은 행을 다루는 규칙

**중복 제거** — 섹션 규칙과 표 규칙에 모두 걸리는 항목이 있다.
예: `## 6. 비기능 요구사항` 아래의 NFR 표는 두 규칙에 다 걸린다.
같은 원문 ID 는 요구사항 **1건**으로 센다.

**기능 / 비기능 판정** — 아래 순서로 정한다.

1. 원문 ID 접두어가 `NFR` · `QE` · `QR` 이면 → 비기능
2. 섹션 제목에 "비기능" · "품질" · "성능" · "보안" 이 있으면 → 비기능
3. 그 외 → 기능

`BR`(업무 규칙)은 3번에 걸려 기능이 된다 — **업무 규칙은 기능 요구사항이다.**
"겹치는 예약을 거절한다" 는 성능도 보안도 아니라 시스템이 하는 일이다.

**원문 ID 보존** — 원문 ID 를 `근거` 열에 병기한다: `과업지시서 BR-01`.

**제안요청ID 열에 넣지 않는다.** 그 열의 정본 패턴은 `templates/id-naming-rules.md` 의
`SFR-{3자리 순번}` 이고, 거기에 `BR-01` 을 넣으면 ID 체계가 무너진다.
`근거` 열은 원래 출처를 적는 자리라 원문 ID 표기에 맞고, 이렇게 해야
요구사항정의서에서 `BR-01` 이 어느 요구사항이 됐는지 역추적할 수 있다.

### Step 3: 행 분할

**컬럼을 채우기 전에 몇 행이 되는지가 먼저다.** 이 건수가 뒤 산출물 전체의 행 수를 정한다.

| 상황 | 처리 |
|------|------|
| `ㅇ` · `-` 불릿 하나 | 요구사항 1건 |
| ID 표의 행 하나 (Step 2 판정 통과) | 요구사항 1건 |
| 한 문장에 이질적 기능이 `및`·`~와 ~를` 로 묶임 | **쪼갠다** |
| 하나가 다른 하나의 수단인 경우 (`~하여 ~한다`) | 쪼개지 않는다 |

**판정 기준: 테스트를 따로 써야 하면 따로 쪼갠다.**

- `상대평가기준 생성 결과 조회 및 다운로드 기능` → 입력도 출력도 다르므로 **2건**
- `헤더정보를 읽어 컬럼 순서를 파악한 후 업로드` → 수단-목적 관계이므로 **1건**

애매하면 추정하지 않고 묻는다. Step 2 의 표 판정 애매성과 같은 중단점 규칙이다.

### Step 4: 분류

- **대분류**: 업무 영역. 출처 우선순위 ① RFP 목차·장 제목 ② ID 표의 분류 열 ③ 모델 분류
- **중분류**: 세부 업무. 대분류 안에서 유일해야 한다
- ③ 으로 갔으면 게이트에서 "문서에 없어 추정했다" 를 명시한다

### Step 5: ID 부여와 상태

- 요구사항ID: 프로파일 채번 규칙. 미설정이면 AskUserQuestion 으로 한 번 묻는다
  (기본 제안 `REQ-{3자리}`)
- 최초 작성이면 상태는 전건 `신규`, 근거는 `과업지시서` 등 출처
- 재실행이면 `templates/AN-02-requirements-definition.md` 의 상태 판정표를 따른다

### Step 6: 개정이력

**manage-revision-history** 스킬로 개정이력 행을 만든다.

## 출력 형식

```
## 개정이력

| 버전 | 개정일 | 개정 사유 | 개정 내용 | 작성자 | 승인자 |
|------|--------|----------|----------|--------|--------|
| 1.0 | 2026.09.03 | 신규 | 최초 작성 | 구본승 | |

## 요구사항 명세 — {시스템명}

| 번호 | 요구사항ID | 대분류 | 중분류 | 요구사항명 | 요구사항 상세내용 | 비고 | 상태 | 요구사항 근거 | 변경 근거 |
|------|-----------|--------|--------|-----------|-----------------|------|------|-------------|----------|
| 1 | REQ-001 | 데이터 전처리·입력 | 상대평가기준 생성 기능 | 벤치마크 EUI·CDF 스코어테이블 생성 기능 | 원단위 통계데이터를 이용한 세부용도별 벤치마크 EUI 테이블 및 CDF 생성 | | 신규 | 과업지시서 | |
```

## 주의사항

- 요구사항은 가능한 원문 표현을 유지 (해석하지 않음)
- 상세내역이 길면 핵심만 요약하되 **조건·제약·수치는 버리지 않는다** — 테스트 경계값의 유일한 출처다
- 요약했으면 비고에 원문 위치를 표기한다
- 원문 ID 는 `요구사항 근거` 열에 병기한다: `과업지시서 BR-01`
