# TE-01 총괄 테스트계획서 양식

시험 단계 전체를 아우르는 **전략 문서**. 개별 테스트 산출물(DE-13/DE-14/ST-01)보다 먼저 작성한다.
감리에서 "테스트를 계획하고 수행했는가"를 증명하는 근거이며, **진입·종료 기준의 유일한 출처**다.

## 파일 형식
Excel (.xlsx) 또는 문서(.docx/.hwp) — 표가 아닌 서술형 섹션 구성

## 시트/장 구성

1. **표지** — 프로젝트명, 문서명, 버전, 작성일
2. **개정이력**
3. **1. 목적 및 범위**
4. **2. 테스트 레벨 및 대상**
5. **3. 추진 체제 및 역할**
6. **4. 테스트 일정**
7. **5. 테스트 환경**
8. **6. 테스트 데이터**
9. **7. 진입기준 / 종료기준**
10. **8. 결함 관리 기준**
11. **9. 위험 및 대응**

## 1. 목적 및 범위

| 항목 | 내용 |
|------|------|
| 테스트 목적 | 과업지시서 요구사항의 충족 여부를 검증하고 결함을 조치하여 인수 가능한 품질을 확보 |
| 대상 시스템 | {시스템명} ({시스템코드}) |
| 대상 요구사항 | 기능 {N}건 / 비기능 {N}건 (AN-02 기준) |
| **포함 범위** | 단위테스트, 통합테스트, 시스템테스트, 인수테스트 |
| **제외 범위** | (예: 외부 연계기관 내부 로직, 상용 솔루션 내부 기능) — 제외 사유를 반드시 명시 |

> **제외 범위는 반드시 적는다.** 비워 두면 감리에서 "테스트 범위 미정의"로 지적된다.

## 2. 테스트 레벨 및 대상

| 레벨 | 산출물 코드 | 대상 | 수행 주체 | 검증 대상 요구사항 |
|------|-----------|------|----------|-----------------|
| 단위테스트 | DE-13 / IM-03 | 화면 단위 | 개발팀 | 기능 |
| 통합테스트 | DE-14 / TE-02 | 업무 흐름 단위 | 개발팀 + 현업 | 기능 |
| **시스템테스트** | **ST-01 / ST-02** | 시스템 전체 | 개발팀 + 인프라 | **비기능** |
| 인수테스트 | DE-14 / TE-06 | 업무 흐름 단위 | **발주처** | 기능 + 비기능 |

**레벨별 진입 순서**: 단위 → 통합 → 시스템 → 인수. 앞 레벨의 종료기준을 충족해야 다음 레벨에 진입한다.

## 3. 추진 체제 및 역할

| 역할 | 담당 | 책임 |
|------|------|------|
| 테스트 총괄 | PM | 계획 수립, 종료 판정, 발주처 보고 |
| 단위테스트 수행 | 개발 담당자 | 케이스 작성·수행, 결함 조치 |
| 통합테스트 수행 | QA / 현업 담당 | 시나리오 수행, 결함 등록 |
| 시스템테스트 수행 | 인프라 / 보안 담당 | 성능·보안 측정, 결과 판정 |
| 인수테스트 주관 | **발주처 담당자** | 인수 판정, 서명·날인 |
| 결함 조치 | 개발 담당자 | 원인 분석, 수정, 재테스트 요청 |

> 인수테스트 수행자에 개발팀 인원을 기재하면 감리 지적 대상이다. **발주처 담당자 실명**이 들어가야 한다.

## 4. 테스트 일정

| 레벨 | 시작 | 종료 | 선행 조건 |
|------|------|------|---------|
| 단위테스트 | YYYY-MM-DD | YYYY-MM-DD | 개발 완료 |
| 통합테스트 | YYYY-MM-DD | YYYY-MM-DD | 단위테스트 종료기준 충족 |
| 시스템테스트 | YYYY-MM-DD | YYYY-MM-DD | 통합테스트 종료기준 충족 |
| 인수테스트 | YYYY-MM-DD | YYYY-MM-DD | 시스템테스트 종료기준 충족 |
| 결함 조치 예비기간 | YYYY-MM-DD | YYYY-MM-DD | — |

> **결함 조치 예비기간을 일정에 넣는다.** 테스트 종료일 = 납기일로 잡으면 결함 조치 시간이 0이 된다.

## 5. 테스트 환경

| 구분 | 내용 |
|------|------|
| 서버 | (예: WAS Tomcat 9, JDK 11, 2core 8GB × 2대) |
| DB | (예: Oracle 19c, 테스트 스키마 `EHR_TEST`) |
| 브라우저 | (예: Chrome 최신, Edge 최신, IE11 지원 여부) |
| 네트워크 | 내부망 / 외부망 / 혼재 |
| 외부 연계 | 실 연계 / **Mock 처리** (Mock이면 어느 인터페이스인지 명시) |
| 테스트 도구 | (예: JMeter, Burp Suite, 수동) |

> **외부 연계를 Mock으로 처리한 인터페이스는 반드시 나열한다.** 실 연계 미검증분은 인수 조건에 영향을 준다.

| 항목 | 내용 |
|------|------|
| 데이터 출처 | 신규 생성 / 운영 데이터 복제 / 혼합 |

## 7. 진입기준 / 종료기준

테스트 레벨별로 각각 정의한다. **종료기준은 수치로 적는다.**

### 진입기준 (Entry Criteria)

| 레벨 | 진입기준 |
|------|---------|
| 단위테스트 | 개발 완료 · 빌드 배포 성공 · 테스트 데이터 준비 완료 |
| 통합테스트 | 단위테스트 종료기준 충족 · 통합 환경 구축 완료 · 시나리오 승인 완료 |
| 시스템테스트 | 통합테스트 종료기준 충족 · 운영 유사 환경 구축 · 성능 목표치 확정 |
| 인수테스트 | 시스템테스트 종료기준 충족 · 발주처 일정 확정 · 사용자 매뉴얼 제공 |

### 종료기준 (Exit Criteria) — 기본값

| 기준 | 목표치 | 비고 |
|------|--------|------|
| 계획 케이스 실행률 | **100%** | 미실행 건은 "점검제외 + 사유" 필수 |
| Critical 결함 잔존 | **0건** | 예외 없음 |
| Major 결함 잔존 | **0건** | 발주처 유예 승인 시에만 Deferred |
| Minor 결함 조치율 | **90% 이상** | 잔여분은 조치 계획 첨부 |
| 요구사항 커버리지 | **100%** | 모든 요구사항이 최소 1건의 테스트에 연결 |
| 적합률 | **95% 이상** | 적합 ÷ (적합+부적합) |

> 종료기준을 충족하지 못한 상태로 다음 레벨에 진입하려면 **PM 승인 + 사유 기록**이 필요하다.
> 이 기록이 없으면 감리에서 "시험 절차 미준수"로 지적된다.

## 8. 결함 관리 기준

결함관리대장(DF-01)의 분류 기준을 여기서 확정한다. 상세: `templates/DF-01-defect-log.md`

### 심각도 (Severity) — 테스터가 판정

| 등급 | 정의 | 예시 |
|------|------|------|
| **Critical** | 업무 중단, 데이터 손실·오염, 보안 취약점, 시스템 다운 | 저장 시 데이터 유실, SQL Injection 가능 |
| **Major** | 주요 기능 오류, 우회 경로 없음 | 승인 처리 불가, 필수 조회 실패 |
| **Minor** | 부분 오류, 우회 가능 | 정렬 오동작, 일부 항목 미표시 |
| **Trivial** | 기능 무관, 표기·UI | 오탈자, 정렬 여백 |

### 우선순위 (Priority) — PM이 판정

| 등급 | 조치 시점 |
|------|---------|
| **High** | 즉시 (당일~익일) |
| **Medium** | 해당 테스트 레벨 종료 전 |
| **Low** | 일정 여유 시 / 차기 배포 |

> 심각도와 우선순위는 **독립적**이다. Trivial-High(발주처 눈에 띄는 오탈자)와 Major-Low(사용 빈도 극히 낮은 기능)가 모두 성립한다.

### 결함 상태 흐름

```
Open → Assigned → Fixed → Retest → Closed
                              └→ Reopen (재테스트 부적합)
        └→ Deferred (차기 이월, 발주처 승인 필요)
        └→ Rejected (결함 아님, 사유 기록 필요)
```

## 9. 위험 및 대응

| 위험 | 발생 가능성 | 영향 | 대응 방안 |
|------|-----------|------|---------|
| 외부 연계기관 테스트 환경 미개방 | 중 | 높음 | Mock 우선 진행 + 연계 테스트 일정 별도 협의 |
| 테스트 데이터 부족 | 높음 | 중간 | 데이터 생성 스크립트 사전 준비 |
| 결함 조치 지연으로 일정 압박 | 높음 | 높음 | 조치 예비기간 확보, Critical 우선 조치 |
| 발주처 인수테스트 일정 미확정 | 중 | 높음 | 착수 시점에 일정 확정 요청 |

## 작성 규칙

1. 총괄 테스트계획서는 **개별 테스트 산출물보다 먼저** 작성한다
2. 종료기준은 **수치로** 적는다 — "충분히 테스트한다" 같은 표현은 감리 지적 대상
3. 제외 범위·Mock 처리 인터페이스·미실행 케이스는 **사유와 함께** 명시한다
4. 개정 시 개정이력에 변경 사유를 남긴다 (종료기준 완화는 특히 근거 필수)
5. 이 문서의 종료기준이 IM-03·TE-02·ST-02·TE-06의 판정 근거가 된다 — 결과서와 수치가 어긋나면 안 된다
