# ST-01 시스템테스트계획서 / ST-02 결과서 양식

**비기능 요구사항을 검증하는 유일한 산출물**. 성능·보안·호환성·접근성·가용성을 다룬다.

## 왜 필요한가

비기능 요구사항(AN-02에서 구분="비기능")은 화면·프로그램에 매핑되지 않는다.
그래서 단위테스트(화면 기준)와 통합테스트(업무 흐름 기준) 어디에도 걸리지 않고,
추적매트릭스에서 **검증 칸이 통째로 비게 된다**. 감리에서 "비기능 요구사항 검증 누락"으로 지적되는 전형적 패턴이다.

시스템테스트ID(`{시스템코드}-ST-{순번}`)가 그 빈칸을 메운다.

## 파일 형식
Excel (.xlsx)

## 시트 구성
1. **표지**
2. **개정이력**
3. **시스템테스트계획** (ST-01) — 측정 항목과 목표치
4. **시스템테스트결과** (ST-02) — 측정 결과와 판정

## 판정 기준 — 3값

| 판정 | 조건 | 후속 |
|------|------|------|
| **적합** | 측정값이 목표치를 충족 | — |
| **부적합** | 측정값이 목표치 미달 | 결함ID 발급 → DF-01 등록 → 조치 → 재측정 |
| **점검제외** | 측정 자체가 불가능 | **사유 필수 기재** |

### 점검제외 사유 (감리 인정 범위)

- 테스트 환경 미준비 (운영 유사 환경 미구축)
- 선행 기능 결함으로 측정 불가
- 외부 환경 변화 (연계기관 시스템 미개방)
- 과업 범위 외 판정 (발주처 협의 근거 필요)

> **"해당없음"과 "점검제외"는 다르다.** 해당없음은 애초에 적용 대상이 아닌 것,
> 점검제외는 적용 대상이지만 이번에 못 잰 것이다. 후자는 사유와 함께 종료보고서에 남는다.

## 결과 통계 (ST-02 하단)

```
[시스템테스트 결과]

총 테스트 항목: N건

판정:
  적합     N건 (N%)
  부적합   N건 (N%)
  점검제외 N건 (N%)  ← 사유별 내역 첨부

유형별 적합률:
  성능 N/N (N%) · 보안 N/N (N%) · 접근성 N/N (N%)
  호환성 N/N (N%) · 유지보수성 N/N (N%) · 법적준수 N/N (N%)

비기능 요구사항 커버리지:
  검증된 비기능 요구사항 N / 전체 비기능 요구사항 N = N%
```

> **커버리지 100%가 목표다.** 비기능 요구사항 중 시스템테스트ID가 붙지 않은 건이 있으면
> 추적매트릭스의 검증 칸이 비고, 감리 지적으로 직결된다.

## 작성 규칙

1. **비기능 요구사항 1건당 최소 1개의 시스템테스트ID**를 부여한다
2. 하나의 요구사항에 측정 항목이 여럿이면 **항목별로 ID를 분리**한다
   (예: "응답 3초 + 동시접속 500명" → `B-ST-001`, `B-ST-002`)
3. 목표치는 **요구사항 원문의 수치를 그대로** 옮긴다. 요구사항에 수치가 없으면 발주처와 협의해 확정하고 근거를 비고에 남긴다
4. 측정 방법에는 **도구명과 조건**을 적는다 — "테스트함"은 불충분
5. 증적(측정 결과 파일·스크린샷)을 반드시 남긴다. 성능·보안은 **증적이 없으면 측정하지 않은 것으로 본다**
6. 보안 취약점은 발견 즉시 Critical로 등록한다 (P1 법적 필수 영역)
7. 성능 측정은 **통합테스트 후반이 아니라 개발 중 주기적으로** 실시하고, 시스템테스트는 최종 확인이다
