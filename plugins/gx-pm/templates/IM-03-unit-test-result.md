# IM-03 단위테스트결과서 양식

DE-13 단위테스트계획서의 행을 그대로 옮기고, 행마다 수행 결과를 적는 고객 산출물이다.
`/gx-단위테스트결과반영` 이 만들고 갱신한다. 코드 IM-03 은 화면 축 시절 gx-pm 의 단위테스트결과서(`archive/commands/gx-테스트결과서.md`)와 같은 자리를 잇는다. **계획서는 건드리지 않는다** — 계획서는 약속, 결과서는
그 약속을 시험한 기록이라 따로 둔다. 계획서를 고치는 것은 `/gx-단위테스트계획서` 뿐이다.

## 파일 형식
Excel (.xlsx). 원본은 프로젝트 폴더의 `{시스템코드}-단위테스트결과서.md` 이고 xlsx 는 이 md 에서 뽑는다.
**xlsx 를 직접 고친 내용은 반영되지 않는다** — 다음 추출 때 md 내용으로 덮인다. 결과를 바꾸려면 md 를
고치거나 다음 반영의 승인 화면에서 말한다.

결과서는 하나를 계속 갱신한다. 반영으로 바뀔 때마다 개정이력이 쌓이고, 쓰기 직전의 결과서는
`backup/{파일 이름}_{YYMMDD}.md` 로 남는다(같은 날 여러 번이면 그날 처음 원본).

## 시트 구성
1. **개정이력** — 규칙의 정본은 `templates/revision-history.md`
2. **단위테스트결과** — 본문 데이터

## 머리말

```markdown
# IM-03 단위테스트결과서 — {사업명}

> 생성: /gx-단위테스트결과반영 · 2026-10-14 16:20
> 근거: DE-13 v2.0
```

`근거` 는 이 결과서가 맞춘 계획서 버전이다(`templates/revision-history.md` §근거 표기).
계획서가 그 뒤 개정되었으면 결과서가 낡은 것이다 — 다음 반영이 계획서에 맞춘다.

## 본문 컬럼 (정본)

| # | 컬럼 | 값 규칙 |
|---|------|--------|
| 1 | 테스트ID | 계획서 원문 |
| 2 | 연계기능ID | 계획서 원문 |
| 3 | 연계요구사항ID | 계획서 원문 |
| 4 | 요구사항명 | 계획서 원문 (옛 계획서에 이 열이 없으면 결과서에도 없다) |
| 5 | 사전조건 | 계획서 원문 |
| 6 | 입력 | 계획서 원문 |
| 7 | 기대결과 | 계획서 원문 |
| 8 | 사후조건 | 계획서 원문 |
| 9 | 의존성 | 계획서 원문 |
| 10 | 테스트담당자 | Pass·Fail 행은 시험한 사람(덮는 테스트의 작성자 실명). 계획서에 배정해 둔 담당자가 있으면 그 값 |
| 11 | 수행일 | Pass·Fail 행은 실행일(PM 확인이면 확인일). `YYYY.MM.DD` |
| 12 | 결과 | `Pass` / `Fail` / `미구현` / `미검증` — 정의는 아래 §결과 상태 |
| 13 | 사유 | 결과를 그렇게 적은 이유 한 줄 — 첫머리는 아래 §결과 상태의 고정어 |

**1~9열은 계획서에서 옮긴 원문이라 결과서에서 고치지 않는다.** 반영할 때마다 계획서 원문으로 다시
맞추므로, 결과서에서 고친 케이스 칸은 되돌아간다. 케이스를 바꾸려면 계획서를 고친다.

## 결과 상태

결과는 네 값이다. 빈칸이 「안 한 것인지, 테스트는 있는데 확인이 안 된 것인지, 일부러 뺀 것인지」
알 수 없게 두지 않으려고, **모든 행이 넷 중 하나와 사유를 갖는다.**

| 결과 | 뜻 | 사유 첫머리 (예) |
|------|----|----------------|
| `Pass` | 이 케이스를 시험하는 테스트가 실행되어 통과했다 | `테스트 통과 — FileSizeLimitTest.rejectsOverLimit (2026.10.10)`, `PM 확인 — 2026.10.11` |
| `Fail` | 이 케이스를 시험하는 테스트가 최근 실행에서 실패했다 | `테스트 실패 — …: expected 3 saved but was 0` |
| `미구현` | 이 케이스를 시험하는 테스트가 없다 | `대응 테스트 없음`, `대응 테스트 비활성 — @Disabled` |
| `미검증` | 테스트는 있지만 이 케이스가 확인되지 않았다, 또는 단위 시험 대상이 아니다 | `실행 결과 없음`, `실행 후 테스트 변경`, `일부만 검증 — 저장 없음 미확인`, `기준 불일치 — 계획 100건 ↔ 테스트 50건`, `케이스 변경`, `제외 — 통합 환경 필요`, `비기능 — 측정 절차로 검증`, `기준값 미확정` |

사람이 손으로 적은 결과에 사유가 없으면 `기존 기입 — 사유 미기재` 로 둔다 — 그 결과는 지키되 빈 사유
칸은 남기지 않는다.

사유는 고객 문서에 나가는 문장이라 레포 경로 대신 `클래스.메서드` 로 쓴다. 전체 경로와 실행 근거는
내부 수행대장(`templates/DE-13-execution-ledger.md`)에 남는다.

**수행률 = Pass ÷ (전체 − 사유가 `비기능`·`기준값 미확정`·`제외` 인 행).** 단위 시험으로 판정하지
않는 행만 분모에서 뺀다.

## 계획서와 맞추기

반영할 때마다 결과서의 행을 지금 계획서에 맞춘다. 순서도 계획서를 따른다.

| 계획서에서 | 결과서에서 |
|-----------|-----------|
| 행이 추가됐다 | 행이 생기고 이번 대조로 판정한다 |
| 케이스를 고쳤다 (행 지문이 바뀜) | 케이스 칸이 새 원문이 되고, 이번 근거로 Pass 가 아니면 `미검증 — 케이스 변경` |
| 행을 지웠다 | 결과서에서도 빠진다. 사람이 적어 둔 값이 있었으면 출력에 알린다 (반영 전 사본에 남는다) |
| 개정만 했다 (행은 그대로) | 머리말 `근거` 의 계획서 버전을 올리고 개정이력에 `보완` 한 행 |

계획서 표가 깨졌거나(칸 수가 머리글과 다름) 테스트ID 가 겹치면 결과서를 쓰지 않는다 — 계획서부터 고친다.

## 개정이력

- 처음 만들 때 `1.0 / 신규`.
- 반영으로 결과서가 바뀌면 `+1.0`. 사유는 무게 순서(`삭제` > `변경` > `추가` > `보완`)로 가장 무거운 것 —
  계획서에서 행이 빠졌으면 `삭제`, 케이스가 바뀌었으면 `변경`, 행이 늘었으면 `추가`, 결과만 바뀌었으면 `보완`.
- **바뀐 것이 없으면 개정이력을 올리지 않는다.** 그날 대조했다는 기록은 수행대장 반영 이력에 남는다.
