# IM-03 단위테스트결과서 양식

DE-13 단위테스트계획서의 행을 그대로 옮기고, 행마다 수행 결과를 적는 고객 산출물이다.
`/gx-단위테스트실행` 이 만들고 갱신한다. 코드 IM-03 은 화면 축 시절 gx-pm 의 단위테스트결과서(`archive/commands/gx-테스트결과서.md`)와 같은 자리를 잇는다. **계획서는 건드리지 않는다** — 계획서는 약속, 결과서는
그 약속을 시험한 기록이라 따로 둔다. 계획서를 고치는 것은 `/gx-단위테스트계획서` 뿐이다.

## 파일 형식
Excel (.xlsx). 원본은 프로젝트 폴더의 `{시스템코드}-단위테스트결과서.md` 이고 xlsx 는 이 md 에서 뽑는다.
**xlsx 를 직접 고친 내용은 반영되지 않는다** — 다음 추출 때 md 내용으로 덮인다. 결과를 바꾸려면 md 를
고치거나 다음 반영의 승인 화면에서 말한다.

결과서는 하나를 계속 갱신한다. 반영으로 바뀔 때마다 개정이력이 쌓이고, 쓰기 직전의 결과서는
`backup/{파일 이름}_{YYMMDD}.md` 로 남는다(같은 날 여러 번이면 그날 처음 원본).

## 시트 구성
1. **개정이력** — 규칙의 정본은 `templates/revision-history.md`
2. **단위테스트결과** — 본문 데이터

## 머리말

```markdown
# IM-03 단위테스트결과서 — {사업명}

> 생성: /gx-단위테스트실행 · 2026-10-14 16:20
> 근거: DE-13 v2.0
```

`근거` 는 이 결과서가 맞춘 계획서 버전이다(`templates/revision-history.md` §근거 표기).
계획서가 그 뒤 개정되었으면 결과서가 낡은 것이다 — 다음 반영이 계획서에 맞춘다.

## 본문 컬럼 (정본)

| # | 컬럼 | 값 규칙 |
|---|------|--------|
| 1 | 테스트ID | 계획서 원문 |
| 2 | 연계기능ID | 계획서 원문 |
| 3 | 연계요구사항ID | 계획서 원문 |
| 4 | 요구사항명 | 계획서 원문 (옛 계획서에 이 열이 없으면 결과서에도 없다) |
| 5 | 사전조건 | 계획서 원문 |
| 6 | 입력 | 계획서 원문 |
| 7 | 기대결과 | 계획서 원문 |
| 8 | 사후조건 | 계획서 원문 |
| 9 | 의존성 | 계획서 원문 |
| 10 | 테스트담당자 | Pass·Fail 행은 이번 시험 수행 책임자. 프로파일 작성자 또는 지정한 실명을 쓰며 커밋 작성자로 추정하지 않는다 |
| 11 | 수행일 | Pass·Fail 행은 이번 실행의 `finished_at` 기준 완료일. `YYYY.MM.DD` |
| 12 | 결과 | `Pass` / `Fail` / `미구현` / `미검증` — 정의는 아래 §결과 상태 |
| 13 | 사유 | 실제 관측을 근거로 이 상태를 판정한 이유 한 줄 |
| 14 | 실제결과 | 이번에 관측한 반환값·화면 문구·데이터 변화. 수행하지 못했으면 막힌 원인을 적고 응답을 만들어 쓰지 않는다 |

**1~9열은 계획서에서 옮긴 원문이라 결과서에서 고치지 않는다.** 반영할 때마다 계획서 원문으로 다시
맞추므로, 결과서에서 고친 케이스 칸은 되돌아간다. 케이스를 바꾸려면 계획서를 고친다.

xlsx 의 세로 병합과 `〃` 풀이도 계획서와 같다 — `templates/DE-13-unit-test-plan.md`
§xlsx 에서는 기능 단위로 묶인다. 두 문서를 나란히 펼쳤을 때 모양이 같아야 한다.

## 결과 상태

결과는 네 값이다. 빈칸이 「안 한 것인지, 기능이 없는 것인지, 일부러 뺀 것인지」
알 수 없게 두지 않으려고, **모든 행이 넷 중 하나와 사유를 갖는다.**

| 결과 | 뜻 | 사유 첫머리 (예) |
|------|----|----------------|
| `Pass` | 이번 로컬 시험의 사전조건·입력이 유효하고 필요한 기대결과·사후조건을 모두 관측하여 일치했다 | `실행 확인 — 오류 안내와 저장 없음 확인` |
| `Fail` | 유효한 사전조건·입력으로 실제 수행했으나 기대결과 또는 사후조건에 구체적인 불일치가 있다 | `기대결과 불일치 — 오류 안내 대신 성공 안내`, `사후조건 불일치 — 3건 중 0건 저장` |
| `미구현` | 라우트·화면·명시적 미구현 응답 등을 확인하여 기능이 아직 제공되지 않음을 확인했다 | `기능 미제공 — 삭제 기능 미구현 확인` |
| `미검증` | 환경·도구·데이터 문제, 미실행·일부 관측, 기준 미확정 등으로 판정하지 못했다 | `실행 환경 미준비`, `브라우저 도구 없음`, `선행조건 미충족`, `일부만 관측 — 저장 없음 미확인`, `케이스 변경`, `제외 — 통합 환경 필요`, `비기능 — 측정 환경 미준비`, `기준값 미확정` |

HTTP 성공 여부만으로 판정하지 않는다. 예외 케이스의 예상 오류 응답은 Pass일 수 있고,
HTTP 200이어도 데이터가 잘못 저장되면 Fail이다. 404 한 번이나 테스트 코드 부재는 기능 미제공의 근거가
되지 않는다. 비기능 행도 조건·기준을 준비할 수 있으면 실제 측정한다. 준비하지 못한 비기능 행만
`미검증 — 비기능 …`으로 남긴다. 새 미구현·미검증 판정의 수행일·담당자는 비운다.

이전 자동 Pass·PM 확인은 이번 Pass로 자동 승계하지 않는다. PM의 말만으로 새 Pass를 기록하지 않으며
현재 실행 증적이 필요하다. 사람이 수정한 수행 칸(`실제결과` 포함)은 **계획 내용이 같은 행만** 승인 시
기본 유지(`keep`)하고 이번 관측은 수행대장에 함께 남긴다. 케이스가 바뀐 행(`case_changed`)에는
새 실행 증적의 판정을 반영하고 옛 값은 백업에 보존한다. 유지한 과거 값을 이번 시험에서 통과한 결과로
설명하지 않는다.

계획 내용이 같아 유지하는 사람의 결과에 사유가 없으면 `기존 기입 — 사유 미기재` 로 둔다 — 그 결과는 지키되 빈 사유
칸은 남기지 않는다.

사유는 판정 이유, 실제결과는 관측 사실이다. 예를 들어 사유는 `실행 확인 — 오류 안내와 저장 없음 확인`,
실제결과는 `HTTP 400, "헤더 형식 오류"; 업로드 전후 TB_SRC_FILE 4건 유지`로 쓴다. 전체 요청·응답과
화면·데이터 확인 파일은 `증적/{시스템코드}/{run_id}/`에 보존하고 내부 수행대장에 연결한다.

**수행률 = Pass ÷ (전체 − 미검증 중 사유가 `비기능`·`기준값 미확정`·`제외` 인 행).**
기존 지표 이름을 유지하지만 의미는 판정 대상의 **통과율**이다. 실제 측정한 비기능 Pass·Fail은 분모에
포함한다. Fail·미구현·그 밖의 미검증도 분모에 남는다.

## 계획서와 맞추기

반영할 때마다 결과서의 행을 지금 계획서에 맞춘다. 순서도 계획서를 따른다.

| 계획서에서 | 결과서에서 |
|-----------|-----------|
| 행이 추가됐다 | 행이 생기고 이번 실제 수행으로 판정한다 |
| 케이스를 고쳤다 (행 지문이 바뀜) | 새 조건으로 수행한 증적의 판정을 반영한다. `keep`은 허용하지 않고 옛 값은 백업에 보존한다 |
| 행을 지웠다 | 결과서에서도 빠진다. 사람이 적어 둔 값이 있었으면 출력에 알린다 (반영 전 사본에 남는다) |
| 개정만 했다 (행은 그대로) | 머리말 `근거` 의 계획서 버전을 올리고 개정이력에 `보완` 한 행 |

계획서 표가 깨졌거나(칸 수가 머리글과 다름) 테스트ID 가 겹치면 결과서를 쓰지 않는다 — 계획서부터 고친다.

## 개정이력

- 처음 만들 때 `1.0 / 신규`.
- 반영으로 결과서가 바뀌면 `+1.0`. 사유는 무게 순서(`삭제` > `변경` > `추가` > `보완`)로 가장 무거운 것 —
  계획서에서 행이 빠졌으면 `삭제`, 케이스가 바뀌었으면 `변경`, 행이 늘었으면 `추가`, 결과만 바뀌었으면 `보완`.
- **바뀐 것이 없으면 개정이력을 올리지 않는다.** 그날 대조했다는 기록은 수행대장 반영 이력에 남는다.
