# 승인 루프 프로토콜

모든 커맨드의 체크포인트에서 적용되는 공통 상호작용 규칙.
각 커맨드 파일에서 `[승인 루프 프로토콜 적용]`으로 참조한다.

## 질문하기 전에

질문은 사용자 판단이 필요한 지점에만 둔다. 진행 안내·파일 경로·다음 제안은 질문이 아니다.
프로파일·자료·현재 대화에서 답을 먼저 찾고, 이미 정한 실행 범위·처리 방식·출력 형식을 다시 묻지 않는다.
사용자가 특정 행 수정, 이어서 작업, Excel 생성까지 요청했다면 그 범위는 지시로 확정돼 있다.
새로운 범위 변경·원문 충돌·필수 미결은 따로 확인하며, 응답 없음은 승인으로 보지 않는다.

산출물 내용·개정이력·출력 형식은 한 검토에 함께 제시한다. 승인한 내용 그대로 저장할 때
같은 개정이력과 xlsx 여부를 따로 재승인받지 않는다. 큰 표는 전체를 대화에 반복하지 않고
건수·변경 행·미결·파일 링크를 먼저 보여주며 요청하면 전체 표를 펼친다.

**도구별 사용자 입력**:

Claude에서는 아래 `AskUserQuestion` 형식을 사용한다. Codex에서는
`skills/gx-pm-workflow/SKILL.md`에 따라 실제 제공된 입력 도구의 스키마로 변환한다.
비동기 질문은 **질문 제출과 응답 수신이 다르다**. 해당 판단에 의존하는 작업은 응답까지
보류하고, 독립적인 읽기·검토는 진행할 수 있다. 질문 도구가 없으면 대화로 묻고 응답을 기다린다.

1. 필요한 사용자 판단은 현재 환경의 질문 도구로 받는다. Claude는 **AskUserQuestion**, Codex는 위 연결 규칙을 따른다.
2. 질문을 출력하거나 비동기 도구를 호출한 것만으로 승인했다고 보지 않는다. 실제 응답까지 관련 결정을 보류한다.
3. 아래는 Claude 도구의 인자 구조다. **`questions` 배열**이며, 각 질문은 `header`·`options`·`multiSelect`를 함께 요구한다:

```json
{
  "questions": [
    {
      "question": "질문 내용을 여기에 작성한다.",
      "header": "12자 이내 라벨",
      "multiSelect": false,
      "options": [
        { "label": "선택지 1 (5단어 이내)", "description": "이 선택지를 고르면 무엇이 달라지는지" },
        { "label": "선택지 2",              "description": "..." }
      ]
    }
  ]
}
```

**인자 규칙**

| 인자 | 규칙 |
|------|------|
| `questions` | 1~4개. 여러 항목을 한 번에 물을 때 배열로 묶는다 |
| `question` | 질문 전문. 물음표로 끝낸다 |
| `header` | **12자 이내** 칩 라벨 (예: `승인`, `시안 선택`, `추출 형식`) |
| `options` | **2~4개**. 각 항목은 `label`(5단어 이내) + `description` |
| `multiSelect` | 복수 선택 허용 여부. 승인·시안 선택은 `false` |

- **"기타" 선택지를 직접 넣지 않는다** — 도구가 자동으로 제공한다.
- 권장안이 있으면 **첫 번째 옵션**에 두고 `label`에 `(권장)`을 붙인다.
- 자유 입력(수정 지시, 담당자명 등)은 도구가 지원하면 옵션 없이 받는다. Claude처럼 옵션이
  필수이면 실제로 선택 가능한 제안값·보류만 두고 직접 입력 경로를 안내한다. 값 수집에 `승인`을 끼워 넣지 않는다.

4. 아래 예시들의 코드 블록은 **`question` 인자에 넣을 본문**이다. 위 구조로 감싸서 호출한다.
5. 질문·승인·선택 요청에 위 형식을 적용한다. **안내만 하는 단계에는 질문 도구를 호출하지 않는다.**

### 질문 문구와 선택지

- 질문 하나에 판단 하나를 담는다. 왜 필요한지, 대상 ID, 제안값, 답에 따른 변화가 짧게 보여야 한다.
- 보통 1~3개씩 묶고 각 도구의 실제 한도를 지킨다. 4개 정책 질문도 도구 한도가 작으면 나눠 묻는다.
- 선택지는 의미가 겹치지 않게 쓰고 권장안을 먼저 둔다. 값 입력이 필요하면 정확한 입력 예를 준다.
- Codex의 자유 입력 지원 질문에는 불필요한 승인 옵션을 만들지 않는다. 경로나 담당자명을 묻는데
  「승인」을 선택할 수 있게 하지 않는다. 파일 업로드가 필요한 질문은 텍스트 전용 입력 도구로 받지 않는다.
- 「수정할 내용 입력」을 골랐지만 수정 내용이 없으면 구체적인 내용을 기다린다. 이를 승인으로 처리하지 않는다.
- 일부 답만 왔으면 답한 항목만 확정한다. 사용자 수정 지시는 해당 항목을 갱신하며 무관한 승인은 유지한다.

---

### 실행 지시와 내용 확정의 범위

`명세를 만들어줘`는 작업 범위의 지시이며 아직 제시하지 않은 업무 기준·CQ의 수락이 아니다.
구체적으로 제시한 CQ 번호·제안값·문서 범위를 명시한 수락만 그 판단에 적용한다.
질문은 원문·대상 ID·AI 추천과 근거·대안과 영향·직접 의견·보류 경로를 포함한다
(`skills/review-confirmations/SKILL.md`). 자료·전제·제안이 바뀌면 영향을 받은 승인만 다시 확인한다.

명세 5종 모두 전체 내용 확정 **전에 review-confirmations**를 적용한다. 초안 저장은 가능하지만
미결을 남긴 채 `확정`·`승인 완료`로 표시하지 않는다. 낱개 커맨드의 저장 뒤 검토는 신규 미결의 최종 대조다.
파이프라인은 각 게이트에서 같은 규칙을 적용한다. 미결이 0건이어도 실측하지 않은 시험을 Pass로 만들지 않는다.

## 산출물 문장·표기 기준 (정본)

AN-02·AN-03·DE-08·DE-13·AN-05·IM-03, 확인요청서와 개정이력에 적용한다. 템플릿의 설명·예시·
작업 지시를 제출 문서에 복사하지 않는다. 사용자와의 대화는 정중한 존댓말, 산출물 본문은 아래 업무 문체로 구분한다.
프로젝트의 승인된 용어·문서 작성 기준이 있으면 먼저 적용하며 표의 열·ID·상태값은 각 양식 정본을 유지한다.

### 문체와 문장 구성

- 설명·처리는 `~한다.`, 의무 조건은 `~해야 한다.`로 쓴다. 요구사항의 권고·허용·금지를 의무로 바꾸지 않는다.
  `검토할 수 있다`를 `구현해야 한다`로 바꾸는 식으로 원문의 구속력을 높이지 않는다.
- 제목·요구사항명·기능명·논리명은 간결한 명사구로 쓴다. 설명·처리·기대결과는 동작이나 관측 결과가 분명한
  문장으로 쓴다. 기본값·코드·시험 입력·상태·개정 사유는 각 열에 맞는 값이나 짧은 구를 유지한다.
- 한 문장에는 하나의 판단 또는 처리 단계를 담는다. 주체가 바뀌면 명시하고, 조건은 동작 앞에 둔다.
  `처리한다`, `관리한다`만 쓰지 말고 대상·조건·결과를 드러낸다. 장문 처리 절차는 번호와 셀 내 줄바꿈으로 나눈다.
- `~해줍니다`, `~하면 돼요`, `~할 예정`, `상기`, `제반`, `기능을 수행할 수 있도록 지원한다` 같은 구어체·불필요한
  수식·중복 표현을 줄인다. 명확한 원문 표현은 존중하고, 단순 문체 교정을 범위 확대로 사용하지 않는다.
- `적절히`, `신속하게`, `충분히`, `정상적으로`처럼 판정하기 어려운 표현은 근거에서 구체화한다. 기준이 없으면
  질문으로 남긴다. 그럴듯한 숫자·역할·정책·오류 문구를 넣어 문장만 완성하지 않는다.

### 용어·수치·근거

- 같은 개념에는 같은 용어를 쓴다. 로그인/로그온 등 혼용은 프로젝트 용어를 따르고, `사용자`·`신청자`·`관리자`처럼
  역할이 다르면 합치지 않는다. 약어는 필요한 경우 처음 한 번 풀어 쓰며 모르는 약어를 임의로 확장하지 않는다.
- ID, 코드값, API 경로, 테이블·컬럼명, 파일명, 인용문, 입력 문자열과 관측 원문은 문체 교정 대상에서 제외한다.
  특히 입력 문자열의 공백·대소문자·기호를 보존한다. 원문 인용과 요약·해석을 구분하고 위치를 남긴다.
- 수치·단위·범위·경계 포함 여부를 유지한다. MB와 MiB, 글자 수와 바이트, 초와 밀리초를 근거 없이 바꾸지 않는다.
  날짜는 서술·개정 표에서 `YYYY.MM.DD`로 맞추되 JSON·API·원문·기존 파일명에 정해진 형식은 유지한다.
- 빈칸의 의미는 양식별로 따른다. `없음`(해당 항목이 없음), `해당 없음`(적용 대상 아님), `[미확정]`(결정 필요)을
  혼용하지 않는다. DE-13 수행 칸과 CQ 미응답 칸처럼 빈칸이 정상인 곳에 임의의 대시·완료값을 채우지 않는다.
- `[가정]`·`[미확정]`, 근거 위치, 검토 상태와 누락 표기는 문체 정리로 지우지 않는다. 조회·계획만으로
  `검증 완료`, `정상 동작`, `준수`를 쓰지 않는다. IM-03 판정은 실제 수행 증적을 따른다.

정중하게 쓰고, 확인요청서에는 판단 내용과 근거가 남도록 작성한다.

### 전달 전 문장 검토

각 저장·추출 전에 문체 혼용, 동일 개념의 용어 혼용, 불명확한 주체·조건, 반복·군더더기, 근거 없는 단정과
템플릿 잔여 문구를 확인한다. 문체만 다듬은 변경은 문서 정비로 구분하며 업무 기준 변경과 섞지 않는다.
원문 의미·수치·ID·승인 범위가 달라질 수 있으면 교정으로 처리하지 않고 변경 전후와 질문을 제시한다.

## 0. 프로젝트 프로파일 로드 + 기존 산출물 감지

모든 커맨드의 워크플로우 시작 전에 다음 두 스킬을 순차 실행한다.

### 0-1. 프로젝트 프로파일 로드

**load-project-profile** 스킬로 활성 프로젝트를 확인한다.

- 프로파일이 없으면 → `/gx-프로젝트설정`을 먼저 실행하라고 안내 후 커맨드 종료
- 프로파일이 있으면 → 활성화 후 이후 단계에서 프로파일 정보를 자동 사용
  - `systemCode` → 산출물 파일명, 채번 규칙의 접두 후보
  - `prefix`, `networkType` → **현재 소비처 없음** (`templates/project-profile-schema.md` §소비처 없는 필드)
  - `framework`, `db` → DDL 문법·데이터타입 해석에 사용
  - `idNaming` → 요구사항ID·기능ID·테스트ID 채번에 사용
  - `type` → 커맨드 워크플로우 분기에 사용
  - `author` → 산출물 작성자명에 사용
  - `assets.sourcePath` → 소스코드 스캔 경로에 사용

프로파일에 이미 있는 정보(시스템코드, 접두어 등)를 사용자에게 다시 물어보지 않는다.

### 0-2. 기존 산출물 감지

**detect-existing-artifact** 스킬로 활성 프로젝트 폴더에 해당 산출물 파일이 있는지 확인한다.

- 파일이 없으면 → 새로 생성 워크플로우 진행 (별도 안내 없음)
- 파일이 있으면 → 요청에서 처리 방식이 정해졌는지 먼저 확인한다. 「3번만 수정」은 열기,
  「기존 것에 추가」는 이어쓰기다. 의도가 불명확할 때만 AskUserQuestion으로 3가지 선택지 제공:

  1. **이어쓰기** — 기존 내용 유지 + 새 항목 추가 (ID 이어서 부여)
  2. **새로쓰기** — 기존 파일 backup/ 폴더에 백업 후 처음부터 재생성
  3. **열기** — 기존 내용 불러와서 특정 항목만 수정/삭제

상세 규칙: `skills/detect-existing-artifact/SKILL.md` 참조

### 0-3. 프로젝트 유형별 워크플로우 분기

프로파일의 `type`에 따라 해당 커맨드의 워크플로우가 분기된다:

| type | 분기 | 설명 |
|------|------|------|
| `new` (A) | 정방향 생성 | 기존 워크플로우 그대로 실행 |
| `enhancement` (B) | 기존 + 추가 | 기존 산출물 로드 → 이어쓰기 모드 기본값 |
| `documentation` (C) | 역방향 생성 | 소스코드/DB에서 산출물 역생성 |
| `change` (D) | 부분 갱신 | 변경 대상만 식별 → 해당 항목만 갱신 |

각 커맨드는 자신의 워크플로우 파일에서 유형별 분기 상세를 정의한다.

## 1. 시안/대안 감지 (detect-alternatives)

### 적용 대상

이 단계는 **입력 문서에 확정되지 않은 선택지가 들어올 수 있는 커맨드**에서만 실행한다.

| 커맨드 | 실행 | 감지 대상 |
|--------|:---:|---------|
| `/gx-요구사항정의서` | ● | RFP의 1안/2안, 미결정 항목 |
| `/gx-명세일괄` | ● | 위와 같다. 구성 5종 중 요구사항 단계에서 1회 실행하며 **게이트로 이월하지 않는다** |
| `/gx-기능명세서` | ○ | 요구사항에서 분해하는 단계라 새 선택지가 들어오지 않음 |
| `/gx-테이블정의서` | ○ | **역생성 전용이라 스키마 설계 선택지가 없음.** 신규 컬럼명은 시안이 아니라 표준용어 MCP 판정이며, `decisionRequired` 는 그 자리에서 묻는다 |
| `/gx-단위테스트계획서` | ○ | 상위 산출물(기능명세·테이블정의)에서 이미 확정됨 |
| `/gx-추적매트릭스` | ○ | 기존 데이터 대조라 대안이 없음 |

● 실행 / ○ 미실행

> 미실행 커맨드에서도 사용자가 승인 루프 중에 대안을 제시하면 그때 선택을 받는다.
> 다만 워크플로우의 고정 Step으로 두지는 않는다.

### 감지 패턴

산출물 생성 **전**, 입력 데이터에서 다음 패턴을 감지한다:

| 패턴 | 예시 |
|------|------|
| N안 표기 | "1안", "2안", "제1안", "제2안" |
| 알파벳 안 | "A안", "B안" |
| 방안/대안 | "방안 1", "방안 2", "대안", "Alternative" |
| 선택 접속사 | "또는", "혹은"으로 연결된 상호배타적 선택지 |
| 섹션 마커 | 제목에 "(대안)", "(선택)", "(옵션)" 포함 |

감지되면 **AskUserQuestion**으로 선택을 요청한다:

```json
{
  "questions": [{
    "question": "시안 선택이 필요합니다. {주제}에 대해 어떤 시안으로 진행할까요?",
    "header": "시안 선택",
    "multiSelect": false,
    "options": [
      { "label": "1안 — {요약}", "description": "요구사항 {N}건, 기능 {N}건 예상" },
      { "label": "2안 — {요약}", "description": "요구사항 {N}건, 기능 {N}건 예상" },
      { "label": "병행", "description": "양쪽 모두 포함. 산출물 양이 약 2배가 됩니다" }
    ]
  }]
}
```

**규칙**: 사용자가 시안을 선택할 때까지 산출물 생성을 진행하지 않는다.
"병행" 선택 시에만 양쪽 모두를 산출물에 포함하되, 각 시안을 명확히 구분 표기한다.

## 2. 단계별 승인 절차

각 Step의 산출물 생성 후 다음 절차를 따른다:

### 2-1. 결과 표시

해당 단계의 변경 요약·미결·개정이력 초안·파일 링크를 출력한다. 작은 표는 전체를,
큰 표는 변경·확인 대상 행을 우선 제시한다. **manage-revision-history**의 초안을 이 검토에 포함한다.
주요 작성 판단은 확인한 자료·적용 기준·작성 이유를 묶어 최대 3건만 짧게 설명한다.
확인이 필요한 항목의 자세한 근거는 `templates/confirmation-request.md`의 「작성한 이유를 함께 설명한다」에
따라 기존 칸에 적는다. 근거 설명을 별도 승인 질문이나 추가 관리대장으로 만들지 않는다.

### 2-2. 승인 요청 (AskUserQuestion 필수)

산출물 표와 개정이력 초안을 함께 제시한다. 아직 승인받지 않은 판단이 있으면 질문 도구로
응답을 기다린다. 같은 범위에 이미 받은 승인·구체적인 작업 지시는 재사용한다.

```json
{
  "questions": [{
    "question": "추출된 {산출물명} {N}건을 확인해주세요. 이대로 확정할까요?",
    "header": "승인",
    "multiSelect": false,
    "options": [
      { "label": "승인", "description": "이대로 확정하고 다음 단계로 진행합니다" },
      { "label": "수정할 내용 입력", "description": "예: 3번 행의 요구사항명을 'XX 관리'로 변경 / 5번 행 삭제" }
    ]
  }]
}
```

> 위 예시는 Claude의 선택형 승인 질문이다. 사용자는 직접 입력으로 수정 지시를 쓸 수 있다.

### 2-3. 수정 반영

사용자가 수정을 요청하면:
1. 피드백을 반영하여 표를 **재생성**
2. 변경된 부분을 간략히 안내 ("→ 3건 변경됨")
3. 요청을 넘어선 새 판단이 있으면 2-2로 돌아간다. 요청한 수정만 정확히 반영했으면 변경 내용과 파일을 안내한다.

### 2-4. 확정

사용자가 다음 중 하나를 말하면 해당 단계를 확정하고 다음으로 진행한다:
- "승인", "OK", "확인", "넘어가", "다음", "좋아", "ㅇㅋ"

**핵심 규칙**: 위 단어 목록은 예시다. 자연어로도 대상과 범위가 명확하면 승인이다.
이미 받은 구체적인 작업 지시도 같은 범위에서 재사용한다. 침묵·시간 경과는 승인이 아니다.

## 3. 정보 수집 (AskUserQuestion 필수)

프로젝트 기본 정보, 프레임워크 선택 등 사용자 입력이 필요한 단계에서도
반드시 **AskUserQuestion 도구**를 사용한다.

여러 항목은 `questions` 배열에 나눠 담는다 (최대 4개).
시스템코드·담당자명처럼 **정해진 선택지가 없는 값**은 직접 입력을 받는다.
옵션이 필수인 도구에서는 근거가 있는 제안값만 제시한다. 이미 자료에서 확인된 값은 다시 묻지 않는다.

```json
{
  "questions": [
    {
      "question": "망 구분은 어떻게 되나요?",

    {
      "question": "프레임워크는 무엇인가요?",
```

## 4. xlsx 추출

사용자가 요청한 출력 형식을 우선한다. Excel을 이미 요청했으면 추출 여부를 다시 묻지 않는다.
정해지지 않았을 때만 최종 검토에 아래 선택을 포함한다. 파이프라인에서는 종료 시 한 번 정한다:

```json
{
  "questions": [{
    "question": "승인된 산출물을 xlsx로 추출할까요?",
    "header": "추출 형식",
    "multiSelect": false,
    "options": [
      { "label": "xlsx 추출 (권장)", "description": "공공 양식 컬럼 순서에 맞춰 생성합니다. 복붙용" },
      { "label": "마크다운만 저장", "description": "xlsx 없이 .md 파일만 남깁니다" }
    ]
  }]
}
```

추출 시:
1. `utils/export-xlsx.py` 스크립트를 **`--strict --separate` 와 함께** 실행
2. 실제 공공 산출물 Excel 양식의 **컬럼 순서에 맞춰** 생성
3. 생성된 xlsx 파일 경로를 사용자에게 안내

`--strict`는 필수 열·중복 헤더·행 길이·고유 ID와 미확정/가정 표식을 검사한다. 명세 파일의 초안 표시와
`requirements-state.json`의 해당 문서 상태·미결 CQ·미반영 상위 변경·내용 지문도 대조한다. 검토용은
`--strict --draft --separate`로 제공한다. 확인요청서 자체는 미결 관리용이므로 질문이 남아도 출력할 수 있다.
검증 오류가 나면 본문·상태를 바로잡으며, 최종본을 내기 위해 검사를 끄지 않는다. 응답 파일의 재생성은
`templates/confirmation-request.md`의 사람이 작성한 Excel 응답 보호 규칙을 따른다.

> **`--separate` 는 선택이 아니다.** 빼면 문서 여러 개가 `{시스템코드}-산출물.xlsx` 한 권으로
> 합쳐지고 개정이력 시트가 `개정이력_1`·`개정이력_2` … 로 번호가 붙는다. 산출물 템플릿의
> 「시트 구성」은 전부 `1. 개정이력 2. 본문` 이라 **문서마다 한 권**을 전제한다.
> 한 문서만 추출할 때도 붙인다 — 파일명이 `{시스템코드}-산출물.xlsx` 대신
> `{시스템코드}-{산출물명}.xlsx` 가 된다.

## 5. 워크플로우 전체 규칙

1. **한 단계씩 진행**: Step N이 승인되어야 Step N+1을 시작한다
2. **되돌림 허용**: 사용자가 "Step 2로 돌아가줘" 등을 요청하면 해당 단계부터 재시작
3. **중단 허용**: 사용자가 "여기까지만" 등을 말하면 현재까지 확정된 내용을 저장
4. **컨텍스트 유지**: 이전 단계에서 승인된 데이터를 다음 단계에서 참조
5. **실제 응답 확인**: 입력·승인이 필요한 경우 현재 환경의 질문 도구를 쓰고 실제 답을 기다린다. 도구 선택과 재질문 생략은 이 문서의 「질문하기 전에」를 따른다.
