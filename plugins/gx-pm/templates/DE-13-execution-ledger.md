# DE-13 단위테스트 수행대장 양식

`skills/apply-test-results` 가 `utils/test-evidence.py write` 로 단위테스트결과서와 **함께** 쓰는 **내부 증적
파일**이다. 손으로 고치지 않는다 — 도구가 매번 다시 쓰고, 옛 담당자 매핑과 반영 이력은 지난 내용을 그대로
옮긴다. 고객사 산출물이 아니라 xlsx 로 추출하지 않는다. 파일은 프로젝트 폴더의
`증적/{시스템코드}-단위테스트수행대장.md` 다. 산출물과 같은 폴더에 두지 않는 이유는 `export-xlsx.py --dir .`
가 그 폴더의 md 를 모두 xlsx 로 뽑기 때문이다 — 내부 증적이 고객 납품물에 섞인다.

## 왜 따로 두나

단위테스트결과서(`templates/IM-03-unit-test-result.md`)에는 결과·사유·실제결과가 나간다. 그 관측이
**어느 실행의 어떤 요청·응답·화면·데이터 확인에서 나왔는지**, 결과 칸의 값을 **누가 썼는지**는 내부
수행대장에 남긴다. 원본 증적은 `증적/{시스템코드}/{run_id}/execution.json` 및 같은 실행 폴더의 파일로
영구 보존한다. 실행 증적은 승인 전에도 저장하고 결과서·수행대장은 승인 후에 함께 쓴다.

| 남기는 것 | 없으면 |
|----------|-------|
| 근거 (run_id·행별 요청·응답·화면·데이터 확인 파일) | 「이 Pass 는 무엇으로 확인했나」에 답할 수 없다 |
| 이번 실제결과·막힌 원인 | 응답 불일치와 미실행을 가릴 수 없다 |
| 행 지문 | PM 이 계획서 케이스를 고친 뒤에도 옛 Pass 가 남는다 |
| 지난 상태·사유·실제결과·수행일·담당자 | 결과서의 값을 이 스킬이 썼는지 사람이 썼는지 가릴 수 없다 |
| 옛 담당자 매핑 | 이전 기록의 작성자 표기를 해석할 수 없다. 신규 담당자 조회에는 쓰지 않는다 |
| 반영 이력 | 수행률이 언제 얼마였는지 보고할 근거가 없다 |

## 열 규칙

| 열 | 값 규칙 |
|----|--------|
| 상태 | `Pass` / `Fail` / `미구현` / `미검증` — 정의는 `templates/IM-03-unit-test-result.md` §결과 상태, 판단 규칙은 `skills/apply-test-results` §판정. 사람 값을 유지한 행도 이번 실행의 판정을 쓰고, 결과서에 남은 값은 비고에 둔다 |
| 사유 | 이번 관측에 따른 판정 이유. 사람 값을 유지한 행은 결과서 사유와 다를 수 있다 |
| 근거 | 해당 run_id의 `execution.json`과 행별 요청·응답·화면·데이터 확인 파일 경로. 토큰·쿠키·비밀번호는 저장 전에 가리고 가린 파일의 SHA-256을 실행 증적에 기록한다. 실행 불가 행도 원인을 기록한 execution.json을 연결한다 |
| 수행일·담당자 | 이번 Pass·Fail만 `finished_at`의 완료일과 실제 시험 수행 책임자를 적는다. 미구현·미검증은 비운다. 커밋 작성자 매핑에서 가져오지 않는다 |
| 행 지문 | 계획서 행의 사전조건·입력·기대결과·사후조건으로 계산한다. 도구가 쓰는 순간의 계획서에서 직접 계산한다 |
| 비고 | 고객 문서에 나가지 않는 내부 메모 — `기존 기입 유지(값, 담당자, 날짜)`(사람 값을 유지하면 도구가 붙인다), `Pass 철회(이전 Pass 날짜)`, 제외 지정일, 계획서 변경 등 |
| 실제결과 | 이번에 관측한 응답·문구·데이터 변화 또는 실행 불가 원인. 기존 8열 뒤에 붙인다. 사람 값을 유지한 행도 이번 실제결과를 적는다 |

## 다시 쓰는 것과 쌓는 것

- **수행 현황은 반영할 때마다 전체를 다시 쓴다.** 지금 계획서의 모든 행이 한 번씩 나온다.
- **결과서와 수행대장은 한 번에 쓴다.** 결과서만 바뀌고 수행대장이 따라오지 못하면 다음 반영 때 이
  스킬이 쓴 값을 사람 값으로 잘못 가린다. 그래도 결과서 버전이 반영 이력의 마지막 `결과서 버전` 과 다르면
  (손 수정, 끊긴 반영) 도구가 알리고, 다른 값은 사람 값으로 보여준다. 계획 내용이 같은 행만 유지할 수 있다.
- **이전 Pass·PM 확인을 이번 Pass로 승계하지 않는다.** 매번 현재 조건으로 수행하고 판정한다.
  PM의 말만으로 새 Pass를 쓰지 않는다. 계획 내용이 같은 행만 기존 사람 값을 기본 유지(`keep`)하고
  이번 관측과 차이를 병기한다. 케이스가 바뀐 행(`case_changed`)은 새 실행 증적의 판정을 반영하고
  옛 값은 백업에 보존한다.
  제외도 이번 실행 범위와 사유를 확인하여 기록한다.
- **반영 이력은 추가하고 옛 담당자 매핑은 보존한다.** 매핑은 신규 실명 조회에 쓰지 않는다. 기존 행을 고치지 않는다. 지난 행의 숫자가
  틀려 보여도 고치지 않고 이번 행만 바르게 쓴다 — 지난 행은 그때의 기록이다. 열이 바뀐
  양식이면 지난 행은 그대로 두고 이번 행부터 새 표로 쓴다.
- **반영 이력은 결과서가 바뀌지 않아도 한 행을 남긴다** — 그날 대조했다는 기록이다. 버전·건수·수행률은
  도구가 쓰는 순간의 결과서에서 센다. 건수는 결과서 `결과` 칸으로 세고, 사람 값을 유지한 행은 그 값으로
  센다(위 예시의 REB-UT-003 은 Fail) — 그래서 수행 현황의 상태를 센 숫자와 다를 수 있다.
- **수행률 = Pass ÷ (전체 − 미검증 중 사유가 `비기능`·`기준값 미확정`·`제외` 인 행).** 사유도 결과서 칸으로 본다.
  지표 이름은 유지하지만 판정 대상의 통과율이다. 실제 측정한 비기능 Pass·Fail은 포함한다.
  정수 %로 적고 괄호에 분자/분모를 둔다.
- `신규 후보`·`보강 후보` 열은 이전 이력과의 호환을 위해 남긴다. 이제 테스트 코드에서 신규 케이스를
  찾지 않으며 실행 중 발견한 계획서 명확화 후보만 선택적으로 센다. 계획서 반영은 `/gx-단위테스트계획서`가 한다.
- 머리말 `> 근거:` 의 소스 경로는 다음 반영 때 이번 경로와 비교하는 데 쓴다 — 바뀌었으면 알린다.
