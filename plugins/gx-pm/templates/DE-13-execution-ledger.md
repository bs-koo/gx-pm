# DE-13 단위테스트 수행대장 양식

`skills/apply-test-results` 가 `utils/test-evidence.py write` 로 단위테스트결과서와 **함께** 쓰는 **내부 증적
파일**이다. 손으로 고치지 않는다 — 도구가 매번 다시 쓰고, 담당자 매핑과 반영 이력만 지난 내용을 그대로
옮긴다. 고객사 산출물이 아니라 xlsx 로 추출하지 않는다. 파일은 프로젝트 폴더의
`증적/{시스템코드}-단위테스트수행대장.md` 다. 산출물과 같은 폴더에 두지 않는 이유는 `export-xlsx.py --dir .`
가 그 폴더의 md 를 모두 xlsx 로 뽑기 때문이다 — 내부 증적이 고객 납품물에 섞인다.

## 왜 따로 두나

단위테스트결과서(`templates/IM-03-unit-test-result.md`)에는 결과와 한 줄 사유까지 나간다. 그 사유가
**어느 레포의 어느 테스트, 어떤 실행 결과에서 나왔는지**, 결과 칸의 값을 **누가 썼는지**는 고객 문서에 둘
자리가 없다. 감리에서 묻는 것이 바로 그것이라 따로 남긴다.

| 남기는 것 | 없으면 |
|----------|-------|
| 근거 (레포·파일·메서드, 실행 결과 파일·verify·PM 확인) | 「이 Pass 는 무엇으로 확인했나」에 답할 수 없다 |
| 제외 사유·PM 확인 | 다음 반영 때 같은 판단을 다시 받는다 |
| 행 지문 | PM 이 계획서 케이스를 고친 뒤에도 옛 Pass 가 남는다 |
| 지난 상태·사유·수행일·담당자 | 결과서의 값을 이 스킬이 썼는지 사람이 썼는지 가릴 수 없다 |
| 담당자 매핑 | 반영할 때마다 같은 실명을 다시 묻는다 |
| 반영 이력 | 수행률이 언제 얼마였는지 보고할 근거가 없다 |

## 열 규칙

| 열 | 값 규칙 |
|----|--------|
| 상태 | `Pass` / `Fail` / `미구현` / `미검증` — 정의는 `templates/IM-03-unit-test-result.md` §결과 상태, 판단 규칙은 `skills/apply-test-results` §상태와 사유. 사람 값을 유지한 행도 이번 대조 결과를 쓰고, 결과서에 남은 값은 비고에 둔다 |
| 사유 | 이번 대조 결과의 사유 — 이 스킬이 결과서 `사유` 칸에 쓴 문장 그대로다(사람 값을 유지한 행은 결과서와 다르다) |
| 근거 | 덮는 테스트를 `{레포}:{파일}#{메서드}` 로, 여럿이면 `, ` 로. 뒤에 실행 근거를 괄호로 — `(결과 파일 2026.10.10)`, `(gx-tdd verify 2026.10.02)`, `(실행 결과 없음)`, `(PM 확인 2026.10.11)`, 낡은 결과는 `(결과 파일 2026.10.10, 이후 테스트 변경)`, 꺼 둔 테스트는 `(비활성)`. 덮는 테스트가 없는 행(`대응 테스트 없음`·`비기능`·`기준값 미확정`)은 비운다 |
| 수행일·담당자 | 이번 대조 결과의 값 — Pass·Fail 행만 채운다. 사람 값을 유지한 행도 대조 결과대로 쓴다. 상태·사유와 함께, 다음 반영 때 결과서의 값을 이 스킬이 썼는지 가리는 기준이다 |
| 행 지문 | 계획서 행의 사전조건·입력·기대결과·사후조건으로 계산한다. 도구가 쓰는 순간의 계획서에서 직접 계산한다 |
| 비고 | 고객 문서에 나가지 않는 내부 메모 — `PM 판정`, `PM 확인(날짜)`, `기존 기입 유지(값, 담당자, 날짜)`(사람 값을 유지하면 도구가 붙인다), `PM 유지(도구 기입 Pass)`, `Pass 철회(이전 Pass 날짜)`, 제외 지정일, 머지 전 브랜치 근거 등 |

## 다시 쓰는 것과 쌓는 것

- **수행 현황은 반영할 때마다 전체를 다시 쓴다.** 지금 계획서의 모든 행이 한 번씩 나온다.
- **결과서와 수행대장은 한 번에 쓴다.** 결과서만 바뀌고 수행대장이 따라오지 못하면 다음 반영 때 이
  스킬이 쓴 값을 사람 값으로 잘못 가린다. 그래도 결과서 버전이 반영 이력의 마지막 `결과서 버전` 과 다르면
  (손 수정, 끊긴 반영) 도구가 알리고, 다른 값은 사람 값으로 보여 덮지 않는다.
- **제외와 PM 확인은 승계한다.** 지난 대장의 `제외`·`PM 확인` 사유 행은 그대로 옮긴다. 단 행 지문이
  달라졌으면 `케이스 변경` 으로 바꾼다 — 바뀐 케이스에도 같은 판단이 맞는지는 사람이 본다. PM 확인
  날짜 뒤에 생긴 실행 결과가 있으면 그 결과로 판정한다.
- **반영 이력과 담당자 매핑은 쌓기만 한다.** 기존 행을 고치지 않는다. 지난 행의 숫자가
  틀려 보여도 고치지 않고 이번 행만 바르게 쓴다 — 지난 행은 그때의 기록이다. 열이 바뀐
  양식이면 지난 행은 그대로 두고 이번 행부터 새 표로 쓴다.
- **반영 이력은 결과서가 바뀌지 않아도 한 행을 남긴다** — 그날 대조했다는 기록이다. 버전·건수·수행률은
  도구가 쓰는 순간의 결과서에서 센다. 건수는 결과서 `결과` 칸으로 세고, 사람 값을 유지한 행은 그 값으로
  센다(위 예시의 REB-UT-003 은 Fail) — 그래서 수행 현황의 상태를 센 숫자와 다를 수 있다.
- **수행률 = Pass ÷ (전체 − 사유가 `비기능`·`기준값 미확정`·`제외` 인 행).** 사유도 결과서 칸으로 본다.
  정수 %로 적고 괄호에 분자/분모를 둔다.
- `신규 후보`·`보강 후보` 는 이번에 제안만 하고 계획서에 넣지 않은 케이스 수다 — 계획서 반영은
  `/gx-단위테스트계획서` 가 한다.
- 머리말 `> 근거:` 의 소스 경로는 다음 반영 때 이번 경로와 비교하는 데 쓴다 — 바뀌었으면 알린다.
