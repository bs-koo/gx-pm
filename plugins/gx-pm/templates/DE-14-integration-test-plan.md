## 사전조건 (Precondition)

시나리오 단위로 하나 기재한다. **Step 1을 시작할 수 있는 상태**를 적는다.

| 사전조건 유형 | 예시 |
|-------------|------|
| 계정·권한 | 관리자 계정으로 로그인된 상태 |
| 선행 데이터 | 과정코드 `C001` 등록 완료, 수강 신청 5건 존재 |
| 시스템 상태 | 외부 연계 시스템 정상, 배치 미수행 상태 |
| 환경 | 테스트 DB 초기화 완료 |

> 사전조건이 없으면 **다른 사람이 같은 시나리오를 재현할 수 없다.**
> "로그인 후" 같은 서술은 어느 계정·어느 권한인지가 빠져 불충분하다.

## 예외 흐름 시나리오

정상 흐름만 있는 통합테스트는 감리에서 검증 충분성 지적을 받는다.
**정상 시나리오 1건마다 최소 1건의 예외 시나리오**를 별도 ID로 만든다.

| 예외 유형 | 시나리오 예시 | 기대 결과 |
|---------|-------------|---------|
| **권한 없음** | 일반사용자 계정으로 관리자 기능 접근 | 접근 차단, 권한 없음 안내 |
| **필수 입력 누락** | 필수 항목 공란으로 다음 단계 진행 | 진행 차단, 안내 메시지 |
| **중복 데이터** | 이미 신청한 과정에 재신청 | 중복 안내, 미등록 |
| **상태 위반** | 마감된 과정에 신청 시도 | 신청 불가 안내 |
| **동시성 충돌** | 두 사용자가 같은 데이터 동시 수정 | 후행 저장 시 충돌 안내 |
| **외부 연계 실패** | 연계 시스템 무응답 (타임아웃) | 오류 안내 + 재시도 또는 폴백 동작 |
| **세션 만료** | 장시간 방치 후 저장 시도 | 재로그인 유도, 데이터 유실 안내 |
| **대용량 처리** | 최대 건수 초과 데이터 일괄 처리 | 처리 완료 또는 제한 안내 |

### 예외 시나리오 최소 기준

| 업무 흐름 성격 | 필수 예외 시나리오 |
|-------------|-----------------|
| 권한이 나뉘는 업무 | 권한 없음 |
| 신청·접수 업무 | 중복 신청, 상태 위반(마감·기간 외) |
| 승인·반려 업무 | 상태 위반(이미 처리된 건 재처리) |
| 외부 연계 업무 | 연계 실패·타임아웃 |
| 결제·정산 업무 | 중복 결제, 결제 실패 후 롤백 |

## 작성 규칙

- 통합테스트ID: `{시스템코드}-TE-{순번}` 형식
- 하나의 시나리오에 여러 Step이 포함됨
- 통합테스트ID·시나리오명·시나리오 구분·사전조건은 첫 Step에만 기재, 이후 Step은 빈칸
- 하나의 시나리오가 여러 요구사항을 커버할 수 있음
- 시나리오는 실제 업무 흐름을 반영 (단순 CRUD가 아닌 업무 프로세스 기반)
- **예외 시나리오는 정상 시나리오와 별도 ID를 부여**한다 (같은 ID의 Step으로 붙이지 않는다)
- 부적합 판정 시 결함ID를 발급하여 결함관리대장(DF-01)에 등록하고, 이 표에는 결함ID만 참조한다

## 작성 주체

> 통합테스트 시나리오는 **업무 흐름을 아는 현업·운영 담당자와 합동 작성**하는 것이 원칙이다.
> 개발자가 단독으로 작성하면 설계 단계에서 중요하게 다뤄진 항목과 예외 업무 흐름이 누락되기 쉽다.
> 현업 참여가 어려운 경우, 최소한 시나리오 목록에 대해 현업 검토·확인을 받고 그 이력을 남긴다.

## 통합테스트 vs 인수테스트

- **통합테스트 (TE-02)**: 개발팀이 수행, 기능 간 연계 검증
- **인수테스트 (TE-06)**: 발주처/감리가 수행, 요구사항 충족 검증
- 두 문서의 양식은 동일하나, 인수테스트는 발주처 관점의 시나리오
