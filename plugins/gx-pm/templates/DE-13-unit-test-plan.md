# DE-13 단위테스트계획서 양식

## 파일 형식
Excel (.xlsx)

## 시트 구성
1. **개정이력** — 규칙의 정본은 `templates/revision-history.md`
2. **단위테스트계획** — 본문 데이터

## 본문 컬럼 (정본)

| # | 컬럼 | 값 규칙 |
|---|------|--------|
| 1 | 테스트ID | 프로파일 채번(기본 `UT-001`). 기능별로 이어서 |
| 2 | 연계기능ID | AN-03 참조. **비기능 테스트는 공란** |
| 3 | 연계요구사항ID | 기능을 경유해 자동 채움. 사용자 입력 금지 |
| 4 | 요구사항명 | AN-02 의 `요구사항명` 을 그대로. 비기능이면 그 요구사항의 이름 |
| 5 | 사전조건 | `계정·권한` / `선행 데이터` / `시스템 상태` 3유형. `없음` 으로 두지 않는다 |
| 6 | 입력 | **테스터가 그대로 넣을 수 있는 값**. 항목명과 값을 짝지어 적는다. 파일이 입력이면 `testdata/` 의 실제 파일 경로를 적는다. 규칙은 아래 §입력은 그대로 넣을 수 있어야 한다 |
| 7 | 기대결과 | 관측 가능한 판정 기준. 화면 문구는 따옴표로 원문 그대로 |
| 8 | 사후조건 | 데이터 결과. 예외 케이스는 "변화 없음" 을 명시한다 |
| 9 | 의존성 | 선행 테스트ID. 없으면 `없음` |
| 10 | 테스트담당자 | 계획서는 공란 |
| 11 | 수행일 | 계획서는 공란 |
| 12 | 결과 | 계획서는 공란. `Pass` / `Fail` 2값 |

**`요구사항명` 은 ID 만으로는 무엇을 시험하는지 알 수 없어서 둔다.**
테스터가 `REB-RE-007` 을 보고 AN-02 를 펴야 한다면 이 문서 하나로 시험을 끝낼 수
없다. 이름은 AN-02 에서 가져오므로 사람이 입력하지 않는다.

## 케이스 도출 규칙 — 기능 1건에서 테스트 N건

| 도출 출처 | 만들어지는 케이스 | 최소 건수 |
|---|---|---|
| 기능 전체 | 정상 흐름 | 1 |
| AN-03 `입력항목` 의 각 제약 (길이·범위·형식) | 경계 — 최소·최대·초과 | 제약당 2 |
| AN-03 `입력항목` 의 각 필수 항목 | 예외 — 미입력 | 필수항목당 1 |
| AN-03 `처리내용` 의 각 분기 (`~이면`) | 예외 — 분기 미충족 | 분기당 1 |
| AN-03 `처리내용` 의 롤백·트랜잭션 | 예외 — 중간 실패 | 있으면 1 |
| DE-08 의 `길이`·`NotNull` | 경계·필수값 보정 | 제약이 다르면 DE-08 이 우선. DE-08 `근거` 에 `[가정]` 이 있으면 표식을 이어받는다 |

**정상 케이스만 있는 기능은 게이트에서 차단한다.**

## 비기능 요구사항의 처리

비기능 요구사항은 기능이 아니므로 AN-03 에 들어가지 않는다.
**`연계기능ID` 를 공란으로 두고 `연계요구사항ID` 만 채운 행**으로 검증한다.

| 테스트ID | 연계기능ID | 연계요구사항ID | 요구사항명 | 사전조건 | 입력 | 기대결과 | 사후조건 | 의존성 |
|---|---|---|---|---|---|---|---|---|
| UT-051 | | REQ-045 | 동시 접속 성능 | 운영 동등 환경, 데이터 10만건 | `동시 사용자=500명 / 지속=30분` | 평균 응답 3초 이내, 오류율 1% 미만 | 측정 로그 보관 | 없음 |

`연계기능ID` 가 공란인 행이 비기능 테스트다. 별도 산출물을 만들지 않는다.

**비기능 행일수록 `요구사항명` 이 필요하다.** `연계기능ID` 가 비어 있어 기능명으로
유추할 수도 없다 — 이름이 없으면 `REQ-045` 만 보고 무엇을 시험하는지 알 길이 없다.
이름은 AN-02 에서 가져온다.

## 입력은 그대로 넣을 수 있어야 한다

**이 문서 하나로 시험이 끝나야 한다.** 테스터가 `입력` 칸을 읽고 그 값을 그대로
넣어 `기대결과` 와 맞는지 보면 된다. 다른 문서를 펴야 하거나 값을 스스로
지어내야 하면 시험이 사람마다 달라진다.

### 항목명과 값을 짝지어 적는다

`유효한 값`·`정상 데이터` 처럼 쓰지 않는다. **무엇에 무엇을 넣는지**를 적는다.

| 나쁨 | 좋음 |
|------|------|
| 유효한 회원정보 | `아이디=testuser01 / 비밀번호=Test@1234! / 이메일=test01@example.com / 이름=홍길동` |
| 잘못된 이메일 | `이메일=test01@example` (도메인 최상위 라벨 없음) |
| 경계값 | `권한명=101자 [가정:100]` |

값이 여럿이면 `/` 로 끊는다. 괄호로 **왜 그 값인지**를 덧붙이면 테스터가
오타로 오해하지 않는다.

### 파일이 입력이면 실제 파일을 만든다

업로드·불러오기 기능은 파일 없이 시험할 수 없다. **`testdata/` 폴더에 실제
파일을 만들고 그 경로를 `입력` 칸에 적는다.**

```
{프로젝트폴더}/
  testdata/
    UT-014_정상_사용량_3건.csv
    UT-015_헤더순서_뒤바뀜.csv
    UT-016_용량초과_1001MB.txt   ← 크기만 맞춘 더미
```

- **파일명은 `{테스트ID}_{무엇인지}.{확장자}`** 다. 어느 케이스의 파일인지가
  이름으로 드러나야 한다.
- **내용은 그 케이스가 노리는 것만 달라야 한다.** 정상 파일과 헤더 오류 파일이
  행 수까지 다르면 무엇 때문에 실패했는지 알 수 없다.
- **큰 파일은 만들지 않는다.** 용량 상한 시험처럼 크기 자체가 조건이면 만드는
  법을 `입력` 칸에 적는다 — `1,001MB 더미 (fsutil file createnew 로 생성)`.
- 실제 개인정보·운영 데이터를 넣지 않는다. 값은 지어낸다.

`testdata/` 는 `templates/project-profile-schema.md` 가 정한 프로젝트 폴더
구조의 하나다.

## 작성 규칙

- `연계요구사항ID` 와 `요구사항명` 은 기능을 경유해 자동으로 채운다. 손으로 넣으면 AN-03·AN-02 와 어긋난다
- 예외 케이스의 `사후조건` 에 "변화 없음" 이 없으면, 안내만 띄우고 저장은 되는 결함을 못 잡는다
- 의존성이 있으면 실행 순서가 고정되고 병렬 실행이 막힌다는 뜻이다
- 개정이력 기입은 `skills/manage-revision-history` 가 담당한다
