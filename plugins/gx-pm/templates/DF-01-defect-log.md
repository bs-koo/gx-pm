# DF-01 결함관리대장 양식

테스트 레벨(단위/통합/시스템/인수)과 무관하게 **모든 결함을 하나의 번호 체계로 관리**하는 문서.
결과서(IM-03/TE-02/ST-02/TE-06)의 부적합 항목은 결함ID로 이 대장을 참조한다.

## 왜 별도 문서인가

기존에는 결과서 안에 부적합 내역·원인·조치를 직접 적었다. 그 방식의 한계:

- 같은 원인의 결함이 여러 화면에서 발견되면 **중복 기록**되고, 조치 완료 시점이 제각각이 된다
- 결함의 **심각도·우선순위**가 없어 "무엇부터 고칠지"를 문서로 설명할 수 없다
- 조치 후 **재테스트 이력**이 남지 않아 "고쳤다"는 주장의 근거가 없다
- 결함 통계(심각도별 분포, 조치율, 잔존 결함)를 낼 수 없어 **종료기준 판정**이 불가능하다

## 파일 형식
Excel (.xlsx) — 단일 시트 (결함관리대장)

## 심각도 (Severity) — 테스터가 판정

| 등급 | 정의 | 판별 질문 |
|------|------|---------|
| **Critical** | 업무 중단, 데이터 손실·오염, 보안 취약점, 시스템 다운 | 이대로 오픈하면 사고가 나는가? |
| **Major** | 주요 기능 오류이며 **우회 경로가 없음** | 사용자가 목적을 달성할 다른 방법이 있는가? |
| **Minor** | 부분 오류이나 **우회 가능** | 불편하지만 업무는 되는가? |
| **Trivial** | 기능에 영향 없음 (표기·정렬·여백) | 기능이 아니라 보기의 문제인가? |

## 우선순위 (Priority) — PM이 판정

| 등급 | 조치 시점 | 판단 기준 |
|------|---------|---------|
| **High** | 즉시 (당일~익일) | 후속 테스트를 막는가? 발주처 시연 대상인가? |
| **Medium** | 해당 레벨 종료 전 | 종료기준에 걸리는가? |
| **Low** | 여유 시 / 차기 배포 | 미뤄도 인수에 지장 없는가? |

> **심각도와 우선순위는 독립적이다.** 발주처 시연 화면의 오탈자는 Trivial-High이고,
> 연 1회 쓰는 배치의 기능 오류는 Major-Low일 수 있다. 두 값을 같이 매기지 않는다.

## 결함 상태 흐름

```
Open ──→ Assigned ──→ Fixed ──→ Retest ──→ Closed
  │                                 │
  │                                 └──→ Reopen ──→ Assigned (루프)
  ├──→ Deferred   (차기 이월 — 발주처 승인 근거를 비고에 기재)
  └──→ Rejected   (결함 아님 — 판단 사유를 비고에 기재)
```

| 상태 | 의미 | 다음 상태 |
|------|------|---------|
| Open | 등록됨, 담당자 미지정 | Assigned / Rejected / Deferred |
| Assigned | 담당자 지정, 조치 대기 | Fixed |
| Fixed | 조치 완료, 재테스트 대기 | Retest |
| Retest | 재테스트 진행 중 | Closed / Reopen |
| Closed | 재테스트 적합, 종결 | — |
| Reopen | 재테스트 부적합, 재조치 필요 | Assigned |
| Deferred | 차기 이월 확정 | — (종료보고서에 잔존 결함으로 기재) |
| Rejected | 결함이 아님으로 판정 | — |

> **Deferred와 Rejected는 반드시 사유를 남긴다.** 사유 없는 Deferred는 감리에서 "결함 미조치"로 본다.

## 결함 통계 (대장 하단 자동 산출)

```
[결함 현황]

총 결함: N건

심각도별:
  Critical  N건 (조치완료 N / 잔존 N)
  Major     N건 (조치완료 N / 잔존 N)
  Minor     N건 (조치완료 N / 잔존 N)
  Trivial   N건 (조치완료 N / 잔존 N)

상태별:
  Closed N · Deferred N · Rejected N · 진행중(Open~Retest) N

조치율 = Closed ÷ (전체 − Rejected) × 100 = N%

발견 단계별:
  단위 N · 통합 N · 시스템 N · 인수 N
```

### 종료기준 판정

총괄 테스트계획서(TE-01) §7의 종료기준과 대조하여 자동 판정한다.

| 기준 | 목표 | 현재 | 판정 |
|------|------|------|------|
| Critical 잔존 | 0건 | N건 | 충족 / **미충족** |
| Major 잔존 | 0건 | N건 | 충족 / **미충족** |
| Minor 조치율 | 90% 이상 | N% | 충족 / **미충족** |

> 하나라도 미충족이면 **다음 테스트 레벨 진입 불가**를 명시하고, 진입하려면 PM 승인 근거를 기록한다.

## 작성 규칙

1. **결함ID는 프로젝트 전체에서 연속 채번**한다. 레벨별로 번호를 나누지 않는다
2. 같은 원인의 결함은 **새 ID를 발급하지 않고** 기존 결함의 "발견 테스트ID"에 추가한다
3. 조치 후 재발한 결함은 **새 ID를 발급**하고 비고에 원 결함ID를 참조한다
4. 재현 절차는 **제3자가 그대로 따라할 수 있는 수준**으로 적는다 — "저장 시 오류"는 불충분
5. Critical 결함은 발견 즉시 PM에게 보고하고, 대장 등록과 별개로 즉시 조치에 착수한다
6. 결과서의 부적합 행은 반드시 결함ID를 참조한다 — 결과서에만 있고 대장에 없는 결함은 감리 지적 대상
7. Deferred·Rejected는 발주처 또는 PM의 승인 근거(회의록·메일)를 비고에 기재한다
