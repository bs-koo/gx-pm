# ID 네이밍 규칙

## 시스템 코드

프로젝트의 각 시스템은 영문 1자리 코드를 가진다.
사용자에게 시스템 목록을 제공받거나, 기존 산출물에서 추출한다.

예시 (ENERGY202507 프로젝트):
| 코드 | 시스템명 |
|------|---------|
| A | 국내외 열사용기자재 검사 시스템 |
| B | 공공기관 에너지이용 합리화 시스템 |
| C | 연구용역 관리 시스템 |
| ... | ... |

## ID 체인

모든 산출물은 하나의 ID 체인으로 연결된다:

```
제안요청ID (SFR-{순번})
  └→ 요구사항ID ({시스템코드}-RE-{순번})
       ├→ [기능] 화면ID ({접두}_{대분류}_{중분류}_{SN})
       │      └→ 프로그램ID (PG_{화면ID})
       │      └→ 단위테스트ID (U_{화면ID})
       │             └→ 테스트케이스ID (TC_{화면ID}_{순번})
       │                    └→ 결함ID ({시스템코드}-DF-{순번})
       ├→ [기능] 통합테스트ID ({시스템코드}-TE-{순번})
       │             └→ 결함ID ({시스템코드}-DF-{순번})
       └→ [비기능] 시스템테스트ID ({시스템코드}-ST-{순번})
                     └→ 결함ID ({시스템코드}-DF-{순번})
```

**체인 갈래 3개**

| 갈래 | 대상 | 검증 산출물 |
|------|------|-----------|
| 화면 갈래 | 기능 요구사항 | 단위테스트(DE-13/IM-03) |
| 흐름 갈래 | 기능 요구사항 (업무 흐름) | 통합테스트(DE-14/TE-02), 인수테스트(TE-06) |
| 품질 갈래 | **비기능 요구사항** | 시스템테스트(ST-01/ST-02) |

비기능 요구사항은 화면·프로그램에 매핑되지 않는 대신 **시스템테스트ID로 검증 추적**된다.
결함ID는 세 갈래 어디에서든 발생할 수 있으며, 결함관리대장(DF-01)에서 단일 번호로 관리한다.

## 각 ID 패턴 상세

### 제안요청ID
- 패턴: `SFR-{3자리 순번}`
- 예시: `SFR-001`, `SFR-027`
- 출처: RFP/과업지시서

### 요구사항ID
- 패턴: `{시스템코드}-RE-{3자리 순번}`
- 예시: `B-RE-001`, `A-RE-015`
- 규칙: 시스템코드는 대문자 영문 1자리

### 화면ID
- 패턴: `{시스템접두}_{대분류2자리}_{중분류2자리}_{SN3자리}`
- 예시: `EHR_01_01_010`, `EHR_05_02_020`
- SN: 010부터 시작, 10 단위 증가
- 시스템접두: 시스템별 3~4자리 영문약어 (예: EHR, KSC)

### 프로그램ID
- 패턴: `PG_{화면ID}`
- 예시: `PG_EHR_01_01_010`

### 단위테스트ID
- 패턴: `U_{화면ID}`
- 예시: `U_EHR_01_01_010`
- 단위: **화면 1개 = 단위테스트 1건**. 화면 안의 개별 검증은 테스트케이스ID로 분해한다.

### 테스트케이스ID
- 패턴: `TC_{화면ID}_{2자리 순번}`
- 예시: `TC_EHR_01_01_010_01`, `TC_EHR_01_01_010_07`
- 순번: 01부터 1단위 증가 (화면ID 안에서만 고유하면 됨)
- 규칙: 하나의 단위테스트(`U_{화면ID}`) 아래에 케이스 N건이 달린다
- 용도: 검사기준 27개 체크리스트가 "무엇을 확인했나"라면, 테스트케이스는 "어떤 데이터로 어떤 결과를 기대했나"를 기록한다

### 통합테스트ID
- 패턴: `{시스템코드}-TE-{3자리 순번}`
- 예시: `A-TE-001`, `B-TE-003`
- 단위: **업무 흐름 1개 = 시나리오 1건**. 시나리오 안의 단계는 Step 번호로 분해한다.
- 예외 흐름: 정상 흐름 시나리오와 **별도 ID**를 부여한다 (예: `B-TE-003` 정상, `B-TE-004` 권한 없음)

### 시스템테스트ID
- 패턴: `{시스템코드}-ST-{3자리 순번}`
- 예시: `B-ST-001`, `A-ST-012`
- 대상: **비기능 요구사항** (성능·보안·호환성·접근성·가용성)
- 규칙: 하나의 비기능 요구사항에 여러 측정 항목이 있으면 항목별로 별도 ID를 부여한다
  (예: "응답시간 3초 이내 + 동시접속 500명" → `B-ST-001`, `B-ST-002`)

### 결함ID
- 패턴: `{시스템코드}-DF-{3자리 순번}`
- 예시: `B-DF-001`, `A-DF-047`
- 규칙: **테스트 레벨과 무관하게 프로젝트 전체에서 연속 채번**한다
  (단위/통합/시스템/인수 어디서 발견되든 같은 번호 체계)
- 중복 결함: 같은 원인이면 새 ID를 발급하지 않고 기존 결함ID에 발견 위치를 추가한다
- 재발 결함: 새 ID를 발급하고 비고에 원 결함ID를 참조한다 (`B-DF-012 재발`)

### 인터페이스ID
- 패턴: `IF-{시스템코드}-{3자리 순번}`
- 예시: `IF-B-001`, `IF-A-003`
- 규칙: 연동 목적이 다르면 같은 외부 시스템이라도 별도 ID 부여

## ID 접두어 일람

| 접두어 | 대상 | 파생 기준 |
|--------|------|----------|
| `SFR-` | 제안요청 | RFP 원문 |
| `-RE-` | 요구사항 | 순번 채번 |
| `PG_` | 프로그램 | **화면ID 파생** |
| `U_` | 단위테스트 | **화면ID 파생** |
| `TC_` | 테스트케이스 | **화면ID + 순번** |
| `-TE-` | 통합테스트 | 순번 채번 |
| `-ST-` | 시스템테스트 | 순번 채번 |
| `-DF-` | 결함 | 순번 채번 |
| `IF-` | 인터페이스 | 순번 채번 |
| `CR-` | 변경요청 | 날짜 + 순번 |

> **파생 ID 주의**: `PG_` `U_` `TC_`는 화면ID에서 문자열로 파생되므로, **화면ID가 바뀌면 전부 재채번**된다.
> 화면목록표는 반드시 승인·확정한 뒤 후속 산출물로 넘어간다.

## 문서 공통 규칙

1. 문서 파일명의 `{시스템명}` 부분을 실제 시스템명으로 대체
2. 문서 내 업무구분은 해당 시스템명으로 기재
3. 문서 내 작성자는 감리대응 담당자명으로 기재
4. 프로젝트 코드: 프로젝트별 부여 (예: ENERGY202507)
