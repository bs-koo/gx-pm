## 이게 뭔가요?

`gx-pm`은 **공공/SI 프로젝트의 PM**을 위한 Claude Code·Codex 플러그인입니다.

RFP를 넣으면 요구사항을 뽑아주고, 요구사항에서 기능(입력항목·처리내용·출력결과)을 도출하고, DDL에서 테이블정의서를 역생성하고, 기능 1건당 단위테스트 케이스를 기계적으로 만들고, 산출물 간 ID가 끊기지 않았는지 추적합니다. 단위테스트계획서가 있으면 프로젝트를 로컬에서 실행해 각 행의 API 요청과 필요한 브라우저 조작을 수행하고, 실제 관측을 단위테스트결과서에 기록합니다.

**v4.5.0**: `/gx-단위테스트실행`은 프로젝트를 로컬에서 실행해 계획서 행마다 실제 API 요청과 필요한
브라우저 조작을 수행합니다. 계획서는 유지하고 결과서의 `실제결과` 열에 관측값을 기록합니다. 결과서
개정이력과 수행대장 반영 이력을 남기며, 요청·응답·화면·데이터 확인 증적을 실행별로 보존합니다.

이제 명세 5개 커맨드 모두 확인 항목을 점검합니다. 질문이 없으면 0건을 알리고, 소량은
대화 답변까지 이력에 남기며, 다량은 확인요청서 Excel로 받습니다. 빈칸은 승인으로 처리하지 않습니다.
`/gx-단위테스트결과반영`은 `/gx-단위테스트실행`의 호환 별칭입니다. 9개 진입 이름이 8개 기능을 제공합니다.

**v4.4.0**: `/gx-기능명세서`·`/gx-테이블정의서`·`/gx-단위테스트계획서` 를 낱개로 불러도 확인요청서가 나옵니다. 확인요청서는 시스템당 한 파일로 두고, 행마다 `항목번호`·`산출물`·`발행처` 를 붙여 어느 요청이 어느 산출물에 대해 물었는지 가릅니다. 묻는 상한은 파일 「최대 3차」가 아니라 **같은 항목은 최대 세 번**입니다. 단위테스트계획서·결과서 xlsx 는 기능 단위로 세로 병합됩니다.

**v4.3.0 당시**: `/gx-단위테스트결과반영`과 **IM-03 단위테스트결과서**가 생겼습니다. 당시 방식은 개발 레포의 테스트 코드·JUnit 실행 결과 대조였습니다. 계획서 유지, 사람 기입 보존, 수행대장 기록은 유지하고 실행 근거를 얻는 방식은 위의 로컬 시험으로 바꿉니다.

**v3.1.0**: 재생성해도 ID가 밀리지 않습니다. 제약이 비어 경계 케이스가 안 나오는 기능과, 근거가 부족한데 확인 요청이 0건인 상황을 게이트에서 알려줍니다.

**v3.0.0**: 플러그인을 화면 축에서 **기능 축**으로 재정렬했습니다. 산출물이 13종에서 **5종**으로, 커맨드가 16개에서 **7개**로 줄었습니다.
`/gx-명세일괄` 하나로 요구사항 → 기능 → 테이블 → 단위테스트 → 추적매트릭스를 순서대로 만들며, 판단이 필요한 **승인 게이트 3곳**에서만 멈춥니다.
ID 체계에서 **파생 ID가 전부 사라져** 어떤 ID를 바꿔도 재채번 파급이 없습니다 — 연결은 전부 `연계~ID` 열이 맡습니다.
내린 화면 축 산출물(DE-03·DE-05·DE-04·ST-01/02·DF-01 등)은 삭제하지 않고 `plugins/gx-pm/archive/`에 보관했습니다.

**v1.3.0부터**: 개발 완료 후 산출물을 맞춰야 할 때, DDL에서 테이블정의서를 **역생성**할 수 있습니다. `/gx-프로젝트설정` 한 번이면 모든 커맨드가 프로젝트 상황에 맞게 자동 동작합니다.

### 일반 PM 도구와 뭐가 다른가요?

| 일반 PM 플러그인 (pm-skills 등) | gx-pm |
|------|------|
| PRD, OKR, 로드맵 | **요구사항정의서, 기능명세서, 요구사항 추적표** |
| GTM, 그로스 루프 | **범위 협상, 공수 산정** |
| TAM/SAM/SOM | **WBS 분해, 진척률 분석** |
| 영어 중심 프레임워크 | **한국어 공공/SI 문서 양식** |

## 설치

### Claude Desktop 앱 (Code 탭)

1. 좌하단 **사용자 지정** 클릭
2. **개인 플러그인** 옆 **`+`** 버튼 → **플러그인 탐색**
3. 상단 **개인** 탭 → **`+`** 버튼 → URL에 `bs-koo/gx-pm` 입력 → **추가**
4. **gx-pm** 탭 선택 → **설치**
5. 프로젝트에서 `/gx-프로젝트설정` → `/gx-명세일괄` 순으로 사용

### Claude Code CLI

```bash
# Claude Code CLI에서 실행
/plugin marketplace add bs-koo/gx-pm
/plugin install gx-pm@gx-pm
```

### Codex CLI / 앱

Codex가 설치된 터미널에서 마켓플레이스를 등록하고 플러그인을 설치합니다. Windows PowerShell은
`codex.cmd`, macOS/Linux는 `codex`를 사용합니다.

```powershell
codex.cmd plugin marketplace add bs-koo/gx-pm
codex.cmd plugin add gx-pm@gx-pm
codex.cmd plugin list -m gx-pm
```

로컬 복제본으로 설치하려면 저장소 루트에서 첫 명령만
`codex.cmd plugin marketplace add .`로 바꿉니다. 설치 후 Codex 앱 또는 CLI에서 **산출물을
저장할 프로젝트 폴더**를 열고 새 대화를 시작합니다. Codex에서는 Claude의 `/gx-*` 슬래시
커맨드 대신 `$gx-pm-workflow` 스킬에 작업을 요청합니다.

```text
$gx-pm-workflow 프로젝트 설정을 시작해줘. RFP와 기존 산출물은 이 폴더에 있어.
$gx-pm-workflow 명세 5종을 만들어줘.
$gx-pm-workflow 단위테스트계획서대로 실행하고 결과 반영해줘. 프로젝트는 D:\projects\reb-api 랑 D:\projects\reb-web 이야.
```

첫 요청에서 프로젝트 유형(A 신규 구축/B 추가 개발/C 산출물 정비/D 변경 관리), RFP·기존
산출물·소스코드·DDL 위치를 알려주면 설정이 수월합니다. 두 번째 요청은 AN-02 요구사항정의서,
AN-03 기능명세서, DE-08 테이블정의서, DE-13 단위테스트계획서, AN-05 추적매트릭스를
순서대로 다룹니다. 한 문서만 필요하면 같은 스킬에 이름을 말하면 됩니다. 예:
`$gx-pm-workflow DDL을 근거로 테이블정의서(DE-08)를 만들어줘`.
각 단계의 선택·승인 요청에는 실제 답을 입력해야 다음 단계로 진행합니다.

테이블정의서와 명세일괄에는 외부 `sqi-comn-term` MCP 연결이 필요합니다.
Windows PowerShell에서는 아래 명령으로 사업부 표준용어 MCP를 사용자 환경에 등록합니다.
사업부 서버 주소가 다른 환경이면 URL을 해당 주소로 바꿉니다.

```powershell
codex.cmd mcp add sqi-comn-term --url http://52.78.238.167:8687/api/v1/mcp
codex.cmd mcp list
```

등록 후 Codex를 다시 시작하거나 새 대화를 열어 `sqi-comn-term` 도구가 보이는지 확인한 다음
테이블정의서 또는 명세일괄을 요청합니다. 연결이 없으면 해당 작업은 선행조건에서 멈춥니다.
상세 연결 안내는 [표준용어 MCP 연계](plugins/gx-pm/docs/표준용어-mcp-연계.md)를 참조하세요.

## 사용법

### 처음 시작할 때

```
/gx-프로젝트설정
```

프로젝트 유형, 기본 정보, 소스코드 경로, DDL을 한 번 설정하면 이후 모든 커맨드가 자동으로 활용합니다. 새 대화를 열어도 설정이 유지됩니다.

### 프로젝트 유형 4가지

| 유형 | 언제 사용 | 커맨드 동작 |
|------|----------|------------|
| **A. 신규 구축** | RFP만 있고, 코드 없음 | 정방향 생성 (RFP → 산출물) |
| **B. 추가 개발** | 기존 시스템에 새 기능 추가 | 기존 산출물에 이어쓰기 |
| **C. 산출물 정비** | 개발 완료, 산출물 부족 | DE-08은 DDL에서 역생성, 나머지는 기존 산출물·RFP로 정비 |
| **D. 변경 관리** | 기존 기능 수정 | 변경 대상만 갱신 |

### 커맨드 목록

**커맨드 이름 = 산출물 이름**입니다. 만들고 싶은 산출물을 그대로 입력하면 됩니다.

| 이렇게 말하면 | 커맨드 | 결과물 |
|--------------|--------|--------|
| "명세 다 만들어줘" | `/gx-명세일괄` | **명세 5종 일괄 (승인 게이트 3곳)** |
| "프로젝트 설정해줘" | `/gx-프로젝트설정` | profile.json (프로젝트 프로파일) |
| "요구사항 뽑아줘" | `/gx-요구사항정의서` | AN-02 요구사항정의서 |
| "기능명세 만들어줘" | `/gx-기능명세서` | AN-03 기능명세서 |
| "DDL로 테이블정의서 만들어줘" | `/gx-테이블정의서` | DE-08 테이블정의서 |
| "단위테스트 계획 세워줘" | `/gx-단위테스트계획서` | DE-13 단위테스트계획서 |
| "단위테스트 결과 반영해줘" | `/gx-단위테스트실행` | 로컬 프로젝트의 API·필요한 화면에서 계획서 행별 시험 → 결과·사유·실제결과를 적은 IM-03 결과서와 수행대장. 계획서는 유지 |
| "추적매트릭스 확인해줘" | `/gx-추적매트릭스` | AN-05 추적매트릭스 |

## 핵심 기능

### 1. 단계별 승인 루프

모든 커맨드는 산출물을 한 번에 생성하지 않습니다. **각 단계마다 사용자 확인을 받고, 수정 요청이 있으면 반영한 뒤 다시 확인**합니다.

```
[산출물 생성] → [결과 표시] → 승인? → No → [수정 반영] → [다시 표시] → 승인? → ...
                                   → Yes → [다음 단계]
```

### 2. 시안/대안 자동 감지

요구사항에 "1안/2안", "A안/B안" 등 복수 시안이 있으면 **자동 감지하여 사용자에게 선택을 요청**합니다. 선택 전에는 산출물 생성을 시작하지 않습니다.

```
⚠ 시안 선택이 필요합니다

  1안: 이중 슬라이더 단일 화면 → 관리 항목 5개 예상
  2안: 쾌적성/온도 별도 관리 → 관리 항목 8개 예상

→ 어떤 시안으로 진행할까요? (1/2/병행)
```

### 3. 기존 산출물 처리

커맨드 실행 시 기존 산출물이 있으면 **3가지 선택지**를 제공합니다:

```
기존 요구사항정의서를 찾았습니다:
  B-요구사항정의서.md (35건, 마지막 수정: 1/15)

  1. 이어쓰기 — 기존 유지 + 새 항목 추가 (B-RE-036부터)
  2. 새로쓰기 — backup/ 폴더에 백업 후 본문 재생성 (ID는 직전 버전에서 승계)
  3. 열기     — 기존 내용에서 특정 항목만 수정/삭제
```

### 4. DDL에서 역생성 (C유형)

개발 완료 후 산출물을 맞출 때, DB 스키마에서 테이블정의서를 **자동 역생성**합니다. 기존 컬럼은 이름을 바꾸지 않고, 신규 컬럼만 표준용어사전 근거로 제안합니다.

| 소스 | 역생성 산출물 | 방식 |
|------|-------------|------|
| DDL (DataGrip/DBeaver 복사) | 테이블정의서 (DE-08) | DDL 파싱 + 표준용어 MCP 표준화 |

소스코드는 `scan-source-index` 스킬로 3단계 점진 스캔해 실제 구현과 산출물을 대조하는 데 씁니다 (풀스캔 200만 → 1.7만 토큰).

### 5. xlsx 추출

승인된 산출물은 **공공 양식 컬럼 순서에 맞춘 xlsx로 즉시 추출**할 수 있습니다. 실제 산출물 엑셀에 바로 복사-붙여넣기가 가능합니다.

```bash
# CLI에서 직접 사용할 수도 있습니다
python utils/export-xlsx.py --dir 결과물/ --output 산출물.xlsx
```

### 6. 확인요청서 — 다섯 문서의 미결을 한곳에서 확인

요구사항정의서·기능명세서·테이블정의서·단위테스트계획서·추적매트릭스 모두 확인 항목을 점검합니다.
앞의 세부 조건뿐 아니라 요구사항의 원문 충돌과 추적 결과의 범위 판단도 포함합니다.
명백한 ID 오류나 이미 확정한 내용은 사용자에게 다시 판단시키지 않습니다.

| 확인 필요 | 기본 동작 |
|---|---|
| 0건 | 0건을 알리고 빈 파일은 만들지 않습니다 |
| 1~5건 | 대화로 실제 답을 받고 확인요청서 md에 항목·답·보류를 기록합니다 |
| 6건 이상 | 확인요청서 md와 xlsx를 발행하고 관련 결정을 기다립니다 |

파일로 검토하고 싶다고 요청하면 소량도 Excel로 받습니다. 시스템당 한 파일을 쓰며
`항목번호`·`산출물`·`물은 횟수`·`발행처`로 구분합니다. 시트는 안내·가정 확인·미확정 확인·요청 이력입니다.
노란 입력 칸만 채우면 됩니다. **빈칸은 미응답**이며, 맞는 값은 `맞음`으로 표시합니다.
다시 부를 때 새 응답부터 반영하고, 같은 파일을 열었다는 이유로 차수를 올리거나 답을 지우지 않습니다.

미결이 남은 문서는 최종본을 보류합니다. 검토가 필요하면 `--draft --separate`로
`검토용초안` Excel을 받을 수 있습니다. 파일명과 모든 시트 제목·인쇄 머리말에 초안임을 표시하고 최종본을 보존합니다.
완료 안내에서 생성 파일, 남은 항목, 재개할 커맨드를 확인할 수 있습니다.

### 7. 미확정이 0이어야 최종본이 나갑니다

`[미확정]` 또는 해당 문서에 영향을 주는 미응답이 남아 있으면 **그 문서의 최종본 xlsx를 보류합니다.**
마크다운은 게이트마다 저장하고, 요청하면 별도 검토용 Excel 초안을 제공합니다.
미결과 무관한 다른 문서는 최종본으로 받을 수 있습니다.

**값을 대신 정하지 않기 때문입니다.** 채우면 해소된 것처럼 보이지만 실은 우리가
정한 값이라, 개발자가 그것을 확정값으로 읽고 착수합니다.

### 8. 낡은 산출물 감지

산출물은 낱개로도 만들 수 있어서, 요구사항정의서만 고치면 나머지가 옛 값으로
남습니다. **ID 는 그대로라 추적매트릭스가 초록입니다** — 끊긴 게 아니라 낡은
것이라 누락 판정에 안 걸립니다.

그래서 머리말에 근거 버전을 적습니다 (`> 근거: AN-02 v2.0`). 상위가 v3.0 이
되면 어느 커맨드를 부르든 이렇게 알립니다.

```
낡은 산출물이 있습니다.

  AN-03 기능명세서    AN-02 v2.0 기준  ← 현재 AN-02 는 v3.0
  DE-13 단위테스트    AN-03 v1.0 기준  ← 현재 AN-03 은 v2.0

  영향 범위: 기능 2건(FN-007·FN-014) · 컬럼 3건 · 테스트 9건

  1. 전부 최신화 (권장)   2. 일부만   3. 표시만 하고 두기
```

## 프로젝트 흐름

### A. 신규 구축 (정방향)

**파이프라인 (권장)** — 커맨드 순서를 외우지 않아도 됩니다.

```
 /gx-프로젝트설정 (A유형)
       ↓
 /gx-명세일괄       (명세 5종 일괄, 승인 게이트 3곳)
       ↓
 /gx-추적매트릭스 (누락 탐지)
```

**각 게이트에서 미결이 6건 이상이면 확인요청서 엑셀을 발행하고 관련 결정을 기다립니다.**
게이트 1의 원문 충돌도 포함합니다. 주로 제약값이 모이는 게이트 2에서 발행한 예는 아래와 같습니다.
채운 뒤 `/gx-명세일괄` 을 다시 부르면 「확인요청서 반영하고 이어가기」가
선택지에 뜹니다. 같은 항목은 최대 세 번까지 묻고, 실행이 이렇게 나뉩니다.

| 회차 | 하는 일 | 끝난 뒤 |
|---|---|---|
| 1 | 게이트 1·2 | 1차 발행 → 중단 |
| 2 | 1차 반영 → DE-13·AN-05 → 게이트 3 | 2차 발행 → 중단 |
| 3 | 2차 반영 → 파급 처리 | 3차 발행 → 중단 |
| 4 | 3차 반영 | 세 번 물은 항목은 미해소. 해당 문서의 미결이 0이면 완료 |

**해당 문서의 미결이 0이 되면 그 자리에서 끝납니다.** 미응답 가정도 포함합니다. 「최대 세 번」이지 「반드시 세 번」이
아닙니다.

**낱개로 만들 때** — 파이프라인 내부에서 도는 순서와 같습니다.

```
 /gx-요구사항정의서 → /gx-기능명세서 → /gx-테이블정의서 → /gx-단위테스트계획서
                                                              ↓
                                                       /gx-추적매트릭스 (누락 탐지)
```

**계획서대로 실제 시험할 때** — 명세일괄 밖에서 따로 부릅니다. 개발 프로젝트와 계획서를 주면
실행부터 결과 반영까지 진행합니다. 프로젝트나 계획서가 바뀌면 다시 불러 재수행합니다.

```
 DE-13 단위테스트계획서 + 로컬에서 실행할 프로젝트
       ↓
 /gx-단위테스트실행   프로젝트 기동 → 행별 준비·실제 API 요청·필요한 브라우저 조작
       ↓
 응답·화면·데이터 관측   기대결과·사후조건 비교, 실행별 증적 보존
       ↓
 결과 승인·반영          IM-03 결과서(실제결과 포함)·수행대장 기록, 계획서는 유지
       ↓
 /gx-추적매트릭스         요구사항별 Pass/Fail·미수행을 결과서로 다시 대조
```

기존 테스트 코드나 JUnit 결과 파일은 필요하지 않습니다. 프로젝트 지침과 설정에서 시작 명령·포트·시험
계정·데이터를 확인하고 로컬 인스턴스를 실행합니다. 사용자가 지정한 경로를 우선하며, 없으면 프로파일의
`assets.testSourcePaths` → `assets.sourcePath` → 실제 애플리케이션인 현재 폴더 순으로 찾습니다.

각 행의 사전조건과 입력을 적용한 뒤 응답·화면 문구·저장 결과를 확인합니다. 화면 조건은 브라우저로,
저장·삭제·미저장은 후속 조회 또는 시험 DB의 전후 데이터로 확인합니다. 필요한 도구·계정·데이터가 없거나
일부만 관측했으면 `미검증`, 기능 미제공이 확인됐으면 `미구현`입니다. 비기능 행도 계획한 측정 조건을
준비할 수 있으면 수행합니다. 기존 Pass나 PM의 통과 확인만으로 이번 Pass를 적지 않습니다.

증적은 `증적/{시스템코드}/{run_id}/execution.json`과 응답·화면·데이터 파일로 보존합니다. 결과서와
수행대장은 결과 검토·승인 후에 기록합니다. 계획 내용이 같은 행만 사람이 적은 값을 기본 유지(`keep`)하고
이번 관측과의 차이를 대장에 함께 남깁니다. 케이스가 바뀐 행(`case_changed`)은 새 실행 증적의 판정을
반영하고 옛 값은 백업에 보존합니다. `수행률` 이름은 유지하지만 계산은 판정 대상의 통과율입니다:
**Pass ÷ (전체 − 비기능 미검증 − 기준값 미확정 − 제외)**. Fail·미구현·그 밖의 미검증은 분모에 남습니다.

결과서가 바뀌면 **결과서 개정이력**에 버전과 변경 내용을 적고, **수행대장 반영 이력**에는 반영일·문서
버전·상태별 건수·수행률·소스 기준을 한 행씩 쌓습니다. 결과서가 그대로여도 수행대장에 이번 대조 기록은
남습니다. 예를 들어 "잘못된 파일은 오류 안내 후 저장하지 않음"이라는 계획 행은 실제 응답 문구와
저장 전후 건수를 함께 확인한 뒤, 결과서에는 판정·사유·관측값을, 증적 폴더에는 응답·조회 파일을 기록합니다.

## 핵심: ID 추적 체인

공공/SI 프로젝트에서 감리 대응의 핵심은 **산출물 간 추적성**입니다. gx-pm은 모든 산출물을 하나의 ID 체인으로 연결합니다.

```
요구사항ID  (B-RE-001)
  └→ 기능ID  (B-FN-001)          ← 파생 아님. 독립 채번, N:M 매핑
       ├→ 테이블·컬럼 (DE-08)     ← 입력항목이 컬럼으로 매핑된다
       └→ 테스트ID (B-UT-001)    ← 파생 아님. 독립 채번, N:1 매핑
            └→ 수행 결과 (IM-03)  ← 같은 테스트ID 로 결과서에 Pass·Fail·미구현·미검증
```

**갈래가 둘입니다.** 기능 요구사항은 기능명세를 거쳐 테스트로, 비기능 요구사항은 기능을 거치지 않고 바로 테스트로 갑니다 (DE-13의 `연계기능ID` 공란 행).

**파생 ID가 없습니다.** 어떤 ID도 다른 ID에서 만들어지지 않으므로, ID를 바꿔도 재채번 파급이 없습니다. 연결은 전부 `연계~ID` 열이 맡습니다.

`/gx-추적매트릭스`로 언제든 추적 상태를 확인할 수 있습니다 (모든 유형에서 사용 가능). `Pass/Fail` 은 단위테스트결과서에서 읽고, Pass·Fail 이 한 건도 없으면 `미수행` 입니다:

```
| 요구사항ID | 요구사항명 | 상태 | 기능ID | 기능명 | 테이블·컬럼 | 테스트 수 | Pass/Fail | 누락 |
|---|---|---|---|---|---|---|---|---|
| B-RE-001 | 벤치마크 스코어테이블 생성 기능 | 유지 | B-FN-001 | 스코어테이블 생성 | TB_SCORE (신규 4) | 6 | 6/0 | |
| B-RE-045 | 동시접속 500명 응답 3초 | 신규 | | | | 2 | 0/0 | 미수행 |
| B-RE-032 | 업로드 통계 데이터 조회 | 신규 | | | | 0 | — | 기능 미도출 |
```

**커버리지 판정**

| 지표 | 목표 |
|------|------|
| 기능 요구사항 → 기능 매핑률 | 100% |
| **비기능 요구사항 검증률** (DE-13 연계기능ID 공란 행) | **100%** |
| 단위테스트 Pass 률 | 100% |

## DB 스키마 연계

DDL 텍스트 기반으로 테이블정의서를 역생성합니다. DataGrip, DBeaver, ERDCloud 등 DDL을 내보낼 수 있는 도구라면 모두 지원합니다. **DE-08은 역생성 전용**입니다 — 요구사항에서 테이블을 추론하는 순방향 경로는 없습니다.

### DDL 복사 방법

| 도구 | 복사 방법 |
|------|----------|
| **DataGrip** | 스키마 우클릭 → SQL Scripts → Generate DDL to Clipboard |
| **DBeaver** | 스키마 우클릭 → Generate SQL → DDL → Ctrl+A → Ctrl+C |
| **ERDCloud** | SQL 내보내기 → 모든 테이블 생성 SQL |

### DDL → 테이블정의서

```
DDL 복사 → /gx-테이블정의서에 붙여넣기 → DE-08 자동 역생성
  → 기존 컬럼은 현행유지 + 표준 권고명 병기
  → 신규 컬럼(기능명세 입력항목 기반)만 표준용어 MCP 근거로 제안·승인
```

## FAQ

<details>
<summary>개발이 끝난 프로젝트에서 산출물을 맞출 수 있나요?</summary>

`/gx-프로젝트설정`에서 **C. 산출물 정비** 유형을 선택하고, DDL을 입력하면 됩니다. `/gx-테이블정의서`가 DDL에서 DE-08을 역생성하고, 나머지 4종(요구사항정의서·기능명세서·단위테스트계획서·추적매트릭스)은 기존 산출물과 RFP를 근거로 정비합니다.
</details>

<details>
<summary>기존 산출물이 있는 프로젝트에서도 사용할 수 있나요?</summary>

네. 커맨드 실행 시 기존 산출물을 자동 감지하여 **이어쓰기**(기존 유지 + 추가), **새로쓰기**(백업 후 본문 재생성), **열기**(부분 수정) 중 선택할 수 있습니다. 이어쓰기는 기존 마지막 번호에 이어서 ID를 부여하고, 새로쓰기는 직전 버전과 대조해 같은 항목이면 기존 ID를 그대로 유지합니다.
</details>

<details>
<summary>여러 프로젝트를 동시에 관리할 수 있나요?</summary>

네. 하나의 작업 폴더에서 여러 프로젝트를 관리합니다. `/gx-프로젝트설정`을 실행하면 기존 프로젝트 목록이 표시되고, 원하는 프로젝트를 선택하거나 새로 생성할 수 있습니다. 프로젝트별로 별도 폴더에 산출물이 저장됩니다.
</details>

<details>
<summary>DDL은 어떻게 입력하나요?</summary>

DB 접속정보는 받지 않습니다. DataGrip에서는 스키마 우클릭 → SQL Scripts → Generate DDL to Clipboard, DBeaver에서는 스키마 우클릭 → Generate SQL → DDL로 전체 DDL을 클립보드에 복사한 뒤 붙여넣으면 됩니다.
</details>

<details>
<summary>비기능 요구사항은 어떻게 검증하나요?</summary>

기능을 거치지 않고 바로 테스트로 갑니다. `/gx-단위테스트계획서`가 DE-13에 `연계기능ID`가 공란인 행을 만듭니다.
결과반영에서는 계획한 부하·데이터·측정 조건과 기준을 준비할 수 있으면 실제 측정합니다. 준비하지 못하면
`미검증 — 비기능 …`으로 남기며, 적은 로컬 데이터의 응답시간으로 대규모 조건을 통과 처리하지 않습니다.
</details>

<details>
<summary>단위테스트 수행 결과는 어디에 적나요?</summary>

**IM-03 단위테스트결과서**에 적습니다. `/gx-단위테스트실행`에 계획서와 실행할 프로젝트 경로를 주면
로컬에서 실제 시험합니다. 결과서에는 행마다 `Pass`·`Fail`·`미구현`·`미검증`, 판정 사유, 실제 응답·문구·
데이터 관측을 적고 계획서 원본은 유지합니다. Pass는 유효한 사전조건·입력과 기대결과·사후조건을 모두
관측해 일치했을 때만 새로 기록합니다. 담당자는 커밋 작성자가 아닌 실제 시험 수행 책임자입니다.
계획서가 모호한 부분은 명확화 후보로 알리고, 계획서 수정은 `/gx-단위테스트계획서`에서 진행합니다.
실행 증적은 `증적/{시스템코드}/{run_id}/`, 내부 수행대장은 `증적/{시스템코드}-단위테스트수행대장.md`에 남습니다.
</details>

<details>
<summary>xlsx 추출은 어떻게 하나요?</summary>

이미 Excel 출력을 요청했다면 다시 묻지 않고 생성합니다. 형식이 미정이면 최종 검토에서 선택합니다.
공공 양식 컬럼 순서에 맞춰 문서별로 생성하며, CLI에서는 `python utils/export-xlsx.py --dir 결과물/ --separate`를 씁니다.
미결 문서를 검토용으로 받으려면 `--draft`를 추가합니다. 기존 최종본은 보존됩니다.
</details>

<details>
<summary>DE-03·DE-05·감리대응 같은 화면 축 이전 산출물은 어디 갔나요?</summary>

삭제하지 않고 `plugins/gx-pm/archive/`에 보관했습니다. 감리가 있는 공공 사업이 오면 되살릴 수 있습니다 — 방법은 `plugins/gx-pm/archive/README.md`를 참조하세요.
</details>
