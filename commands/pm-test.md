# /pm-test — 테스트 계획서 생성

화면목록표(DE-03)와 요구사항정의서(AN-02)를 기반으로 단위테스트계획서(DE-13)와 통합테스트계획서(DE-14)를 자동 생성하는 워크플로우.

> **공통 규칙**: 모든 체크포인트에서 `templates/approval-protocol.md`의 승인 루프 프로토콜을 적용한다.

## 호출 예시

```
/pm-test
/pm-test [화면목록표 업로드]
/pm-test B 시스템 테스트 계획서 만들어줘
```

## 워크플로우

### Step 1: 입력 데이터 로드

- 이전 `/pm-design` 결과가 있으면 자동 로드
- 없으면 화면목록표 입력 요청
- 요구사항정의서도 함께 로드 (통합테스트용)

### Step 2: 화면 유형 판별

**generate-unit-test-plan** 스킬의 화면 유형 판별 적용:
- 목록형, 등록형, 수정형, 상세형, CRUD통합형, API형 등

### Step 3: 화면 유형 검토 [필수 중단점 — 승인 루프]

화면 유형 판별 결과를 표시하고 **반드시** 확인을 받는다.
이 판별이 단위테스트 항목 수와 내용을 결정하므로 정확해야 한다.

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📋 화면 유형 판별 결과를 확인해주세요

| 화면ID | 화면명 | 판별 유형 |
|--------|--------|----------|
| ... | ... | ... |

주요 확인 사항:
1. 화면 유형이 실제 구현과 일치하나요?
2. "CRUD통합형"으로 판별된 화면이 정말 전체 CRUD를 포함하나요?
3. API형/배치형 등 화면이 아닌 프로그램은 올바르게 분류되었나요?

✅ 승인 — "승인" 또는 "OK"
✏️ 수정 — 변경 내용 입력

  수정 예시:
  • "SC-003은 CRUD통합형이 아니라 입력+조회형이야"
  • "SC-010은 API형으로 변경"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### Step 4: 단위테스트계획서 생성

화면 유형 승인 결과를 기반으로 단위테스트 항목을 생성:
1. 검사기준 자동 매핑 (공통/조회/입력/수정/삭제/첨부/출력)
2. 단위테스트ID 부여 (U_{화면ID})
3. 사용자구분 판별

### Step 5: 단위테스트 검토 [필수 중단점 — 승인 루프]

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📋 단위테스트 항목 {N}건을 확인해주세요

✅ 승인 — "승인" 또는 "OK"
✏️ 수정 — 변경 내용 입력

  수정 예시:
  • "SC-001에 '빈 값 입력 시 기본값 적용' 테스트 추가"
  • "SC-005의 예외처리 항목 삭제"
  • "전체적으로 경계값 테스트를 더 추가해줘"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### Step 6: 통합테스트시나리오 생성

**generate-integration-test** 스킬 적용:
1. 요구사항-화면 매핑
2. 업무 흐름 기반 시나리오 그룹핑
3. 통합테스트ID 부여 ({시스템코드}-TE-{순번})
4. Step 분해 (사용자행위 → 시스템결과)
5. 테스트 데이터 제안

### Step 7: 통합테스트 검토 [필수 중단점 — 승인 루프]

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📋 통합테스트 시나리오 {N}건을 확인해주세요

주요 확인 사항:
1. 시나리오 그룹핑이 실제 업무 흐름과 일치하나요?
2. 각 시나리오의 사전조건이 적절한가요?
3. 테스트 데이터가 현실적인가요?
4. 누락된 E2E 시나리오가 있나요?

✅ 승인 — "승인" 또는 "OK"
✏️ 수정 — 변경 내용 입력
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```
